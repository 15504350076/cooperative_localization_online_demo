# 2026-08-11两次三盒复测：结论、证据与复现步骤

复核日期：2026-10-22。对象：`three_boxes_20260811_054640.zip`、`three_boxes_20260811_060745.zip`，参照上一轮`three_boxes_20260811_012046`。原始包只读，未校时、删帧或改写传感器数据；只运行离线分析，未修改默认UWB三角形算法或RTE算法。

**结论：两轮都恢复了三盒车载IMU和UWB第三条边，采集完整性明显改善；但都还不能作为时间连续、姿态可靠的多传感器融合验收数据。054640整体比060745好，060745出现更严重的时钟跳变和点云间断。**

## 2. 在哪个终端执行哪条命令

在Ubuntu工程根目录打开终端，加载本工程消息环境。两轮已经解压；直接逐轮完整分析，每轮编号只在循环首行出现一次：

```bash
source /opt/ros/humble/setup.bash
source install/ros2-uwb-online/setup.bash
for RUN in data/three_boxes_20260811_{054640,060745}; do
  bash tools/analyze_box_sensors.sh "$RUN"/uwb_imu_livox_v20[123]_*/ || break
done
python3 -B data/复核三盒复测_20260811.py
```

每轮应看到三盒各四项完成，末尾“失败项目总数：0”。程序等待所有阶段结束，期间打印运行进度。之后还要执行最后一条复核脚本，它从原始数据库核对计数、重新计算三盒时间差和四元数步进，并输出本报告配套的CSV和中文问题图。**脚本正常结束只代表统计完成，不代表数据质量合格。** 本次两轮的24个主分析阶段及两轮补充复核均已完成。

如果只复核一轮，编号只填一处：

```bash
RUN=data/three_boxes_20260811_060745
bash tools/analyze_box_sensors.sh "$RUN"/uwb_imu_livox_v20[123]_*/
python3 -B data/复核三盒复测_20260811.py "$RUN"
```

平时`bash tools/analyze_box_sensors.sh`可自动选择最新的三盒非空实验，本次会选060745；“最新非空”不等于“时间质量合格”。指定上述`RUN`可避免以后新增包时复核对象变化。

若从原始ZIP重新开始，ZIP内已有实验根目录，先执行`unzip -n data/three_boxes_20260811_054640.zip -d data`，再对`RUN`下三个`tar.gz`执行`tar -xzf "$ARCHIVE" -C "$RUN"`；另一轮同理。解压后结构必须为`$RUN/uwb_imu_livox_v201_*/imu/metadata.yaml`，不能多套一层实验根目录。已解压时无需重复解压覆盖。

## 5. 车载IMU：第一轮仍异常，第二轮更严重

|轮次|盒号|消息回退|消息间隔>100毫秒|记录回退|相邻姿态>10度|最大相邻姿态角|
|---|---:|---:|---:|---:|---:|---:|
|054640|201|5|1|2|1|179.997574度|
|054640|202|3|4|0|1|179.994362度|
|054640|203|1|1|0|1|179.993199度|
|060745|201|30|2|6|1|179.994672度|
|060745|202|10|13|1|2|179.999632度|
|060745|203|3|5|1|4|179.997696度|

最容易人工复核的例子是**060745盒203**，打开`三盒IMU异常明细.csv`并筛选盒号203：

1. 帧7443→7444：消息时间`1786428478118590000`→`1786427209119590000`纳秒，消息间隔**−1268999毫秒，即回退1268.999秒**；同一步姿态旋转约179.997696度。
2. 帧10510→10511：消息间隔**+1267001毫秒，即前跳1267.001秒**，姿态又接近180度跳变。中间3067帧消息时间落在上一轮附近的时段，不是正常1毫秒连续时序。
3. 这两步的记录间隔仍是毫秒量级，因此不能用“本机记录时钟也回退了”解释掉这次1269秒的消息头异常；两类问题应分别调查。

相邻姿态角使用单位化四元数内积的绝对值计算，已消除`q`与`−q`代表同一旋转的影响。这里接近180度的突变不是单纯四元数符号翻转。仍需上交确认姿态解算重置、消息来源或驱动组帧情况；不能据此宣称盒子物理上瞬间转了180度，也不能直接把这种姿态作为航位推算的连续输入。原始角速度/加速度可供单独诊断，不等于已经验收可用。

## 6. 记录时间也回退，不能拿它算正常采样率

从三盒车载IMU记录时间差中得到：

|轮次|盒201最小记录间隔|盒202最小记录间隔|盒203最小记录间隔|
|---|---:|---:|---:|
|054640|−2.020177秒|+0.000058秒|+0.000059秒|
|060745|**−29.016181秒**|**−6.866567秒**|**−2.840162秒**|

证据是`时间连续性复核.csv`中`/imu/raw`行的“最小记录间隔（毫秒）”列；注意表格上面换算成了秒。第二轮201不止IMU，Livox和UWB多个流也有记录时间回退。现有证据只能说明录包时间序列不单调，尚不能确定是系统授时阶跃、ROS时钟切换、记录端行为还是其他原因。

本次修正了离线统计：**某流记录时间回退时，不再用消息数量除以首末记录跨度输出虚高频率；相关频率及依赖该记录时间的UWB趋势、跨度比显示`nan`（不可用）**。例如第二轮201约18万条车载IMU的首末记录跨度只有122.35秒，不能因此判断传感器变成了1467赫兹。正常正消息间隔中位数仍约1毫秒，但也不能据此忽略中途回退。相关回归检查已通过。

## 7. Livox：第二轮有长间断，202/203内置IMU有回退

第一轮三盒点云和内置IMU消息时间均无回退；点云头最大相邻间隔约100.32～100.35毫秒，逐点帧内首末跨度约100毫秒。201记录时钟回退仍会影响基于记录时间的配对。

第二轮具体问题：

|盒号|点云消息时间回退|点云头最大相邻间隔|内置IMU消息回退|逐点帧内首末跨度最大值（按纳秒解释）|
|---|---:|---:|---:|---:|
|201|0|**9400.320毫秒**|0|100.310毫秒|
|202|0|**1700.014毫秒**|**38**|**1700.004毫秒**|

具体看每盒`雷达分析.txt`的两段“消息时间”行，不要只看“记录时间”行：

- 201点云只有1518帧，消息头一次跨越9.4秒；内置IMU最大消息间隔4079.979毫秒。点云非空仍有明显连续性缺口；是否丢包、缓存阻塞、驱动打包或源时钟问题需继续查，不能直接宣称物理停采9.4秒。
- 202内置IMU最小消息间隔−58.560毫秒，203为−58.653毫秒；“回退次数”分别38和43。这与第一轮两者均为0不同。
- 第二轮`点云帧内时间跨度异常.csv`中，202**帧1549（从0起）**包含11232个点，首末点时间跨度1700.004毫秒。第一轮该异常表只有表头；第二轮202共20帧、203共18帧超过150毫秒。应确认该驱动逐点`timestamp`单位和组帧逻辑，不能强行把每帧固定当作100毫秒做去畸变。

两轮各盒XYZ全零点占比约：201为51.66%/51.64%，202为55.39%/55.29%，203为45.41%/45.40%；XYZ均有限。全零占比与此前同量级，表示相当一部分点不能当有效空间点使用；这是数据特征，**没有厂家有效回波标准和现场遮挡信息，不能仅凭45%～55%判定雷达故障**。可视化与点云算法应过滤全零点；点云形状看起来正常也不能抵消上面的时间问题。

## 8. UWB时间：三边齐了，及时性和同步仍需查

第一轮202记录时钟未检出回退，但其`时间连续性复核.csv`中：UWB源1的记录减消息时间中位数约3.28～3.35秒，源2/3约0.29～0.31秒。第二轮202该差值的源1上升至约26.6～26.9秒；203约28.7～29.1秒。差值包含时间源偏差、处理与传输等待，不能直接等同网络延迟，但也不能按“同一年的时间戳”宣布同步通过。

对第一轮202/203又做了独立的接收近邻检查，可复现：

```bash
RUN=data/three_boxes_20260811_054640
for BOX in 202 203; do
  python3 -B tools/compare_uwb_timestamps.py "$RUN"/uwb_imu_livox_v${BOX}_*/uwb
done
```

打开202的`uwb/UWB时间对比/三盒UWB时间对比.md`，看“三个源盒事件的近邻配对”表：在同一记录盒接收时刻相差不超过20毫秒、互为最近邻的事件中，源1/2的`E`中位数约2898.630毫秒，源1/3约3102.413毫秒。对应`三盒UWB时间对比.png`左图保留全量纵轴，右图仅放大±10毫秒，**不要把右图图外点当作已经合格**。`E`是两源消息时间差减接收时间差，仍含测距时隙与处理传输等待差，不是硬件同步误差。

第一轮201及第二轮三个接收盒均存在UWB方向的记录时间回退，不能直接套用这个依赖接收时间单调的二分近邻检查；因此未给它们生成伪精确的近邻同步结果。三边覆盖统计不依赖此配对，仍可独立使用。

## 9. 接下来优先让上交确认什么

1. **车载IMU消息头与姿态来源**：为什么有整秒回退，为什么060745盒203出现约1269秒回退并伴随姿态重置；同时保存原始设备计数器/采样时刻、发布时刻，检查同话题发布者数量、驱动组帧和旧缓存。
2. **三盒记录端时间来源**：系统授时是否在录包期间阶跃，ROS是否启用仿真时间；保存录包前后授时状态和日志。不要先用常数偏移或线性拟合把异常掩盖。
3. **第二轮Livox连续性**：201点云9.4秒消息间隔，202/203内置IMU回退，以及202帧1549内1.7秒逐点跨度；同时核对驱动时间单位和设备网络/接收/丢包日志。
4. **UWB三源发布与接收链路**：源1相对其他源的消息时间/到达关系为何偏离秒至数十秒，完整三边是否能在原在线超时内到齐。下一轮补三边卷尺真值，才能区分波动与绝对误差。

本次两个ZIP仍只有UWB、车载IMU、Livox话题，**没有相机图像、视觉里程计或视觉位姿消息，不能验证三盒视觉ROS2输出进度，也不能验证论文融合定位精度**。视觉已安装的口头进度与ROS2实际消息验收应分开。
