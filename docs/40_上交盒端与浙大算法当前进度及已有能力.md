## 1. 结论先行

- 三盒的 IMU、UWB 驱动和 ROS 2 数据链已经能够启动和录包。
- 三车 UWB 三边测距已经能够离线构造人为定义坐标系下的三角形相对位置；这条最简链路已经由实测包验证。
- 201 盒已经完成浙大 AArch64 程序的原生编译、在线启动和有效 `/cooperative_localization/poses_2d` 输出验收；约 60 秒在线录包也已完成输入输出统计。

- 最新实测仍未证明 IMU 与 UWB 的 `header.stamp` 属于可直接融合的统一时基，因此不能把两者按原始消息时间戳直接送入正式融合。
- GNSS 的串口配置、驱动入口和 ROS 消息接口存在，但最近联合包没有记录 `/gnss/fix`，尚未证明三盒均能输出有效的真实卫星定位结果。
- 201雷达在域0、Cyclone DDS、`ROS_LOCALHOST_ONLY=1`下已发现点云和内置IMU话题，两路各有1个RELIABLE发布者；但10秒频率检查和单帧订阅均未收到消息。下一步查设备、驱动日志及数据传输链，尚不能确定具体原因；202、203未完成相同验收。
- 相机是否存在、Topic 和数据质量尚未确认。

## 3. 最新实测已经证明什么

`joint_time_20260918_171701` 已将 UWB 默认录包盒改为 201，并证明：

- 三盒 IMU 和 201 观察到的 UWB 数据都能完整录制约 180 秒；
- 三盒 IMU 约 1000 Hz，UWB 每个有向测距流约 9.6 Hz；
- 本轮未发现消息时间戳回退或重复；
- 在 201 的同一接收时钟上，不同 UWB 源的配对到达时间差中位数约为 0.698～1.810 ms；这衡量的是配对消息到达 201 的相对错开，不是纯粹的无线传播时延；
- UWB 消息的“录包接收时刻减消息测量时刻”中位数约为 399～403 ms；
- 三盒 IMU 的同一差值分别约为 -15.221 s、-9.990 s、-4.002 s，说明原始 IMU 与 UWB 消息时间不能直接视为同一时基；
- UWB 有完整三边历元，但仍存在少量不满足三角不等式的异常组合，算法必须过滤；
- 三盒上游四元数仍观察到共同时间附近的约 180°跳变，不能直接当作连续姿态真值。

以上数值只代表该次数据。换硬件版本、驱动版本或时间源后必须重新验收。

## 4. GNSS 到底“有没有”

应当分成三层回答：

1. **配置和硬件接口层：有。** 参数文件中配置了 `/dev/ttyS6`，`gnss_uwb` 节点也包含 GNSS 数据采集入口。
2. **ROS 接口层：有约定。** 预期 Topic 是 `/gnss/fix`，消息类型为 `cooperative_interfaces/msg/GnssPosition`。
3. **当前可用定位数据层：尚未确认。** 最新联合包没有 `/gnss/fix`，现有 UWB 日志中的 `Received UWB GNRMC` 是 UWB/授时链路中的 RMC 文本，不能单独证明已经获得真实卫星定位。

因此当前准确表述是：**盒端具备 GNSS 配置和软件入口，但三盒真实 GNSS 定位是否都可用、是否为 RTK、采用什么时间源，仍待现场验证。**

验收至少需要看到三盒 `/gnss/fix` 中的节点号、非零且有限的经纬高、有效定位状态、连续频率、协方差，以及与 UTC/其他传感器时间的关系。

## 8. 在线输出相对位置的最短落地方案

第一版只使用 UWB，不等待 IMU、GNSS、雷达或相机接入。运行关系如下：

```text
201、202、203 的 gnss_uwb
  -> 在共享 ROS_DOMAIN_ID=107 中发布 /uwb/range
  -> 只在 201 启动 zju_cooperative_fusion_node
  -> 按相同 header.stamp 收齐 1—2、1—3、2—3 三条无向边
  -> 检查距离、三角不等式和最小三角形高度
  -> 解算瞬时规范三角形
  -> 发布 /cooperative_localization/poses_2d
  -> GCS直接订阅，或由一个很薄的适配节点转换成上交正式消息
```

202、203 不需要部署融合节点，也不需要把原始 IMU 发送给 201。它们只需要继续正常发布 UWB 测距；融合节点在 201 只运行一份。

### 8.1 第一版输出的坐标含义

UWB-only 每个有效历元都规定：

- 车1位于 `(0, 0)`；
- 车1指向车2的当前连线为 `+X`，车2位于 `(d12, 0)`；
- 车3固定取 `+Y` 的镜像分支；
- 三车 `position_valid=true`，但 `yaw_valid=false`。

因此它能在线输出队形形状、相对坐标和边角关系，但坐标轴会随当前车1—车2连线转动。仅靠三条标量距离不能确定相对北向、地图方向、车辆朝向，也不能恢复三角形绕平面的整体转角。若 GCS 需要固定坐标轴下的连续轨迹，必须再提供公共方向或相对运动观测。

### 8.2 当前程序已有部分

- 输入消息：`cooperative_interfaces/msg/UwbRange`；
- 在线节点：`zju_cooperative_fusion_node`；
- 通用启动入口：`zju_coop_bringup/launch/vehicle.launch.py`，通过参数选择输入能力；`uwb_only.launch.py`只是不启动其他适配节点的最小诊断快捷方式，不是另一套算法，也不是正式部署的必选入口；
- 模式：`input_mode=uwb_only`；
- 几何解算：`zju_coop_solve_three_node_formation()`；
- 输出消息：`cooperative_localization_msgs/msg/CooperativePose2DArray`；
- 输出 Topic：`/cooperative_localization/poses_2d`，Reliable、Volatile、Depth 1；
- ROS 自动测试和最新真实 bag 回放均已产生三车有效位置，航向按不可观处理。

### 8.3 盒端运行步骤

1. 将 `cooperative_interfaces`、`cooperative_localization_msgs`、`zju_coop_ros2` 和 `zju_coop_bringup` 构建并安装到 201。
2. 三盒使用相同的 `ROS_DOMAIN_ID=107` 和 `rmw_fastrtps_cpp`，共享链路设置 `ROS_LOCALHOST_ONLY=0`。
3. 启动三盒已有的 `gnss_uwb`，在 201 确认 `/uwb/range` 能看到节点 1、2、3 组成的三条边。
4. 只在201启动一份融合节点。正式部署可以统一使用 `vehicle.launch.py`；当前只有UWB时把 `input_mode` 保持为默认的 `uwb_only`，本地惯导即使暂时收不到IMU也不会阻塞UWB输出：

```bash
source /opt/ros/humble/setup.bash
source <浙大盒端工作空间>/install/setup.bash
export ROS_DOMAIN_ID=107
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOCALHOST_ONLY=0

ros2 launch zju_coop_bringup vehicle.launch.py \
  namespace:=vehicle_1 \
  run_fusion:=true \
  input_mode:=uwb_only
```

若只想排查“UWB消息能否直接形成三角形”，也可以临时使用更小的 `uwb_only.launch.py`；两种启动方式最终调用的是同一个融合可执行程序。

5. 在另一个 201 终端检查在线结果：

```bash
source /opt/ros/humble/setup.bash
source <浙大盒端工作空间>/install/setup.bash
export ROS_DOMAIN_ID=107
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOCALHOST_ONLY=0

ros2 topic hz /cooperative_localization/poses_2d
ros2 topic echo --once /cooperative_localization/poses_2d \
  cooperative_localization_msgs/msg/CooperativePose2DArray
```

只有 `position_valid=true` 的结果可以交给 GCS 使用。三边齐全但三角几何失败时会发布 `position_valid=false`；缺边历元直接丢弃。GCS还必须按消息时间戳设置结果超时，不能把长期没有更新的上一帧继续当作当前有效位置。

### 8.4 上线前还需补齐

- 确认上交实时消息中，同一物理历元的三边确实使用完全相同的 `header.stamp`；
- 与上交冻结 GCS 的 Topic、消息包、QoS、坐标含义、无效标记和期望频率；
- 做可移动盒子的动态试验；当前静止包只能证明链路和静态队形，不能给出动态延迟与定位精度。

代码当前已经完成：

- 通用 `vehicle.launch.py` 和用于最小排障的 `uwb_only.launch.py`；
- 同一无向边双向测量取均值；双向差异不再由适配层重复硬拦截；
- 统一短等待窗后处理完整历元，单向值也可直接参与；
- 缺边历元超时失效；
- 三边齐全后只调用一次三角形几何求解器；不满足三角不等式、退化或数值条件的历元输出 `position_valid=false`；
- 不会把上一帧位置伪装成新的有效测量，GCS应另设结果超时。

`fusion.yaml` 中原有的互惠差异、距离变化率和跳变参数名仍保留，以兼容旧 launch/YAML，但当前 UWB-only 不再使用它们做适配层二次门控；最终几何判定集中在三角形求解器。

在这些工作完成前，可称为“在线 UWB 相对队形原型”；完成动态和 GCS 验收后，才可称为正式在线相对定位输出。

### 8.6 同一程序接入可选传感器的边界

部署层可以只保留一份 `vehicle.launch.py` 和一份融合程序。当前参数含义为：

- `input_mode:=uwb_only`：只要三条同历元UWB边可用，就输出规范相对三角形；这是无其他传感器时的安全默认值；
- `input_mode:=imu_uwb`：只有三车NodeState已经具备同一时间基准、同一公共水平坐标系和有效初始化时才允许启用；
- 点云、RGB和GNSS均通过各自适配节点转换成算法认可的观测，不要求修改GCS输出Topic和消息类型。

“发现某个Topic存在”不能直接等同于“允许把它加入滤波”。自动加入前至少还需确认消息持续有效、时间可对齐、坐标系和外参已知、质量字段合格，而且加入后不能悄悄改变输出坐标系。否则插入一只时间错误或外参错误的传感器，结果会比不用它更差。

因此推荐的即插即用策略是：程序始终可以启动，UWB作为当前保底输入；其他传感器缺失时不阻塞输出，出现时先进入“检测到但未采用”状态，满足该类传感器的验收条件后再由参数允许参与融合，失效后自动退出并把对应有效标志降级。输出始终使用 `/cooperative_localization/poses_2d`，不能满足任何相对定位可观测条件时发布无效状态，而不是编造位置。

当前代码已经做到同一可执行程序支持 `uwb_only` 与 `imu_uwb`，点云和RGB也有可选订阅/输入校验；尚未做到在运行中无条件自动切换所有传感器组合，也不应仅靠Topic出现就自动切换。尤其从纯UWB规范坐标系切换到公共ENU时会改变坐标轴含义，必须重置会话或提供明确坐标变换，不能对GCS伪装成同一个连续坐标系。

### 8.7 本轮代码精简依据

参考工程采用的共同模式是“输入缓冲/时间配对 → 一次估计更新 → 统一输出”：FAST-LIO 在缓冲区中配对 IMU 与点云后进入单一处理循环；Omni-swarm 将跨机观测同步和后端异常值处理分开，不在每层重复做同一拒绝。当前节点据此调整为：ROS 适配层只做消息基本合法性、节点身份和同历元归并；UWB-only 在三边齐全后只调用一次三角形几何求解器；IMU/UWB 模式的参考时间桥只保护时间跳变，具体状态合法性仍由 SDK 处理。旧参数名保留，但不再触发重复的互惠差、距离速率和跳变三重硬门控。

### 8.8 当前调用关系与程序逻辑

#### 8.8.1 总体数据流

```text
上交 gnss_uwb ──> /uwb/range ───────────────┐
                                             │
上交 navcore ──> /imu/raw ─> 本地惯导节点 ──> /cooperative_localization/node_state
                                             │
                                             v
                              zju_cooperative_fusion_node
                                             │
                                             v
                         /cooperative_localization/poses_2d
                                             │
                                             v
                                            GCS
```

点云和相机目前是可选输入：本地惯导节点可以订阅并做消息格式检查，但当前不会改变主定位结果。GNSS也不自动加入融合，避免一个未确认时间源或坐标系的传感器改变输出含义。

#### 8.8.2 启动阶段

`vehicle.launch.py`启动 `zju_local_inertial_node` 和 `zju_cooperative_fusion_node`。融合节点构造时依次完成：读取参数、检查车辆编号和参考车、创建 SDK 句柄、创建订阅/发布器、按 `input_mode` 创建定时器。

- `input_mode=uwb_only`：不依赖 IMU 和 NodeState，只订阅 `uwb_range`，适合当前三车最小链路；
- `input_mode=imu_uwb`：同时订阅 NodeState 和 UWB，将两者交给 SDK 的分布式融合器；
- 对外仍只发布 `CooperativePose2DArray`，默认话题为 `/cooperative_localization/poses_2d`。

#### 8.8.3 UWB-only 调用链

1. `on_uwb_range()` 做一次基本检查：时间戳有效、源/目标不同且属于配置车辆、距离为有限正数。`rolling`不参与算法。
2. `on_uwb_only_range()` 将源/目标转换为无向边 `01、02、12`，按消息 `header.stamp` 放入同一个历元；同一条边的两个方向分别保存。
3. `process_uwb_epochs()` 等待短窗口，让同历元的其它边或反向测量到达。三条边齐全后进入求解；缺边到期则丢弃该历元，不拿上一帧冒充新测量。
4. `solve_uwb_epoch()` 对同一无向边的双向值取均值，组装 C ABI 的三边结构，调用一次 `zju_coop_solve_three_node_formation()`。
5. 三角不等式、退化程度和数值合法性由几何求解器统一判定。成功时更新三车相对坐标；失败时发布同一输出消息但将 `position_valid=false`。
6. `publish_uwb_formation()` 把求解结果转换成 `CooperativePose2DArray` 发布。参考车坐标为 `(0,0)`，`yaw_valid=false`，因为三条距离不能提供车辆自身航向。

这条链路有意保持很短：消息适配层负责“能不能交给算法”，几何函数负责“这组三边能不能解”，不再在中间重复做互惠差、跳变速率和几何判定。

#### 8.8.4 IMU/UWB 调用链

1. `zju_local_inertial_node::on_imu()` 检查 IMU 时间顺序和基本格式，完成 FRD/FLU 等输入变换，把数据送入 C API 的 15 状态惯导处理器。
2. 惯导节点从 SDK 读取当前状态，发布 `NodeState`；其 `header.stamp` 是状态对应的测量时间，不是 ROS 回调到达时间。
3. 融合节点 `on_node_state()` 检查公共坐标系、车辆编号和时间递增，使用参考车 NodeState 建立 UWB 时间桥，再调用 `zju_coop_distributed_push_node_state()`。
4. 融合节点收到 UWB 后构造带测量时间和接收时间的测距包，调用 `zju_coop_distributed_push_range()`。SDK在测量时刻对齐状态、计算距离创新并决定是否更新。
5. 发布定时器调用 `zju_coop_distributed_get_pose2d_v2()`，将 SDK 快照转换成同一个 `CooperativePose2DArray` 输出接口。

#### 8.8.5 这样分层的原因

- ROS 节点是适配层，不重复实现滤波、三角求解和异常值模型，减少“入口判一次、SDK再判一次”造成的逻辑分叉；
- 时间戳必须按测量时间融合，接收时间只用于判断数据是否过旧或建立在线时间桥，不能把接收时刻当成测量时刻；
- UWB-only 必须在没有 IMU 时仍能输出，所以三角形几何求解不能依赖 NodeState；
- 缺边和时间异常属于输入链路问题，几何不成立属于模型问题，分别在归并层和几何求解器处理；
- 保留消息、话题、参数名和 C ABI 不变，便于继续使用现有 launch、录包、Foxglove 和 GCS 对接程序；
- 只有涉及设备边界、时间回退、非法数值和坐标系的检查才保留，避免过度防御掩盖正式算法路径。

## 9. 当前问题与待办（统一清单）

下面是当前仍影响正式验收的事项，历史测试数据和原详细清单已保留在归档目录：

- 三盒 IMU、UWB 的共同时间尚未完成硬件级验收；现有包可检查连续性，但不能据此给出物理同步精度。
- 上游 IMU 四元数曾出现约 180° 突变；浙大自有姿态传播不直接依赖该四元数，但仍需上交解释来源。
- UWB 仍存在缺边、互惠噪声和异常距离；当前节点按同历元归并后交给三角形几何求解器，尚未完成动态场景的外点统计和长期稳定性验收。
- 没有独立卷尺、RTK 或其他真值时，只能评价有效率、连续性和静态重复性，不能宣称绝对定位精度。
- 201 盒 Livox 进程和话题已发现，但测试窗口未收到有效点云样本；相机仍未确认，雷达和视觉尚未接入主融合。
- GNSS 只有接口和串口配置证据，真实 `/gnss/fix`、解类型、时间源和真值用途仍需现场验收。
- UWB-only 在线相对位置已在 201 盒最小链路跑通，但正式 GCS Topic、QoS、状态字段和端到端联调仍待冻结。
