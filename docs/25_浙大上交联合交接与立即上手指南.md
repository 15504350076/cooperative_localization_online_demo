## 1. 接手后先记住的结论

1. 浙大算法和 ROS 2 主链已经在 Ubuntu 22.04 x86-64 完成实现与自动测试；尚未完成 RK3588/AArch64 实盒部署验收。
2. 上交已经提供并运行了 `navcore`、`gnss_uwb` 和 MID360 驱动链，当前仓库也已按上交消息复现 `cooperative_interfaces`；车1能收到约 1000 Hz IMU，UWB RMC 授时日志也能递增。
3. 上交已确认 `/imu/raw` 原始坐标系为 **FRD：前、右、下**。浙大算法内部使用 **FLU：前、左、上**，适配参数为 `imu_sensor_to_flu_xyzw: [1, 0, 0, 0]`，即绕 `+X` 轴旋转 180°。
4. 当前车1 IMU 时间戳虽然已从全零发展到非零，但历史连续数据出现过约 `0.9 s` 回退和约 `1.1 s` 跳变，因此统一时间验收仍未通过。此问题修复前不得做正式惯导积分、三车闭环或精度结论。
5. 当前正式 UWB 消息只有 `header/src_id/target_id/distance`，没有序号、标准差、NLOS、`valid/status`。浙大适配层暂时自增序号、从参数读取标准差，并把合法包视为 `OK`。这是首版兼容，不是完整生产质量接口。
6. 点云和相机将来要加，但当前原始 C ABI 只校验格式；可选 ICP、视觉地标和 SLAM 是独立前端，默认关闭，尚未进入惯导或协同滤波。
7. 第一轮不要从 `cooperative_inertial_ekf.cpp` 的旧 45 维集中式路径开始改。实盒首版主线是：每车 `local_inertial_node` 维护本车 15 维惯导，参考车 `cooperative_fusion_node` 汇聚低带宽 `NodeState + UWB`。

当前项目可以概括为：**软件闭环已具备，车1传感器链已部分打通，三车生产闭环尚未过闸门。**

## 2. 最小系统和数据流

### 2.1 首版生产链路

```text
每辆车本机
上交 IMU/STM32/UWB 硬件
  -> 上交 navcore / gnss_uwb 驱动与协议解析
  -> /imu/raw（FRD车体系、NED姿态，约1000 Hz，仅本机 DDS）
  -> 浙大 zju_local_inertial_node
  -> FRD/NED/SI 适配为 FLU/ENU/SI
  -> 启动静止窗口估计roll、pitch和剩余陀螺零偏
  -> 浙大本车 15 维 ESKF
  -> NodeState（默认20 Hz）
  -> localhost NodeState 校验桥
  -> /cooperative_localization/node_state（共享 DDS）

参考车1
三车 NodeState + 上交 /uwb/range
  -> 浙大 zju_cooperative_fusion_node
  -> UWB 时刻状态对齐 + 二维协同修正
  -> /cooperative_localization/poses_2d（默认10 Hz）
  -> 上交 GCS / 记录与评价端
```

### 2.2 为什么有 localhost 桥

上交要求 `navcore` 和原始 `/imu/raw` 使用 `ROS_LOCALHOST_ONLY=1`，而三车 `NodeState`、UWB 和协同结果需要共享 DDS。Fast DDS 中两种 `ROS_LOCALHOST_ONLY` 进程不能直接互相发现，因此浙大 `vehicle.launch.py` 提供：

```text
localhost DDS
  local_inertial_node -> /cooperative_localization/node_state_local
  -> 127.0.0.1 校验数据报（版本、长度、CRC）

shared DDS
  node_state_shared_relay -> /cooperative_localization/node_state
```

桥只转发紧凑 `NodeState`，不转发 IMU、点云或图像。这样原始高频数据不经过 5G Mesh，也不会让远端误订阅其他车 IMU。

### 2.3 当前不在主线中的路径

- `CooperativeInertialEkf`：旧集中式 45 维回归基线，不是首版三盒部署入口；
- `zju_coop_online`：临时 ZJCL/UDP 演示，不是实盒 ROS 2 生产入口；
- GNSS 距离后备：仅在 UWB 测距失效但 UWB 授时仍有效时显式启用；
- 点云、相机、ICP、视觉、RTAB-Map：独立可选前端，默认关闭且不反馈主滤波；
- GNSS 初始化/RTK 相对真值 C ABI：算法库已有，正式上交 wrapper 和实盒 RTK 尚未完成。

## 4. 坐标系契约

### 4.1 上交原始 IMU：FRD

```text
+X：Forward，车头前方
+Y：Right，车辆右侧
+Z：Down，车辆下方
```

水平静止时，若消息是算法所需的比力语义，原始 `/imu/raw` 应满足：

```text
|accel| ~= 9.81 m/s^2
accel.z ~= -9.81 m/s^2
```

车顶俯视逆时针转动为正航向变化；在 FRD 右手系中，原始 `gyro.z` 应为负。

### 4.2 浙大算法输入：FLU

```text
+X：Forward，车头前方
+Y：Left，车辆左侧
+Z：Up，车辆上方
```

三车参数当前一致：

```yaml
imu_sensor_to_flu_xyzw: [1.0, 0.0, 0.0, 0.0]
imu_navigation_to_enu_xyzw: [0.7071067811865475, 0.7071067811865475, 0.0, 0.0]
gyro_scale_to_rad_s: 1.0
accel_scale_to_m_s2: 1.0
enable_static_imu_initialization: true
static_imu_initialization_duration_s: 10.0
```

变换结果为：

```text
[x, y, z]_FLU = [x, -y, -z]_FRD
```

因此水平静止时适配后的 `accel.z` 应约为 `+9.81 m/s²`；车顶俯视逆时针 `+90°` 时，适配后 `gyro.z` 积分应约为 `+1.57 rad`。

注意：`frame_id: imu_link` 只是身份字符串，不会自动完成换轴。真正的向量、姿态和三类协方差转换由 `ImuInputTransform` 执行。

### 4.3 导航与输出坐标

| 坐标系 | 定义 | 用途 |
|---|---|---|
| `common_enu` | `+X East, +Y North, +Z Up` | 三车本地 NodeState 的共同导航系 |
| `coop_ref_1_enu` | 原点是参考车1同历元位置，轴向仍平行 `common_enu` | 协同二维结果 |

`VehiclePose2D.yaw_rad` 是车辆自身 FLU 前向相对 ENU 东轴的航向：东向为 0，北向为 `+pi/2`，逆时针为正，范围 `[-pi, pi)`。它不是从参考车指向本车的方位角，也不是两车航向差。

## 5. 时间契约

### 5.1 唯一算法时域

实盒主链统一使用 `UWB_SYSTEM_TIME`，单位纳秒。它是本次 UWB Master 同步历元开始后的运行时间：

- 不是 Linux 系统时间；
- 不是 ROS/SystemTime UTC；
- 不是未转换的 GNSS UTC；
- 不是串口接收、ROS 回调或消息发布时间。

下列时间戳必须在同一数值时域：

- `/imu/raw.header.stamp`：实际 IMU 采样时刻；
- `/uwb/range.header.stamp`：双方冻结的实际测距事件时刻；
- `/gnss/fix.header.stamp`：转换到 UWB 时域后的 GNSS 测量时刻；
- `NodeState.header.stamp`：本地惯导最后接受的 IMU 时刻；
- `CooperativePose2DArray.header.stamp`：整组结果的统一算法时刻。

### 5.2 首轮运行规则

- 数字开关固定选择 `UWB_PPS`；
- 不支持运行中静默切换 PPS；
- 同一 IMU 流、同一节点状态流、同一无向 UWB 边必须非零且严格递增；
- Master 重启、PPS 切换、时间回拨或大幅跳变后，修复源头并整组重启定位链；
- `steady_clock` 只用于把本机经过时间映射到 UWB 时域，不能冒充测量时间；
- GNSS 距离后备不能在 UWB 授时失效时维持主链。

### 5.3 当前车1时间问题

已观察到：

```text
1785647429.996285000 -> 1785647429.096316000
```

时间回退约 `0.9 s`，随后又出现约 `1.1 s` 跳变。该现象优先检查：

1. RMC 秒进位；
2. PPS 捕获秒号与 IMU 小数秒拼接；
3. 双缓冲或线程交换导致旧帧倒灌；
4. UWB Master/计时器重启；
5. 日志显示链是否混入多发布者。

浙大节点在运行后检测到归零、回退、超出时间窗或积分间隔拒绝时会锁存故障并停算、停发。修复上游时间后必须重启本地惯导节点。

## 6. 上交输入接口

### 6.1 Topic 总表

| Topic | 类型 | 上交发布端 | 浙大消费端 | 范围 | 当前状态 |
|---|---|---|---|---|---|
| `/imu/raw` | `sensor_msgs/msg/Imu` | `navcore` | 每车 local node | `ROS_LOCALHOST_ONLY=1` | 车1数据可达；时间未过验收 |
| `/uwb/range` | `cooperative_interfaces/msg/UwbRange` | `gnss_uwb` | 参考车 fusion | 共享 DDS | 类型已接入；有效多边数据待验收 |
| `/gnss/fix` | `cooperative_interfaces/msg/GnssPosition` | `gnss_uwb` | 可选 GNSS 后备 | 共享 DDS | 室内日志无有效定位；主线默认不用 |
| `/node/id` | `cooperative_interfaces/msg/Identity` | `gnss_uwb` | 联调身份核验 | 共享 DDS | 消息已知；三车需逐盒复核 |
| MID360 点云 | 待运行时确认 | Livox 驱动 | 可选本机前端 | 默认本机 | 驱动进程可见，topic未冻结 |
| RGB 图像 | 待确认 | 相机驱动 | 可选本机前端 | 默认本机 | 启动方式/topic未确认 |

### 6.2 `/imu/raw`

浙大逐字段读取，不把 ROS 消息内存强转成 C 结构：

| ROS 字段 | 浙大处理 | 要求 |
|---|---|---|
| `header.stamp` | 写入 `timestamp_ns` | UWB时域、非零、严格递增 |
| `header.frame_id` | 校验为 `imu_link` | 长度须适配 C ABI |
| `orientation` | FRD->NED姿态转为FLU->ENU姿态 | 仅在有效且归一化时使用 |
| `orientation_covariance` | 旋转到FLU | `[0] < 0` 表示未提供姿态 |
| `angular_velocity` | FRD转FLU并乘单位比例 | 最终必须为 rad/s |
| `angular_velocity_covariance` | 旋转并按比例平方缩放 | 单位 rad²/s² |
| `linear_acceleration` | FRD转FLU并乘单位比例 | 最终为 m/s² 比力 |
| `linear_acceleration_covariance` | 旋转并按比例平方缩放 | 单位 m²/s⁴ |

当前静态包中的姿态四元数与重力姿态和扣偏积分基本一致，但它由同一套 IMU 的 AHRS 生成，不是独立真值。三个协方差数组仍为全零；全零表示“未知”，不表示高置信度。若某版本姿态只是占位值，上交应按 ROS 约定设置 `orientation_covariance[0] = -1`。

### 6.3 `/uwb/range`

当前上交消息定义：

```text
std_msgs/Header header
uint32 src_id
uint32 target_id
float32 distance
```

当前适配：

| 上交字段 | C ABI 字段/行为 |
|---|---|
| `header.stamp` | `timestamp_ns`，必须属于 `UWB_SYSTEM_TIME` |
| `src_id` | `from_node`，必须是逻辑车辆号而不是硬件UWB十进制ID |
| `target_id` | `to_node`，必须是另一已配置逻辑车辆号 |
| `distance` | `range_m`，必须有限、为正且单位为米 |
| 无序号 | 浙大 fusion 进程内暂时自增 `sequence` |
| 无标准差 | 从 `fusion.yaml: range_std_m` 读取，当前默认 `0.1 m` |
| 无质量字段 | 合法输入暂时设置 `valid=true, status=OK` |
| 无 NLOS 字段 | 当前不能从设备质量主动降权，只能依赖创新/NIS与统计退化 |

生产版建议通过版本化消息补充 `sequence/range_std_m/NLOS/valid/status`，但在双方冻结前不得擅自改变现有字段顺序和类型。

### 6.4 `/gnss/fix`

当前上交 `GnssPosition` 包含：

- `header`；
- `node_id`；
- `status`；
- WGS-84 `latitude/longitude/altitude`；
- 3×3 ENU `position_covariance`；
- `position_covariance_type`。

主 IMU+UWB 链默认不消费 GNSS。显式 GNSS 后备只把同历元三车 GNSS 几何位置转换为低置信度距离，不把绝对经纬度直接写入本地惯导。RTK 初始化/真值 C ABI 是另一条独立上下文，不能把真值回灌后再用同一真值评价。

### 6.5 `/node/id`

```text
uint32 node_id
uint16 uwb_id
```

`node_id` 是协同定位逻辑编号；`uwb_id` 是硬件标签编号，不能互换。当前期望：

| 车辆 | IP | `node_id` | 十六进制 UWB | 十进制 `uwb_id` |
|---|---|---:|---:|---:|
| 车1 | `192.168.1.201` | 1 | `0x49D9` | 18905 |
| 车2 | `192.168.1.202` | 2 | `0x5695` | 22165 |
| 车3 | `192.168.1.203` | 3 | `0xF541` | 62785 |

每次启动前必须同时核对 IP、参数文件、`/node/id` 和实际 UWB 标签。车3旧记录为 `0x4A9D` / `19101`，2026-08-06现场参数已变为 `0xF541` / `62785`，暂按当前值测试并由上交确认标签更换和三盒映射。更早历史记录中车3还曾出现 `node_id=1, uwb_id=22165` 的错配。

## 7. 浙大输出接口

### 7.1 `/cooperative_localization/node_state`

类型：`cooperative_localization_msgs/msg/NodeState`。默认每车 20 Hz、Best Effort、Keep Last 5。

| 字段 | 语义 |
|---|---|
| `header.stamp` | 本车惯导最后接受的 IMU 时刻，不是发布时间 |
| `header.frame_id` | `common_enu` |
| `node_id` | 本车逻辑编号 |
| `position_enu_m[3]` | 公共ENU绝对位置 |
| `velocity_enu_mps[3]` | 公共ENU速度 |
| `orientation_flu_to_enu_xyzw[4]` | FLU到ENU单位四元数 |
| `valid` | 整条状态是否可用于协同层 |

完整 15×15 协方差、陀螺零偏和加计零偏只留在本车，不跨 Mesh 发布。

### 7.2 `/cooperative_localization/poses_2d`

类型：`cooperative_localization_msgs/msg/CooperativePose2DArray`。默认参考车 10 Hz、Reliable、Keep Last 1。

```text
header.stamp       整组三车统一算法时刻
header.frame_id    coop_ref_1_enu
reference_node_id  1
vehicles[]
  node_id
  x_m, y_m
  yaw_rad
  position_valid
  yaw_valid
```

消费者必须检查每车有效位和整个消息时间年龄。Topic 仍在 10 Hz 发布不代表某辆车的位置仍有效。UWB 当前只修正二维相对位置，不直接观测航向；航向来自各车本地惯导。

### 7.3 可选反馈 Topic

`/cooperative_localization/feedback/poses_2d` 默认关闭。打开后内容与 GCS 结果相同，但规划端仍需自身 watchdog、失联停车和急停。GNSS 距离后备模式下不得开启规划反馈。

## 8. C ABI 和代码调用关系

### 8.1 公开边界

唯一公开头文件是 [c_api.h](../include/zju_coop/c_api.h)。调用方必须：

1. 先调用对应 `*_init()`；
2. 再填写业务字段；
3. 检查每次返回码；
4. 检查 processing/update disposition，不能只看 `ZJU_COOP_OK`；
5. 一个 handle 只串行调用；
6. 创建成功后恰好销毁一次；
7. 不自行猜 `struct_size`、版本、stride 或保留字段。

本车惯导关键顺序：

```text
zju_coop_config_init
zju_coop_create
zju_coop_inertial_config_init
zju_coop_configure_inertial
循环：zju_coop_imu_packet_init -> zju_coop_push_imu
定时：zju_coop_get_node_state
zju_coop_destroy
```

参考车协同关键顺序：

```text
zju_coop_config_init
zju_coop_distributed_create
循环：zju_coop_distributed_push_node_state
循环：zju_coop_distributed_push_range
定时：zju_coop_distributed_get_pose2d_v2
zju_coop_distributed_destroy
```

### 8.2 当前内部拆分

| 文件 | 职责 |
|---|---|
| `src/api/c_api.cpp` | 主算法、分布式融合、GNSS C ABI 翻译和异常隔离 |
| `src/api/c_api_raw_input.cpp` | 点云/图像原始输入校验，不依赖 `Engine` |
| `src/api/c_api_detail.hpp` | 仅供 API 实现共享的私有 ABI 校验工具，不安装 |
| `include/zju_coop/c_api.h` | 保持不变的公开声明和结构布局 |

这次拆分只按真实职责拆翻译单元，没有新增“感知大接口”或新 handle。等点云/视觉真正产生相对位姿、里程计或绝对约束时，再给独立前端定义小而稳定的结果接口；原始大数据不直接塞进惯导 `Engine`。

### 8.3 源码阅读顺序

1. [vehicle.launch.py](../ros2/zju_coop_bringup/launch/vehicle.launch.py)：先看进程和 Topic；
2. [local_inertial_node.cpp](../ros2/zju_coop_ros2/src/local_inertial_node.cpp)：看 IMU 到 NodeState；
3. [imu_input_transform.hpp](../ros2/zju_coop_ros2/src/imu_input_transform.hpp)：看 FRD 到 FLU；
4. [inertial_eskf15.cpp](../src/core/inertial_eskf15.cpp)：看 15 维本车传播；
5. [cooperative_fusion_node.cpp](../ros2/zju_coop_ros2/src/cooperative_fusion_node.cpp)：看 NodeState/UWB 到结果；
6. [distributed_fusion2d.cpp](../src/core/distributed_fusion2d.cpp)：看二维修正；
7. [c_api.h](../include/zju_coop/c_api.h) 和 `src/api/c_api*.cpp`：最后看稳定边界。

`cooperative_inertial_ekf.cpp` 是旧集中式回归路径。除非任务明确要求维护旧模式，否则不要把首版三盒逻辑重新堆回这个大类。

## 13. 常见故障定位

| 现象 | 优先检查 | 禁止做法 |
|---|---|---|
| 看不到 `/imu/raw` | 两端 Domain/RMW/localhost、navcore PID、ttyS4占用 | 改成共享DDS绕过隔离要求 |
| 时间一直为0 | UWB RMC、PPS源、navcore授时链 | 写死 `dt=0.001` |
| 时间回拨/跳变 | RMC秒进位、PPS配对、旧帧倒灌、Master重启 | 放宽算法门限继续积分 |
| 静止 z 为负 | 先确认原始FRD，再检查 `[1,0,0,0]` 是否加载 | 直接在算法核心交换轴 |
| NodeState无输出 | local日志是否锁存时间故障、IMU是否被接受 | 用定时器伪造状态时间 |
| UWB有发布者但无数据 | `topic hz/echo`、标签映射、单车是否本来无边 | 把发布者存在当成测距通过 |
| UWB被拒绝 | 逻辑ID、正距离、同域时间、NodeState历史、新鲜度 | 用硬件UWB ID填src/target |
| Pose2D位置无效 | NodeState是否齐全、近期有效边连通、超时 | 忽略 `position_valid` |
| yaw有效但位置无效 | UWB超时而本地惯导仍新鲜，属于可能现象 | 把yaw当成UWB修正结果 |
| 点云/图像返回成功但位置不变 | 当前只 `VALIDATED_NOT_USED` | 宣称已融合感知数据 |
| x86可运行、盒端库加载失败 | 是否把x86 `.so` 复制到AArch64 | 跨架构复用二进制 |
| `Tag ID unknown` | 完整硬件ID映射和参数表 | 临时把unknown标签当逻辑节点 |

## 14. 修改和交付纪律

1. 修改公开 C ABI 前必须说明版本、布局、兼容性、调用方和测试；优先新增而不是改旧字段。
2. ROS消息逐字段转换，不做内存强制转换；上交正式消息变更后同步修改消息复现、适配、测试和文档。
3. 原始点云/图像留在独立前端；主 `Engine` 接受的是经过定义、带时间和协方差的低维观测。
4. 旧集中式、分布式主线、GNSS上下文和原始输入不要共用一个有大量无关状态的大对象。
5. 防御性检查集中放在 C ABI、ROS/网络边界和时间边界；核心数值代码不重复堆相同检查。
6. 不覆盖他人未提交工作。交接前执行：

```bash
git status --short
git diff --check
git diff --stat
```

7. 每次交付至少记录：commit/tag、目标架构、编译器、ROS 2/RMW、配置文件、测试命令、结果和已知问题。
8. 任何“通过”结论必须附原始日志、bag或自动测试输出；口头确认只可写“已确认”，不能替代实测。
