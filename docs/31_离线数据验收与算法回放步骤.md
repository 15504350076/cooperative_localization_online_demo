# 31_离线数据验收与算法回放步骤

没有互联网、没有AI、三盒也不在线时，只要原始包已收回，按本页在**我们自己的Ubuntu开发电脑**检查。无需向201、202、203上传分析程序。没有互联网但局域网仍通时，现场采集照[21精简步骤](21_上交盒端传感器节点启动与可用性检查_精简执行版.md)执行。

顺序：**核对每盒采集清单 → 数据完整性 → 单传感器质量 → 时间关系 → 算法回放 → 输出结果 → 有真值才评精度。**

### 1.1 先打开实验目录，认识每个文件

不要一拿到压缩包就直接运行总分析。先把实验目录展开，确认“原始证据”和“分析结果”都在：

```bash
RUN=data/joint_time_20261016_150956
find "$RUN" -maxdepth 2 -type f -printf '%P\n' | sort
```

典型目录应类似下面这样：

```text
joint_time_20261016_150956/
├── manifest.json                         # 本轮计划：盒号、域、时长、是否录在线输出
├── 采集状态.json                         # 录包程序的就绪判定和错误
├── 实验备注.txt                          # 静止/移动、启动顺序、PPS和现场异常
├── *_imu_rec_v1.log                      # 201录IMU的rosbag日志
├── *_imu_rec_v2.log                      # 202录IMU的rosbag日志
├── *_imu_rec_v3.log                      # 203录IMU的rosbag日志
├── *_uwb_rec_v1.log                      # 201录共享UWB/在线输出的日志
├── *_rec_v*/metadata.yaml                # 这个bag实际录到哪些Topic、各有多少条
├── *_rec_v*/*.db3                        # 原始消息数据库，最重要的原始证据
├── 联合时间初查.md                       # 快速发现时间区间、零值和回退
├── 联合时间验收.md                       # 逐流频率、Header和接收时间统计
├── 联合时间详细统计.csv                  # 逐流机器可读统计
├── 联合时间轴对比.png                    # 时间关系可视化
└── *_uwb_rec_v*/online_analysis/         # 录到在线输出时才会有
    ├── 在线相对定位分析.md                # 输出频率、有效率、坐标和UWB边
    ├── analysis.json                      # 同一结论的机器可读版本
    ├── uwb_records.csv                    # 每条测距及两个时间
    └── pose_records.csv                   # 每帧三车位置和有效标志
```

每个文件回答的问题不同：

| 先打开的文件 | 它能证明什么 | 不能证明什么 |
|---|---|---|
| `manifest.json` | 本轮原计划录哪些盒子、哪个盒子录UWB、是否要求在线输出 | 实际是否收到消息 |
| `采集状态.json` | 录包进程是否建立了全部请求订阅，SSH/下载是否报错 | 消息是否持续、时间是否同步 |
| `实验备注.txt` | 当时是否静止、是否移动、启动顺序和现场操作 | 传感器自身时间正确 |
| `*.log` | rosbag是否启动、订阅了什么、是否出现`unknown type`、是否正常结束 | 话题中的消息内容 |
| `metadata.yaml` | 实际Topic、消息类型、消息数量、bag跨度 | 消息数非零就代表质量合格 |
| `.db3` | 原始消息本体；所有自动报告都从这里读出 | 直接打开不方便人工阅读 |
| `联合时间验收.md/.csv` | 每条IMU/UWB流的频率、时间基准、回退、接收差值 | 绝对定位精度 |
| `online_analysis/在线相对定位分析.md` | 算法是否输出三车位置、有效比例、坐标和UWB边 | 没有真值时的定位误差 |
| `.tar.gz` | 传输和归档用的原始包 | 不解压时不能用`ros2 bag info`读取 |

以`joint_time_20261016_150956`为例，人工查看应得到这条证据链：

```text
manifest.json: include_poses=true
  ↓
采集状态.json: all_subscribed=true, errors=[]
  ↓
201的metadata.yaml: /uwb/range、/node/id、/cooperative_localization/poses_2d均非空
  ↓
联合时间验收.md: 202盒IMU Header约34万秒，与其他流约17.8亿秒不同
  ↓
online_analysis/在线相对定位分析.md: 位置输出约9.24 Hz、1660帧全部有效
  ↓
最终结论: 纯UWB在线输出链路通过；202盒IMU时间基准仍不能用于IMU融合
```

如果在第二步就看到`all_subscribed=false`，先查日志；如果`metadata.yaml`没有目标Topic，不要继续看算法结果；如果在线输出存在，再把`联合时间验收.md`和`在线相对定位分析.md`放在一起判断。这样可以区分“没录到”“录到了但时间有问题”和“算法输出正常但还没有真值”。

Windows上只查看目录结构时可用：

```powershell
$run = ".\data\joint_time_20261016_150956"
Get-ChildItem $run -Recurse -File | Select-Object FullName,Length
Get-Content "$run\manifest.json"
Get-Content "$run\采集状态.json"
```

PowerShell只适合查看清单和日志；`metadata.yaml`、`.db3`的Topic内容和时间统计仍在Ubuntu终端执行本页后续命令。

### 1.2 每一步运行后看什么

本页不是“运行一个总程序后结束”。每个程序都会在实验目录生成可复核文件，按下面顺序看：

| 操作 | 生成或读取的文件 | 先看什么 | 判定方向 |
|---|---|---|---|
| `ros2 bag info` | 不生成文件，只读取`metadata.yaml` | Topic、类型、消息数、跨度 | 先确认包不是空包、话题没有缺失 |
| `record_joint_time.py --analyze` | `时间戳统计.json`、`联合时间初查.md` | 每路首末Header、零值、回退、重复 | 发现时间基准或连续性初筛异常 |
| `analyze_joint_time.py` | `联合时间验收.md`、`联合时间详细统计.csv`、`联合时间轴对比.png` | 每流频率、Header时间、接收回退、R−H | 判断哪一路时间基准不一致；R−H不是纯网络延迟 |
| `analyze_imu_bag.py` | 各IMU目录的`imu_analysis.txt` | 频率、长间隔、角速度/加速度有限性、姿态跳变 | 判断单盒IMU是否可作为连续输入 |
| `export_uwb_bag_readable.py` | `UWB测距分析.md`、`UWB测距数据.csv`、曲线图 | 六个有向流、三条无向边、距离离群和间断 | 判断测距是否齐全、几何数据是否异常 |
| `compare_uwb_timestamps.py` | `UWB时间对比/三盒UWB时间对比.md`及CSV/PNG | 源盒间接收配对差、Header差、未配对数 | 只作到达关系诊断，不证明硬件同步 |
| `analyze_online_bag.py` | `online_analysis/在线相对定位分析.md`、`analysis.json`、两个CSV | 输出频率、有效帧、三车坐标、缺边 | 判断协同结果是否实际录入、是否有效 |
| `analyze_lidar_bag.py` | 终端报告或重定向的`雷达短包分析.txt` | 点云/雷达IMU计数、频率、零点、点内时间 | 判断雷达是否出数；不代表已进入主融合 |
| `analyze_gnss_bag.py` | `GNSS户外静止分析.md`、`GNSS数据.csv`、PNG | fix状态、坐标连续性、消息时间 | 判断GNSS是否有效；无真值不能给精度 |
| `analyze_camera_samples.py` | `相机单帧分析.md`、预览图 | 格式、尺寸、亮度、三路画面差异 | 只能判断单帧采集，不证明同步 |

最终写结论时，至少引用三类证据：

1. `metadata.yaml`：证明实际录到了哪些话题；
2. `联合时间验收.md`及专项报告：证明数据质量和时间问题；
3. `在线相对定位分析.md`：证明算法是否真的输出了协同结果。

只有终端打印、没有生成报告的命令（例如`ros2 bag info`、实时`topic echo`）用于现场快速检查；完整数据验收必须保留上述报告和原始`.db3`，不能只保存一张终端截图。

## 2. 逐盒检查数据完整性

按实际计划填写清单，**没有计划采的传感器写“未采”，不要写“通过”**。目前GNSS可能只在201有效，相机也可能还未接入。

| 对象 | 核对什么 | 当前常见频率，仅作参考 |
|---|---|---|
| 201、202、203各自IMU | 每盒各一个`/imu/raw`包，来源按采集清单核对 | 约1000 Hz，以设备实际配置为准 |
| 三盒共享UWB | 在201的共享包中按`src_id/target_id`核对；三条无向边1—2、1—3、2—3均出现 | 每条有向流约10 Hz，不能把总Topic频率当作单边频率 |
| 各盒雷达 | 每盒`/livox/lidar`和`/livox/imu`都非空，文件/目录标明盒号 | 点云约10 Hz、Livox IMU约200 Hz |
| 实际采集GNSS的盒子 | `/gnss/fix`非空；201有GNSS不代表202、203也有 | 常见约1 Hz，以配置为准 |
| 实际采集相机的盒子 | 图像话题及消息类型；标定数据`CameraInfo`或独立标定文件 | 按相机配置 |
| 在线位置结果包 | `/uwb/range`和`/cooperative_localization/poses_2d`均非空 | 输出配置10 Hz，实际受完整三边输入限制 |

**继续终端A，检查四个联合包：**

```bash
cat "$RUN/manifest.json" "$RUN/采集状态.json" "$RUN/实验备注.txt"
for BAG in "$RUN"/*_imu_rec_v* "$RUN"/*_uwb_rec_v*; do
  if [ -f "$BAG/metadata.yaml" ]; then ros2 bag info "$BAG"; fi
done
```

另有雷达、GNSS或相机包时，每个也执行一次`ros2 bag info 包目录`。重点看：

- 预期话题是否存在，类型是否正确，消息数是否大于0。
- 实际数据跨度是否覆盖实验过程。180秒录包通常略短于180秒；明显只剩几秒要查日志和中断情况。
- 消息数与频率、时长是否大致相符。例如1000 Hz录180秒约18万帧，200 Hz约3.6万帧；不能仅因“有文件”就通过。
- 三盒IMU分别核对，雷达包也分别核对。一个共享UWB包不能代替各盒雷达/IMU包。

`all_subscribed=true`只说明建立了订阅。`Messages: 0`或话题计数为0表示未录到数据；空包里的“2262年”是占位时间，不是传感器时间。文件名日期来自电脑或盒子，只作实验编号，不能据此判断同步。

## 3. 自动检查IMU、UWB和单传感器质量

### 3.1 三盒IMU与共享UWB

**继续终端A：**如果刚解压的是最新一轮，直接运行下面这一条，不需要把实验编号填进命令：

```bash
bash tools/analyze_joint_recording.sh
```

脚本会在`data/`下按实验编号倒序寻找最新的`joint_time_*`目录，并确认其中同时有IMU和UWB的`metadata.yaml`；运行前会打印实际选中的目录。只想复核指定历史包时，才写完整路径：

```bash
bash tools/analyze_joint_recording.sh data/joint_time_20261016_150956
```

如果手里只有`joint_time_*.zip`，先在`data/`下解压，保留压缩包原名和解压出的同名目录；不需要重命名。若最新压缩包还没有解压，自动选择器会跳过它并提示当前选中的已解压目录，避免把半成品当成新数据分析。

先看这些结果：

| 文件 | 看什么 |
|---|---|
| `联合时间验收.md`、`联合时间详细统计.csv` | 各流消息数、频率、完整首末Header、Header零值/回退/重复、接收时间回退/重复 |
| `联合时间初查.md` | 原始首末时间，不能把“区间交集”当同步证明 |
| 各IMU目录的`imu_analysis.txt` | 加速度/角速度是否有限、频率和长间隔是否异常；静止时模长和波动是否合理 |
| UWB目录的`UWB测距分析.md` | 来源身份、三条无向边、距离是否为正/有限、异常跳变和间断 |
| UWB目录的`UWB时间对比/三盒UWB时间对比.md` | 完整三边同Header历元数量、各源盒Header关系和未配对情况 |

分析脚本失败时先看报错：空包回到第2节处理，缺ROS接口回到第1节处理。脚本只读原始数据库，生成的CSV、MD、PNG是离线派生文件。若共享UWB包的`metadata.yaml`中已经有`/cooperative_localization/poses_2d`，同一条总分析命令还会自动生成`online_analysis/在线相对定位分析.md`；不需要再填写该轮目录。

IMU上游四元数仅作参考；目前主要检查原始加速度、角速度及其时间，姿态解算用浙大程序。UWB的`rolling`不参与本验收。

### 3.2.1 三盒 UWB、IMU、Livox 联合包（一条命令分析）

新版一键录制收回的是一个 `three_boxes_*.tar.gz`。在**本地Ubuntu工程根目录**执行，下面命令自动选择`data/`下最新的总包，不需要填写本轮编号：

```bash
ARCHIVE=$(find data -maxdepth 1 -type f \( -name 'three_boxes_*.tar.gz' -o -name 'three_boxes_*.zip' \) -print | sort --reverse | head -n1)
if [ -n "$ARCHIVE" ]; then
  case "$ARCHIVE" in
    *.zip) RUN=${ARCHIVE%.zip}; [ -d "$RUN" ] || unzip -n -q "$ARCHIVE" -d data ;;
    *.tar.gz) RUN=${ARCHIVE%.tar.gz}; [ -d "$RUN" ] || tar --extract --gzip --keep-old-files --file "$ARCHIVE" --directory data ;;
  esac
  for archive in "$RUN"/uwb_imu_livox_v*.tar.gz; do
    BOX_DIR=${archive%.tar.gz}
    [ -d "$BOX_DIR" ] || tar --extract --gzip --keep-old-files --file "$archive" --directory "$RUN"
  done
fi
```

总包及三盒原始压缩包均保留；目录已完整解压则跳过相应解压命令。之后按下面步骤加载消息环境、运行分析，分析脚本会自动选择最新且三盒目录完整的一轮。

在**本地Ubuntu开发电脑、工程根目录**运行，不在上交Windows或盒子里运行。分析前加载ROS并构建当前消息定义；旧安装版本可能缺少`rolling`，同名消息也会把距离读错：

```bash
source /opt/ros/humble/setup.bash
colcon --log-base log/three-box-analysis build --base-paths ros2/cooperative_interfaces --build-base build/three-box-analysis --install-base install/three-box-analysis --packages-select cooperative_interfaces
source install/three-box-analysis/local_setup.bash
bash tools/analyze_box_sensors.sh
```

构建环境不变时以后只需`source`，不用每轮重编。脚本可接一个或多个已解压盒端目录，依次调用现有时间、IMU、点云和UWB分析程序；较大的点云包需要等待，出现“完成”才结束该盒分析。

每盒查看`联合时间验收.md`、`联合时间详细统计.csv`、`IMU分析.txt`、`雷达分析.txt`和`uwb/UWB测距分析.md`。共享UWB按方向拆流；不要将三个录包机的UWB接收时间混成一条流。报告完成不代表同步通过，静止包也不能证明毫秒级硬件同步。

本轮总报告见[data/三盒UWB_IMU_Livox联合分析_20260809.md](../data/三盒UWB_IMU_Livox联合分析_20260809.md)。

### 3.2.2 最新三盒Livox点云可视化复现与回放

三盒目录已解压时，在本地Ubuntu工程根目录运行；省略目录参数会自动选择`data/`下最新且三盒Livox包完整的一轮：

```bash
source /opt/ros/humble/setup.bash
python3 tools/visualize_livox_bags.py
```

结果在该实验的`livox_visualization/`：PNG为三盒俯视/侧视总览；安装`plotly`时还生成可离线旋转、缩放的3D HTML。工具按SQLite写入顺序选取本轮固定窗口，过滤非有限XYZ和全零点；默认201累积225条96点小消息，202/203各累积10条消息，未进行运动补偿或跨盒配准。具体窗口及点数在`summary.json`，本轮绘制点数应为10417、84757、100081。

看整段动态点云时，两个本地终端均加载ROS并设置`ROS_DOMAIN_ID=0 ROS_LOCALHOST_ONLY=1 RMW_IMPLEMENTATION=rmw_fastrtps_cpp`。终端1启动`rviz2`，将Fixed Frame设为`livox_frame`，添加`PointCloud2`，Topic设为`/livox/lidar`，Reliability设为Best Effort；201的Decay Time先设为1秒以累积小消息。终端2执行：

## 4. 比较各盒各传感器时间

只用**同一轮、覆盖同一实际过程**的包。历史雷达短包可以单独检查质量，不能拼进新联合包后宣称同步。

**继续终端A：** 第一项仍是联合目录，后面可放多个同轮雷达、GNSS或标准图像bag。只有哪些包就传哪些，不需要手动对照单帧：

```bash

```

有GNSS或图像时，继续在命令末尾加其实际bag目录。`联合时间验收.md`和CSV会汇总全部选中流；再次运行覆盖派生报告，原始包不变。每个雷达/图像目录名应含盒号，避免来源混淆。共享UWB只选一个录包盒的包，不要混合不同录包机的接收时间。

按下面顺序判断：

1. **完整时间基准**：Header是否同一时间体系。例如一盒只有`20936`秒、另外两盒为`1785584xxx`秒，不能直接融合。UWB模拟RMC不是现实UTC；同轮各传感器需要明确映射，不能各自把首帧归零来“对齐”。
2. **连续性**：逐流看零值、Header回退/重复、间隔尖峰；接收回退单独看`receive_rollback`。接收检查按数据库写入顺序，异常还可能涉及缓存/并发顺序，需要日志确认根因，不能仅凭它断言系统时钟回拨。
3. **覆盖与推进速度**：各流是否覆盖约定过程，Header跨度是否相符，`R−H`是否持续漂移。跨盒接收时钟未独立校准，不能用接收时间直接证明同步。
4. **算法的历元条件**：当前纯UWB算法按`uwb_epoch_max_span_ms=10`归并三条无向边，三边最早到最晚的Header跨度超过10 ms才视为缺边。三边在整包中都出现，只说明测距关系齐全；10 ms窗口内的完整历元数量约束实际输出频率。缺两个反向流不一定缺三条无向边，但要在结果里注明。
5. **同步精度**：IMU、点云、相机、GNSS采样频率不同，不要求每一帧Header完全相等。最近邻差值还包含采样网格与观测语义；静态包通常只能排除明显异常。毫秒级同步需要共同硬件事件、PPS捕获或经过标定的事件对齐证据。

**测量时间对齐以Header为主，在线算法不依赖是否录包。** 同步判断先核对Header的来源、采样事件定义、纪元映射、逐流连续性及共同事件；只比较相近数值不足以证明物理同步。跨传感器不用逐帧Header完全相等。

R是录包进程给收到的消息附加的记录时间，不是测量时间，也不是独立真值。`R−H`只作辅助诊断；未经时钟校准不能据其大小判定传感器不同步或推断网络延迟。三盒同时录制仍各有记录时间，不能当作统一时钟；并行采集方法见21号6.1.2。发现差异时保留原时间，不平移或用R替换Header。

## 7. 能评价到哪一步

| 已有数据 | 能给出的结论 |
|---|---|
| 只有传感器包 | 数据是否齐全、是否有明显数值/时间异常、当前UWB能形成多少同历元三边 |
| 输入和算法新输出包 | 算法是否产生结果、有效比例、更新间断、坐标/消息约定是否正确 |
| 静止且没有外部真值 | 位置波动/重复性；不能给绝对定位精度 |
| 同时刻且已统一坐标的三车位置真值 | 相对位置误差、RMSE、P95等精度指标 |

GNSS只在201时，不能获得三车相对位置真值。三车GNSS或全站仪等真值还需统一时间、坐标，并处理天线/雷达/IMU安装杆臂。纯UWB的真值也应转换到本算法相同的“车1原点、车1→车2为+X、车3取+Y”坐标定义。

GNSS可以只录作真值而不参与算法；授时源选择与“是否把GNSS定位观测送入算法”分别记录。GNSS受干扰或无效时仍能验软件输出和重复性，但这一段不能作为定位精度真值。

## 10. 传感器专项异常的处理顺序

### 10.1 IMU时间基准异常

若三盒IMU均有消息、各自不回退，但某盒Header约为`3×10^5`秒而其他流为`1.7×10^9`秒，这是时间基准不一致，不是网络延迟。保留原始Header，反馈上交检查该盒IMU驱动的时间源和`pps_source`；不要在离线脚本中平移时间后冒充已同步。

当前最新完整在线包`joint_time_20261016_150956`的证据是：201、203的`/imu/raw`以及UWB Header都在约`1785906722`秒，202的`/imu/raw`在约`342834`秒。因此目前看到的“不一致”是**202盒IMU时间戳相对201/203 IMU和UWB不一致**。不能据此认定UWB PPS源已经错误：UWB与201、203 IMU处在同一数量级，现有bag只能定位到202 IMU的时间基准异常，不能证明PPS硬件线路本身的根因。

上交需要核对并回复：202盒`/imu/raw.header.stamp`由哪一路时钟、哪个计数器和哪个单位生成；`pps_source: 1`时202的IMU是否真正使用UWB PPS；IMU驱动启动时是否重新建立了UWB时间映射。反馈时应明确说“202 IMU Header与201/203 IMU及UWB Header不在同一时间基准”，不要笼统写成“所有传感器时间都不一样”。

### 10.2 UWB边缺失或时间跨度过大

先按`src_id/target_id`合并为三条无向边，再看每个历元是否齐全。只有一个方向缺失不一定等于无向边缺失；双向值通常由算法配对/平均。用`UWB测距分析.md`、融合日志和在线输出报告交叉判断。

在`joint_time_20261016_150956`中，实际出现的有向流为`1→2、1→3、3→1、3→2`，没有`2→1、2→3`。所以“202盒发出的两条测距方向”仍缺失；但无向边`1—2、1—3、2—3`均已有至少一个方向，三角形几何仍能建立，纯UWB位置也能输出。今后反馈时要区分“缺202的出向流”和“缺202相关无向边”，两者不是同一件事。

### 10.3 雷达与视觉

雷达包单独运行`analyze_lidar_bag.py`；视觉若只有V4L2裸帧或JPEG文件，运行对应相机脚本只能检查格式、画面和采集时间，不能当作ROS图像节点已经接入。只有取得连续的`Image/CompressedImage`、`CameraInfo`和逐帧时间戳，才把它们加入第4节联合时间验收。
