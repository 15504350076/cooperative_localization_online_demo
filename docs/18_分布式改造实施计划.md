# 18 分布式改造实施计划与验收记录

## 1. 实施结论

2026-08-17 已按“最简 IMU＋UWB 到 GCS”目标完成源码实施，并把对上交的 `NodeState v1` 冻结为 `Header/node_id/p/v/q/valid`：

```text
上交每盒 sensor_msgs/msg/Imu publisher
  -> 浙大 zju_local_inertial_node
  -> 单车 15 维惯导＋本机 P15
  -> 紧凑 NodeState
  -> ROS 2 publish/subscribe + DDS + 5G Mesh IP
  -> 参考车 zju_cooperative_fusion_node
  <- 默认：上交 /uwb/range
     显式应急：三车 NavSatFix -> GNSS 派生距离
  -> 二维测距修正
  -> /cooperative_localization/poses_2d @ 10 Hz
  -> 上交 GCS
  -> 可选 /cooperative_localization/feedback/poses_2d -> 从车规划模块
```

跨车不发原始 IMU，也不发 `bg/ba` 或 225 个协方差元素。当前仍由参考车集中运行一个很小的 `2(N-1)` 维修正器，三车时只是 4 维；它不是原有的 45 维原始 IMU 联合滤波。若现场连紧凑 NodeState 都不能汇聚到任一节点，需另立项设计无中心信息滤波和交叉相关性管理，本版本没有实现该能力。

## 3. 先失败测试、再实现、再回归

本轮保持下列顺序：C++ 断言仍进入既有 `zju_coop_tests` 目标，不改变 CTest 7 项验收数字；ROS 行为由各包 launch test 单独锁定：

1. 先记录原工程 7/7 CTest 和 14/14 独立自检基线。
2. 先在 `tests/test_distributed_fusion2d.cpp` 写相对 ENU、UWB 修正持久性、对齐、超时和无向边去重的失败测试，再实现 `DistributedFusion2D`。
3. 先在 `tests/test_c_api.cpp` 和 `tests/c_header_smoke.c` 引用未实现的 NodeState/distributed 入口，再增量实现 C ABI，保留旧结构静态布局断言。
4. 先写 `test_pipeline.launch.py` 的 IMU→NodeState→UWB→Pose 端到端断言，再实现 ROS 2 两节点和 remap。
5. 审计发现原 UWB 测试创新为 0 后，把基线改为 5 m、量测改为 4 m，明确断言输出向 4 m 改善，使“UWB 路径完全失效”时测试必然失败。
6. 先写缺少位置、速度、姿态初值的三进程负测试，再锁定节点必须 fail-fast 的参数规则。
7. 最终审计对 `status=INVALID, valid=true` 新增失败测试；它在修正前得到 `Tests: 191, Failures: 1`，将质量码条件改为拒绝 `status>=2` 后恢复 191/191。

### 5.1 一键解析仿真

在完成上述 build 并 source 对应 install 树后，直接运行：

```bash
RMW_IMPLEMENTATION=rmw_fastrtps_cpp \
ros2 launch zju_coop_bringup simulation.launch.py
```

默认为无噪声理想链路；可用以下命令做可重复的轻量故障注入：

```bash
RMW_IMPLEMENTATION=rmw_fastrtps_cpp \
ros2 launch zju_coop_bringup simulation.launch.py \
  uwb_noise_std_m:=0.02 \
  uwb_drop_every_n:=10 \
  uwb_nlos_every_n:=25 \
  gyro_noise_std_rad_s:=0.0002 \
  accel_noise_std_m_s2:=0.01
```

GCS 输出为 `/cooperative_localization/poses_2d`，对照真值为 `/simulation/ground_truth/poses_2d`。该仿真器只用解析平面轨迹验证秒级到短时软件链路；周期“NLOS”实际是 2–3 边的正距离离群值，不是真实多径传播、NLOS 识别、车辆动力学、时钟漂移或网络模型。通过该仿真不等于长时漂移、RK3588 性能或实车精度已验收。

### 5.3 默认关闭的 GNSS 距离后备

正常模式不需要任何额外参数，fusion 只订阅 `/uwb/range`，GNSS 后备节点不存在于运行图中：

```bash
ros2 launch zju_coop_bringup vehicle.launch.py \
  namespace:=vehicle_1 run_fusion:=true
```

只在 UWB 测距暂不可用、三车 UWB 共同授时仍有效且 GNSS 驱动已把 `NavSatFix.header.stamp` 转换为 `UWB_SYSTEM_TIME` 时，参考车显式启用后备：

```bash
ros2 launch zju_coop_bringup vehicle.launch.py \
  namespace:=vehicle_1 run_fusion:=true \
  use_gnss_range_fallback:=true \
  gnss_topic_1:=/vehicle_1/gnss/fix \
  gnss_topic_2:=/vehicle_2/gnss/fix \
  gnss_topic_3:=/vehicle_3/gnss/fix \
  gnss_range_std_m:=3.0 \
  gnss_sync_slop_ms:=50
```

两个从车仍用 `run_fusion=false`，不启动后备节点。开关会同时把 fusion 输入从 `/uwb/range` 切到私有 `/cooperative_localization/gnss_derived_range`，并将测距标准差从 `0.1 m` 切到 `3.0 m`。不允许运行时自动切换或同时融合两种来源；每次切换都必须重启参考车整个 `vehicle.launch.py`，以同时重建 fusion 并启动或停止后备节点。

后备节点只使用合法且近似同时的 `NavSatFix`，并用三车有效且近期的 NodeState 建立共同时间活性门禁；真实 UTC 时间戳不会直接转发成融合测距时间。它默认忽略高度，用 WGS-84 ECEF 弦长生成地面车水平距离，不使用 `NavSatFix` 协方差、不能从标准状态判断 RTK Fixed，也没有 GNSS/UWB 天线杆臂补偿。因此 `3.0 m` 是未标定前的保守初值，该模式只能维持软件闭环和 GCS 显示，不能作为 UWB 或协同定位精度验收。

### 5.4 默认关闭的从车协同结果反馈

参考车始终发布 GCS Topic。正常 UWB 模式下，如需把同一份修正后结果反馈给从车规划模块，只需在参考车启动时增加一个参数：

```bash
ros2 launch zju_coop_bringup vehicle.launch.py \
  namespace:=vehicle_1 run_fusion:=true \
  enable_follower_feedback:=true
```

开启后新增 `/cooperative_localization/feedback/poses_2d`，消息类型仍为 `cooperative_localization_msgs/msg/CooperativePose2DArray`，10 Hz、reliable、volatile、depth 1；默认关闭时该 Topic 没有发布者。两个从车不需要再启动 fusion，其规划模块按 `node_id` 取本车结果并检查有效位、消息年龄和接收 watchdog。该开关只增加结果发布，不把修正回灌本地惯导；参数在启动时生效，切换需重启参考车 fusion。GNSS 距离后备模式因当前结果没有来源/质量字段，必须保持反馈关闭。

Gazebo 一键入口使用同名参数：

```bash
ros2 launch zju_coop_gazebo three_vehicle_gazebo.launch.py \
  headless:=false record_bag:=true \
  enable_follower_feedback:=true
```

## 7. 三盒在线运行全流程

1. 上交在每个传感器盒上启动数据节点，发布本车 `sensor_msgs/msg/Imu`；正常模式还需可见 UWB 节点发布 `/uwb/range`。GNSS 后备模式则需参考车通过 DDS 收到三车 `NavSatFix`，且其 `header.stamp` 已转换为与 NodeState 一致的 `UWB_SYSTEM_TIME`；真实 GNSS UTC 只能留作诊断字段，不能直接进入融合时间轴。
2. 三台盒子都使用相同 `ROS_DOMAIN_ID`和 `RMW_IMPLEMENTATION=rmw_fastrtps_cpp`；5G Mesh 只需提供三机 IP 可达和 DDS 发现/数据通路。
3. 分别把真实公共 ENU 初始 `p/v/q/bg/ba` 写入本车 YAML，并保证三车使用同一 ENU 原点、轴向和生效时刻。三份演示 YAML 的数字不能直接用于实车。
4. 每个车载盒启动 `zju_local_inertial_node`，通过 launch remap 把内部 `imu` 连到上交本车 IMU topic。
5. 两个从车用 `run_fusion=false`，只发布 `/cooperative_localization/node_state`；参考车用 `run_fusion=true`，同时启动自己的 local 和 fusion。`namespace:=vehicle_1/2/3` 会自动加载同名 `vehicle_N.yaml`；非标准命名空间必须显式传 `local_config`，防止误用另一辆车的 `node_id`。
6. DDS 把三车紧凑 NodeState 传到参考车，fusion 按当前选定测距 Topic 的 `header.stamp` 对齐两端状态并更新 4 维位置修正量。
7. fusion 以 10 Hz 发布一条 `CooperativePose2DArray`，其 `vehicles` 含三车；GCS 订阅固定结果 Topic。若参考车显式开启反馈，则同一数组另发到专用反馈 Topic，供从车规划模块订阅；本地惯导状态不被覆盖。
8. 运行期监看 local 的 IMU disposition 和 fusion 的 UWB processing/update/NIS 节流日志。“节点在运行”不等于“每个输入已被算法消费”。

如果 5G Mesh 不转发组播发现，使用 Fast DDS Discovery Server 或静态 peer 配置解决，不改算法核心，也不把 5G 驱动写进 ROS 节点。

13. 模拟 RMC 与 PPS 的配对规则：RMC 在 PPS 前或后发送、对应哪个脉冲、UTC 来源、有效状态、相对 PPS 的 P99 和最大发送延迟。
14. 三盒 PPS 边沿偏差、连续一小时漂移、失去 SYNC/重锁/重启时的时间跳变实测；“百微秒级”必须说明是单盒抖动、盒间偏差、相对超帧还是相对 UTC。
15. 设备时间到 ROS 时间的映射位置和算法。第一版建议验收最终 IMU/UWB `header.stamp` 的跨盒误差 P99 不超过 1 ms、最大不超过 2 ms、连续一小时无时间倒退；核心 100 ms 超前/500 ms 延迟只是输入拒绝保护，不是同步精度指标。
16. 三车 GNSS Topic 名、频率、QoS、`header.stamp` 共同时域、海拔是否为 WGS-84 椭球高、协方差可信度以及 RTK Fixed/Float 的独立质量表示。
17. GNSS 天线、UWB 天线和车体 FLU 原点的三组杆臂，以及地面车后备距离应使用水平距离还是三维斜距。

## 10. 主要风险和第一版能力边界

| 项目 | 当前控制 | 明确边界 |
|---|---|---|
| 时间域不一致 | 实盒 Header 统一 UWB 时域，Header＋`steady_clock` 估计同域接收时刻，双时间门限拒绝异常包 | 当前无正式同步状态/session 接口；失锁由上交停发，Master 时间回拨或超门限向前跳变后首版整组重启，启用 GNSS 后备时同时重启后备节点 |
| 公共 ENU 初始不正确 | `p/v/q` 必填且缺少时 fail-fast | 没有自动 GNSS 初始化和失锁切换 |
| 单纯 IMU 漂移 | 软件内按初值补偿 `bg/ba`，P15 按随机游走增长 | 零偏不写回硬件，也没有外部观测持续校正它 |
| UWB 时刻错位 | 每车 64 帧缓存，插值，100 ms 有限外推，超限拒绝 | 不做乱序重排或延迟后验回放 |
| 新 NodeState 覆盖 UWB 后验 | 基线 `B` 与持久修正 `C` 分存，输出 `B+C` | NodeState 不当作独立绝对量测反复融合 |
| 测距失联或连续拒绝 | 非参考车必须经近期 Accepted 测距边连到参考车才置 `position_valid=true` | 数值仍保留用于诊断；规划必须检查有效位并另设 Topic 接收 watchdog |
| 任一车辆状态停更 | 三车共同算法时刻超过门限后整组位置和航向均无效 | 消费者还必须检查 `header.stamp` 年龄，不能只看 Topic 到达频率 |
| 无会话编号 | 重新初始化时整组四节点重启，重建 fusion 清空全部历史和后验 | 不支持单车热重启；时间戳不能识别初始化会话 |
| 从车结果反馈 | 默认关闭；参考车可在正常 UWB 模式发布与 GCS 完全相同的专用反馈数组 | 只供规划消费，不修正从车本地 `p/v/q/bg/ba/P15`；GNSS 后备模式禁止开启 |
| 姿态 reset Jacobian | 新 UWB 路径不注入本地姿态 | 旧 45 维集中式路径的 reset Jacobian 仍缺失，本轮没有修改 |
| 外参系统误差 | 约定 IMU 已为 FLU，UWB 杆臂默认零 | 这两个前提未在实车确认 |
| 高度和航向可观性 | UWB 用三维斜距、只修正 E/N；yaw 取本地惯导 | 不修正 U/速度/yaw，不融合磁罗盘、GNSS 航向、雷达或视觉 |
| 正式 UWB 类型 | 临时消息严格复制已知四字段 | 包名不同仍不互通；正式接入时只换 ROS 映射层 |
| GNSS 距离后备 | 默认关闭；私有 Topic；与 UWB 严格互斥；要求共同授时有效及 GNSS Header 已转到 UWB 时间域；保守 `range_std_m=3.0` | 忽略高度和杆臂，不判断 RTK Fixed，不使用每帧协方差；只是 UWB 测距延期时的 GCS 应急链路，当前禁止规划控制消费，也不是精度验收 |
| 带宽 | 跨车只发紧凑 `p/v/q` 状态 | 仍需有一个节点收到三车 NodeState 和 UWB，不是无中心算法 |
| 雷达/视觉扩展 | 默认不创建感知订阅或前端；显式开启可得到平面 ICP 与已知地标视觉 Odometry | 两类 Odometry 尚未融合；真实设备仍需标定、质量建模和版本化约束入口 |
| Gazebo | 独立可选包、Fortress、ENU/FLU、零杆臂、1 秒静止初始化、平滑起步和 2 号车一次 S 弯、DDS/GZ 双分区隔离；解析仿真继续作快速 CI | headless 同机闭环已通过，但底盘/轮胎/悬架只是首版模型，也不部署到 RK3588 |
| ROS 进程退出 | 2026-08-18 全量回归首次收尾时有一个 local 节点在 SIGINT 后偶发 `-11`；同一用例连续 5 次和随后 12 项全量重跑均通过 | 原因尚未定位；上线守护与长时门禁前必须继续观察退出/重启可靠性，不能用重跑通过抹去该记录 |

`CooperativeCorrection` 反馈的代码接口本轮没有增加。保留的架构边界是：参考车修正器独立于 local handle，未来只能通过新的普通 C 结构和明确的 timestamp/session_id/covariance 契约反馈，不能让 ROS 消息进入核心，也不能把位置修正直接硬覆盖本地 ESKF 名义状态。只有在部署系统能真实生成、持久化并切换 `session_id` 时才应增加该字段，固定常数没有识别能力。
