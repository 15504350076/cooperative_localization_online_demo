# 协同定位扩展能力、接口与运行环境设计

日期：2026-07-20  
状态：待用户确认后实施  
适用工程：`cooperative_localization_online_demo`

## 1. 目标

在不破坏现有 UWB-only C ABI v1、ZJCL 1.0 和 ZJLG 1.0 的前提下，为上交 ROS 2 wrapper 提供可查询的能力边界，并把未来 IMU、激光雷达、多目视觉、节点状态、链路状态和时间同步状态的扩展方式冻结为“独立版本化接口”。同时形成一份可直接交接的当前输入输出协议、代码来源、运行环境、运行命令和验证矩阵。

## 2. 已核查现状

- `c_api.h` 已使用 `struct_size`、`abi_version`、显式数组 stride 和 opaque handle，具备基本 ABI 防护。
- 当前公开输入只有 `zju_coop_push_range`；直接输出只有 Localization、Observation、Network。
- AlgorithmStatus、Alert 由 online/replay 参考适配层产生，不是 C ABI v1 的直接输出。
- `types.hpp` 有内部 Capability 枚举，但上交调用方无法通过 C ABI 查询实际能力。
- 当前配置解析严格拒绝未知字段，不适合提前加入“打开后仍无算法行为”的伪开关。
- 当前源代码未包含外部 GitHub URL、第三方版权头或 Eigen/GTSAM/Ceres/PCL/OpenCV 依赖。
- 本机为 Windows 11 x64；已验证 Visual Studio 2022 v143、CMake 3.29.5、Python 3.11.9。没有可用 WSL Linux 发行版。

## 3. 方案比较

### 方案 A：冻结 v1，新增能力查询，未来采用独立类型化接口（采用）

优点：不破坏既有调用方；当前支持与未来规划可以明确区分；后续仍使用普通 C 结构体；不会让上交误以为未实现的传感器已经可用。缺点：未来每种新观测需要增加一个版本化结构和 push 函数。

### 方案 B：现在增加通用 TLV/void* 扩展输入

优点：表面上只需一个入口。缺点：类型安全差，字段/单位只能在外部约定，容易把 C ABI 变成第二套线协议，不符合“算法接口使用普通 C/C++ 结构体”的既定要求，因此不采用。

### 方案 C：直接向现有 config、Range 和 step 结构追加字段

优点：文件少。缺点：改变结构大小和字段偏移，容易破坏已经冻结的 ABI v1，也会迫使当前用户重新编译，因此不采用。

## 4. C ABI 兼容扩展

软件版本从 `0.1.0` 提升为 `0.2.0`，C ABI 版本继续为 `0x00010000`。原因是新增符号和能力查询属于向后兼容的软件功能，不改变任何既有结构、函数签名、枚举值或所有权规则。

### 4.1 公开能力位

新增三组 `uint64_t` 掩码。位号一经发布不得复用：

| 掩码 | 位 | 名称 | 0.2.0 状态 |
|---|---:|---|---|
| input | 0 | UWB_RANGE | 支持 |
| input | 1 | IMU | 预留，关闭 |
| input | 2 | LIDAR_RELATIVE | 预留，关闭 |
| input | 3 | MULTI_CAMERA_RELATIVE | 预留，关闭 |
| input | 4 | NODE_STATE | 预留，关闭 |
| input | 5 | LINK_STATE | 预留，关闭 |
| input | 6 | TIME_SYNC_STATE | 预留，关闭 |
| direct output | 0 | LOCALIZATION | 支持 |
| direct output | 1 | OBSERVATION | 支持 |
| direct output | 2 | NETWORK | 支持 |
| adapter output | 0 | ALGORITHM_STATUS | 参考适配层支持 |
| adapter output | 1 | ALERT | 参考适配层支持 |

“预留，关闭”只保证位号，不表示已有数据结构、算法实现或性能。

### 4.2 能力结构与函数

在 `c_api.h` 新增固定 64 B 的结构：

```c
typedef struct zju_coop_capabilities {
  uint32_t struct_size;
  uint32_t abi_version;
  uint64_t supported_input_mask;
  uint64_t direct_output_mask;
  uint64_t adapter_output_mask;
  uint64_t reserved[4];
} zju_coop_capabilities_t;
```

新增：

```c
zju_coop_error_code_t zju_coop_capabilities_init(
    zju_coop_capabilities_t* value);

zju_coop_error_code_t zju_coop_get_capabilities(
    zju_coop_capabilities_t* value);
```

调用方先 init，再 get。get 严格校验 `struct_size` 和 `abi_version`，成功时一次性写入完整结构，失败时不部分写入。该函数不需要 handle，不改变算法状态，可在加载动态库后、创建实例前调用。

### 4.3 后续类型化入口规则

在真实字段、单位、坐标系、协方差和时间语义冻结后，按以下顺序新增独立结构和函数，不修改 Range：

```text
zju_coop_push_imu_v1
zju_coop_push_lidar_relative_v1
zju_coop_push_multi_camera_relative_v1
zju_coop_push_node_state_v1
zju_coop_push_link_state_v1
zju_coop_push_time_sync_state_v1
```

每个输入结构必须包含 `struct_size`、`abi_version`、节点号、序列、采样时间、接收时间、valid/status，并使用传感器专用质量字段。函数尚未实现前，对应 capability 位必须保持 0；不得先导出空函数或静默丢弃数据。

## 5. 当前协同定位子部分接口

### 5.1 生产 C ABI 输入

当前唯一算法输入是 `zju_coop_range_packet_t`：from/to node、sequence、上交统一采样时间、wrapper 接收时间、range m、range standard deviation m、NLOS 标志/概率、valid、status。上交负责 UWB UART/TLV 解析和全部平台内/跨平台时间同步。

### 5.2 生产 C ABI 输出

- `zju_coop_localization_t[]`：每节点 x/y/vx/vy、二维位置协方差、valid、状态；yaw/z 无效。
- `zju_coop_observation_t[]`：每候选边窗口计数、NLOS/有效率、频率、状态、融合动作、原因位和协方差缩放。
- `zju_coop_network_t`：节点/可达/有效边数量、连通、可观、状态和原因位。
- `zju_coop_range_processing_result_t`：每个 Range 的处理结论、创新、NIS、滤波动作和协方差缩放。

AlgorithmStatus 和 Alert 由参考适配层生成；生产 ROS 2 中由上交 wrapper 复用该语义还是后续扩展 C ABI，继续作为双方接口评审项。

### 5.3 临时在线协议

ZJCL 1.0 使用 40 B 小端公共头和 CRC32：Range 24 B 输入；Localization 64 B、Network 20 B、Observation 80 B、Alert 40 B、AlgorithmStatus 48 B 输出。ZJLG 1.0 记录方向、接收时间和完整 ZJCL 帧。ZJCL/UDP 只用于当前受控网络 demo，不替代上交 ROS 2/DDS 和正式 GCS 网关。

## 6. 代码来源说明

当前代码不是从网上下载某个工程后改名，也不是不参考资料的自由发挥：

1. 需求、平台、分工、字段和验证边界来自用户提供的 V3 方案、内部闭环协议、AIBrainBox 规格、接口需求和数据流图。
2. 查阅了用户目录中的 `EKF_dis2.m` 等历史 MATLAB 程序，用于理解已有测距 EKF、先验和门限思路；这些程序依赖已知邻节点位置/先验，不能直接作为当前三车联合在线 SDK，因此当前 C++ 核心重新设计实现。
3. 联合 Range EKF、全协方差、刚性/可观性、退化窗口、C ABI、ZJCL/ZJLG、UDP、参考 GCS 和自动测试是围绕现有需求独立实现。
4. 前期可以调研公开项目思路，但当前交付树没有复制或链接外部算法项目，也没有新增第三方算法库。若以后引入开源组件，必须新增来源 URL、版本、许可证、修改说明和 ARM64 验证记录。

## 7. 运行环境和支持矩阵

| 环境 | 状态 | 口径 |
|---|---|---|
| Windows 11 x64 + VS2022 | 已验证 | 当前开发机实际 Release、单测、在线/回放烟测环境 |
| Windows 10 x64 + VS2022/2019 | 代码候选，待实测 | WinSock/C++17 路径具备，但不能沿用 Win11 结果作为证据 |
| Windows 7 x64 | 不支持 | 当前 VS2022、Python 3.11 和 ROS 2 Humble 目标链路不以 Win7 为支持平台 |
| Visual Studio 2017 | 待验证，不推荐交付 | 若用户“win17”指 VS2017，需单独安装 v141、验证 C++17 filesystem、DLL 和全部测试 |
| Ubuntu 22.04 amd64 | 代码候选，待实测 | 可用 GCC/G++、CMake 和 Python 构建；当前无本机 Linux 环境证据 |
| Ubuntu 22.04 arm64/RK3588 | 目标平台，待盒端验证 | ROS 2 Humble Tier 1 arm64；必须在 AIBrainBox 重建 `.so`，不能复制 Windows DLL |

最低工程环境：64 位 OS、CMake 3.16+、支持 C++17 和 `std::filesystem` 的编译器、Python 3.8+（模拟器/GCS/自动测试），以及可用 UDP loopback。算法动态库和 C ABI 本身不依赖 Python 或 ROS 2；online/replay 不依赖 ROS 2；上交生产 wrapper 才依赖 ROS 2。

Windows 预编译程序使用 MSVC 动态运行库，目标机需要匹配的 Microsoft Visual C++ 2015–2022 Redistributable。Ubuntu 应在目标架构本机或正确 sysroot 的交叉工具链重新编译。

## 10. 错误与兼容策略

- 能力查询失败只返回既有错误码，不抛出异常。
- 未置位的 capability 表示调用方不得发送该类输入或期待该类直接输出。
- 新增公开位号和函数只能向后兼容；修改既有字段偏移、单位或枚举必须升级 ABI major。
- ZJCL 1.0 payload 不因能力查询改变；如未来在线协议增加新消息，使用新 message type，并同步 C++/Python golden bytes、日志、GCS 和文档。
