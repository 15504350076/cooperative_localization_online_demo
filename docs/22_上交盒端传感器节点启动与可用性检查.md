这份文档一边给操作步骤，一边解释命令和输出。现场只想复制命令时，用 [21 精简执行版](21_上交盒端传感器节点启动与可用性检查_精简执行版.md)；不知道某一步为什么这样做、输出该怎么看，再查这里。

本文新命令与21号统一使用`ROS_DOMAIN_ID=0`；旧测试使用过107，历史记录不改。首次切换须按21号页首说明一起重启相关驱动、算法并对齐录包端，修改文档不会改变盒子上的旧进程。雷达的实际Domain、RMW和本机通信设置必须从驱动进程核对，不能把测试终端曾使用的Cyclone DDS当成上交配置。

## 先确定这次要做什么

- **只查某盒有没有出数据**：看第1节，再看第2节的UWB或第3节的IMU。
- **三盒一起录包查时间**：确认各盒驱动和数据正常后，直接用第6节的一键录包。手动录包是备选，不必再做一遍。
- **检查雷达或相机**：分别看第4、5节；只测IMU/UWB时可以跳过。
- **接入浙大算法**：传感器检查完成后，再看第3.2.3节和第6节。

如果要录 GNSS+IMU 联合包，固定按“第1节核对 → 第2节启动并确认 UWB/GNSS → 第3节启动、检查并确认 IMU → 第6节联合录包”执行。第2.5节的GNSS单独检查是可选项；但不能在确认IMU之前直接开始第6节录包。

标题中的“三盒都执行”是指201、202、203各做一次；“任选单盒执行”是指在共享ROS网络里选一盒观察或录包。**录包在哪个盒子上，不代表数据只来自那个盒子。**

下文新增的终端输出、PID、日期、测量值均为**说明格式的示例，不是盒子当前实测结果**。标有“节选”或省略号的输出只用于阅读；实际运行仍复制完整的bash命令块。重复出现的环境命令沿用首次解释，后面重点说明本步骤新增的参数与输出。

每段命令整块复制。不要带上终端提示符 `firefly@firefly:~$`、`>` 或Markdown代码围栏。多行命令尚未输入完时出现 `>`，通常只是Shell在等后面的内容。

先记住两件事就够了：已有驱动不要重复启动；不确定是谁开的进程，先核对，不要直接停。查询命令不会改驱动，`source/export`只影响当前终端和随后启动的程序；录包、压缩会生成文件。

先查看当前盒子的IP、车辆配置、传感器进程、串口设备和串口占用情况，避免带着错误编号启动节点或抢占上交正在调试的进程。

~~~bash
hostname
hostname --all-ip-addresses
grep --extended-regexp 'node_id|uwb_id|uart_uwb|uart_gnss' /home/firefly/imu_ws/install/gnss_uwb/share/gnss_uwb/config/params.yaml
pgrep --list-full --full '^/home/firefly/imu_ws/install/navcore/lib/navcore/navcore( |$)'
pgrep --list-full --full '^/home/firefly/imu_ws/install/gnss_uwb/lib/gnss_uwb/gnss_uwb( |$)'
pgrep --list-full --full 'start_livox|livox_ros_driver2'
pgrep --list-full --full --ignore-case 'camera|v4l2|gscam|mipi|image|vision|vins|orb_slam|realsense|usb_cam'
ls --format=long /dev/ttyS* /dev/ttyUSB* /dev/ttyACM* 2>/dev/null
fuser --verbose /dev/ttyS4 /dev/ttyS5 /dev/ttyS6
NAV_PID=$(pgrep --newest --full '^/home/firefly/imu_ws/install/navcore/lib/navcore/navcore( |$)')
test -n "$NAV_PID" && tr '\0' '\n' < "/proc/$NAV_PID/environ" | grep --extended-regexp '^(ROS_DOMAIN_ID|RMW_IMPLEMENTATION|ROS_LOCALHOST_ONLY)='
~~~

下文优先使用完整长参数，帮助用`--help`，不是`--h`。SSH选项、Bash条件表达式等没有对应长写法的保持原样；各程序参数不能机械地多加一个短横线。

这几行从“我连的是谁”查到“谁在使用设备”。`hostname`显示主机名，`hostname --all-ip-addresses`（全部IP地址）列出本机IP；三盒都可能叫firefly，所以要靠IP和车辆配置区分。`grep --extended-regexp`（**extended regular expression**，扩展正则表达式）从参数文件中筛出四个字段，表达式里的`|`表示任选一个匹配。

接着看进程：`pgrep --list-full --full`中的`--full`（完整命令行），按完整命令匹配；`--list-full`（列出完整命令行），把PID（**Process ID**，进程编号）和命令一起显示，别把它记成“查所有进程”；路径两端的`^`与`( |$)`避免把相似名字也算进去。雷达查询匹配Livox启动脚本、launch和驱动节点；相机查询额外使用`--ignore-case`（忽略大小写）匹配常见驱动或图像名称。它们是名称筛查：雷达三行通常只是一套启动链，相机无输出也不能排除名称不同或尚未进入当前DDS环境。`ls --format=long`使用长列表格式，显示设备和权限，`*`匹配同类设备名，`2>/dev/null`隐藏不存在设备等报错。`fuser --verbose`使用详细输出，列出打开串口的进程，输出中的`F`表示以写方式打开，不表示传感器正在正常出数。

最后两行读取运行中IMU的环境。`$(...)`把查询结果存到`NAV_PID`；`pgrep --newest`选择最新启动的进程，只取最新一个，所以查重复启动仍要看前面的完整列表。`test -n`检查字符串长度非零，可用 **non-empty / non-zero length** 助记，确认PID不为空，成功后`&&`才执行后半句。`<`把进程环境文件交给`tr`，它把NUL（空字符）分隔符`\0`换成换行`\n`（**newline**），再由`grep`筛出ROS环境项。

例如看到`/dev/ttyS4 ... 1052120 ... navcore`，就能把串口占用与PID对应起来。若环境只打印`ROS_LOCALHOST_ONLY=0`，只能确认这一项，不能据此认定域号是107。

以下是格式示例，进程命令和设备列表作了节选：

按命令的执行顺序对应输出，不是每条命令都会打印标题：

| 输出来自哪一行 | 能读出什么 | 不能据此断定什么 |
|---|---|---|
| `hostname` | Linux主机名是firefly | 不能靠它区分三盒 |
| `hostname --all-ip-addresses` | 系统配置了两个IP，其中201对应本轮车1 | 不证明两者都能从电脑访问，也不说明走Wi-Fi还是网线 |
| `grep --extended-regexp ... params.yaml` | 磁盘配置为车1、标签18905、两个串口路径 | 文件可能在进程启动后改过，不等于运行中参数已更新 |
| 两条精确路径的`pgrep` | 两个程序有对应的PID | 不证明传感器正常出数，也不说明由谁启动 |
| `ls --format=long ...` | 系统提供了这些设备文件 | 不等于外部模块已接好 |
| `fuser --verbose ...` | 哪个进程打开了哪个串口 | 不证明串口收到了有效帧 |
| 最后读取`/proc` | 该IMU进程环境中查到localhost为0 | 缺失项不能据此猜成域107 |

`crw-rw----`开头的`c`是 **character device**（字符设备）；后面三组分别为所有者、所属组、其他人的权限。`r/w/x`分别是 **read/write/execute**（读/写/执行），`-`表示没有该权限。`root dialout`是所有者与组，不是正在使用设备的人；`4, 68`是主/次设备号，不是波特率；文件日期不是传感器采样时间。

没有输出也有含义：`pgrep`没有匹配通常不打印任何行，退出码为1；`grep`没有匹配也类似。`fuser`未显示占用还要结合权限与报错，不能保证系统内绝对没有占用者。`No such file or directory`要查路径，`Permission denied`要查权限；读取`/proc/<PID>/environ`失败也可能是查询期间进程已退出。

**这段Shell语法怎么读**

- `NAV_PID=...`是赋值，等号两侧不能加空格；`$NAV_PID`才是取值。`$(...)`先执行内部命令，再用它的标准输出替换这一段。
- 单引号保留内部字符；双引号允许展开变量，同时避免带空格的路径被拆成多个参数。正则用单引号，是为了原样交给`grep/pgrep`。
- `/dev/ttyS*`由Shell展开路径；引号里的正则则由查询程序解释。`^`是行首，`$`是行尾，`( |$)`表示空格或结束。
- `A | B`把A的标准输出交给B；`A && B`在A成功时执行B；`A || B`在A失败时执行B。“成功”指退出码0，不是打印了正常字样。
- 标准输入、标准输出、标准错误的编号分别为0、1、2。`< 文件`接入输入；`2>/dev/null`丢弃错误信息。`/dev/null`是丢弃内容的特殊设备，不是日志文件。
- `tr`可按 **translate**（转换字符）记忆；这里转换的是读出的分隔符，没有修改进程环境文件。

查到的`--ros-args --params-file ...`是驱动原启动命令的一部分：前者标记ROS参数区，后者指定参数文件（**parameters file**）。

处理原则：

- 进程已存在：不重复启动；
- 串口空闲且进程不存在：可以启动；
- 串口被其他 PID 占用：不要启动第二份驱动；
- `ttyS4/5/6` 不存在：先查参数文件，不创建或猜测设备名。
- IP、`node_id`、`uwb_id` 与上表任一项不一致：先停止本次启动操作并让上交确认配置。
- 已有 `navcore` 的DDS环境与本文一致：保留进程；环境不一致或不明：核对精确PID后回原终端按 `Ctrl+C`，再按3.1使用正确环境重启。

## 🔷【三盒都执行】2. UWB/GNSS：先启动并确认授时

UWB RMC 是 IMU 授时的前置条件。`gnss_uwb` 必须先启动并保持运行；其启动终端连续看到有效且递增的 `Received UWB GNRMC` 后，才能执行第3节启动 `navcore`。UWB/GNSS 使用 `/dev/ttyS5`、`/dev/ttyS6` 和 `ROS_LOCALHOST_ONLY=0`；IMU使用 `/dev/ttyS4` 和 `ROS_LOCALHOST_ONLY=1`。这是硬件/驱动的授时顺序，不要求两个ROS节点经DDS互相发现。

三盒分别按“2.1核对配置和占用 → 2.2启动并确认UWB RMC → 2.3核对身份和Topic”的顺序执行。2.4是测距验收，不是IMU启动闸门：单盒暂时没有测距时，仍可先通过RMC日志判断授时源。

### 🔷【三盒都执行】2.1 检查参数、进程和 DDS 环境

确认本车 `node_id`、`uwb_id`、串口配置、进程 PID、串口占用和进程实际 DDS 环境。下面的查询命令不会改变现有进程；之后的配置修改和重启仅在需要切换授时源时执行。

~~~bash
grep --extended-regexp 'node_id|uwb_id|uart_uwb|uart_gnss' /home/firefly/imu_ws/install/gnss_uwb/share/gnss_uwb/config/params.yaml
grep --line-number 'pps_source' /home/firefly/imu_ws/install/gnss_uwb/share/gnss_uwb/config/params.yaml
GNSS_UWB_PID=$(pgrep --newest --full '^/home/firefly/imu_ws/install/gnss_uwb/lib/gnss_uwb/gnss_uwb( |$)')
printf 'GNSS_UWB_PID=%s\n' "${GNSS_UWB_PID:-未运行}"
test -n "$GNSS_UWB_PID" && tr '\0' '\n' < "/proc/$GNSS_UWB_PID/environ" | grep --extended-regexp '^(ROS_DOMAIN_ID|RMW_IMPLEMENTATION|ROS_LOCALHOST_ONLY)='
fuser --verbose /dev/ttyS5 /dev/ttyS6
~~~

`pps_source`是上交驱动选择PPS授时源的参数：`0`表示GNSS PPS，`1`表示UWB PPS。三盒联测必须先确认三盒取值一致。当前室内、没有三盒共同有效GNSS PPS时统一设为：

```yaml
pps_source: 1
```

具体的“查配置 → 备份改值 → 退出旧进程 → 重新启动 → 核对日志”命令统一放在[21号精简版第2节](21_上交盒端传感器节点启动与可用性检查_精简执行版.md#2-按需启动uwbgnss)，在201、202、203分别执行。三盒都要检查，但只修改不符合的盒子；已确认按1运行的不必重复重启。修改前结束正在进行的录包和定位测试。

备份修改块中的`readlink --canonicalize`找到配置的真实路径，避免安装目录中的符号链接被`sed --in-place`替换掉；`cp --preserve`复制并保留原文件属性，备份名带日期时间，末尾会打印完整路径。`sed --in-place --regexp-extended`表示原地编辑、使用扩展正则；这里只把独立的`pps_source: 0`改成1，保留缩进和行尾注释，不改其他参数。两个`grep`检查用于拒绝字段缺失、重复或非0的情况。外层`(...)`是子Shell，`set -e`让失败时停止后续操作，`exit`不会退出SSH。

备份文件名为`params.yaml.bak.<日期时间>`，位于输出所示目录中；需要恢复时先停节点，再将该备份复制回打印出的配置路径并重启。安装目录中的配置可能在上交重新安装或部署后变化，更新驱动后应重新核对。

改文件不会更新旧进程，必须重启`gnss_uwb`加载新配置，不能只重启`navcore`。`switch uwb pps source`只证明选择了UWB PPS分支，不证明PPS实际到达、RMC秒号正确或消息已经同步；还需录新包验证。当前室内三盒测试不混用两种源；若GNSS只在201用于真值，三盒仍统一UWB授时，GNSS真实UTC与UWB模拟时间的映射单独验证。单盒户外GNSS授时测试可以使用0，不要求另外两盒参与；以后采用三盒GNSS授时前，须确认各盒有效PPS、RMC秒号和消息时域一致，而不是只看参数相同。

#### 找不到原启动终端时

只在确认本盒进程属于本次测试、或上交已同意停止时使用。在本盒任意SSH终端先查询：

```bash
pgrep --list-full --full '^/home/firefly/imu_ws/install/gnss_uwb/lib/gnss_uwb/gnss_uwb( |$)'
```

核对输出确为本盒`gnss_uwb`，记下行首PID。下面会要求手动输入这个PID，并再次校验可执行文件完整路径；不用输入`navcore`或launch的PID。

```bash
(
read -r -p '输入刚才核对过的gnss_uwb PID：' GNSS_UWB_PID
case "$GNSS_UWB_PID" in ''|*[!0-9]*) printf 'PID无效，未停止\n'; exit 1 ;; esac
UWB_EXE=$(readlink --canonicalize "/proc/$GNSS_UWB_PID/exe")
EXPECTED_UWB_EXE=$(readlink --canonicalize /home/firefly/imu_ws/install/gnss_uwb/lib/gnss_uwb/gnss_uwb)
test -n "$UWB_EXE" && test "$UWB_EXE" = "$EXPECTED_UWB_EXE" || { printf '进程已退出或路径不符，未停止\n'; exit 1; }
ps --format pid,args --pid "$GNSS_UWB_PID"
kill -INT "$GNSS_UWB_PID" || exit 1
sleep 2
pgrep --list-full --full '^/home/firefly/imu_ws/install/gnss_uwb/lib/gnss_uwb/gnss_uwb( |$)'
fuser --verbose /dev/ttyS5 /dev/ttyS6
)
```

`kill -INT`只向核对过的PID发送中断信号（SIGINT），让驱动正常退出，不会批量停止IMU或雷达。末尾两项查询应无占用输出，然后回21第2.3节启动。如果还有PID、自动出现新PID或串口仍被占用，先查原launch/自启动服务，不反复强杀、不启动第二份。参数文件已为1但运行日志仍为GNSS分支时，也需要核对进程启动参数中的实际`--params-file`。

#### 如何理解上面的进程和环境查询

这里沿用第1节的查法，只把对象换成`gnss_uwb`。`printf`按格式输出，`%s`中的`s`表示 **string**（字符串）、`\n`表示 **newline**（换行）；`${GNSS_UWB_PID:-未运行}`的意思是PID为空时显示“未运行”。`"$GNSS_UWB_PID"`中的双引号让变量作为一个完整参数传入。

已有进程的环境不能通过当前终端的 `export` 修改。若它与计划使用的 DDS 环境不一致，回到原启动终端按 `Ctrl+C` 干净退出后，再用目标环境重启；停止前先核对PID和串口，避免误停其他服务。

**可能出现的结果**

~~~text
GNSS_UWB_PID=1051979
ROS_DOMAIN_ID=0
RMW_IMPLEMENTATION=rmw_fastrtps_cpp
ROS_LOCALHOST_ONLY=0
~~~

表示查到了进程，且查出的三项环境与本文UWB配置一致，仍需用后面的串口占用与数据核对。另一种输出是：

~~~text
GNSS_UWB_PID=未运行
~~~

这是命令设置的默认提示，不是系统原生字段。此时`test -n`失败，后面的环境读取被跳过。若只有PID、没有环境行，不能当成没有进程：可能变量未显式设置，或环境读取失败。

`${变量:-默认值}`在变量未设置或为空时使用默认值，仅决定本次展开的文本，不把“未运行”写回PID变量。

### 🔷【三盒都执行】2.2 UWB启动终端：启动并确认授时

这是启动终端，建议每盒新开一个终端；该终端只运行本节点并保持前台输出。执行前必须完成2.1，确认本盒IP、`node_id`、`uwb_id` 与第1节表格一致，`gnss_uwb` 进程不存在，且UWB串口 `/dev/ttyS5` 没有被其他 PID 占用。GNSS测试还要求 `/dev/ttyS6` 存在且空闲。若进程已经存在，不要再次启动，回到原日志终端检查。

设置本终端的 DDS 环境并启动本盒UWB/GNSS节点；它不会占用IMU串口 `/dev/ttyS4`。

~~~bash
source /opt/ros/humble/setup.bash
source /home/firefly/imu_ws/install/setup.bash
export ROS_DOMAIN_ID=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOCALHOST_ONLY=0

ros2 launch gnss_uwb gnss_uwb_launch.py
~~~

前五行是在准备这个终端。第一个`source`加载ROS 2 Humble，第二个加载上交工作空间，让Shell能找到驱动和自定义消息。`export`把设置传给随后启动的程序：0是ROS 2默认通信域，也是本指南后续测试的统一域，不是盒号或时钟号；`rmw_fastrtps_cpp`选择Fast DDS；`ROS_LOCALHOST_ONLY=0`允许跨盒通信。

最后的`ros2 launch`依次填写包名和启动文件名，真正启动节点。后面观察和录包前重复这组环境命令，是因为新开终端不会自动继承另一个终端的设置；解释相同，不再逐段重复。

启动后保持该终端运行。启动IMU前必须连续看到至少两条类似 `Received UWB GNRMC: $GNRMC,001319.928,A,...` 的日志，其中时间字段递增且状态为 `A`。`Received GNSS line: $GNRMC,,V,...` 是无效GNSS定位行，不能作为UWB授时成功依据。若没有有效递增的UWB RMC，不执行第3节。

若日志同时出现 `open rmc UART device: /dev/ttyVUSB0`，而参数文件写的是 `uart_gnss: /dev/ttyS6`，先向上交确认 `ttyVUSB0` 是否为驱动创建的 RMC 虚拟串口；不要自行改串口路径。`switch uwb pps source`表示按`pps_source: 1`选择UWB PPS；`switch gnss pps source`表示按`pps_source: 0`选择GNSS PPS。日志只能说明程序选择了分支，仍需让上交确认对应硬件PPS实际存在并到达IMU。

若 `/dev/ttyS5` 出现 `Permission denied`、`Device busy` 或打开失败，停止自己本次启动的节点并把完整日志和2.1结果发给上交。若仅 `/dev/ttyS6` 打开失败，则只判GNSS不可用；节点仍在运行、S5成功打开且UWB RMC/测距正常时，可以继续UWB测试。

**启动命令中的名字分别指什么**

| 写法 | 含义与作用 |
|---|---|
| `source 文件` | 在当前Shell执行环境脚本，让路径设置留在当前终端；正常时经常没有输出 |
| `/opt/ros/humble/setup.bash` | ROS 2基础环境；ROS为 **Robot Operating System** |
| `imu_ws/install/setup.bash` | 上交工作空间安装后的环境；`ws`常作 **workspace** 的缩写 |
| `ROS_DOMAIN_ID` | 通信域编号；ID为 **identifier**。相同域不代表已经联网或同步 |
| `RMW_IMPLEMENTATION` | 选择 **ROS Middleware**（ROS中间件）实现；这里是Fast DDS对应的C++实现包 |
| `DDS` | **Data Distribution Service**，负责发现与消息通信，不是传感器授时协议 |
| `ROS_LOCALHOST_ONLY` | **local host only**，是否只限本机；本节0允许跨主机通信 |
| `ros2 launch 包名 文件名` | 用ROS命令行的launch子命令，读取指定包内的启动文件 |

`export 名称=值`使随后启动的子进程继承该变量，不修改已有进程。换SSH窗口要重新设置环境。

日志可能如下，省略号不是完整RMC报文：

~~~text
[INFO] [gnss_uwb-1]: process started with pid [1051979]
[gnss_uwb-1] [INFO] [...] [gnss_uwb]: switch uwb pps source
[gnss_uwb-1] [INFO] [...] [gnss_uwb]: open uwb uart device: /dev/ttyS5 460800
[gnss_uwb-1] [INFO] [...] [gnss_uwb]: Received UWB GNRMC: $GNRMC,001319.928,A,...
[gnss_uwb-1] [INFO] [...] [gnss_uwb]: Received UWB GNRMC: $GNRMC,001320.928,A,...
~~~

`INFO/WARN/ERROR`是信息/警告/错误级别；方括号里的日志时间不要直接当成采样时间。`460800`是串口波特率。`RMC`通常展开为 **Recommended Minimum Specific GNSS Data**，是NMEA语句类型；`GN`是发送者标识，不能仅凭它认定有真实卫星定位。`001319.928`按语句格式表示00时13分19.928秒，`A`表示语句声明有效，`V`表示无效。上交可能使用模拟RMC，其日期起点仍需另行核对。

`PPS`是 **Pulse Per Second**（每秒脉冲）。选择PPS源、RMC递增都不等于已经证明PPS到达IMU、秒与小数秒正确配对、三盒处于同一时间轴。

`Package 'gnss_uwb' not found`先查工作空间环境；设备`No such file or directory`先查路径；`Permission denied`查权限。持续`Tag ID unknown`需检查标签映射及实际车辆边，不要只凭启动成功就开始正式验收。

### 🟢【任选单盒执行】2.3 UWB观察终端：核对运行时车辆身份

必须使用另一个终端，不要在2.2正在输出日志的启动终端中粘贴。设置与2.2完全相同的 DDS 环境。

查看UWB/GNSS节点和Topic，并读取节点实际发布的车辆身份。整块复制执行。

~~~bash
source /opt/ros/humble/setup.bash
source /home/firefly/imu_ws/install/setup.bash
export ROS_DOMAIN_ID=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOCALHOST_ONLY=0

ros2 node list --no-daemon
ros2 topic list --no-daemon --show-types | sort
ros2 topic list --no-daemon --show-types | grep --extended-regexp 'cooperative_interfaces/msg/(UwbRange|GnssPosition|Identity)'
ros2 interface show cooperative_interfaces/msg/Identity
ros2 topic info --no-daemon --verbose /node/id
timeout --signal=INT 3s ros2 topic echo --no-daemon --once /node/id cooperative_interfaces/msg/Identity
timeout --signal=INT 5s ros2 topic echo --no-daemon --field node_id /node/id cooperative_interfaces/msg/Identity
~~~

先用`node list`和`topic list`看能发现什么。`--no-daemon`就是 **no daemon**（不使用守护进程），让支持该选项的查询直接发现节点，减少旧守护进程环境的干扰；`--show-types`同时显示Topic类型。`| sort`只是排序，下一行的`grep`则只保留上交接口。

`interface show`查看消息有哪些字段；`topic info --verbose`中的 **verbose** 表示详细输出，查看发布者、订阅者和QoS（**Quality of Service**，服务质量）。最后两行才真正读数据：`echo --once`中的 **once** 是“一次”，拿到一条后退出；`--field node_id`中的 **field** 是“字段”，只打印车辆号。`timeout --signal=INT 5s`中的 **signal** 是信号，INT表示 **interrupt**（中断），`s`是 **seconds**（秒）；它在5秒后发送SIGINT让观察命令结束，这5秒也包括启动和发现时间。

单盒测试时应看到该盒身份；三盒都启动后，在任意一盒连续观察5秒，应收齐逻辑 `node_id=1/2/3`。启动初期短暂出现 `Tag ID unknown` 可以等待动态识别；随后出现 `Received new UWB tag ID: <node_id> <uwb_id>` 且能发布对应车辆边即可继续。参与测距的ID持续unknown且没有对应车辆边时才判映射失败。

**从“看得到名字”到“收到身份”**

~~~text
/gnss_uwb
/node/id [cooperative_interfaces/msg/Identity]
/uwb/range [cooperative_interfaces/msg/UwbRange]
~~~

第一行可能来自节点列表，后两行来自带类型的Topic列表。`cooperative_interfaces/msg/Identity`依次是包名、消息类别、类型名，大小写不能错。`interface show`显示定义：

~~~text
uint32 node_id
uint16 uwb_id
~~~

`uint`是 **unsigned integer**（无符号整数）；32、16是位数，不是车辆数量。`echo --once`读到的才是值：

~~~yaml
node_id: 1
uwb_id: 18905
---
~~~

`---`是消息分隔标记；`--field node_id`只留下车辆号，不打印完整消息。5秒未收齐只能说明本次窗口未观察齐，需要排查发现、网络与进程，不能直接判定某盒断电。

| `topic info --verbose`字段 | 含义 |
|---|---|
| `Publisher count` | 发现的发布端点数量，不是消息条数，也不直接等于盒子数 |
| `Subscription count` | 订阅端点数量；本节点自己也可能订阅身份 |
| `Node name / namespace` | 节点名/命名空间，同名不等于同一进程 |
| `GID` | **Globally Unique Identifier**，端点标识，不是UWB ID或IP |
| `Reliability: RELIABLE` | 可靠传输；`BEST_EFFORT`为尽力而为，两端QoS须兼容 |
| `Durability: VOLATILE` | 不为后来订阅者保留历史样本，需要等待新消息 |
| `History / Depth` | 缓存策略/深度，`UNKNOWN`不能单独作为驱动故障证据 |
| `Deadline / Lifespan / Liveliness` | 期望更新间隔/样本寿命/存活性策略，`Infinite`不是零频率 |

`The passed message type is invalid`先查类型拼写与环境。等到timeout结束却没有消息，说明这次订阅窗口未拿到样本；发布者数量非零不能代替收消息。

### 🟠【参与测距盒启动】＋🟢【任选单盒观察】2.4 检查UWB测距

三盒形成三条无向几何边`1-2、1-3、2-3`；ROS消息则按有序的`src_id→target_id`记录。如果三个盒各自报告到另外两个盒，最多出现`3×2=6`个方向：`1→2、2→1、1→3、3→1、2→3、3→2`。最新录包确实如此，但这只能证明驱动发布六向记录；正反向究竟是两次独立空口测距，还是同一次协议交换产生的共享/派生结果，必须由上交冻结协议语义。定位几何仍按三条无向边处理，正反向可用于一致性检查，不能默认成六个相互独立量测。

时间数字必须分开读：IMU正常中位周期约`1 ms`（约1000 Hz），每个UWB方向正常中位周期约`100 ms`（约10 Hz）。`>200 ms`只是在离线报告中统计UWB长间隔的阈值，不是正常周期；`R−H`是录包接收时刻与消息测量时刻之差，含时钟基准差和处理链影响，也不是采样周期或纯网络延迟。

先按目标选择参与盒子，不要一开始同时启动全部传感器：

| 测试目标 | 参与盒子 | 需要运行 | 预期结果 |
|---|---|---|---|
| 单盒授时 | 任意1盒 | 本盒 `gnss_uwb` | UWB RMC有效递增；没有车间测距不判失败 |
| 单条测距边 | 车1+车2等任意2盒 | 两盒UWB硬件参与；当前联调默认两盒均运行 `gnss_uwb` | 只要求出现对应1条车辆边；功能冒烟可忽略第3盒的其他边 |
| 三车测距 | 车1+车2+车3 | 三盒均运行 `gnss_uwb` | 最好收到 `1-2`、`1-3`、`2-3` 三边；进入融合至少保证三节点测距图连通 |

功能冒烟可以让第3盒保持现状，只按 `src_id/target_id` 筛选目标边；严格双盒精度测试必须让第3盒UWB停止或断电。若上交确认被测标签上电后无需运行ROS节点，也可只在结果输出盒运行 `gnss_uwb`；在该行为冻结前，参与测距的两边默认都启动。

检查 `/uwb/range` 的发布者和10秒内真正出数的无向测距边。正式分边频率、连续性和精度以2.4.1录包为准。

~~~bash
source /opt/ros/humble/setup.bash
source /home/firefly/imu_ws/install/setup.bash
export ROS_DOMAIN_ID=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOCALHOST_ONLY=0

UWB_TOPIC=/uwb/range
UWB_TYPE=$(ros2 topic type --no-daemon "$UWB_TOPIC")
if [ -z "$UWB_TYPE" ]; then
  printf '未发现 UWB Topic：%s\n' "$UWB_TOPIC"
else
  ros2 interface show "$UWB_TYPE"
  ros2 topic info --no-daemon --verbose "$UWB_TOPIC"
  EDGE_COUNTS=$(PYTHONUNBUFFERED=1 timeout --signal=INT 10s ros2 topic echo --no-daemon --qos-profile sensor_data "$UWB_TOPIC" "$UWB_TYPE" 2>/dev/null | awk '/^[[:space:]]*src_id:/ {src=$2} /^[[:space:]]*target_id:/ && src != "" {dst=$2; if (src < dst) print src "-" dst; else print dst "-" src; src=""}' | sort | uniq --count)
  if [ -n "$EDGE_COUNTS" ]; then
    printf '10秒内实际无向测距边及消息数：\n%s\n' "$EDGE_COUNTS"
  else
    printf 'UWB测距冒烟失败：10秒内没有测距边\n' >&2
  fi
fi
~~~

这一段先查类型，再观察数据。`UWB_TOPIC=...`是变量赋值，等号两边不留空格；`if [ -z "$UWB_TYPE" ]`中的`-z`检查长度为零（**zero length**，助记），在类型为空时走“未发现”分支，`else`是有类型时的处理，`fi`结束分支。

长管道的流程是：`echo`读消息，AWK记下`src_id`和`target_id`，把小ID放前面组成`1-2`这样的边，再用`sort | uniq --count`数各边条数；`uniq --count`对应`--count`（计数）。AWK的`$2`是当前行第二列；单引号防止它被Shell提前展开。每处理完一条边清空`src`，不沿用上一条消息。`PYTHONUNBUFFERED=1`中的 **unbuffered** 是“不缓冲”，减少Python输出缓冲；`--qos-profile sensor_data`中的 **profile** 是配置集，`sensor_data`是传感器数据配置。

这里统计的是“有哪些无向边的消息”，还没检查距离值和时间戳质量。当前UWB-only算法还要求同一个`header.stamp`下同时具备`1-2、1-3、2-3`三条无向边；精简执行版第3节给出了同历元计数命令，结果必须大于0。最新`joint_time_20260916_214229`中有8429个这种完整历元，因此实包可以直接进入当前逐历元三角形解算。相同Header只说明应用层可配对，不证明三次空口测距在物理上严格同时。`2>/dev/null`会隐藏错误；若没有结果且原因不清，单独执行不隐藏错误的echo查看。

测距通过条件：`src_id/target_id` 使用逻辑车辆号 `1/2/3`，距离有限、为正且单位为米，时间戳非零，并能收到本轮目标车辆边。终端输出只做冒烟检查；时间是否属于 `UWB_SYSTEM_TIME`、是否分边严格递增以及测距误差都以录包验收。`topic info` 的 `Publisher count` 只表示ROS端点数量，不表示已有测距数据；只有 `echo` 成功或bag中 `/uwb/range` 的 `Count` 大于0才证明出数。只有一辆车时没有测距消息也不否定UWB RMC授时。

`Tag ID unknown` 先看后续能否识别并出数。参与盒的ID持续未知、且对应测距边一直没有数据时，把完整日志发给上交。

曾经出现过三盒身份都在线、但实际只有1—2测距的情况。所以要分别查看身份和测距边，不能用前者代替后者。

**AWK数的是边，不是测距精度**

对如下输入：

~~~yaml
src_id: 2
target_id: 1
~~~

第一条规则记下`src=2`，第二条读到1后输出`1-2`。`/正则/ {动作}`是AWK的“条件→处理”，`[[:space:]]*`允许缩进，`&&`是逻辑且。`print src "-" dst`是拼接，不是减法；`src=""`清空暂存值，避免跨消息沿用。

结果示例：

~~~text
     96 1-2
     95 1-3
     97 2-3
~~~

左列是观察窗口内解析出的条数，右列是**无向边**。`1→2`和`2→1`会合并，不能据此确认两个方向都发布，也不能把96直接叫96Hz。`sort`让同边相邻，`uniq --count`才能正确统计重复行。

实际消息格式示例：

~~~yaml
header:
  stamp:
    sec: 1786400000
    nanosec: 123000000
  frame_id: ''
src_id: 1
target_id: 2
rolling: 123
distance: 2.35
---
~~~

当前上交正式字段顺序是`Header、src_id、target_id、rolling、distance`。按本工程接口，`distance`单位米，两端ID为逻辑车辆号；`rolling`只供上交调试，浙大保留字段但不用于配对、同步或定位。消息没有标准差字段，分析报告的标准差需由多帧计算。上述AWK不读取距离，距离为0也能被计边，所以“有边”不等于“距离有效”。

#### 🟢【任选单盒执行】2.4.1 固定几何录包

先修改 `EXPECTED_EDGES`、场景和三条卷尺真值。双车1—2填 `EXPECTED_EDGES="1-2"`；三车填 `EXPECTED_EDGES="1-2 1-3 2-3"`。三边均按UWB天线中心之间测量。命令自动识别录包盒、ROS在线车辆和10秒内实际测距边；任一目标边缺失就不开始60秒录包。无真值时保留 `unknown`，只能检查连通性和算法链路，不能评价测距或定位精度。

~~~bash
source /opt/ros/humble/setup.bash
source /home/firefly/imu_ws/install/setup.bash
export ROS_DOMAIN_ID=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOCALHOST_ONLY=0

(
case " $(hostname --all-ip-addresses) " in
  *" 192.168.1.201 "*) RECORDER_ID=1 ;;
  *" 192.168.1.202 "*) RECORDER_ID=2 ;;
  *" 192.168.1.203 "*) RECORDER_ID=3 ;;
  *) printf '无法根据IP识别录包车辆，未录包\n' >&2; exit 1 ;;
esac

UWB_TYPE=$(ros2 topic type --no-daemon /uwb/range)
test "$UWB_TYPE" = cooperative_interfaces/msg/UwbRange || { printf 'UWB Topic不存在或类型错误：%s\n' "$UWB_TYPE" >&2; exit 1; }

EXPECTED_EDGES="1-2 1-3 2-3"
SCENE=static_triangle
TRUE_D12_M=unknown
TRUE_D13_M=unknown
TRUE_D23_M=unknown

ONLINE_IDS=$(PYTHONUNBUFFERED=1 timeout --signal=INT 5s ros2 topic echo --no-daemon --field node_id /node/id cooperative_interfaces/msg/Identity 2>/dev/null | awk '/^[[:space:]]*[0-9]+[[:space:]]*$/ {gsub(/[[:space:]]/, ""); print}' | sort --numeric-sort --unique | paste --serial --delimiters=-)
test -n "$ONLINE_IDS" || { printf '未收到 /node/id，未录包\n' >&2; exit 1; }

OBSERVED_EDGES=$(PYTHONUNBUFFERED=1 timeout --signal=INT 10s ros2 topic echo --no-daemon --qos-profile sensor_data /uwb/range "$UWB_TYPE" 2>/dev/null | awk '/^[[:space:]]*src_id:/ {src=$2} /^[[:space:]]*target_id:/ && src != "" {dst=$2; if (src < dst) print src "-" dst; else print dst "-" src; src=""}' | sort --unique | paste --serial --delimiters=' ')
test -n "$OBSERVED_EDGES" || { printf '10秒内没有实际测距，未录包\n' >&2; exit 1; }
MISSING_EDGES=
for EDGE in $EXPECTED_EDGES; do
  case " $OBSERVED_EDGES " in
    *" $EDGE "*) ;;
    *) MISSING_EDGES="${MISSING_EDGES}${MISSING_EDGES:+ }${EDGE}" ;;
  esac
done
printf 'ROS在线车辆：%s\n实际测距边：%s\n录包车辆：%s\n' "$ONLINE_IDS" "$OBSERVED_EDGES" "$RECORDER_ID"
test -z "$MISSING_EDGES" || { printf '缺少目标边：%s，未录包\n' "$MISSING_EDGES" >&2; exit 1; }

EDGE_TAG=$(printf '%s' "$OBSERVED_EDGES" | tr ' ' '_')
mkdir --parents /home/firefly/uwb_test
UWB_BAG="/home/firefly/uwb_test/uwb_online_v${ONLINE_IDS}_edges_${EDGE_TAG}_rec_v${RECORDER_ID}_${SCENE}_$(date +%Y%m%d_%H%M%S)"
timeout --foreground --signal=INT --kill-after=5s 60s ros2 bag record --output "$UWB_BAG" /uwb/range /node/id
if [ -f "$UWB_BAG/metadata.yaml" ]; then
  BAG_INFO=$(ros2 bag info "$UWB_BAG")
  printf '%s\n' "$BAG_INFO"
  RANGE_COUNT=$(printf '%s\n' "$BAG_INFO" | sed --quiet 's/.*Topic: \/uwb\/range .* Count: \([0-9][0-9]*\).*/\1/p')
  test -n "$RANGE_COUNT" || RANGE_COUNT=0
  printf 'online_node_ids=%s\nexpected_edges=%s\nprecheck_observed_edges=%s\nrecorder_vehicle=%s\nscene=%s\ntrue_distance_1_2_m=%s\ntrue_distance_1_3_m=%s\ntrue_distance_2_3_m=%s\nrange_message_count=%s\n' "$ONLINE_IDS" "$EXPECTED_EDGES" "$OBSERVED_EDGES" "$RECORDER_ID" "$SCENE" "$TRUE_D12_M" "$TRUE_D13_M" "$TRUE_D23_M" "$RANGE_COUNT" > "$UWB_BAG/test_info.txt"
  UWB_ARCHIVE="${UWB_BAG}.tar.gz"
  tar --directory "$(dirname "$UWB_BAG")" --create --gzip --file "$UWB_ARCHIVE" "$(basename "$UWB_BAG")"
  printf 'SFTP 下载文件：%s\n' "$UWB_ARCHIVE"
  ls --format=long --human-readable "$UWB_ARCHIVE"
  sha256sum "$UWB_ARCHIVE"
  test "$RANGE_COUNT" -gt 0 || printf '录包无效：/uwb/range 为0条，只能作为故障诊断证据\n' >&2
else
  printf '录包失败：未生成 metadata.yaml，未执行分析和压缩\n' >&2
fi
)
~~~

这段较长，但只有三件事：确认录包对象、录60秒、打包下载。

开头的`( ... )`把变量和`exit`限制在子Shell内，检查失败不会退出当前SSH。`case`按本机IP选`RECORDER_ID`，每个`;;`结束一个分支，`esac`结束选择。`test ... || { ...; exit 1; }`表示条件不满足就打印原因并退出；`>&2`把提示送到错误输出。

`ONLINE_IDS`从身份消息中保留整行整数，`sort --numeric-sort --unique`按数值排序并去重；`paste --serial --delimiters=-`串行合并各行，以`-`分隔，最后那个`-`是分隔符的值，拼成`1-2-3`。`OBSERVED_EDGES`沿用上一节的分边方式，用`sort --unique`去重，再用空格连接。`for EDGE in $EXPECTED_EDGES`逐边检查；`${MISSING_EDGES:+ }`只在已有内容时补一个空格。它们分别回答“谁在线”和“哪些边出数”，不是同一件事。

`tr ' ' '_'`把边列表中的空格改成下划线用于文件名；`mkdir --parents`创建父目录，缺少的上级目录一起创建，已有目录也能继续。`date +%Y%m%d_%H%M%S`生成本机日期时间：`Y`是四位 **year**（年），`m`是 **month**（月），`d`是 **day**（日），`H`是24小时制 **hour**（时），`M`是 **minute**（分），`S`是 **second**（秒）；尤其别把小写月份`m`和大写分钟`M`弄反。`ros2 bag record --output`，指定新包目录，后面列要录的两个Topic；超时选项的退出处理见第3.4.1节。

结束后，`[ -f ... ]`中的`f`可按 **regular file**（普通文件）记忆，检查是否有元数据，`bag info`读摘要。`sed --quiet 's/.../\1/p'`从摘要提取测距Count：`--quiet`关闭自动打印，脚本中的`s`是 **substitute**（替换），`p`是 **print**（打印），其中`\(...\)`捕获数字、`\1`取这个数字；为空时暂记0，要结合摘要排除格式变化。`printf ... > test_info.txt`保存本轮信息，`>`会覆盖同名文件。

最后`tar --directory`切到指定目录；`--create --gzip --file`创建gzip压缩归档并指定文件名，不是生成ZIP文件；`dirname/basename`分别取父目录和目录名。`ls --format=long --human-readable`使用长列表格式和易读文件大小，以KB/MB等易读大小显示文件，`sha256sum`给出校验值，下载后可用来核对文件是否完整。原包不会被删除。`pgrep --full`匹配完整命令行，`test -f`检查普通文件，`tar --file`指定归档文件；Shell的`test -f`没有长选项。

最后的`test "$RANGE_COUNT" -gt 0`中，`gt`表示 **greater than**（大于），用于整数比较；这里检查测距条数是否大于零。

`online_node_ids` 表示 `/node/id` 中活跃的ROS身份；`precheck_observed_edges` 才表示录包前真正出数的UWB边。文件名和 `test_info.txt` 同时保存这两者以及录包车辆。最终边集合仍以bag离线解析为准。

**长命令中的变量逐个对应什么**

| 变量 | 来源 | 示例及用途 |
|---|---|---|
| `RECORDER_ID` | 本机IP | 3：在哪个盒子录 |
| `EXPECTED_EDGES` | 操作者设置 | `1-2 1-3 2-3`：要求哪些边；两盒实验应改为目标边 |
| `ONLINE_IDS` | 身份观察 | `1-2-3`：看到了哪些身份 |
| `OBSERVED_EDGES` | 测距观察 | `1-2 1-3 2-3`：预检查见到的无向边 |
| `MISSING_EDGES` | 期望与观察比较 | 空字符串表示没有缺少目标边 |
| `SCENE` | 操作者设置 | `static_triangle`：静止三角形 |
| `TRUE_D12_M / TRUE_D13_M / TRUE_D23_M` | 操作者填写 | 三条天线中心卷尺距离；未测为`unknown`，此时不能评价精度 |
| `EDGE_TAG` | 空格替换 | `1-2_1-3_2-3`：用于目录名 |
| `UWB_BAG / UWB_ARCHIVE` | 自动拼接 | 原始包目录 / 下载压缩文件 |
| `BAG_INFO / RANGE_COUNT` | 录后查询 | 包摘要 / UWB消息总条数 |

`case " $(hostname --all-ip-addresses) " in`给IP两侧补空格，再匹配完整IP，避免部分数字碰巧匹配。`*)`是兜底分支，`;;`结束一个分支，`esac`结束选择。`MISSING_EDGES=`表示空字符串。`for EDGE in $EXPECTED_EDGES`这里刻意不加引号，让空格分开的边逐个进入循环；文件路径变量则要加引号。

身份规则中的`^[[:space:]]*[0-9]+[[:space:]]*$`只接受整行整数。`+`为至少一次，`*`为零次或更多；`gsub(..., "")`是 **global substitution**（全局替换），删除空白。`paste --serial --delimiters=' '`拼成空格分隔的一行，身份列表则用短横线分隔。

预检查正常时：

~~~text
ROS在线车辆：1-2-3
实际测距边：1-2 1-3 2-3
录包车辆：3
~~~

随后应出现订阅和录包日志。缺边时可能是：

~~~text
ROS在线车辆：1-2-3
实际测距边：1-2
录包车辆：3
缺少目标边：1-3 2-3，未录包
~~~

这是主动停止，不是“距离全为零”。`10秒内没有实际测距，未录包`则是该窗口未解析出边，需用不隐藏stderr的echo排除通信或类型错误。

目录名示例：

~~~text
uwb_online_v1-2-3_edges_1-2_1-3_2-3_rec_v3_static_triangle_20260911_100000
~~~

依次记录可见身份、预检查边、录包盒、场景、本机日期。目录名不是质量证书：录制中可能缺边，还需离线逐边统计。

包摘要节选示例：

~~~text
Storage id:        sqlite3
Duration:          59.5s
Messages:          1980
Topic information: Topic: /uwb/range | Type: cooperative_interfaces/msg/UwbRange | Count: 1800 | Serialization Format: cdr
                   Topic: /node/id | Type: cooperative_interfaces/msg/Identity | Count: 180 | Serialization Format: cdr
~~~

`Messages`是所有Topic总数；`Count`为当前Topic条数，不是每条边条数。`CDR`为 **Common Data Representation**（通用数据表示），是序列化格式；`sqlite3`是存储后端。摘要时长不能证明消息头时间正确。

`sed --quiet 's/.../\1/p'`从UWB摘要行提取计数：`.*`匹配任意长度内容，`[0-9][0-9]*`匹配至少一位数字，`\( ... \)`是捕获组，`\1`引用第一组；`\/`使斜杠成为路径字符，末尾`p`打印替换结果。版本改变摘要格式时解析失败也会回退为0，需对照原摘要。

`printf ... > test_info.txt`写文件而非屏幕；`>`覆盖，`>>`才是追加。`dirname/basename`取父目录/末尾名称。`tar --directory 父目录 --create --gzip --file 压缩文件 包名`让归档包含相对包名。压缩成功通常无输出；`ls --format=long --human-readable`显示大小，`sha256sum`输出SHA-256（**Secure Hash Algorithm 256-bit**）摘要和文件名，用于核对传输完整性，不衡量测距精度。

### 🟢【任选单盒执行】2.5 检查GNSS数据

按需检查 `/gnss/fix` 的发布者、频率和一帧定位数据。若上交以后修改Topic，只需调整 `GNSS_TOPIC`。

~~~bash
source /opt/ros/humble/setup.bash
source /home/firefly/imu_ws/install/setup.bash
export ROS_DOMAIN_ID=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOCALHOST_ONLY=0

GNSS_TOPIC=/gnss/fix
GNSS_TYPE=$(ros2 topic type --no-daemon "$GNSS_TOPIC")
if [ -z "$GNSS_TYPE" ]; then
  printf '未发现 GNSS Topic：%s\n' "$GNSS_TOPIC"
else
  ros2 topic info --no-daemon --verbose "$GNSS_TOPIC"
  timeout --signal=INT 8s ros2 topic hz "$GNSS_TOPIC" --window 3
  timeout --signal=INT 3s ros2 topic echo --no-daemon --once "$GNSS_TOPIC" "$GNSS_TYPE"
  timeout --signal=INT 8s ros2 topic echo --no-daemon --field node_id "$GNSS_TOPIC" "$GNSS_TYPE"
fi
~~~

这是与UWB相同的“查类型—看发布者—读消息”流程。`--window 3`中的 **window** 是统计窗口，让频率统计使用最近3个间隔样本的窗口；GNSS比IMU慢，因此观察时间设得更长。`--field node_id`用于检查共享Topic里实际出现了哪些车辆。没有卫导条件时可以跳过本节，不必等GNSS有效才检查UWB测距。

通过条件：三盒都运行时，连续观察应收齐 `node_id=1/2/3`；各车经纬高为有限值，定位状态有效。室内未 RTK 定解不等于驱动故障。

**收到GNSS消息不等于定位有效**

GNSS为 **Global Navigation Satellite System**（全球卫星导航系统）；RTK为 **Real-Time Kinematic**（实时动态差分定位）。消息字段节选示例：

~~~yaml
node_id: 2
status: -1
latitude: 0.0
longitude: 0.0
altitude: 0.0
position_covariance_type: 0
~~~

按本工程定义，`status: -1`是`STATUS_NO_FIX`，不能把本例零经纬度当成真实位置。`latitude/longitude`是纬度/经度，单位度；`altitude`是高程，单位米；`position_covariance`是位置协方差，单位平方米，类型0表示未知。接口的FIX、SBAS_FIX、GBAS_FIX枚举不能自行当作接收机“RTK fixed”状态码。

三盒共用Topic时，`hz`可能统计三盒消息混合后的总频率。应结合`node_id`分车看，不能把总频率当单车频率。

## 🔷【三盒都执行】3. IMU：UWB授时就绪后启动并检查

上交要求 `navcore` 及 `/imu/raw` 只在本车可见。以后启动、观察、实时显示和录制 IMU 时都使用 `ROS_LOCALHOST_ONLY=1`；因此三辆车可以保留相同的 `/navcore_node` 和 `/imu/raw`，其他车辆不会看到。本节IMU命令不得改成 `ROS_LOCALHOST_ONLY=0`；第2节UWB/GNSS仍为三车共享，继续使用 `ROS_LOCALHOST_ONLY=0`。

执行本节前，本盒2.2的 `gnss_uwb` 必须仍在运行，且已经确认至少两条有效递增的UWB RMC。已有 `navcore` 且观察端能用 `ROS_LOCALHOST_ONLY=1` 看到非零时间戳时，保持原进程并直接做3.2；不要为了“按顺序重来”而重启。只有节点未运行时才执行3.1。

部署边界已适配：盒端 Fast DDS 中，`ROS_LOCALHOST_ONLY=0` 的进程不能直接发现 `ROS_LOCALHOST_ONLY=1` 的 `navcore`。浙大车辆launch设置 `use_localhost_imu_bridge:=true` 后，本地惯导和本地发送端使用 `ROS_LOCALHOST_ONLY=1`，只把NodeState CDR经带版本、长度和CRC校验的127.0.0.1数据报送到共享转发端；共享转发端使用 `ROS_LOCALHOST_ONLY=0` 发布 `/cooperative_localization/node_state`。原始 `/imu/raw` 不会被转发。该桥已完成本机双DDS隔离实测，仍须在RK3588上验收。

### 🔷【三盒都执行】3.1 IMU启动终端：仅在未运行时启动

保持2.2的UWB启动终端运行，另开一个终端执行本模块。

确认 `gnss_uwb` 仍在运行，然后以前台方式启动IMU节点。仅在UWB RMC已验证、`navcore` 未运行且 `/dev/ttyS4` 空闲时整块执行。若 `navcore` 已运行，命令只会报告PID并退出，不会停止或重启它。

~~~bash
source /opt/ros/humble/setup.bash
source /home/firefly/imu_ws/install/setup.bash
export ROS_DOMAIN_ID=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOCALHOST_ONLY=1

GNSS_UWB_PID=$(pgrep --newest --full '^/home/firefly/imu_ws/install/gnss_uwb/lib/gnss_uwb/gnss_uwb( |$)')
NAV_PID=$(pgrep --newest --full '^/home/firefly/imu_ws/install/navcore/lib/navcore/navcore( |$)')
if [ -z "$GNSS_UWB_PID" ]; then
  printf 'gnss_uwb 未运行：未启动 navcore\n' >&2
elif [ -n "$NAV_PID" ]; then
  printf 'navcore 已运行（PID=%s）：不重复启动\n' "$NAV_PID" >&2
elif fuser --silent /dev/ttyS4; then
  printf '/dev/ttyS4 已被其他进程占用：未启动 navcore\n' >&2
else
  printf 'GNSS_UWB_PID=%s；请确认其日志中的UWB RMC已有效递增\n' "$GNSS_UWB_PID"
  ros2 launch navcore navcore_launch.py
fi
~~~

IMU沿用相同ROS域和中间件，但把`ROS_LOCALHOST_ONLY`设为1，只在本盒发现。`if/elif/else`按顺序检查：UWB驱动没运行、IMU已经运行、串口被占用；满足任何一项都不再启动。`-z`查空字符串、`-n`查非空，`fuser --silent`只返回是否占用而不打印详情。只有最后的`else`会运行`ros2 launch`。

这段命令不能自动检查RMC日志是否有效，仍需先看上一启动终端。

**四个分支分别会做什么**

| 条件 | 含义 | 后续 |
|---|---|---|
| UWB的`-z`成立 | 未找到UWB驱动 | 提示先启动它，不启动IMU |
| IMU的`-n`成立 | 已有IMU驱动 | 提示检查原进程，不再启动 |
| `fuser --silent`成功 | 串口有占用者 | 提示检查占用，不启动 |
| 前面都不成立 | 达到代码中的启动条件 | 提示确认RMC，然后launch |

`[`也是条件测试命令，`[ 条件 ]`内侧要留空格。`elif`是 **else if**（否则再判断），`fi`结束整个分支。这里只会执行第一个成立的分支，不是启动四次。

~~~text
[INFO] [navcore-1]: process started with pid [1052120]
[navcore-1] [INFO] [...] [navcore_node]: NavCore node initialized with frame_id: imu_link, uart_name: /dev/ttyS4, baud_rate: 921600
[navcore-1] [INFO] [...] [navcore_node]: Starting IMU data acquisition loop...
~~~

`frame_id`为坐标系名，`uart_name`为串口路径，`baud_rate`为波特率；UART为 **Universal Asynchronous Receiver/Transmitter**（通用异步收发器）。921600不是IMU采样频率。“开始采集循环”仍不证明已经出数。Ctrl+C后`process has finished cleanly`表示节点退出，不是留在后台继续采集。

### 🔷【三盒都执行】3.2 IMU观察终端：检查数据与时间戳

在同一辆车的新终端里依次看节点、Topic、到达频率和一帧完整消息。最后再抽查几次时间戳；这些操作只订阅ROS消息，不会另开串口或重启驱动。

~~~bash
source /opt/ros/humble/setup.bash
source /home/firefly/imu_ws/install/setup.bash
export ROS_DOMAIN_ID=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOCALHOST_ONLY=1

ros2 node list --no-daemon
ros2 topic list --no-daemon --show-types | grep --extended-regexp '^/imu/raw '
ros2 topic info --no-daemon --verbose /imu/raw
timeout --signal=INT 5s ros2 topic hz /imu/raw --window 200
timeout --signal=INT 3s ros2 topic echo --no-daemon --once --qos-profile sensor_data /imu/raw sensor_msgs/msg/Imu
for sample in 1 2 3 4 5; do
  timeout --signal=INT 2s ros2 topic echo --no-daemon --once --qos-profile sensor_data --field header.stamp /imu/raw sensor_msgs/msg/Imu
done
~~~

前面的查询选项与第2.3节相同。重点看`topic info`是否只有一个IMU发布者，再看`hz --window 200`给出的接收频率；它不是硬件采样频率证明。`echo --once`显示一帧原值，不转换单位或轴向。

最后的`for ...; do ...; done`把抽查命令执行五次，`--field header.stamp`只保留时间戳。每次都重新订阅，拿到的不是连续五帧，不能据此计算1ms采样间隔。此时看到`Subscription count: 0`也不奇怪：查询发生时可能还没启动后面的临时订阅。

`timeout` 结束 ROS 2 命令时，偶尔会出现 `coroutine ... was never awaited`、`failed to initialize wait set` 等退出清理警告。只要频率结果已经输出，且随后的命令仍能正常读取消息，这类提示不代表 IMU 节点或传感器数据失败。

通过条件：

1. 当前只有一个 `/navcore_node` 发布 `/imu/raw`；
2. 发布频率约为 1000 Hz；
3. `frame_id` 为 `imu_link`，角速度和加速度为有限值；
4. 5 个抽查时间戳非零且递增；这只是烟雾检查，不能证明连续性或 1 ms 采样间隔；
5. 上交已确认 IMU 原始轴系为 FRD（前/右/下）；单位和是否按比力解释仍需验收。

时间戳仍为0时，说明 `gnss_uwb` 虽运行，但UWB到IMU的授时链仍未打通。停止自己刚启动的 `navcore`，保持 `gnss_uwb` 运行，把UWB启动日志和IMU输出一起反馈给上交；不能用固定 `0.001s` 代替正式时间戳。

**频率和IMU字段逐项看**

~~~text
average rate: 999.8
        min: 0.001s max: 0.002s std dev: 0.00015s window: 200
~~~

`average rate`是平均到达频率，单位Hz（**hertz**）；`min/max`是相邻到达间隔最小/最大值，单位秒；`std dev`为 **standard deviation**（标准差），这里指间隔波动，不是陀螺噪声；`window`是统计窗口规模。`--window 200`不是“收200帧退出”，窗口尚未装满时显示值可能小于200。

关键消息字段示例（省略协方差）：

~~~yaml
header:
  stamp:
    sec: 1786400000
    nanosec: 123000000
  frame_id: imu_link
orientation:
  x: 0.0
  y: 0.0
  z: 0.0
  w: 1.0
angular_velocity:
  x: 0.0002
  y: -0.0001
  z: 0.0003
linear_acceleration:
  x: 0.02
  y: -0.03
  z: -9.80
~~~

IMU为 **Inertial Measurement Unit**（惯性测量单元）。`orientation`为姿态四元数，分量无量纲，单位四元数模应接近1；`angular_velocity`为角速度，ROS标准要求rad/s（弧度每秒）；`linear_acceleration`按标准为m/s²。这是接口要求，不保证驱动一定正确换算，本项目曾修正角速度单位。

完整消息时间是“sec秒＋nanosec纳秒”，1秒为十亿纳秒。`nanosec`应在0～999999999；它在秒进位时变小正常，要比较完整时间。`imu_link`只是名字，不自动说明轴向。FRD为 **Forward–Right–Down**（前右下），FLU为 **Forward–Left–Up**（前左上），需结合安装和接口确认。

协方差（**covariance**）数组全0表示未知，不是没有误差。静止时加速度通常仍含重力对应的比力响应，不能因z接近±9.8就判定上下运动。`nan`（**not a number**，非数）和`inf`（无穷）不是有效有限测量。低接收频率可能来自驱动、通信或观察端负载，不立即等同硬件低采样率。

### 🔷【三盒都执行】3.2.1 连续时间戳验收

需要新的 IMU 观察终端；2.2 的 `gnss_uwb` 和 3.1 的 `navcore` 都保持运行。本检查只订阅，不重启节点、不占用串口。

连续读取约 15 秒的 IMU 时间戳，检查是否非零、严格递增，并报告相邻间隔。`dt>10 ms` 记录为消息间隙；`dt>100 ms` 已超过当前 SDK 默认 `max_imu_dt_s=0.1 s`，直接判失败。若观察端资源不足导致大量间隙，再用3.4.5的2分钟压缩录包做最终确认。

~~~bash
source /opt/ros/humble/setup.bash
source /home/firefly/imu_ws/install/setup.bash
export ROS_DOMAIN_ID=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOCALHOST_ONLY=1

timeout --signal=INT --kill-after=5s 15s ros2 topic echo --no-daemon --qos-profile sensor_data --field header.stamp /imu/raw sensor_msgs/msg/Imu |
awk '
/^[[:space:]]*sec:/ { sec = $2 + 0 }
/^[[:space:]]*nanosec:/ {
  nsec = $2 + 0
  if (sec < 0 || nsec < 0 || nsec >= 1000000000) {
    invalid++
    next
  }
  samples++
  if (sec == 0 && nsec == 0) zero++
  if (have) {
    dt = (sec - previous_sec) * 1000000000 + nsec - previous_nsec
    if (dt <= 0) {
      bad++
      if (bad <= 10) printf "异常: %d.%09d -> %d.%09d, dt=%d ns\n", previous_sec, previous_nsec, sec, nsec, dt
    } else {
      positive++
      if (dt_min == 0 || dt < dt_min) dt_min = dt
      if (dt > dt_max) dt_max = dt
      if (dt >= 500000 && dt <= 2000000) near_1ms++
      if (dt > 10000000) gaps++
      if (dt > 100000000) long_gaps++
    }
  }
  previous_sec = sec
  previous_nsec = nsec
  have = 1
}
END {
  printf "samples=%d invalid=%d zero=%d rollback_or_duplicate=%d near_1ms=%d/%d gaps_gt_10ms=%d gaps_gt_100ms=%d dt_min_ns=%d dt_max_ns=%d\n", samples, invalid, zero, bad, near_1ms, positive, gaps, long_gaps, dt_min, dt_max
  if (samples >= 1000 && invalid == 0 && zero == 0 && bad == 0 && long_gaps == 0 && near_1ms * 2 >= positive) print "STAMP_CHECK=PASS"
  else print "STAMP_CHECK=FAIL"
}'
~~~

AWK按`sec:`和`nanosec:`两种行读取时间，分别是 **seconds**（秒）和 **nanoseconds**（纳秒）；后面的变量`dt`按 **delta time**（时间差）记忆。`[[:space:]]*`允许前面的缩进。`$2 + 0`把第二列按数值处理；`invalid++`等写法是计数加一，`next`跳过非法记录。

有上一帧后，先算秒差、再加纳秒差，得到整数纳秒量级的`dt`，避免直接相减很大的浮点绝对时间。`bad`计回退或重复，`near_1ms`计0.5～2ms间隔，`gaps/long_gaps`计超过10/100ms的间隔；更新`previous_*`供下一帧使用。

`END`在输入结束时汇总。`%d`中的`d`表示 **decimal**（十进制整数）；`%09d`的`9`指定最少九位、`0`表示不足时用零填充，把纳秒补足九位。这里的PASS/FAIL只是这条订阅流的检查结果，打印FAIL本身没有设置非零退出码，也不表示三盒同步已验证。

通过条件：至少观察到 1000 帧、`zero=0`、`rollback_or_duplicate=0`、`gaps_gt_100ms=0`，且至少一半已观察相邻间隔在 0.5–2 ms。`ros2 topic echo` 可能因终端负载丢掉部分观察帧，所以不要求一定得到 15000 帧；若因观察端性能导致失败，用3.4.5的2分钟压缩录包做最终统计。出现回退、重复或超过 100 ms 的间隔时，先让上交检查 RMC 秒进位、PPS 与 IMU 小数秒拼接；不放宽算法门限，也不固定写死 `dt=0.001 s`。

某次录包通过只代表那一段数据；换盒、重启或更新驱动后仍要复查。发现异常时保留原包，不通过修改时间戳把它变成“通过”。

**连续时间统计逐项读**

以下理想化示例有1200帧，正间隔均为1ms：

~~~text
samples=1200 invalid=0 zero=0 rollback_or_duplicate=0 near_1ms=1199/1199 gaps_gt_10ms=0 gaps_gt_100ms=0 dt_min_ns=1000000 dt_max_ns=1000000
STAMP_CHECK=PASS
~~~

| 字段 / 变量 | 含义 |
|---|---|
| `samples` | 进入统计的帧数，第一帧没有前驱，因此间隔数通常少1 |
| `invalid` | 秒或纳秒范围非法记录数，`next`会跳过该记录 |
| `zero` | 完整时间等于0的帧数 |
| `rollback_or_duplicate / bad` | 时间差≤0次数：负为回退，零为重复 |
| `near_1ms / positive` | 0.5～2ms间隔数 / 全部正间隔数，不含回退或重复 |
| `gaps_gt_10ms / gaps` | 大于10ms的间隔数，gt按 **greater than** 记忆 |
| `gaps_gt_100ms / long_gaps` | 大于100ms的间隔数，是上一类子集，不能相加 |
| `dt_min_ns / dt_max_ns` | 正间隔最小/最大值；无正间隔时默认0没有物理意义 |
| `previous_sec / previous_nsec` | 上一条参与统计的时间 |
| `have` | 已有上一帧的标志，防止把第一帧与默认0比较 |

计算式为：

$$
\Delta t_{\mathrm{ns}}=(s_k-s_{k-1})\,10^9+(n_k-n_{k-1}).
$$

`==/!=`是相等/不等；`<=/>=`是小于等于/大于等于；`&&/||`为逻辑且/或；`++`是加一。`near_1ms * 2 >= positive`即至少一半正间隔在目标范围。门限针对本流程约1000Hz的IMU，不是所有型号通用指标。

~~~text
异常: 1786400001.001000000 -> 1786400000.002000000, dt=-999000000 ns
~~~

这是后收到的消息时间变小999ms，即回退。相反，`dt=1001000000 ns`是向未来跳1001ms，相对预期1ms多跳约1秒，不叫倒退。脚本逐条打印前10个非正间隔；正向大跳通过gap计数和最大间隔体现。

PASS只证明该观察窗口满足所列门限，不证明零偏、姿态或三盒同步。FAIL要分原因，样本不足与时间回退不是同一个问题。

### 🔷【三盒都执行】3.2.2 IMU单位、轴向和符号验收

只有时间戳连续还不能直接积分。先用3.3实时显示或3.4录包，完成下列验收：

1. 消息必须符合 ROS `sensor_msgs/msg/Imu`：角速度单位为 `rad/s`，线加速度单位为 `m/s²`；
2. 算法输入契约是车体 FLU：`+x`向前、`+y`向左、`+z`向上；上交已确认当前消息为 FRD（前/右/下），三车参数使用 `imu_sensor_to_flu_xyzw: [1,0,0,0]` 绕 X 轴180°转为 FLU，不查 TF；
3. 车辆水平静止时，原始 `/imu/raw` 加速度模长应约为 `9.81 m/s²`，FRD 的 `z` 应约为 `-9.81 m/s²`；适配后 FLU 的 `z` 应约为 `+9.81 m/s²`；
4. 缓慢完成一次从车顶俯视的逆时针 `+90°` 偏航，原始 FRD `ωz` 积分应约为 `-1.57 rad`，适配后 FLU 应约为 `+1.57 rad`；用它确认单位、比例和正负号，不用单帧静止值判定比例；
5. 若上游不提供可信姿态，应按ROS约定使 `orientation_covariance[0] = -1`，不把占位四元数标成有效姿态。

历史静止样本的 `z≈-9.78 m/s²` 与上交确认的 FRD `+Z`向下相符；按当前 FRD→FLU 参数转换后为 `z≈+9.78 m/s²`，满足算法的静止符号契约。上交已修复角速度单位，最新静止包与四元数变化对比已排除旧的“度每秒冒充弧度每秒”比例错误，但仍必须用已知转角确认动态比例和正负号。最新包三组协方差仍全为0；按ROS语义这表示协方差未知，不代表零噪声，姿态是否可用仍需上交明确。验收未通过时不执行3.2.3。

### 🔷【三盒都启动】＋🟢【任选单盒观察】3.2.3 单车算法验证

只有 3.2.1 输出 `STAMP_CHECK=PASS` 且3.2.2通过，才进行本步骤。需要确认盒端已部署与 aarch64 匹配的 `zju_coop_ros2` 和 `libzju_coop.so`；本机 x86_64 编译产物不能直接复制到盒子上。下面的 `ZJU_WS` 必须改成实际部署目录；路径不存在时命令会停止，不会影响已有节点。

保持 UWB 启动终端和 `navcore` 启动终端运行，另开一个本机终端。先只启动本车 ZJU 惯导，不启动参考车融合、不启用点云、视觉、SLAM 或 GNSS 兜底。

验证 `on_imu()` 能从本机DDS消费 `/imu/raw`，并以20 Hz把有效本车NodeState选择性转到共享DDS。原始IMU仍只在本车可见。

~~~bash

if [ ! -f "$ZJU_WS/install/setup.bash" ]; then

fi
source /opt/ros/humble/setup.bash

export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOCALHOST_ONLY=0

case " $(hostname --all-ip-addresses) " in
  *" 192.168.1.201 "*) VEHICLE=vehicle_1 ;;
  *" 192.168.1.202 "*) VEHICLE=vehicle_2 ;;
  *" 192.168.1.203 "*) VEHICLE=vehicle_3 ;;
  *) printf '无法根据IP识别车辆，未启动浙大节点\n' >&2; exit 1 ;;
esac
printf '本盒配置：%s\n' "$VEHICLE"
ros2 launch zju_coop_bringup vehicle.launch.py namespace:="$VEHICLE" imu_topic:=/imu/raw use_localhost_imu_bridge:=true run_fusion:=false enable_point_cloud_input:=false enable_camera_input:=false enable_lidar_frontend:=false enable_lidar_slam:=false use_gnss_range_fallback:=false
~~~

`ZJU_WS=${ZJU_WS:-...}`优先使用你已设置的部署路径，否则用默认路径。`[ ! -f ... ]`表示找不到安装环境就退出；注意这里不在子Shell里，`exit 1`会退出当前SSH Shell，所以先确认路径。

`case`把本机IP映射为车辆配置。launch后面的`名称:=值`是ROS启动参数，不是Shell赋值：`namespace`选本车配置，`imu_topic`选输入，`use_localhost_imu_bridge:=true`打开本机到共享DDS的状态桥；其余`false`关闭融合和暂不使用的输入。

命令按本盒 `192.168.1.201/202/203` 自动选择 `vehicle_1/2/3`。无法识别IP时直接退出，不能手工把三盒都设成 `vehicle_1`；该值决定加载的 `node_id` 和惯导初值。

**launch参数逐个对应什么**

通用写法是`ros2 launch <package> <launch_file> name:=value`；尖括号只是位置说明，不要输入。`name:=value`是launch参数，和Shell的`NAME=value`赋值不同。

| 参数 | 英文含义 / 本次值 | 作用 |
|---|---|---|
| `namespace` | 命名空间，vehicle_1/2/3 | 选择本车配置 |
| `imu_topic` | IMU话题，/imu/raw | 指定输入 |
| `use_localhost_imu_bridge` | 使用本机IMU桥，true | 启用本机IMU与共享状态侧的桥接路径 |
| `run_fusion` | 运行融合，false | 不启动协同融合 |
| `enable_point_cloud_input` | 启用点云输入，false | 不接点云 |
| `enable_camera_input` | 启用相机输入，false | 不接相机 |
| `enable_lidar_frontend` | 启用激光雷达前端，false | 不启动该前端 |
| `enable_lidar_slam` | 启用激光SLAM，false | 不启动该建图定位模块 |
| `use_gnss_range_fallback` | 使用GNSS距离备用来源，false | 不以GNSS推算距离替代真实UWB |

SLAM为 **Simultaneous Localization and Mapping**（同时定位与建图）。`true/false`是真/假开关。这些参数由本工程launch定义，不是每个ROS包都支持。`ZJU_WS`是浙大工作空间路径，必须指向盒端实际部署的位置。

正常先看到如`本盒配置：vehicle_3`，随后是进程启动日志。`未找到浙大工作区`说明检查未通过，不再启动；有上交驱动不等于已部署浙大程序。`Package 'zju_coop_bringup' not found`先查安装路径与环境，不要反复重启传感器。

另开本机观察终端检查输出：

~~~bash
ZJU_WS=${ZJU_WS:-/home/firefly/zju_coop_ws}
if [ ! -f "$ZJU_WS/install/setup.bash" ]; then
  printf '未找到浙大工作区：%s\n' "$ZJU_WS" >&2
  exit 1
fi

~~~

先加载浙大工作空间，才能识别`NodeState`自定义类型。后面的`info/hz/echo`与检查IMU时相同，只是Topic换成状态输出；`--window 20`用于约20Hz的输出。`--field node_id`核对车辆号，最后五次抽查只看时间是否推进，不做连续采样间隔判断。

通过条件：共享侧约20 Hz、`header.stamp`非零且递增、`node_id`与本车一致、`valid=true`，位置/速度/四元数为有限值；另在其他车辆上确认看不到 `/imu/raw`。是否进入三车融合，以本轮三车身份、测距边和时间检查结果为准。

**NodeState是解算状态，不是新的原始测量**

~~~yaml
header:
  stamp:
    sec: 1786400000
    nanosec: 123000000
  frame_id: common_enu
node_id: 3
position_enu_m: [0.0, 0.0, 0.0]
velocity_enu_mps: [0.0, 0.0, 0.0]
orientation_flu_to_enu_xyzw: [0.0, 0.0, 0.0, 1.0]
valid: true
~~~

ENU为 **East–North–Up**（东北天），`m`为米，`mps`为 **meters per second**（米每秒）；`xyzw`为四元数分量顺序。`orientation_flu_to_enu`把FLU载体系向量转到ENU导航系。`valid: false`不能作为有效解算状态使用。

消息时间应承接最后接受的IMU测量时间，不是电脑显示时刻。零位置和单位四元数仅为字段示例，不要求三盒都取这个值。名字叫`common_enu`不会自动产生正东/正北，共同初始位置和航向仍需定义与来源。

单盒约20Hz不表示三盒共享Topic总共20Hz。多发布者混合后的时间戳也可能交错，须按`node_id`分开判断递增性；五次echo只能抽查。

### 🔷【三盒都执行】3.3 实时显示IMU

必须在IMU启动终端已经运行 `navcore` 的前提下，在另一个终端执行。若3.2已经结束，可直接复用其观察终端；不要把命令粘贴到UWB或IMU启动终端。

实时订阅全部 `/imu/raw` 数据，但每 100 帧只打印 1 帧；输入约为 1000 Hz 时，终端显示约为 10 Hz。输出包含时间戳、三轴角速度和三轴加速度，不录包、不生成文件，按 `Ctrl+C` 停止本显示命令。

~~~bash
source /opt/ros/humble/setup.bash
source /home/firefly/imu_ws/install/setup.bash
export ROS_DOMAIN_ID=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOCALHOST_ONLY=1

PYTHONUNBUFFERED=1 ros2 topic echo /imu/raw sensor_msgs/msg/Imu --no-daemon --qos-profile sensor_data --csv --no-arr | awk -F, 'NR % 100 == 0 {printf "t=%s.%09d gyro=[%s, %s, %s] accel=[%s, %s, %s]\n", $1, $2, $9, $10, $11, $13, $14, $15; fflush()}'
~~~

这里`--csv`中的CSV是 **Comma-Separated Values**（逗号分隔值），让echo输出逗号分隔数据；`--no-arr`中的`arr`是 **array**（数组），表示不展开数组。AWK的`-F`指定 **field separator**（字段分隔符），后面的`,`是分隔符的值。`NR`是 **Number of Records**（已读记录数，此处是一行一条记录），所以`NR % 100 == 0`每100行显示一次，不是求100帧平均值，更没有把ROS发布或录包降到10Hz。

当前输出布局中，第1/2列是秒和纳秒，第9～11列是角速度，第13～15列是加速度；`fflush()`中的 **flush** 是刷新，把缓冲输出及时送出。更换ROS版本或echo选项后，要对照一帧普通输出确认列号。

输出格式为 `t=秒.纳秒 gyro=[x, y, z] accel=[x, y, z]`。当前授时未通时 `t` 会一直是 `0.000000000`，但角速度和加速度仍会实时变化。该命令只负责显示，不换算单位、不补偿零偏，也不改变原始 Topic。

**显示10Hz不代表IMU变成10Hz**

~~~text
t=1786400000.100000000 gyro=[0.0002, -0.0001, 0.0003] accel=[0.02, -0.03, -9.80]
t=1786400000.200000000 gyro=[0.0003, -0.0001, 0.0002] accel=[0.01, -0.02, -9.81]
~~~

`t`来自消息，`gyro`是 **gyroscope**（陀螺仪）的角速度，`accel`是 **acceleration**（加速度）。示例两行相差0.1秒，因为每100帧挑1帧；输入若80Hz，显示约0.8Hz。

`NR % 100`的百分号是取余，`== 0`表示整除。`printf`格式串依次对应时间、三轴角速度、三轴加速度；`%s`原样打印字符串，`%09d`以至少九位整数打印纳秒。格式符中的百分号与取余不是同一用途。

停止这个显示管道不会停止另一个终端的驱动。若一直没输出，先用普通echo区分无消息、CSV列布局变化和输出缓冲。

### 🔷【三盒都执行】3.4 静止连续采集IMU

#### 🔷【三盒都执行】3.4.1 录制并显示保存位置

终端 1 的 `navcore` 必须保持运行；请在终端 2（实时显示已停止后）或另开终端 3 执行。不要在终端 1 中执行录包命令。

车辆静止且 IMU 完成预热后，连续录制10秒 `/imu/raw`。命令根据 `192.168.1.201/202/203` 自动把车辆号写入目录名，结束后打包并打印下载路径。

~~~bash
source /opt/ros/humble/setup.bash
source /home/firefly/imu_ws/install/setup.bash
export ROS_DOMAIN_ID=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOCALHOST_ONLY=1

mkdir --parents /home/firefly/imu_test
(
case " $(hostname --all-ip-addresses) " in
  *" 192.168.1.201 "*) VEHICLE_ID=1 ;;
  *" 192.168.1.202 "*) VEHICLE_ID=2 ;;
  *" 192.168.1.203 "*) VEHICLE_ID=3 ;;
  *) printf '无法根据IP识别车辆，未录包\n' >&2; exit 1 ;;
esac
IMU_BAG="/home/firefly/imu_test/imu_v${VEHICLE_ID}_static_$(date +%Y%m%d_%H%M%S)"
timeout --foreground --signal=INT --kill-after=5s 10s ros2 bag record --output "$IMU_BAG" /imu/raw
printf '本次录包目录：%s\n' "$IMU_BAG"
if [ ! -f "$IMU_BAG/metadata.yaml" ]; then
  printf '录包失败：未生成 metadata.yaml，请确认 /imu/raw 持续发布\n' >&2
  exit 1
fi
find "$IMU_BAG" -maxdepth 1 -type f -printf '%f  %k KB\n'
ros2 bag info "$IMU_BAG"
IMU_ARCHIVE="${IMU_BAG}.tar.gz"
tar --directory "$(dirname "$IMU_BAG")" --create --gzip --file "$IMU_ARCHIVE" "$(basename "$IMU_BAG")"
printf 'SFTP 下载文件：%s\n' "$IMU_ARCHIVE"
ls --format=long --human-readable "$IMU_ARCHIVE"
sha256sum "$IMU_ARCHIVE"
)
~~~

录包和压缩沿用第2.4.1节的写法：`case`识别本盒，`--output "$IMU_BAG"`指定新目录，只录`/imu/raw`。`find -maxdepth 1 -type f`中的 **max depth** 是最大遍历深度，**type** 是文件类型，`f`代表 **regular file**（普通文件）；整句只列包目录第一层的普通文件。`-printf`可按 **print formatted**（格式化打印）理解，里面的`%f`是文件名（**filename**）、`%k`是以1KB块计的占用空间。

这里的`timeout --foreground`中的 **foreground** 是“前台”，让录包进程仍可访问当前终端，避免因读取终端被作业控制暂停；到10秒时`--signal=INT`请求正常结束，再给`--kill-after=5s`（**kill after**，之后强制结束）的退出宽限。若最终被强制结束，可能来不及写完元数据，因此后面先检查文件再分析和压缩。录制跨度略短于10秒也可能是启动、发现耗时，不应只凭这一点判故障。

目录和压缩包格式分别为 `imu_v<车辆号>_static_<时间>/` 与 `imu_v<车辆号>_static_<时间>.tar.gz`。原目录保留供本机 `ros2 bag info/play` 使用。

`--foreground` 防止 `ros2 bag record` 读取终端时被暂停为 `T` 状态；`--kill-after=5s` 保证其收到 `SIGINT` 后仍不退出时不会永久卡住。未生成录包目录或 `metadata.yaml` 表示本次没有可用包，不要继续执行 `reindex`/`info`。

**录包日志和文件分别说明什么**

日志通常依次包含这些字样，前缀和PID会不同：

~~~text
Opened database '.../imu_v2_static_20260911_100000_0.db3' for READ_WRITE.
Listening for topics...
Subscribed to topic '/imu/raw'
Recording...
Writing remaining messages from cache to the bag. It may take a while
Recording stopped
~~~

`READ_WRITE`表示读写方式打开数据库；`Listening`表示在等Topic；`Subscribed`表示已建立订阅，仍应确认最终消息数；`Writing remaining messages`是在把缓存写入磁盘，此时不要断电或关终端。`Recording stopped`是录包结束，不是传感器驱动结束。

例如摘要节选为：

~~~text
Files:             imu_v2_static_20260911_100000_0.db3
Storage id:        sqlite3
Duration:          9.50s
Messages:          9500
Topic information: Topic: /imu/raw | Type: sensor_msgs/msg/Imu | Count: 9500 | Serialization Format: cdr
~~~

这里约9500条/9.5秒≈1000条每秒，只能粗看录入速率；严谨统计间隔还需区分首末帧、消息时间和接收时间。`Start/End`是包摘要时间范围，不是自动读取每条`header.stamp`后的质量结论。

目录内通常有：

| 文件 | 用途 |
|---|---|
| `metadata.yaml` | 包的元数据（**metadata**），记录Topic、类型、文件与计数等；不是测量正文 |
| `..._0.db3` | SQLite数据库，存序列化消息；可能有多个分片 |
| `...tar.gz` | 整个目录的归档压缩文件，下载它；原目录仍保留 |

YAML为 **YAML Ain't Markup Language**，是一种文本数据格式。`find -printf '%f  %k KB\n'`中`%f`打印文件末尾名称，`%k`为以KiB块计的占用量；这套格式符属于find，不能套用printf命令的`%f`浮点数含义。`-maxdepth 1`只查看第一层，`-type f`只选普通文件。

出现`录包失败：未生成 metadata.yaml`要查前面的第一条错误。目录根本不存在时，不能用reindex重建出不存在的数据；目录存在但无消息，也不能靠压缩变成有效包。仅有元数据仍不足以证明录到了数据，必须看Count和数据库。

**为什么超时结束不一定算失败**

`timeout --foreground --signal=INT --kill-after=5s 10s ...`中，10s是运行期限，5s是发出INT后的额外退出宽限。INT为 **interrupt**，SIG为 **signal**；最后必要时强制终止可能损失尚未落盘内容。

正常达到timeout期限，常见退出码为124，即使ROS已经响应INT并正常收尾；命令提前正常完成一般为0。137通常与KILL强制结束有关，不能当正常录包。这里用元数据和实际内容继续核对，没有简单把所有非零码都当“没录到”。

`--foreground`解决的是前台终端访问与作业控制问题，不是让消息更同步。历史中的进程状态`T`是停止/暂停（不是运行缓慢）；收到Ctrl+C仍不退出时先核对精确PID，不要批量杀掉所有ROS进程。

#### 🟢【录包所在单盒执行】3.4.2 重新找到最近一次录包

重新登录后定位新旧命名中最近一次IMU录包，列出文件并查看摘要。

~~~bash
source /opt/ros/humble/setup.bash
source /home/firefly/imu_ws/install/setup.bash

IMU_METADATA=$(ls --format=single-column --sort=time /home/firefly/imu_test/imu_v*_static_*/metadata.yaml /home/firefly/imu_test/imu_static_*/metadata.yaml 2>/dev/null | head --lines 1)
IMU_BAG=${IMU_METADATA%/metadata.yaml}
printf '最近录包目录：%s\n' "${IMU_BAG:-未找到}"
test -n "$IMU_BAG" && find "$IMU_BAG" -maxdepth 1 -type f -printf '%f  %k KB\n'
test -n "$IMU_BAG" && ros2 bag info "$IMU_BAG"
~~~

`ls --format=single-column --sort=time`每行一个文件，按修改时间从新到旧列出；`head --lines 1`取第一行。`${IMU_METADATA%/metadata.yaml}`去掉末尾文件名，得到包目录；这是字符串处理，不删除文件。`test -n ... &&`让后面的查询只在找到了目录时执行。这里选的是修改时间最新的文件，不保证盒子日期本身正确。

摘要中的时长应接近 10 秒、消息数应接近 10000；消息数明显偏少时先检查录制期间 `/imu/raw` 是否中断。

**“最新包”按什么选出来**

`ls --format=single-column --sort=time`列的是匹配的元数据文件，`head --lines 1`只取按修改时间排序后的第一行；`2>/dev/null`隐藏未匹配到某组路径的错误。两种目录模式用于兼容新旧命名，不会自动包含所有其他实验目录，例如`imu_v2_2min_...`不在这里的static模式内。

正常先打印最近包路径，后面是文件列表和bag摘要。没有匹配时会打印命令设置的“未找到”等默认提示，`test -n`使后续查询跳过。变量替换`${IMU_METADATA%/metadata.yaml}`中的`%`删除**匹配的字符串后缀**，不是百分比、取余或删除磁盘文件。

系统时间曾被调过时，修改时间最新不一定就是你心中的“最新实验”，先核对打印出的完整目录，再看数据。

#### 🟢【录包所在单盒执行】3.4.3 回放并查看具体IMU数据

需要两个终端。终端 1 执行回放命令，终端 2 执行查看命令；回放结束后回到终端 1 按 `Ctrl+C`。如果终端 1 仍在运行实时 `navcore`，请把回放放到另一个空闲终端，并将下面说明中的“终端 1”理解为“回放终端”。

回放最近一次录包，并把录制的 `/imu/raw` 重命名为 `/imu/replay`，避免与正在运行的实时 IMU Topic 混淆。

~~~bash
source /opt/ros/humble/setup.bash
source /home/firefly/imu_ws/install/setup.bash
export ROS_DOMAIN_ID=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOCALHOST_ONLY=1

IMU_BAG=$(ls --format=single-column --directory --sort=time /home/firefly/imu_test/imu_v*_static_*/ /home/firefly/imu_test/imu_static_*/ 2>/dev/null | head --lines 1)
test -n "$IMU_BAG" && ros2 bag play "$IMU_BAG" --loop --remap /imu/raw:=/imu/replay
~~~

`ls --format=single-column --directory --sort=time`比上一段多了`--directory`（列目录本身而不是目录内容）。`bag play --loop`中的 **loop** 是循环，`--remap`是 **remap**（重新映射）；`--remap /imu/raw:=/imu/replay`把回放输出改名，避免混进实时IMU Topic。

**回放会发生什么**

正常会看到播放器打开数据库、开始发布的日志，具体文案随版本变化。此时原包里的消息内容不变，但发布Topic由`/imu/raw`改为`/imu/replay`；因此现场驱动无需因为回放而停机。

`--loop`会在到达包尾后重新播放。再次回到包头时，消息头时间自然回到包的起始时刻，不能把这种回放循环当成传感器时钟故障。

该查找命令按目录修改时间选最新目录，没有先确认它包含有效元数据。如果恰好选中失败录包目录，可能报`No storage could be initialized`或路径/元数据错误；对照打印和实际文件，选正确的已有包。没有匹配时，`test -n`失败，播放器不会启动，也可能没有额外提示。

回放期间在终端 2 查看一帧完整数据，并抽查回放频率。该模块只订阅 `/imu/replay`，不会读到实时 `/imu/raw`。

~~~bash
source /opt/ros/humble/setup.bash
source /home/firefly/imu_ws/install/setup.bash
export ROS_DOMAIN_ID=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOCALHOST_ONLY=1

ros2 topic list --no-daemon --show-types | grep --extended-regexp '^/imu/replay '
timeout --signal=INT 5s ros2 topic hz /imu/replay --window 200
timeout --signal=INT 3s ros2 topic echo --no-daemon --once --qos-profile sensor_data /imu/replay sensor_msgs/msg/Imu
~~~

这里只查询`/imu/replay`，其余选项和实时观察相同。看到的数据来自已录包，不是对当前传感器的再次测量。

旧包若 `header.stamp` 为0，仍可用于分析数值、噪声和零偏是否稳定，但不能验证传感器采样时刻或进行正式惯导积分。验证角速度比例时，另录一段已知时长、已知转角的数据。

**如何确认读的是回放**

~~~text
/imu/replay [sensor_msgs/msg/Imu]
average rate: 999.5
~~~

普通echo仍会显示原消息的`frame_id`和原`header.stamp`，不会因为播放时间是今天就自动换成今天。Topic改名不改变消息内部坐标系和时间。

看不到`/imu/replay`先确认播放器还在运行、两个终端的ROS环境一致；能发现发布者但读不到消息，还需检查播放器是否暂停、QoS是否兼容。回放到达速率也受电脑负载影响，不是对硬件采样率的再次测量。

#### 🔷【三盒各自下载】3.4.4 下载录包

在 MobaXterm 左侧 SFTP 文件栏进入 `/home/firefly/imu_test/`，下载录制结束时打印的 `imu_v<车辆号>_static_<时间>.tar.gz`，不要只下载 `metadata.yaml`。旧包仍按原名称保留。

#### 🔷【三盒都执行】3.4.5 可选：录制2分钟压缩包

终端 1 的 `navcore` 保持运行；在终端 2（实时显示已停止后）或另开终端 3 执行。车辆静止并完成 IMU 预热后执行，录制期间不要启动第二个 IMU 驱动。

连续录制 120 秒 `/imu/raw`，用于统计噪声、零偏和消息到达情况。预计约 120000 帧；录制时由 rosbag 使用 zstd 压缩，结束后自动封装成一个 `.tar` 文件供 SSH/SFTP 下载。该操作不会修改节点或占用串口。

~~~bash
source /opt/ros/humble/setup.bash
source /home/firefly/imu_ws/install/setup.bash
export ROS_DOMAIN_ID=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOCALHOST_ONLY=1

mkdir --parents /home/firefly/imu_test
(
case " $(hostname --all-ip-addresses) " in
  *" 192.168.1.201 "*) VEHICLE_ID=1 ;;
  *" 192.168.1.202 "*) VEHICLE_ID=2 ;;
  *" 192.168.1.203 "*) VEHICLE_ID=3 ;;
  *) printf '无法根据IP识别车辆，未录包\n' >&2; exit 1 ;;
esac
IMU_BAG_2MIN="/home/firefly/imu_test/imu_v${VEHICLE_ID}_2min_$(date +%Y%m%d_%H%M%S)"
timeout --foreground --signal=INT --kill-after=30s 120s ros2 bag record --compression-mode file --compression-format zstd --compression-threads 1 --output "$IMU_BAG_2MIN" /imu/raw
printf '本次录包目录：%s\n' "$IMU_BAG_2MIN"
if [ ! -f "$IMU_BAG_2MIN/metadata.yaml" ]; then
  printf '录包失败：未生成 metadata.yaml，未执行封装\n' >&2
  exit 1
fi
ros2 bag info "$IMU_BAG_2MIN"
IMU_ARCHIVE="${IMU_BAG_2MIN}.tar"
tar --directory /home/firefly/imu_test --create --file "$IMU_ARCHIVE" "$(basename "$IMU_BAG_2MIN")"
printf 'SFTP 下载文件：%s\n' "$IMU_ARCHIVE"
ls --format=long --human-readable "$IMU_ARCHIVE"
sha256sum "$IMU_ARCHIVE"
)
~~~

与10秒录包相比，这里把时长换成120秒，并加上`--compression-mode file --compression-format zstd`：**compression**是压缩，**mode**是模式，**file**表示文件级，**format**是格式，`zstd`是 **Zstandard**。`--compression-threads 1`中的 **threads** 是线程，使用一个压缩线程，退出宽限也增加到30秒。

包内已压缩，最后用`tar --create --file`只封装成一个`.tar`，不再加`--gzip`做第二次gzip压缩。下载时注意它和前面的`.tar.gz`扩展名不同。

在 MobaXterm 左侧 SFTP 文件栏进入 `/home/firefly/imu_test/`，下载命令最后打印的 `imu_v<车辆号>_2min_<时间>.tar` 文件并整体发送。

收到新录包后，优先保留并使用消息中通过验收的真实 `header.stamp`。只有旧的零时间戳包在做非正式噪声试算时，才可临时按 1000 Hz 生成等间隔时间；这类包不能用于授时验收或正式轨迹结论。静止包用于统计噪声和零偏；确认角速度比例还需另录一段已知转角过程。

**压缩录包与普通10秒录包的区别**

| 选项 | 英文 / 值 | 实际影响 |
|---|---|---|
| `--compression-mode file` | 压缩模式＝文件级 | 对存储文件做压缩，不是降低采样率 |
| `--compression-format zstd` | 压缩格式＝Zstandard | 包内可能出现`.db3.zstd`文件 |
| `--compression-threads 1` | 压缩线程数＝1 | 限制压缩并行度，仍会占CPU和磁盘 |
| `--kill-after=30s` | 退出宽限30秒 | 给写盘与压缩留时间，超出仍可能强制终止 |
| `tar --create --file` | create＋file | 只归档，包内已有压缩，不再套gzip |

示例文件结构：

~~~text
imu_v2_2min_20260911_100000/
    metadata.yaml
    imu_v2_2min_20260911_100000_0.db3.zstd
imu_v2_2min_20260911_100000.tar
~~~

文件级压缩可能在文件关闭或分片后继续处理，所以停止采集后还要等压缩结束，不要把等待直接视为卡死。原始采样数据不因压缩而降采样；但资源不足仍可能影响录入完整性，要查最终Count和连续性。

若出现不支持压缩格式或找不到压缩插件的错误，先确认盒端rosbag安装能力，不要把生成的小文件当成已完成的2分钟数据。

### 🟢【仅故障单盒执行】3.5 看不到 `/imu/raw` 时检查

只读检查 `navcore` 是否存活、是否占用 `/dev/ttyS4`、实际继承了什么 DDS 环境，以及检查终端当前能发现哪些节点和 Topic。该模块不会停止或重启任何进程。

~~~bash
source /opt/ros/humble/setup.bash
source /home/firefly/imu_ws/install/setup.bash
export ROS_DOMAIN_ID=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOCALHOST_ONLY=1

~~~

按“进程—串口—DDS发现”这条线排查即可。最后两行是在当前观察终端查ROS，读取`/proc`则是在查驱动进程自己的环境；两个结果要对照，不能把刚执行的`export`当成驱动已经采用的设置。

按本文已验证的配置，`navcore` 和观察终端应使用相同的 `ROS_DOMAIN_ID`、`RMW_IMPLEMENTATION`、`ROS_LOCALHOST_ONLY`。进程环境中未出现 `ROS_DOMAIN_ID` 时，未另行覆盖的标准默认通常是域0，不能按域107判断；单靠环境缺项仍不足以排除程序内部设置。不同RMW并非理论上绝对不能互通，但本流程不混用未经验证的组合。

**把几项结果组合起来定位**

| 查询现象 | 优先检查 | 不要直接下的结论 |
|---|---|---|
| `NAV_PID`为空 | 驱动是否启动、是否已退出、执行路径是否与查询一致 | 不是“串口一定坏了” |
| PID存在，S4由别的PID占用 | 两个PID的来源和原启动终端 | 不直接停止别人的进程 |
| PID和串口对应，Topic列表为空 | 驱动与观察端的域、RMW、本机限制 | 不先改硬件配置 |
| Topic存在，echo一直无样本 | 发布循环、串口输入、QoS、订阅发现 | 发布端点存在不等于有数据 |
| 数值变化但消息时间为0或回退 | 授时与时间戳生成链 | 不是靠修改ROS域就能修好 |

`/proc/<PID>/environ`展示进程环境，而本终端`node/topic list`展示观察者能发现什么。两个层次都要查。若未显示某个环境变量，只能说未在这份环境里读到，不能把当前Shell刚export的值套给旧进程。

### 🟢【所需单盒执行】4.2 启动雷达

需要雷达时直接执行下面整块，自动判断启动链是否存在，不再人工决定是否启动；最小IMU+UWB流程不需要本模块。不要在多个终端同时执行。

~~~bash
if pgrep --full '[l]ivox_ros_driver2_node|[r]os2 launch livox_ros_driver2|[s]tart_livox[.]sh' >/dev/null; then
  printf 'Livox启动链已运行，跳过，不重复启动\n'
else
  ROS_DOMAIN_ID=0 /bin/bash /home/firefly/livox_ws/start_livox.sh
fi
~~~

`pgrep --full`检查实际驱动、ROS launch和启动脚本三种进程，避免驱动尚在初始化时又拉起一份。`[l]`、`[r]`、`[s]`分别匹配对应字母，但查询命令自身含方括号，不会因为自己的模式文字而匹配自己；`[.]`匹配文件名中的点。`>/dev/null`隐藏PID，只用退出码判断：匹配到为0，`if`执行跳过分支；未匹配到才执行`else`。这只检查启动链存在，不判断设备出数或服务健康。

`ROS_DOMAIN_ID=0 /bin/bash ...`只给新启动进程设置域0，避免启动脚本未指定域号时继承旧终端的107；它不会修改已有进程。`/bin/bash`用Bash执行盒端现有的启动脚本，启动后保持终端运行。这里不额外指定RMW，避免把浙大测试设置带入上交驱动。脚本是否由上交提供、何时提供，当前仓库没有记录，不能据此下结论。

**这条命令只负责执行已有脚本**

`/bin/bash`是解释器的绝对路径，后面的路径是脚本文件，都是位置参数，不带短选项。`bash`全称 **Bourne Again SHell**。它与`source`不同：通常在子进程执行脚本，不把脚本里的环境设置留给当前Shell。

正常可能显示launch与驱动初始化日志，具体取决于盒端现有脚本。若是`No such file or directory`先核对脚本路径；若出现连接雷达失败，启动脚本存在也不等于设备网络和供电正常。该脚本是否会后台化取决于脚本内容，不仅凭当前终端返回提示符判断。

**用雷达自己的环境查，别混成UWB环境**

本轮201实际发现的是：

~~~text

/livox/lidar [sensor_msgs/msg/PointCloud2]
/livox/imu [sensor_msgs/msg/Imu]
~~~

`node info /livox_lidar_publisher`会按`Subscribers/Publishers`等分类列出订阅/发布接口。以后如果上交改名，要以实际Publisher列表为准，相应替换下方命令，不凭名称猜类型。

本段不预设RMW实现；雷达与新的UWB测试命令是否使用相同RMW，要以实际进程环境为准。观察者用错RMW可能什么也查不到；加载失败、缺RMW实现或节点不存在，分别应先查安装路径、依赖、驱动与实际环境，而不是重复启动。

先各收一条消息，不先反复测频率。点云用`--no-arr`隐藏数组，保留消息头、点数维度等信息；雷达IMU只看消息头。

~~~bash
timeout --signal=INT 10s ros2 topic echo --no-daemon --once \
  --qos-profile sensor_data --no-arr \
  /livox/lidar sensor_msgs/msg/PointCloud2
timeout --signal=INT 5s ros2 topic echo --no-daemon --once \
  --qos-profile sensor_data --field header \
  /livox/imu sensor_msgs/msg/Imu
~~~

`timeout`限制等待时长，`--signal=INT`到期发送中断信号；`--once`收到一条就退出，所以没有消息时到期返回不代表测试成功。`--no-daemon`直接发现ROS图，避免依赖守护进程缓存；`--qos-profile sensor_data`选择传感器数据订阅策略。`--no-arr`中的arr是array（数组），这里不展开点云的`data`和`fields`数组；`--field header`中的field表示字段，只打印消息头。

雷达IMU的消息头可能如下（仅示例，不是本轮测到的数值）：

~~~yaml
stamp:
  sec: 1786400000
  nanosec: 200000000
frame_id: livox_frame
---
~~~

点云输出则保留`header`、`height`、`width`、`point_step`等字段。`width × height`是该帧点数，大于0才是非空消息，但不保证点坐标有效或时间同步正确。此前无样本时的历史结果见后文；当前已进入短包检查阶段。

**收不到消息时，只做一次发布端检查，不继续录空包：**

~~~bash
ros2 topic info --no-daemon --verbose /livox/lidar
ros2 topic info --no-daemon --verbose /livox/imu
~~~

| 看到什么 | 能得出的结论与下一步 |
|---|---|
| `Unknown topic`或节点列表为空 | 当前ROS图未发现目标；先核对本终端环境和驱动是否仍在运行 |
| `Publisher count: 1`，但单帧订阅超时 | 发布端点存在，观察端没收到样本；不能直接断定硬件没有输出 |
| `Subscription count: 0` | 查询时没有发现订阅端；之前的`echo/hz`已退出时可以正常出现，不是故障原因 |
| `lo ... disabling multicast` | 回环接口不支持组播的提示；本轮仍能发现节点，不能单凭这行认定故障，也不能据此保证数据传输正常 |
| 两路实际消息均能收到 | 再执行4.4节测频率、录短包；雷达IMU与外部IMU的同步仍需另验 |

本轮发布端为`RELIABLE`、`VOLATILE`，与`echo --qos-profile sensor_data`订阅在可靠性和持久性上兼容，不能再把无消息归因于“没给hz指定sensor_data”。当前Humble的`topic hz`本来就使用`sensor_data`订阅，且不提供`--qos-profile`参数；此前建议给`hz`加该参数是错误的。参数依据见ROS 2 Humble官方源码：[hz](https://github.com/ros2/ros2cli/blob/humble/ros2topic/ros2topic/verb/hz.py)、[echo](https://github.com/ros2/ros2cli/blob/humble/ros2topic/ros2topic/verb/echo.py)。

两路都收不到时，下一步是查看已有Livox启动日志，核对雷达供电、网线、设备IP和驱动配置中的主机接收IP，同时保留DDS数据传输问题这一可能性。不是继续重复执行相同的`hz/echo`，也不是再启动一份驱动。如果是自启动、没有原终端，可先只读查看现有进程的输出去向：

~~~bash
LIVOX_PID=$(pgrep --newest --full '/livox_ros_driver2_node( |$)')
if test -n "$LIVOX_PID"; then
  ps --format pid,ppid,lstart,args --pid "$LIVOX_PID"
  readlink "/proc/$LIVOX_PID/fd/1" "/proc/$LIVOX_PID/fd/2"
fi
~~~

`fd/1`和`fd/2`分别是标准输出、标准错误的去向。若指向日志文件，可`tail --lines 80 日志完整路径`；若是`pipe:[...]`或终端设备，不要直接读取抢走输出，向上交索取自启动服务日志。设备和主机IP应按实际Livox配置核对，不照抄猜测的地址；配置字段可参考[Livox驱动官方说明](https://github.com/Livox-SDK/livox_ros_driver2#readme)。尚未定位原因前不擅自修改IP、DDS配置或停止已有驱动。

#### 4.5 三盒雷达与多传感器时间验收

这项验收不是把所有时间戳硬对成同一个数，而是确认它们能否映射到同一测量时间轴。三个盒子都要各自完成雷达非空帧、频率、短包和时间检查；201通过不能代表202、203通过。

| 比较对象 | 什么时候必须做 | 采到数据后的用途 |
|---|---|---|
| `/livox/lidar` Header 与 `/livox/imu` Header | 用雷达内置 IMU 去畸变或做 Livox LIO | 配对点云帧内的内置 IMU |
| `/livox/lidar` Header 与车载 `/imu/raw` Header | 用车载 IMU 做 LIO/融合 | 按点云时间取 IMU 区间并传播 |
| `/livox/lidar` Header 与 `/uwb/range` 测量时间 | 雷达里程计进入协同定位 | 把雷达相对运动和 UWB 距离放入同一历元 |
| `/imu/raw` Header 与 `/uwb/range` 测量时间 | 启用当前 IMU/UWB 模式 | IMU 高频传播、UWB 量测更新 |

Header/测量时间用于配对和状态更新；录包接收时间只用于计算到达延迟、成批到达、丢包和超时。不能因为接收时间不同就直接判定不同步，也不能用接收时间替换错误的测量时间。GNSS若只作真值仍要记录其时间并验证可对齐，但不进入相对定位状态。

静止包只能验连续性，不能识别一个恒定的时间偏移。要估计偏移，三盒同时录制15～30秒，保持两盒静止，只移动或转动一盒一次；用 IMU 角速度/加速度突变、点云里程计变化和 UWB 距离变化的事件起点，在各自测量时间轴上做对比。若偏移随时间变化，优先让上交修正时钟/授时；不要只在软件里写死一个常数。

数据采到后按以下顺序处理：

1. `analyze_lidar_bag.py`检查点云字段、点数、逐点时间、Header单调性、接收间隔及 `/livox/imu` 的频率；
2. 联合包分析工具检查该盒 `/imu/raw`、`/uwb/range`，比较 Header 时间和跨传感器共同事件；
3. 三盒结果合并后再决定是否允许雷达进入融合，不在单盒短包上直接改时间戳或补点。

当前工程的初始化分两层：

- **雷达前端**：第一帧有效、非退化点云保存为参考帧，局部位置 `(0,0)`、yaw `0`；随后用平面 ICP 更新局部里程计。它只建立雷达局部坐标，不能给公共 ENU、绝对位置或车体航向。
- **协同定位**：车辆静止采集 IMU（当前配置10秒）估计重力方向和启动陀螺零偏；用同一测量历元的三条 UWB 距离恢复三车初始三角形；再用人工摆放或外部方向源确定公共水平航向。点云/视觉只有在时间、外参和质量通过后才加入。

当前点云回调会把原始 `PointCloud2` 连同测量时间、接收时间、字段和 `frame_id` 送入 C ABI 做格式检查；主 `poses_2d` 仍由 UWB-only 或 IMU/UWB 分支发布，雷达尚未改变主输出。要做真正的雷达惯导融合，还需确认 Livox 时间类型（无同步、PTP/gPTP、GPS/UWB转换）、逐点时间单位、车体外参，并完成三盒复测。Livox/FAST-LIO类系统也要求点云与IMU同步、逐点时间和外参有效，不能只看到两个Topic就开始融合。

**SSH密钥这一段会改什么**

SSH为 **Secure Shell**（安全远程登录）；`ssh-keygen`生成密钥，`ssh-copy-id`把本机公钥追加到远端用户授权中。三种东西不要混：

| 文件或内容 | 在哪里 | 用途 |
|---|---|---|
| `id_ed25519`私钥 | 电脑上 | 证明客户端身份，不能发给别人 |
| `id_ed25519.pub`公钥 | 电脑上，公钥副本加入盒子 | 允许相应私钥持有者登录 |
| `known_hosts`里的主机公钥记录 | 电脑上 | 核验连接到的服务器是不是预期盒子 |

`$HOME`是当前Linux用户主目录；`.ssh`是隐藏目录，前面的点是目录名的一部分；`.pub`表示 **public**（公钥）。这些Linux命令不直接适用于Windows PowerShell，Windows步骤见脚本使用说明。

可能出现保存位置、密钥口令、服务器密码、主机指纹确认等提示。密钥口令与盒子登录密码不是同一个东西；带口令的密钥用于无人值守时需要合适的agent配置。遇到覆盖已有密钥询问应停止核对，不能为了“重新配置”覆盖他人的密钥。

`Number of key(s) added: 1`表示公钥已加入，不代表传感器启动。脚本使用`BatchMode=yes`（批处理模式），不弹出密码交互；`Permission denied (publickey,password)`说明无人值守认证未通过。主机指纹变化先通过可信渠道核对，不关闭SSH校验来绕过。

`--boxes`中的 **boxes** 是盒子列表，列出逻辑盒号与IP的对应关系；`--uwb-recorder 2`中的 **recorder** 是录制端，把共享UWB录包位置换成盒2；`--duration 180`中的 **duration** 是持续时间，设置每路录制时长。录包位置改变，不会把测距来源限制为盒2。

**脚本参数与位置参数怎么区分**

`--boxes`后允许多个`盒号=IP`，直到遇到下一个选项；例如`2=192.168.1.202`是脚本解析的字符串，不是Shell变量赋值。`--uwb-recorder 2`必须指向列表中已有的盒号；`--duration 180`单位秒，必须是整数。

当前脚本默认三盒、201录UWB、每路180秒。201是相对定位解算参考车；三盒IMU仍分别在本机录制。代码仍保留最低时长限制：至少150秒，且不小于`90 + 20 × 盒子数`秒；这是当前参数校验规则，不表示仍有固定90秒动作计划。三盒使用180秒或900秒均符合要求，10秒不符合。

本例结果为三路各盒IMU包和一路`uwb_rec_v2`包。UWB包的rec_v2只说明录制位置，不限制数据必须以车2为测距端点。参数不合法时可能由解析器给出`error:`，或者脚本报告配置问题；此时先改本地参数，不去改盒端驱动。

电脑加载现有ROS消息环境，生成时间初查报告（将目录名换成本次实际目录）：

```bash
source /opt/ros/humble/setup.bash
source install/ros2-sjtu-adapter-current/setup.bash
python3 tools/record_joint_time.py --analyze data/joint_time_实际编号
```

两个`source`为离线解码加载ROS和上交消息类型。`--analyze`就是 **analyze**（分析），表示读取已回收的目录并分析，不是重新SSH录包；后面的`实际编号`要替换成真实目录名。

结果为 `联合时间初查.md` 与 `时间戳统计.json`：按每盒IMU、每条有向UWB列出消息时间范围、零值、重复、回退及共同区间。分析环境需有 `cooperative_interfaces`；缺包不会影响已完成的采集，可加载正确工作空间后重跑分析。

**共同区间存在不代表时钟已同步。** 本轮报告用于识别明显时间域问题；动作对应及同步误差需进一步离线检查或上交PPS诊断。自动启动录包不会校准盒子时钟。


**离线分析的输出与限制**

运行后会显示类似：

~~~text
时间报告：.../data/joint_time_20260911_100000/联合时间初查.md
~~~

其中：

| 产物 | 内容与用途 |
|---|---|
| `联合时间初查.md` | 给人阅读的各流时间范围、计数与初查结果 |
| `时间戳统计.json` | 结构化统计，便于程序继续读取；JSON为 **JavaScript Object Notation** |

`--analyze 目录`选择离线分支，不再启动SSH录制。输入应是整轮回收目录，不是某个CSV文件；`source install/.../setup.bash`是相对工程根目录的路径，离开工程目录执行会找不到。

`No module named 'rosbag2_py'`表示当前Python缺少对应ROS读取环境；缺`cooperative_interfaces`则是自定义消息解码环境未加载。采集在Windows成功不代表Windows当前Python也具备离线ROS环境，可以把整轮数据复制到已有ROS环境的分析电脑。

时间范围有交集，只说明首末范围重叠，不证明中间连续、没有漂移或所有必需流都齐全。报告未出现某路时，应先查缺数据，不把“已有几路重叠”写成“三盒同步”。

### 🔷【三盒各执行】A. 启动本机IMU录包

四个录包终端的 `RUN_ID` 必须填写同一个实验编号；每轮换新编号，例如 `joint_time_01`。复制整块，录制会持续运行；完成下面C的动作后，在此终端按一次 `Ctrl+C`，随后自动显示包信息并压缩。若命令块被中断、未执行压缩，可按D处理。

```bash
source /opt/ros/humble/setup.bash
source /home/firefly/imu_ws/install/setup.bash
export ROS_DOMAIN_ID=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOCALHOST_ONLY=1

(
RUN_ID=joint_time_01
case " $(hostname --all-ip-addresses) " in
  *" 192.168.1.201 "*) RECORDER_ID=1 ;;
  *" 192.168.1.202 "*) RECORDER_ID=2 ;;
  *" 192.168.1.203 "*) RECORDER_ID=3 ;;
  *) echo '无法识别盒号'; exit 1 ;;
esac
mkdir --parents /home/firefly/time_test
BAG="/home/firefly/time_test/${RUN_ID}_imu_rec_v${RECORDER_ID}"
printf '本次目录：%s\n' "$BAG"
ros2 bag record --output "$BAG" /imu/raw
test -f "$BAG/metadata.yaml" || { echo '未正常落盘，请检查录包输出'; exit 1; }
ros2 bag info "$BAG"
tar --directory "$(dirname "$BAG")" --create --gzip --file "${BAG}.tar.gz" "$(basename "$BAG")" &&
printf '下载：%s.tar.gz\n' "$BAG"
)
```

这是手动版本，不设自动结束时间。`RUN_ID`由你填写，`case`自动补上录包盒号。`ros2 bag record`在前台持续录IMU，正常结束后才检查元数据、显示摘要和压缩；最后的`&&`使下载提示只在压缩成功后打印。

**手动IMU录包的提示与结束方式**

~~~text
本次目录：/home/firefly/time_test/joint_time_01_imu_rec_v1
...
Subscribed to topic '/imu/raw'
Recording...
~~~

这一步没有timeout，采集会持续，后面的bag info与tar要等录包退出才执行。Ctrl+C应按在录包终端，不是驱动终端。若整块命令被中断导致没有继续压缩，保留原目录，用D的补打包操作。

`RUN_ID`中的run表示一次实验；rec为 **recorder/recording**（录制端/录制），v为本工程文件名中的vehicle（车辆）标签，不是ROS协议字段。同一次四路共用RUN_ID，下次要换新编号；已有同名目录时rosbag通常拒绝覆盖，不要删除旧实验来凑名字。

### 🟢【任选一盒执行一次】B. 启动共享UWB录包

```bash
source /opt/ros/humble/setup.bash
source /home/firefly/imu_ws/install/setup.bash
export ROS_DOMAIN_ID=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOCALHOST_ONLY=0

(
RUN_ID=joint_time_01
case " $(hostname --all-ip-addresses) " in
  *" 192.168.1.201 "*) RECORDER_ID=1 ;;
  *" 192.168.1.202 "*) RECORDER_ID=2 ;;
  *" 192.168.1.203 "*) RECORDER_ID=3 ;;

printf '本次目录：%s\n' "$BAG"
ros2 bag record --output "$BAG" /uwb/range /node/id

```

结构与A相同，只是通信范围改为共享DDS，录制Topic换成`/uwb/range /node/id`，文件名标明这是UWB包。四个终端的`RUN_ID`必须相同，才能把本轮数据对应起来。

`expected_v1-2-3` 只表示计划三盒参与，实际测距边仍以包里的 `src_id/target_id` 为准。`rec_vN` 表示录包所在盒子，不是测距来源限制。

**共享UWB包与本机IMU包的差别**

~~~text
本次目录：/home/firefly/time_test/joint_time_01_uwb_expected_v1-2-3_rec_v3
...
Subscribed to topic '/uwb/range'
Subscribed to topic '/node/id'
~~~

两个Topic是`bag record`后面的两个位置参数，表示一起录制；不是设置它们之间的时间同步。`expected`为预期参与车辆，`rec`为录制盒。UWB为 **Ultra-Wideband**（超宽带）。

这条手动命令不像2.4.1那样先检验每条目标边。即使只有身份、没有测距，也可能创建目录和元数据，所以结束后必须看`/uwb/range`的Count并逐边核查，不能只看文件名包含1-2-3。

### 🔷【三盒联合操作】C. 全部录包后按一个秒表做动作

把盒子摆成非退化三角形，动作时保持高度和姿态基本不变。由一人用手机秒表统一口令，时间从四路录制就绪后开始计，不是从任何包的首帧开始计。

| 秒表时间 | 动作 |
|---|---|
| 0～15秒 | 三盒静止 |
| 15～25秒 | 只平移盒1约0.5～1米，再停住 |
| 25～35秒 | 三盒静止 |
| 35～45秒 | 只平移盒2约0.5～1米，再停住 |
| 45～55秒 | 三盒静止 |
| 55～65秒 | 只平移盒3约0.5～1米，再停住 |
| 65～90秒 | 三盒静止 |

平移方向应让涉及该盒的距离有明显变化，避免只绕另一盒做等距离运动。**平移主要看加速度，不能期待陀螺一定有明显变化。**

90秒后，依次在四个**录包终端**按 `Ctrl+C`，等待落盘和压缩完成。把实际动作、秒表大致时刻、三盒是否重启及异常情况写成随包备注；本轮不要求启动浙大NodeState或融合程序。

### 🟢【各包所在盒执行】D. 下载和判定

从各盒 `/home/firefly/time_test/` 下载同一 `RUN_ID` 的4个压缩包及实验备注。检查三个IMU包消息数均非零、UWB包含三条测距边，并且四包都覆盖完整动作过程。若未自动压缩，在对应盒上设置实际目录后执行：

```bash
BAG=/home/firefly/time_test/填实际包目录名
ros2 bag info "$BAG"
test -f "$BAG/metadata.yaml" &&
tar --directory "$(dirname "$BAG")" --create --gzip --file "${BAG}.tar.gz" "$(basename "$BAG")"
```

将`BAG`改成已经存在的实际目录。`bag info`先查看是否可读，`test -f`确认有元数据，最后把整个目录压缩。这里不能从不存在的目录“补出”一次录包；同名压缩文件已存在时会被覆盖。

离线检查先比较**原始消息时间戳**的范围和重叠区间，再检查回退、重复、时间尺度及各盒运动与相应UWB变化的对应关系。不能把四个包各自首帧都减到零后，便认为实现了同步。

本实验用于发现时间域不同、秒级错位及明显漂移。IMU加速度和UWB距离是不同物理量，运动起点也会受测距频率、阈值和传输延迟影响，不能直接把两条曲线的峰值差当成时钟误差。**约10Hz的UWB也不意味着本实验能保证100ms或更高的同步精度。** 毫秒级同步需上交提供共同事件时间标记或PPS捕获与消息时间映射的诊断证据；接收时间差均值接近也不能单独证明同步。


**补打包的成功与失败各是什么样**

正常先显示bag摘要，tar成功时一般没有额外输出，文件在原目录旁生成`.tar.gz`。若出现：

~~~text
Bag path '...' does not exist!
~~~

说明`BAG`路径不对或那轮根本没形成包，不是“缺少一次压缩”。如果元数据存在但数据库损坏，`bag info`失败也不能继续把归档当成有效数据。

本段各行默认独立执行：`bag info`失败不会自动阻止下一行，后面的`test -f`也只检查元数据存在。所以应先读懂info结果再取走压缩包。已有同名压缩文件会被tar覆盖，原包目录不会因此被删除；不要把`BAG`填成上级目录或占位文字。

## 🔷【三盒联合执行】7. 三车最小联调顺序

三盒均可执行本节；仍应按顺序逐项验收，不要一次启动所有可选传感器后再排查。

1. 🔷 **【三盒都执行】** 核对IP、`node_id`、`uwb_id`、完整硬件ID映射、串口、DDS环境和已有进程；同时只读查询雷达、相机进程，不把“进程存在”等同于“已有数据”；
2. 🔷 **【三盒都执行】** 分别通过UWB RMC并确认正式`UwbRange`结构；按2.4先验证双盒已知距离边，再验证三盒已知三角形；三条无向边均出数且同Header完整历元数大于0；
3. 🟢 **【开发电脑执行】** 回放真实UWB包进入`input_mode=uwb_only`节点，检查`poses_2d`三车位置有效、航向无效；随后再与上交GCS做消息联调。此最小路径不要求先启动IMU；
4. 🔷 **【需要惯性融合时才执行】** 分别通过IMU连续时间戳、单位、轴向和静止初始化，再按第6节核对三车IMU/UWB时间域；具备统一水平航向初值前，不把三套IMU水平坐标直接拼成公共导航系；
5. 🔷 **【需要IMU/UWB融合时才执行】** 设置本机IMU桥接，验收三车NodeState与共享测距，再启动`input_mode=imu_uwb`融合；当前实测时间/航向条件未满足前，只保留为实验路径；
6. 🟠 **【参与测距盒操作】** 断开/恢复一条UWB边，观察位置有效标志是否按缺边失效并恢复；
7. 🔷 **【可选传感器分别执行】** MID360必须先收到非空点云消息，相机必须先收到真实图像消息，再分别录包和接入；201已完成一包非空点云和内置IMU短包，但点云接收连续性、时间源和零点语义仍待确认；202、203雷达尚未验收。201相机已报告安装三目，实际图像数据尚未验收。

停止前台进程时回到对应终端按 `Ctrl+C`，确认出现 `process has finished cleanly`。不要使用 `pkill`、`killall`，不要停止用途不明的已有服务，也不要启动占用同一串口的第二份驱动。

## 想记住这些命令，可以这样查和联想

参数字母不是跨程序统一的缩写。同一个字母在不同命令中可以完全不同；有正式长选项时优先记长选项，没有时只给助记，不硬编“全称”。

| 常见名称 | 英文来源或助记 | 在本文做什么 |
|---|---|---|
| Shell / Bash | Shell为命令解释器；Bash为Bourne Again SHell | 解释变量、管道、判断与循环 |
| grep | 名称源于编辑器命令“global regular expression print” | 按模式筛选文本 |
| pgrep | 可按process＋grep理解 | 查进程，不是查Topic |
| sed | stream editor，流编辑器 | 从摘要行中抽出计数 |
| AWK | Aho、Weinberger、Kernighan三位作者姓氏首字母 | 逐行读字段、计算、汇总，不是三个功能词的缩写 |
| ls / pwd / cd | list / print working directory / change directory | 列目录、显示当前位置、切换目录 |
| mkdir | make directory | 建目录 |
| printf | print formatted | 按格式打印 |
| tar | tape archive，历史名称“磁带归档” | 今天也用于把目录封装为单文件 |
| gzip / zstd | GNU zip / Zstandard | 两种压缩工具或格式 |
| SSH / SFTP | Secure Shell / SSH File Transfer Protocol | 远程登录 / 基于SSH传文件 |
| PID / IP | Process ID / Internet Protocol | 进程号 / 网络协议；IP地址不是传感器ID |

几个最容易记混的例子：

| 写法 | 本命令中的意思 |
|---|---|
| `pgrep --full` | full，匹配完整命令行 |
| `test -f 文件` | 检查普通文件（regular file）是否存在 |
| `tar --file 文件` | 指定归档文件，不是检查存在 |
| `pgrep --newest` | newest，选最新进程 |
| `test -n 字符串` | 检查非空字符串 |
| `sort --numeric-sort` | numeric sort，按数值排序 |
| `head --lines 1` | 取1行 |
| `sed --quiet` | 关闭自动打印 |
| `grep --invert-match` | invert match，反选 |
| `fuser --verbose` | verbose，详细 |
| `ps --format 字段列表` | 指定输出列 |
| `ros2 bag record --output 目录` | 指定录包输出目录 |

没有长选项的写法仍保留，如`awk -F,`、`test -f`、SSH的`-o`。`paste --serial --delimiters=-`末尾的`-`是分隔符的值，不是新选项。

长选项通常直接写出了含义。例如`--once`一次、`--field`字段、`--window`窗口、`--verbose`详细；是否允许`--选项=值`或`--选项 值`以该工具帮助为准。

**看到命令失败，先分清在哪一层**

- Shell报`command not found`：没找到命令，也可能把提示符或粘贴控制字符一起贴进来了。
- ROS报`Package ... not found`：命令存在，但没有找到对应包，先查安装和source。
- 类型报`invalid`或Python模块找不到：先查消息定义与当前环境。
- SSH报`Host key verification failed`：主机身份校验问题；`Permission denied`可能是登录认证问题，不能按串口权限处理。
- 驱动报串口`Permission denied`：这是盒端设备访问问题，与电脑SSH密钥是两回事。
- 没有消息但程序还在等：可能只是等待发布或发现，不是所有“无输出”都叫卡死。
- 已收到数据、timeout发INT后才有清理警告：先区分观察命令退出与驱动本身崩溃，不要把两者混为一谈。

想查看某个参数的本机定义，可在空闲终端输入`pgrep --help`、`tar --help`、`ros2 topic echo --help`或`ros2 bag record --help`。这些帮助命令只显示说明，不启动采集；本机安装版本的帮助比跨版本照搬选项更可靠。
