# 17 分布式本地惯导与参考车协同融合设计

## 1. 文档状态与结论

本文按 2026-08-17 已落盘源码、C ABI、ROS 2 消息、节点、配置和测试定稿，取代早期的大型候选方案。`NodeState v1` 已冻结为无 `sequence`、无初始化代次、无零偏、无协方差的紧凑接口。当前实现的最小闭环是：

```text
每辆车本机 sensor_msgs/msg/Imu
  -> 单节点 15 维惯导（名义 p/v/q/bg/ba + 本机 P15）
  -> 紧凑 NodeState（p/v/q，不传原始 IMU、零偏和 P15）
  -> ROS 2 publish/subscribe
  -> DDS
  -> 5G Mesh 提供的 IP 链路
  -> 参考车 DistributedFusion2D（二维位置修正）
  +  /uwb/range
  -> /cooperative_localization/poses_2d
  -> 上交 GCS
```

这里的“分布式”指三车高频 IMU 分别在本机解算，跨车只传低频紧凑状态和 UWB。第一版二维协同修正仍在参考车一处运行，它不是无中心、对等共识或联邦滤波。

当前已实现 Ubuntu 22.04 x86-64 纯 C++ 和单机 ROS 2 Humble/Fast DDS 闭环验证。跨盒 DDS、RK3588/AArch64、5G Mesh 现场和实车都尚未验收，不得把本文当成这些门禁已通过的证明。

## 2. 各方职责与第一版前提

### 2.1 上海交通大学侧

上交多传感器盒子侧负责：

- IMU、GNSS、激光雷达和 UWB 原始数据采集；
- 利用 UWB 完成三盒时间同步，并为 ROS 2 `header.stamp` 提供明确时间语义；
- 发布本车标准 `sensor_msgs/msg/Imu`；
- 发布正式 UWB 消息，已知业务字段为 `std_msgs/Header header`/`uint32 src_id`/`uint32 target_id`/`float32 distance`；
- 提供 5G Mesh 网卡、IP 可达性和现场网络条件；
- GCS 订阅浙大发布的二维位姿数组。

### 2.2 浙江大学侧

浙大侧负责：

- 普通 C/C++ 算法核心、`libzju_coop.so` 和稳定 C ABI；
- 每车本地 15 维惯导、参考车二维 UWB 修正及 GCS 输出；
- ROS 2 适配节点，订阅上交 publisher 发出的标准 IMU 和正式 UWB，逐字段映射到 C ABI；
- 缓存、对齐、时间门限、数值校验、单元测试和集成测试；
- 从本机原生构建的 SDK 连接 ROS 2 节点，RK3588 上必须使用 AArch64 产物。

### 2.3 第一版固定假设

- 节点 ID 固定为 1、2、3，1 号车是参考车。
- GNSS 失锁前三车获得同一公共 ENU 下的初始 `p/v/q/bg/ba`；当前通过 YAML 提供。正常模式下 GNSS 不进入协同更新；只有显式开启应急开关时，参考车才把同步 `NavSatFix` 转成低置信度距离临时替代 UWB。
- 车体系为 FLU：`+x` 向前、`+y` 向左、`+z` 向上。
- 惯导四元数表示 FLU 到 ENU 的旋转，对外排列是 `[x,y,z,w]`。
- 第一版是短时理想三车演示，UWB 修正不反馈到从车本地惯导。

## 3. 现有源码结构审查证据

### 3.1 `InertialEskf15` 不持有 15×15 协方差

`src/core/inertial_eskf15.hpp` 中 `InertialEskf15` 的持久成员只有：

- `initialization_`；
- `config_`；
- 名义惯性状态 `state_`；
- 上一帧 IMU `previous_`；
- 时间基准标志 `has_previous_`。

类中没有 `DenseMatrix`、`15×15` 数组或其他持久协方差成员。`push_imu()` 通过 `ImuProcessingResult` 返回当次的 `phi` 和 `qd`，因此它是“名义状态传播器＋误差线性化结果生成器”，不是自持协方差的完整滤波会话。

### 3.2 `Phi`、`Qd` 和联合协方差由谁维护

`InertialEskf15::push_imu()` 在每个合法 IMU 间隔内计算：

\[
\delta x_{k+1}=\Phi_k\delta x_k+w_k,
\qquad \operatorname{Cov}(w_k)=Q_{d,k}.
\]

`src/core/cooperative_inertial_ekf.hpp/.cpp` 中 `CooperativeInertialEkf` 持有 `DenseMatrix covariance_`，维度为 `15N×15N`。它负责：

\[
P_{ii,k+1}=\Phi_{i,k}P_{ii,k}\Phi_{i,k}^{T}+Q_{d,i,k},
\]

\[
P_{ij,k+1}=\Phi_{i,k}P_{ij,k},
\qquad
P_{ji,k+1}=P_{ji,k}\Phi_{i,k}^{T}.
\]

误差状态顺序固定为：

```text
δp_ENU, δv_ENU, δtheta_FLU, δbg_FLU, δba_FLU
```

当 `N=1` 时，`covariance_` 恰好是本车 `15×15` 的 `P15`；当 `N=3` 时，现有集中式回归基线仍持有 `45×45` 联合协方差。`RangeEkf` 另外维护仅测距回退模式的 `4(N-1)` 状态和协方差，不是惯导 `P15`。

### 3.3 旧 C ABI 为什么原先不足

改造前的公开路径只能：

1. `zju_coop_create()` 创建一个拥有全部节点的 `Engine`；
2. `zju_coop_configure_inertial()` 一次配置所有车的惯导初值；
3. `zju_coop_push_imu()` 把带 `node_id` 的三车原始 IMU 送入同一 `15N` 滤波器；
4. `zju_coop_push_range()` 直接更新该联合状态；
5. `zju_coop_get_pose2d_v2()` 从同一联合状态取结果。

旧接口没有对外导出单车绝对 ENU `p/v/q` 的 `NodeState`，没有接收其他车 `NodeState` 的入口，也没有与集中式 `Engine` 隔离的二维修正句柄。因此它无法表达“每车一个本地惯导，参考车只收紧凑状态”。

当前最小实现没有再新增一套 `LocalInertialEkf15` 类和专用 local handle，而是复用既有 `zju_coop_handle_t + Engine + CooperativeInertialEkf`，每辆车用 `N=1` 配置。新增的只是紧凑状态导出和独立二维融合会话。

### 3.4 姿态误差注入后仍缺少 ESKF reset Jacobian

`InertialEskf15::inject_error()` 当前执行：

\[
q_{b}^{n}\leftarrow q_{b}^{n}\operatorname{Exp}(\delta\theta),
\]

并把 `δp/δv/δbg/δba` 直接加到名义状态。`CooperativeInertialEkf::update_range()` 先用 Joseph 形式计算后验协方差，再调用 `inject_error()`，但代码没有使用与右乘误差定义一致的 `G_reset`对注入后协方差执行坐标重置：

\[
P^{++}=G_{reset}P^{+}G_{reset}^{T}.
\]

结论是“缺失仍存在”，本轮没有修改它。第一版本地 `N=1` 节点不接收 UWB，参考车二维修正也不注入本地姿态，所以新闭环不触发这条姿态重置路径；保留的集中式 45 维模式仍受该数学缺口影响。

### 3.5 集中式 UWB 更新没有对齐各车 IMU 状态

`RangeEkf` 的仅测距回退路径会在更新前调用 `predict_to(packet.timestamp_ns)`。但 `CooperativeInertialEkf::update_range()` 仅检查 UWB 自身的测距时间顺序，预测距离时直接读取两个 `InertialEskf15` 当前保存的最新位置。

`Engine::push_range()` 的测量/接收时间门限和全局 UWB 顺序检查，不能证明两车惯导都已处在该 UWB 测量时刻。因此现有集中式 45 维 UWB 更新没有按测距时刻插值或外推各车状态。新的 `DistributedFusion2D` 通过 `NodeState` 历史对齐解决了新路径的这个问题，没有回写或改造旧集中式算法。

### 3.6 集中式逻辑的耦合点

| 耦合点 | 现有集中式行为 | 最小新路径 |
|---|---|---|
| 句柄 | 一个 `zju_coop_handle_t` 拥有一个多车 `Engine` | 每车一个单节点旧句柄；参考车另有 `zju_coop_distributed_handle_t` |
| 初始化 | 三车初值一次进入同一 `configure_inertial` | 各车从自己的 YAML 初始化；重新初始化时整组节点协调重启 |
| IMU | 参考车收三车原始 IMU | 每车只订阅本车 IMU |
| 协方差 | 一个 `15N×15N` 联合矩阵 | 各车本机 `15×15`；参考车另有 `2(N-1)×2(N-1)` 修正协方差 |
| UWB | 直接向多车 15N 名义状态注入 | 只修改参考车的二维位置修正量 |
| 时间 | 使用各传播器当前状态 | 以 UWB 测量时刻查询每车缓存 |
| 输出 | 从联合滤波器直接生成 Pose2D | 对齐本地基线＋持久 UWB 修正生成 Pose2D |

## 4. 已实现的最小总体架构

### 4.1 每辆车

```text
上交 IMU publisher
  -> sensor_msgs/msg/Imu
  -> 浙大 zju_local_inertial_node
  -> zju_coop_create(N=1)
  -> zju_coop_configure_inertial(N=1)
  -> zju_coop_push_imu
  -> zju_coop_get_node_state
  -> cooperative_localization_msgs/msg/NodeState @ 20 Hz
```

本地惯导不订阅 UWB，不依赖其他车 NodeState，网络断开时仍可继续本地传播。

### 4.2 参考车增加的融合路径

```text
三车 /cooperative_localization/node_state
                        \
                         -> zju_cooperative_fusion_node
上交 /uwb/range   /      -> zju_coop_distributed_handle_t
                                  -> DistributedFusion2D
                                  -> CooperativePose2DArray @ 10 Hz
```

参考车的本地 IMU 也只进入它自己的 `zju_local_inertial_node`。融合节点不订阅任何车的原始 IMU。

## 5. 本地 15 维惯导的实际组合

### 5.1 不新增 `LocalInertialEkf15`

最小实现直接把现有 `CooperativeInertialEkf` 配置成单节点：

- `zju_coop_create()` 的 `reference_node_id` 等于本车 ID；
- `zju_coop_configure_inertial()` 的 `node_count=1`；
- 内部 `filters_` 只含一个 `InertialEskf15`；
- 内部 `covariance_` 为 `15×15`。

这样复用了已有初值校验、IMU 时序、中值积分、`Phi/Qd` 生成、协方差传播和事务回滚，没有两套 15 维惯导实现。

### 5.2 初始化、IMU 输入和本地状态

YAML 对每辆车提供：

```text
node_id
initial_position_enu_m[3]
initial_velocity_enu_mps[3]
initial_orientation_flu_to_enu_xyzw[4]
initial_gyro_bias_flu_rad_s[3]
initial_accel_bias_flu_m_s2[3]
expected_imu_frame_id
common_enu_frame_id
publish_rate_hz
```

`sensor_msgs/msg/Imu` 的 `header.stamp` 映射为采样时刻。实盒中它必须是 `UWB_SYSTEM_TIME`；本地节点用该时标加 `steady_clock` 估计同域接收时刻，不直接使用 ROS/SystemTime。`use_sim_time=true` 时保留 Gazebo `/clock` 路径，避免仿真暂停时单调时钟继续前进。角速度、线加速度、三组协方差和合法姿态逐字段复制到 `zju_coop_imu_packet_t`。IMU 消息没有业务 sequence，ROS 适配节点只在进程内为 C ABI 生成自增计数。

名义状态为：

```text
p_ENU, v_ENU, q_FLU_to_ENU, bg_FLU, ba_FLU
```

零偏只在软件中用于 `omega_measured-bg` 和 `specific_force_measured-ba`，不写回 IMU 寄存器或上交驱动。第一版本地路径只做惯性传播，零偏名义值没有外部观测持续校正，对应误差协方差按随机游走增长。

## 6. 已冻结的紧凑 `NodeState v1` 契约

### 6.1 算法核心与 C ABI

`src/core/distributed_fusion2d.hpp` 的普通 C++ `NodeState` 和 `zju_coop_node_state_t` 的业务字段一致：

| 字段 | 类型 | 语义 |
|---|---|---|
| `node_id` | `uint32` | 固定车辆 ID；非零，当前实现范围为 1..65535，必须与 UWB `src_id/target_id` 一致 |
| `timestamp_ns` | `uint64` | 本地惯导最后一次接受的 IMU 样本时刻，不是发布或接收时刻 |
| `receive_timestamp_ns` | `uint64` | 融合端接收该状态的同时域时刻 |
| `position_enu_m[3]` | `double[3]` | 公共 ENU 绝对位置 `[E,N,U]`，m；不是相对参考车位置 |
| `velocity_enu_mps[3]` | `double[3]` | ENU 速度 `[vE,vN,vU]`，m/s |
| `orientation_flu_to_enu_xyzw[4]` | `double[4]` | 右手系 FLU 到 ENU 的单位四元数 `[x,y,z,w]`，无量纲 |
| `valid` | C ABI 中 `uint8` 布尔 | 时间、位置、速度和姿态整条状态是否可使用；假值必须丢弃 |

`struct_size/abi_version/reserved` 是 ABI 边界字段，不是算法状态。生产端 `zju_coop_get_node_state()` 把 `receive_timestamp_ns` 置 0；参考车 ROS 回调生成接收时刻后才调用 `zju_coop_distributed_push_node_state()`。

NodeState 故意不包含：

- sequence；
- 初始化代次或其他会话编号；
- `bg/ba`；
- `15×15` 协方差或其行主序 225 元素。

完整 `bg/ba/P15` 留在本车的 `CooperativeInertialEkf(N=1)` 内。二维修正器用自己的小协方差，不将相邻本地惯导状态误当作独立绝对量测反复融合。

### 6.2 ROS 2 `NodeState.msg`

已落盘的消息恰为：

```text
std_msgs/Header header
uint32 node_id
float64[3] position_enu_m
float64[3] velocity_enu_mps
float64[4] orientation_flu_to_enu_xyzw
bool valid
```

ROS 消息只有一个跨网时间 `header.stamp`，对应 C ABI `timestamp_ns`。它必须非零且对同一 `node_id` 严格递增。实盒中 NodeState 和 UWB 的 Header 均使用 `UWB_SYSTEM_TIME`。`receive_timestamp_ns` 不跨网发送；参考车以本车 NodeState 为 UWB 时钟锚点，并用 `steady_clock` 推进同域当前时刻。Gazebo 则统一使用 `/clock`。两条路径都不会用 Linux/ROS UTC 覆盖量测时标。

`header.frame_id` 第一版固定为字面值 `common_enu`。公共 ENU 为右手系：`+x` 东、`+y` 北、`+z` 上；三车必须预先冻结同一个原点、轴向和生效时刻。只修改 `frame_id` 字符串不会执行坐标变换。车体系为 FLU：`+x` 前、`+y` 左、`+z` 上。四元数表示 `FLU -> common_enu`，排列为 `[x,y,z,w]`；`q` 与 `-q` 表示同一姿态。由此计算的航向以东为 0、向北为 `+pi/2`、从东向北逆时针为正。

`std_msgs/Header` 本身只含 `stamp` 和 `frame_id`，没有 ROS 1 的 `seq`。本接口也不另加业务 sequence、初始化代次、发布时刻或接收时刻。

### 6.3 Topic、频率和 QoS

| 项目 | `NodeState v1` 固定值 |
|---|---|
| 消息全名 | `cooperative_localization_msgs/msg/NodeState` |
| Topic | `/cooperative_localization/node_state` |
| 发布者 | 每车一个 `zju_local_inertial_node`；同一 Topic 多 publisher，以 `node_id` 区分 |
| 标称频率 | 20 Hz；只有出现新的状态时刻才发布，同一时刻不重复发布 |
| QoS history/depth | `KEEP_LAST(5)` |
| QoS reliability | `BEST_EFFORT` |
| QoS durability | `VOLATILE` |
| 接收超时 | 融合应用层 300 ms；超时不改变消息 QoS |

同一 `node_id` 在一个运行会话内只能有一个 publisher。`valid=false` 表示整条状态不可用，接收端直接丢弃；它不是心跳。当前浙大发布节点仅在本地惯导已经就绪时发布，并把 `valid` 设为真。

## 7. 时间、缓存和重新初始化

### 7.1 NodeState 入队

每辆车的 `NodeRecord` 最多保存 64 帧。入队条件是：

- `node_id` 已配置；
- `valid=true`；
- 测量时刻和接收时刻均非零，差值不超过配置的超前/延迟门限；
- `p/v/q` 有限，四元数可归一化；
- 同一车的 `timestamp_ns` 必须严格大于已缓存最新时刻。

重复包和乱序包直接拒绝，当前不设重排窗、不插入到历史中间、不回放已完成的 UWB 后验。在 20 Hz NodeState 配置下，64 帧约对应 3.2 s 历史，但这只是由当前频率推导的时长，核心实际限制是帧数。

### 7.2 UWB 时刻对齐

对每个 UWB 测量时刻 `t_r`，两端 NodeState 分别执行：

1. 缓存中有 `t_r` 的精确样本时直接使用。
2. `t_r` 位于两帧之间时，位置和速度线性插值；姿态先选择四元数同半球，再做归一化线性插值（最短弧 nlerp）。当前不是 SLERP。
3. `t_r` 晚于最新帧时，使用 `p(t_r)=p_k+v_k(t_r-t_k)` 做有限前向外推，速度和姿态保持最新值。当前融合节点把上限设为 100 ms。
4. `t_r` 早于该车最早缓存，或前向外推超限，拒绝该 UWB。不做反向外推。

UWB 包自身也必须通过测量时刻/接收时刻的超前和延迟门限。同一无向边以 `(min(src,target), max(src,target))` 归一化，该边时间必须严格递增；反向重复的同时刻测距会被拒绝，同一时刻的另一条边仍可正常更新。此外，已消费 UWB 的全局时间不允许倒退。

### 7.3 超时和重新初始化

GCS 有效位同时检查整组输出的统一算法时刻和各车最新 `receive_timestamp_ns`，当前 YAML 配置 `node_state_timeout_ms=300`。任何一车停发导致统一时刻冻结时，整组位置和航向均降为无效，避免 10 Hz Topic 仍在发布却携带旧历元。统一时刻新鲜时，参考车的 `position_valid` 还要求参考车状态新鲜；非参考车还必须通过未超时、且最近一次更新被滤波接受的测距边连通到参考车。NIS 拒绝只推进测距去重/时间基线，不刷新这条“成功协同修正”新鲜度；仅收到 `NodeState` 或测距长期中断时，从车位置数值继续保持有限以供诊断，但 `position_valid=false`。`yaw_valid` 由统一时刻、本车姿态和本车状态新鲜度决定，因为测距不修正航向。当前最小实现让统一时刻、NodeState 和成功测距路径共用 300 ms 超时门限。

`NodeState v1` 不携带会话编号，因此时间戳单调性只能识别同一运行会话内的重复和乱序，不能识别“同一车辆已经换了一套初值”。任一车重新设置 `p/v/q/bg/ba`、公共 ENU 或复位惯导时，第一版必须协调停止并重启三个 local 节点和 fusion 节点。重建 fusion 句柄会同时清空 NodeState 历史、二维修正、修正协方差和 UWB 去重时间基线；测试 `distributed_fusion_new_handle_clears_history_and_uwb_correction` 锁定了该行为。

禁止只热重启一辆车后继续使用旧 fusion：即使新状态时间戳更大，它仍会叠加旧 UWB 修正。`VOLATILE` 只能避免 DDS 向新订阅者发送历史保留样本，不能替代会话编号。

## 8. 参考车二维协同修正

### 8.1 状态、基线与后验分离

对每辆非参考车 `i`，对齐 NodeState 给出相对航位推算基线：

\[
B_i(t)=
\begin{bmatrix}
p_{i,E}(t)-p_{r,E}(t)\\
p_{i,N}(t)-p_{r,N}(t)
\end{bmatrix}.
\]

`DistributedFusion2D` 只估计非参考车的二维位置修正：

\[
C=
\begin{bmatrix}
\Delta E_2&\Delta N_2&\Delta E_3&\Delta N_3
\end{bmatrix}^{T}.
\]

一般 `N` 车的状态维度是 `2(N-1)`，三车时是 4 维，不包含速度修正、高度修正或姿态修正。输出为：

\[
X_i(t)=B_i(t)+C_i.
\]

修正量 `C` 和对应协方差是独立持久对象；NodeState 只更新基线。因此新 NodeState 到达时不会执行 `C=0`，也不会用新基线直接覆盖 UWB 后验。测试 `distributed_fusion_uwb_correction_survives_new_node_state` 锁定了这一行为。

### 8.2 协方差与过程模型

修正协方差维度为 `2(N-1)×2(N-1)`。初始对角标准差取基础节点配置中最大的 `position_std_m`。UWB 时间前进时，修正量本身保持不变，协方差对角增加：

\[
Q_{position}=\frac{1}{4}\sigma_a^2\Delta t^4.
\]

这是第一版的最小位置修正不确定度增长模型，不是带速度修正的常速状态转移。

### 8.3 UWB 更新

对齐后的两端三维位置为：

\[
\tilde p_i=
\begin{bmatrix}
p_{i,E}+\Delta E_i\\
p_{i,N}+\Delta N_i\\
p_{i,U}
\end{bmatrix},
\]

参考车的 `ΔE/ΔN` 固定为 0。预测距离使用三维欧式斜距：

\[
h(C)=\|\tilde p_j-\tilde p_i\|_2.
\]

雅可比只对非参考车的 `ΔE/ΔN` 非零。测量方差使用 ROS 参数 `range_std_m` 的平方，当前为 0.1 m 标准差。算法计算 NIS，超门限时不更新修正量；接受时用 Joseph 形式更新协方差并保持对称。

每条无向边另外保存“最后一次 Accepted 更新的测量时刻和接收时刻”。输出时要求二者都未超时，再从参考车沿新鲜的 Accepted 边计算连通分量；只有位于该分量中的非参考车才设置 `position_valid=true`。因此一条测量历元已经陈旧但刚到达的延迟包、一条被拒绝的异常测距，都不会把旧修正伪装成刚刚更新；参考车—从车—另一从车的两跳有效路径仍可保持后者有效，而任一车辆停发导致的整组旧历元也不会继续冒充实时结果。

当前 UWB 预测把 IMU 位置当作 UWB 天线位置，即天线杆臂默认为零且没有杆臂参数。在实车精度验收前必须得到每车 IMU 原点到 UWB 天线相位中心的 FLU 外参，并在量测模型中显式使用。

| 用途 | 部署 Topic | QoS |

### 10.3 UWB 临时消息

`zju_coop_test_msgs/msg/UwbRange.msg` 严格使用已提供字段：

```text
std_msgs/Header header
uint32 src_id
uint32 target_id
float32 distance
```

因消息不含测距标准差、LOS/NLOS 和质量状态，ROS 节点用 `range_std_m=0.1` 参数，并向 C ABI 填写 `valid=true/status=OK`。正式部署必须用上交正式包全名替换 `zju_coop_test_msgs`依赖；只改 ROS 映射层，不改算法 C ABI。

### 10.4 Bringup

`vehicle_1.yaml`、`vehicle_2.yaml`、`vehicle_3.yaml` 分别提供三车公共 ENU 初值，当前演示位置为 `(0,0,0)`、`(3,0,0)`、`(0,4,0)`，初速度和零偏均为 0，姿态分别对应航向 `0`、`+π/2`、`-3π/4`。`fusion.yaml` 固定三车、1 号参考车、10 Hz 输出、0.1 m 测距标准差和 300 ms NodeState 超时。

`vehicle.launch.py` 在每台车上启动 local 节点；`run_fusion` 默认关闭，只有显式设为 `true` 才启动 fusion。`namespace:=vehicle_1/2/3` 默认分别加载同名 `vehicle_N.yaml`，也可用 `local_config` 显式覆盖；非标准命名空间应显式指定配置，避免把错误的 `node_id` 带到实车。它通过 remap 把节点内的 `imu/node_state/uwb_range/poses_2d/feedback_poses_2d` 映射到上表 Topic；可选的 `point_cloud/camera_image` 输入默认关闭。`use_gnss_range_fallback` 和 `enable_follower_feedback` 均默认 `false`：前者关闭时 fusion 只订阅 `/uwb/range`，后者关闭时不创建反馈发布者。

### 10.5 默认关闭的 GNSS 距离后备

若上交 UWB 测距未在演示期限前可用、但 UWB 共同授时已经可用，参考车可显式启动 `zju_gnss_range_fallback_node`。它订阅三车标准 `sensor_msgs/msg/NavSatFix` 和已有 NodeState，要求 `NavSatFix.header.stamp` 已由驱动转换为与 NodeState 相同的 `UWB_SYSTEM_TIME`。只有三车 NodeState 均有效、`frame_id=common_enu`、近期到达且最新状态时刻相互接近时才处理 GNSS；时间门限以该共同时间为基准，不再把 ROS 系统时间或真实 UTC 当作量测时间。真实 UTC 的 `NavSatFix` 会因不在共同时间域而被拒绝。

三车 GNSS 还必须均有有效 fix、时间戳严格递增、同一批最大时间差默认不超过 `50 ms`；程序拒绝零时间、未来超过 `100 ms`、接收延迟超过 `500 ms` 或缓存驻留超过 `500 ms` 的数据。每组三车数据只发布一次 `(1,2)/(1,3)/(2,3)` 三条距离，三条消息统一使用该组三车时间戳最大值。`use_sim_time=true` 时当前时刻取 `/clock`，避免仿真暂停后 steady time 继续前进；实盒默认 `false`，由 NodeState 锚点加 steady time 推进。NodeState 活性门禁不是硬件 SYNC 锁定状态的替代品；在正式同步状态接口冻结前，上交驱动在失锁时必须停止或判无效相关输入。

地面首版把 WGS-84 经纬度转到 ECEF 后计算水平弦长，默认忽略噪声较大的 GNSS 高度；因此它近似的是“同高条件下 GNSS 天线间水平距离”，不是经过射频传播和双向测时得到的 UWB 斜距。输出使用独立 Topic `/cooperative_localization/gnss_derived_range`，不会伪装成 `/uwb/range`。launch 开关同时把 fusion 输入切到该 Topic，并把 `range_std_m` 从 UWB 默认 `0.1 m` 切到保守的 GNSS 默认 `3.0 m`。

正常模式和后备模式严格互斥，不做运行时自动切换。切换时必须重启参考车整个 `vehicle.launch.py`，从而同时重建 fusion、启动或停止后备节点，并清空旧测距时间基线、后验和噪声模型。该模式只用于 UWB 测距延期时维持 IMU→NodeState→GCS 软件链路，不能替代共同授时，也不能作为 UWB 时间同步、UWB精度或协同定位合同精度的验收依据；GNSS 共基站误差相关、RTK状态、天线/UWB杆臂和实际距离标准差仍需现场确认。

### 10.6 可选 Gazebo 首版

`zju_coop_gazebo` 与算法包隔离，首版使用 ROS 2 Humble 官方配套的 Gazebo Fortress。现有解析三车仿真继续作为快速、确定性的 CI 基线；Gazebo 用于增加车辆动力学、轮地接触和仿真 IMU，不替换算法节点。

首版车辆采用两驱动轮加固定低摩擦球形支撑的差速底盘：车体 `0.8×0.5×0.2 m`、质量 `20 kg`、轮半径 `0.15 m`、轮距 `0.60 m`。固定支撑用于约束首版平面模型的随机俯仰，不等同于实车悬架。Gazebo 世界 `X/Y/Z` 解释为 ENU 东/北/天，车辆模型 `X/Y/Z` 为 FLU 前/左/上，正航向绕 `+Z` 从东向逆时针增加。IMU 与 UWB 参考点首版均与车体参考原点同轴，杆臂取零；该假设不能替代实车外参标定。

数据链为：

```text
Gazebo DiffDrive + 100 Hz IMU + 50 Hz PosePublisher
              │ ros_gz_bridge，统一 /clock
              ├── sensor_msgs/Imu ──> 三个现有 local node
              └── 三车共同历元真值 ──> 20 Hz 三边 UWB 与评估 truth
                                           │
                                           v
                                  现有 fusion 与 GCS 输出
```

Gazebo Fortress 自带 IMU，但没有可直接用于本项目的原生 UWB 测距传感器。SDFormat 语法虽然保留 `wireless_receiver/wireless_transmitter` 类型，Fortress 官方功能对照仍把 Wireless 标为未迁移，`gz-sensors` 的受支持传感器列表也没有 UWB。工程中常见的实现分三级：用真值位姿计算距离并由 ROS 节点发布、编写 Gazebo System 插件加入遮挡/传播/噪声、接入真实硬件或回放实测数据。本版采用第一级：`gazebo_scenario.py` 从三车同历元真值计算三维欧氏距离并发布既定 `UwbRange`，只验证接口、时间和融合链路，不模拟 DW1000、PPS/RMC/SYNC、射频传播或 NLOS 识别。

三车模型还各带一个低负载 5 Hz 单线 GPU 激光雷达和一个 10 Hz、`320×240` RGB 相机，安装位姿只是首版仿真假设。`enable_lidar/enable_camera` 只桥接并校验标准 `PointCloud2/Image/CameraInfo`；`enable_lidar_frontend/enable_visual_frontend` 会自动启动所需桥，并在各车本机运行平面 ICP 里程计或已知四色地标板的单目平面定位，输出 `/vehicle_N/lidar/odometry`、`/vehicle_N/visual/odometry`。`enable_lidar_slam` 会自动启动雷达桥、ICP 及其 `lidar_odom→front_lidar` TF，再为每车启动独立 RTAB-Map 二维后端，输出 `/vehicle_N/lidar_slam/map` 和独立持久化数据库；启动时不会自动删除旧数据库。该方案参考本机 `Swarm-SLAM` 的 RTAB-Map 用法，但不复制或启动整套多车后端。五个开关均默认 `false`。原始 C ABI 仍只返回 `VALIDATED_NOT_USED`，这些前端输出只作评估和录包，尚未进入 NodeState 或 UWB/GCS 融合。相机光学坐标由前端显式处理；工程只在 SLAM 开启时发布所需的最小雷达 TF，不等同于完整生产 TF 树。

三车真值和 local 初始位置均为 `(0,0,0.25)`、`(4,0,0.25)`、`(0,3,0.25)`，航向为 `0`、`0`、`+π/2`，初速度均为零。只有自动验收测试把 2 号 local 的东向初值改为 `4.5 m`，用于验证 UWB 只改善 GCS 后验而不覆盖本地 NodeState。模型原点、IMU 和 UWB 参考点重合在车体中心。三车独立 `PosePublisher` 的带时间戳模型位姿用于生成 UWB，不能使用会在 Humble bridge 中丢失子帧信息的 SceneBroadcaster 全局 GUI 位姿流。

1、2 号车以 `0.30 m/s` 前进，3 号车以 `0.25 m/s` 直行；2 号车在起步后 8 秒内执行 `ω=0.15·sin(2πt/8)` rad/s 的一次平滑 S 弯，先左转、再右转并回到接近初始航向。起步 15 秒后三车统一以 `+0.25 rad/s` 持续左转，1、2 号车形成半径约 `1.2 m` 的圆路，3 号车形成半径约 `1.0 m` 的圆路。围墙内范围约 `30×28 m`（ENU `x=[-3,27]`、`y=[-3,25]`）；物理地面仍为 `100×100 m`，Gazebo GUI 的辅助网格单独扩大为居中覆盖围墙的 `40×40 m`。循环包络经 300 秒数值门禁检查，与围墙、实体柱及其他车辆均保留安全余量，可长时运行而不再直行撞墙。前 12 秒已验收轨迹不变，因此现有 S 弯、UWB 和感知门禁仍有效。DiffDrive 用 `0.30 m/s²` 上限从零速平滑起步，并用 `0.50 rad/s²` 上限平滑进入圆路。Gazebo 初始暂停并持续接收零速度命令，5 秒后统一解暂停；仿真时间开始后先保留 `1 s` 的有效静止 IMU，再下发目标速度，保证传感器桥和可选前端先完成发现。local/fusion 使用仿真时间，轨迹相位和 UWB/truth 均只使用 Gazebo 位姿自带的仿真时间戳。每次 launch 默认生成唯一 `IGN_PARTITION`，避免残留 Gazebo 实例串入 `/clock`、IMU 或位姿；需要外部 Gazebo 工具接入时可显式传 `ign_partition:=<同一名称>`。当前 VMware 环境以 OGRE2 运行服务端相机/雷达，以 OGRE1 运行 GUI。GUI 默认使用虚拟显卡加速，避免 `llvmpipe` 全 CPU 渲染导致闪烁；headless 自动测试则显式传入 `software_rendering:=true`。`headless:=true` 只关闭 GUI，无显示器 CI 仍需单独验收 EGL/驱动环境。

一键 launch 默认不录包，以免最小演示意外占用磁盘；需要以仿真时间录制 `/clock`、三车 IMU、`/uwb/range`、truth、NodeState 和 GCS 输出时追加 `record_bag:=true`。若感知桥或前端被启用，同一录包还保存三车点云、图像、CameraInfo 和两类 Odometry；SLAM 开启时还保存三路 OccupancyGrid 和 `/tf`。数据位于启动目录的 `bags/gazebo_three_vehicle_<时间戳>/`，`bag_output:=<路径>` 可覆盖。该录包只用于 x86 同机仿真，不得照搬为三盒 Mesh 上的全 Topic 集中录制方案。

世界 `real_time_factor=1.0`；首次启动前的受控暂停是初始化流程的一部分，运行后仍不支持仿真时钟倒退或任意暂停后续跑。Gazebo 只在 x86-64 开发机运行；RK3588 只部署 SDK 和 ROS 适配节点。

RViz 不是算法、GCS 或 RK3588 部署依赖。当前 `CooperativePose2DArray` 是自定义消息，RViz 默认不能直接显示，且本工程不发布完整生产 TF 树；但 `enable_lidar_slam:=true enable_slam_rviz:=true` 可在 x86 开发机打开项目预设，显示参考车 1 的 OccupancyGrid、当前点云和最小 SLAM TF。三车地图目前各自位于独立 `lidar_map`，没有跨车地图配准或公共 TF，因此不应直接叠加。若还需对比 truth 与协同定位结果，应另加独立 MarkerArray 适配器，不把 RViz 类型写入算法核心，也不在 RK3588 上运行 RViz。

截至 2026-08-19，本机已安装 Gazebo Fortress 6.18.0 和 `ros_gz 0.244.25`，RTAB-Map 0.22.1 由本机已有 ROS 2 overlay 提供。Gazebo 的静态资产、默认关闭感知的物理闭环、显式开启感知和前端、显式开启三车 SLAM 的测试为 `4/4`。开启用例验证三车 5 Hz 点云、10 Hz 图像/CameraInfo、平面 ICP Odometry、已知地标视觉 Odometry、三路含未知/空闲/占用单元的非空 OccupancyGrid，以及原 IMU→NodeState→UWB→GCS 主链；视觉结果按同历元 Gazebo 绝对真值门禁，ICP 按雷达杆臂后的相对运动门禁。该结果只证明 Ubuntu 22.04 x86-64 同机短时低速仿真前端和建图冒烟链，不代表前端输出已融合、闭环地图精度已验收，也不代表自然场景视觉、真实雷达、RK3588、跨盒通信或实车精度通过。

## 11. GCS 二维输出契约

### 11.1 消息

`VehiclePose2D.msg` 为：

```text
uint32 node_id
float64 x_m
float64 y_m
float64 yaw_rad
bool position_valid
bool yaw_valid
```

`CooperativePose2DArray.msg` 为：

```text
std_msgs/Header header
uint32 reference_node_id
cooperative_localization_msgs/VehiclePose2D[] vehicles
```

GCS Topic 固定为 `/cooperative_localization/poses_2d`，当前发布频率为 10 Hz，始终由参考车发布。设置 `enable_follower_feedback:=true` 后，参考车还会以相同频率把完全相同的数组发布到 `/cooperative_localization/feedback/poses_2d`；默认值为 `false`，此时专用反馈 Topic 没有发布者。

两条 Topic 承载同一个参考车权威结果：GCS 使用原 Topic，从车任务/编队规划器只使用默认关闭的专用反馈 Topic，并按 `node_id` 取本车结果；无需二次融合，也不得写回本地惯导 `p/v/q/bg/ba/P15`。当前消息没有机器可读的测距来源字段，因此显式 GNSS 距离后备模式只允许 GCS 应急显示，必须关闭规划反馈。各车高频底盘跟踪、失联停车和急停始终留在本车。规划消费者除检查每车有效位外，还必须检查 `header.stamp` 年龄并设置 Topic 接收 watchdog，不能因 Topic 仍以 10 Hz 发布就忽略统一算法时刻、车辆状态或测距失联。

### 11.2 坐标与航向

- `x_m = p_node,E - p_reference,E + 对应二维修正`；
- `y_m = p_node,N - p_reference,N + 对应二维修正`；
- 参考车正常时 `x_m=0`、`y_m=0`；
- 坐标原点跟随参考车，但轴向始终与公共 ENU 平行，不随参考车车头旋转；
- `header.frame_id` 为 `coop_ref_<reference_node_id>_enu`；
- `header.stamp` 为三车最新 NodeState 时刻最小值所确定的公共算法时刻。

航向把 FLU 前向轴 `[1,0,0]` 通过 `q_FLU_to_ENU` 旋转到 ENU，然后计算：

\[
\psi=\operatorname{atan2}(f_N,f_E).
\]

东向为 0，向北为 `+π/2`，逆时针为正，范围归一化为 `[-π,π)`。它是车辆自身相对 ENU 东轴的航向，不是从车相对参考车车头的夹角。UWB 不直接观测航向，第一版 `yaw_rad` 完全来自各车本地惯导。

## 12. ROS 2、DDS 与 5G Mesh 的边界

```text
rclcpp publish/subscribe
        -> rmw_fastrtps_cpp
        -> Fast DDS/RTPS/UDP
        -> 5G Mesh IP 网络
```

5G Mesh 是 IP 承载，不是算法 API；DDS 是 ROS 2 中间件，不是二维滤波器。三盒部署时必须使用相同 `ROS_DOMAIN_ID` 和 `RMW_IMPLEMENTATION=rmw_fastrtps_cpp`。若 Mesh 不传送 DDS 发现组播，应在 Fast DDS 部署配置中设静态 peer 或 Discovery Server，无需修改算法核心。

只有参考车 fusion 订阅紧凑 NodeState，任何远端节点都不应订阅其他车 IMU。对所有 Topic 执行远端 `ros2 bag -a` 会重新把原始 IMU 或点云拉过 Mesh，不属于本设计。

## 13. 第一版能力边界与升级入口

### 13.1 已实现能力

- 三车本机 IMU 独立传播和本机 `P15`；
- 低带宽 NodeState 跨车传输；
- UWB 测量时刻的缓存插值/有限外推；
- 非参考车二维位置修正；
- 只有经近期 Accepted 测距路径连到参考车的从车位置才标记有效；
- GCS 要求的三车二维相对位置和 ENU 航向数组；
- 默认关闭、可由参考车一键开启的同数组从车规划反馈；
- 旧 UWB-only 和集中式 45 维路径继续存在，可用于回归对照。
- 默认关闭的 GNSS 派生距离后备可在 UWB 测距延期但共同授时有效时维持参考车融合输入；它不替代 UWB 授时或测距验收。

### 13.2 明确不包含的能力

- 协同结果可选反馈给从车规划模块，但 UWB 修正不回灌从车本地 `p/v/q/bg/ba/P15`，也没有导出 `CooperativeCorrection` 接口。
- 不估计高度、速度修正或航向修正。
- 不对 NodeState 乱序重排，不做延迟量测后验回放。
- 不支持单车热重新初始化或运行中增删车辆；任何初始化变化都要求整组四节点协调重启。
- 不建模 UWB 天线杆臂、NLOS 概率或设备质量字段。
- 正常模式不订阅 GNSS；显式应急模式只把三车 `NavSatFix` 几何距离作为低置信度测距，不把 GNSS 位置直接写入本地惯导。雷达和视觉前端默认不启动；显式启动时会发布独立 Odometry，但仍不反馈本地惯导或协同融合。
- 不支持无中心协同滤波。若 5G Mesh 连紧凑 NodeState 和 UWB 都无法会聚到任一节点，需要另行设计对等信息融合和交叉相关性管理，不能用当前实现声称已解决。

### 13.3 雷达和视觉的升级边界

当前平面 ICP 和已知地标视觉前端已经证明“原始数据在本车处理并产生小型位姿结果”的链路，但其 `Odometry` 仍是诊断输出。下一步若融合，必须把处理后的位姿/相对运动连同测量时刻、坐标方向、协方差和质量标志定义成版本化约束，补齐延迟对齐和相关性测试；不应把跨车 `PointCloud2` 或图像放入算法核心，也不能把累计 Odometry 当作逐帧独立绝对观测重复融合。
