# 三车 IMU＋测距协同定位算法与可观测性说明

## 1. 当前算法解决什么问题

当前仓库并存两条算法路径。首版分布式路径由每车在本机计算 15 维惯导，只发布紧凑 NodeState；参考车按 UWB 测量时刻对齐三车状态，维护不覆盖本地惯导的二维协同修正并发布 GCS 结果。原参考盒集中接收三车 IMU、维护 15N 联合协方差的实现继续保留，作为回归基线。两条路径中每个节点的名义状态都包含位置、速度、姿态、陀螺零偏和加计零偏，误差状态为：

```text
[δp(3), δv(3), δθ(3), δbg(3), δba(3)]
```

集中式基线的三车联合协方差为 45×45，保留节点间交叉相关性；分布式首版则由每车自行维护 15×15 协方差，NodeState 不传输协方差，参考车只估计平面位置修正。算法核心不依赖 ROS 2；已实现的 ROS 2 适配节点把标准 IMU 和自定义 UWB 消息逐字段映射成普通 C 结构体。`config/range_only_demo.ini` 另保留二维恒速兼容路径，供回退和回归使用。

## 2. 三车为什么能够确定二维相对位置

三条边 AB、AC、BC 构成非共线三角形时，三条距离可以确定三角形的形状，但仅靠距离仍存在整体平移、整体旋转和镜像歧义：

- 把 A 固定在 `(0,0)`，消除整体平移；
- 使用外部初始二维坐标确定 x/y 朝向和镜像分支；
- 为每辆车提供同一公共 ENU 下的初始航向，完成当前理想初始对准；
- 后续测距保持三车相对几何，默认由各节点瞬时 IMU 递推位置、速度和姿态。

因此，初版创建算法时必须提供 A/B/C 的外部位置初值和公共 ENU 初始航向。初值可来自 GNSS 失锁前状态、人工测量或任务配置；正式联调前需由双方冻结初值来源、精度和注入时刻，上交平台把所需初值交给浙大适配节点/算法库。只指定 A 为原点而不提供 B/C 初值，无法唯一确定 x/y 轴朝向和镜像分支。

当前 demo 默认：

| 车辆 | node_id | 初始坐标 | 公共 ENU 初始航向 |
|---|---:|---:|---:|
| A | 1 | `(0,0) m` | `0 rad` |
| B | 2 | `(3,0) m` | `π/2 rad` |
| C | 3 | `(0,4) m` | `-3π/4 rad` |

这里的航向表示本车 FLU 前向 `+x` 轴相对 ENU 东向 `+x` 轴的逆时针夹角，规范范围为 `[-π,π)`。UWB 标量测距的量测方程只含节点间位置距离，不直接含姿态或航向；因此测距不能直接校正航向。运动状态和滤波交叉相关可能产生间接耦合，但静止或缺少有效运动激励时不应宣称 UWB 已使航向可观。

## 3. 测量模型

节点 i、j 的标量距离模型为：

```text
h_ij(x) = sqrt((x_j-x_i)^2 + (y_j-y_i)^2)
innovation = measured_range - h_ij(x)
NIS = innovation^2 / innovation_variance
```

NIS 超过配置门限时拒绝该次滤波更新，并将残差拒绝计入观测质量窗口。NLOS 或恢复期观测可通过放大测量协方差降权。

## 4. 动态有效边与退化

候选边不是固定有效边。引擎按数据时间、观测状态和 `edge_timeout_ns` 动态生成当前有效图：

- 三边有效且三点非共线：二维相对几何可观；
- 缺少一条边：三车瞬时二维几何一般不刚性，输出标记为不可观；
- 三点近共线：刚度矩阵秩不足，标记几何退化；
- 边持续缺失：置 `LINK_TIMEOUT`，节点可达数和有效边数同步变化；
- 时间偏差超限：拒绝该包并置 `TIME_SYNC_TIMEOUT`。

默认惯性模型可以在短时缺测时连续递推，兼容模式则使用常速度预测；两者都不能把预测结果解释为新的几何约束。

## 5. 观测质量状态机

每条候选边维护配置化滑动窗口。默认窗口为 2 s、测距标称 20 Hz，并统计收到数、有效数、NLOS 数、残差拒绝数和丢弃数。

状态可在 `UNKNOWN → NORMAL/DEGRADED → SUSPENDED → REJECTED → RECOVERING → NORMAL` 之间转换；融合动作分别为正常使用、降权、暂缓、拒绝和试探恢复。所有阈值都在 `config/demo.ini`，未硬编码在算法源文件中。

## 6. 当前输出能力边界

当前同时保留两条输出语义：

- C ABI v1 `Localization`：`x/y`、`vx/vy`、二维位置协方差、定位状态和原因位；旧结构固定 `yaw_valid=false`、`z_valid=false`；
- Pose2D C ABI v2：公共 `timestamp_ns/reference_node_id/frame_id`，以及每辆车的 `node_id/x_m/y_m/yaw_rad/position_valid/yaw_valid`；
- 临时 UDP 类型 105 和浏览器 GCS：映射 Pose2D v2 的 x/y/yaw，`yaw_valid` 有效时绘制航向箭头；
- Network、Observation、演示层 AlgorithmStatus/Alert：继续提供网络、观测质量和原因位。

Pose2D 的 x/y 表示 `node-reference`，坐标轴与公共 ENU 平行；frame 采用 `coop_ref_<reference_node_id>_enu`。yaw 表示每辆车自身的 ENU 航向，不表示“相对参考车车体系的偏航角”。z、高度、完整三维姿态和地理绝对坐标仍未输出。首版 ROS 2 消息及上交当前UWB消息结构已在Ubuntu x86-64同机验证；有效实测UWB、跨盒DDS和RK3588仍未验证。

## 7. 初版与 V3 完整方案的差距

当前已经实现标准 IMU 瞬时量的 15 维预测、集中式 15N 基线、分布式每车本地惯导与 NodeState、参考车二维 UWB 修正、Pose2D C ABI v2、ROS 2 GCS 发布、临时 UDP/GCS 和 Gazebo 三车闭环。尚未实现激光/视觉相对观测前端、协同修正反馈、无中心或显式多跳约束传播。当前 Ubuntu 22.04 x86-64 验证不构成 RK3588、跨盒网络或实车验证证据。

若增加第 4 辆车和冗余测距，可提高几何冗余和单边失效容忍度，但不能替代时间同步和外部初始坐标。
