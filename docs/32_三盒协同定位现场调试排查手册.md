# 三盒协同定位现场调试与排查手册

适用场景：三盒传感器检查、UWB在线相对定位、联合录包和数据收回；需要时再检查单独启用的RTE。优先使用同目录HTML版，按现象点击展开；本Markdown是可编辑源文件。修改后在工程根目录执行 `python3 tools/build_field_troubleshooting.py`，重新生成HTML。默认步骤与21号文档一致，现场设备或部署版本不同时，以实际安装配置和话题为准。

## 使用前：先确认位置和上下文

### 第一次到现场，先做什么？
- 按顺序查供电与连接、盒号、三盒UWB、各盒IMU、各盒Livox、消息头时间、201在线位置，最后录包。传感器启动和录包的完整顺序看21号文档第0～7节。
- 检查前先记录本次日期、人员、盒号、各盒摆放位置、是否静止、启动顺序、障碍物、实际运动、哪个时刻出现问题。需要移动实车时，由现场负责人员安排并确认周围安全。
- 不要同时重启多个环节：先保留现象、日志和消息，再只改变一个条件复测。不要用编造的数据、清空原包或盲目放宽参数使输出看起来正常。

### 命令前，怎样分清在哪台机器执行？
- 上交调试电脑通过网线连接201；常用地址为 `192.168.1.201`。从201通过自组网进入202的 `192.168.2.202` 或203的 `192.168.2.203`。实际地址变化时以现场配置为准。
- 【当前盒】表示在201、202或203各自的SSH终端执行；【201】只在201执行；【本地Ubuntu】是我们的开发电脑工程目录；【调试电脑】是连接201的上交电脑。进入SSH后先确认盒号。
```bash
hostname --all-ip-addresses
pwd
```
- ROS命令用新终端时，需要在该终端加载对应环境；新终端的环境不会改变已经启动的驱动。自组网通道和ROS域号等按本轮约定，本文示例为当前部署的默认域0。

### 怎样准备三个常用ROS终端环境？
- 【当前盒：UWB】用来查看跨盒共享测距；每盒IMU和Livox采用本机隔离配置，不能只在201代替202、203检查。
```bash
source /opt/ros/humble/setup.bash
source /home/firefly/imu_ws/install/setup.bash
export ROS_DOMAIN_ID=0 ROS_LOCALHOST_ONLY=0
```
- 【当前盒：车载IMU】在每个需要检查的盒分别执行。若驱动本身不是在此配置启动，需要先核对驱动实际环境，不能只改检查终端。
```bash
source /opt/ros/humble/setup.bash
source /home/firefly/imu_ws/install/setup.bash
export ROS_DOMAIN_ID=0 ROS_LOCALHOST_ONLY=1
```
- 【当前盒：Livox】按21号第6.1节加载雷达工作空间、`ROS_LOCALHOST_ONLY=1`，RMW沿用该盒实际雷达进程或启动脚本。不要把某盒的RMW或设备网口名直接套到其他盒。
- 【201：默认在线算法】另开终端，先加载UWB环境，再加载201已安装的 `/home/firefly/zju_coop_ws/install/ros2-box/setup.bash`。没有这个安装目录时先按41号文档部署，不把开发机的x86程序直接复制到盒上运行。

### 看到频率或一帧数据，就算通过了吗？
- 不算完整验收。先检查是否持续收到预期内容，再检查每路 `header.stamp` 是否非零、连续、时间域可比较；需要融合时，还要确认不同传感器的时钟来源与实际采样时刻关系。
- `ros2 topic hz` 是观察端收到消息的频率，受网络和本机负载影响；有频率不保证无丢帧、数值正确或硬件同步。对高频大消息不要长期完整打印，优先短时查看频率或录包分析。
- 三盒同一型号不代表每盒、每一轮都正常；车载IMU、Livox内置IMU、Livox点云和UWB是四种不同的数据流，逐路判断。

## 一、连接、供电和设备识别

### 调试电脑连不上201，SSH超时
- 【调试电脑】检查网线、供电、网卡IP及网段；用 `ping 192.168.1.201` 辅助检查，失败可能是网络、地址、供电或ICMP策略，不能只凭ping断定设备损坏。
- 【201本地终端或现场屏幕】确认设备已启动，执行 `hostname --all-ip-addresses` 和 `ip -br addr`，核实网线对应网口的地址。确认后使用实际地址连接；不要直接改盒子网络配置。
- 网络通但SSH仍失败时，保存完整报错并检查 `systemctl status ssh --no-pager`；连接被拒绝与超时分别记录。

### 201能登录，但连接不上202或203
- 【201】分别检查自组网IP、链路状态和目标是否通电。先分别运行：
```bash
ip -br addr
ping -c 4 192.168.2.202
ping -c 4 192.168.2.203
```
- 在能进入目标盒时，核对目标盒 `ip -br addr`；检查自组网设备连接、距离和遮挡。不要把调试电脑网线侧 `192.168.1.*` 当成盒间自组网地址。
- `ping`成功而SSH失败，继续检查SSH服务、密钥和用户名；`ping`失败也可能被禁，不直接等同SSH不可用。

### SSH提示输入的是账户密码还是私钥口令？
- `firefly@... password`通常是登录账户密码；`Enter passphrase for key .../id_rsa`是解锁201上私钥的口令，两者不同。
- 【201】执行 `ssh-add -l`。如果显示已加载对应密钥且仍要求口令，检查当前终端 `SSH_AUTH_SOCK` 是否指向已加载密钥的代理；按21号第0.2节检查，不生成或覆盖现有私钥。
- 代理退出、201重启或密钥清除后可能再次要求输入；新终端只有正确加载同一代理时才可复用，不保证跨重启免输入。

### 登录202后命令却在201执行，或盒号混淆
- 【当前盒】执行 `hostname --all-ip-addresses`，并在终端标签标明201、202、203。三盒均可能显示相同主机名，不能只看提示符中的 `firefly`。
- `BOX=202`通常只是文件名标记，不会把在201执行的命令转发到202。必须实际SSH进入目标盒或使用明确的三盒控制脚本。

### 某盒启动后没有任何设备或USB/串口节点
- 【当前盒】先核对供电、接线、是否完全启动，查看设备节点及内核最近日志；具体设备编号以该盒为准。
```bash
ip -br addr
ls -l /dev/ttyS4 /dev/ttyS5 /dev/ttyS6 2>/dev/null
dmesg --ctime | tail -80
```
- 同时记录供电状态、插拔和启动时间；不要在未确认归属时拔插正在录包的设备或改写设备权限。

### 磁盘空间不足、设备时间显示不对或CPU占满
- 【当前盒】执行 `df -h /home/firefly`、`df -i /home/firefly`、`date -u`、`uptime` 和 `top`；记录目录容量、进程及时间。不同盒应分别查看。
- 时间显示或时区不同不直接证明消息头不同步；仍以各消息 `header.stamp` 的时间基准和连续性分析为准。磁盘不足先整理已备份数据，不在现场删除未备份原始包。

## 二、ROS通信与启动环境

### 进程存在，但 `ros2 topic list` 看不到话题
- 【当前盒】先确认检查终端加载了对应工作空间，比较 `ROS_DOMAIN_ID`、`ROS_LOCALHOST_ONLY`、`RMW_IMPLEMENTATION`；注意空值通常表示系统默认，不等于已验证正确。
```bash
printf 'DOMAIN=%s LOCAL=%s RMW=%s\n' "${ROS_DOMAIN_ID:-默认}" "${ROS_LOCALHOST_ONLY:-默认}" "${RMW_IMPLEMENTATION:-默认}"
ros2 topic list --no-daemon --show-types
```
- 车载IMU和Livox按本机配置检查，UWB在共享域检查。用 `ros2 daemon stop` 后重新使用 `--no-daemon` 可排除CLI缓存；它不会修复驱动或网络。

### 能看到话题名，但 `echo` 没有消息
- 【当前盒】先看发布者、类型与QoS；再用短时 `echo`。话题名可能来自其他节点或缓存，不能只凭列表判断。
```bash
ros2 topic info --no-daemon --verbose /uwb/range
timeout 8s ros2 topic echo --once --no-daemon /uwb/range
```
- 区分“没有发布者”“有发布者但不兼容/不出数”“有数据但订阅端没收到”。核对域、隔离配置、RMW、消息类型和QoS；别先重启所有盒。

### 同一话题有多个发布者，数据像在互相覆盖
- 【当前盒】执行 `ros2 topic info --no-daemon --verbose /imu/raw` 或相应话题，结合进程、PID、盒号和域判断发布者来源。
- 检查是否重复启动驱动、不同盒的同名IMU误进共享域，或回放与实时设备同时发布。先在原终端有序停止多余进程，保留正确的一份；不要用模糊命令杀死所有ROS进程。

### `package not found`、`command not found` 或找不到消息类型
- 确认当前机器安装了ROS 2 Humble，并在同一终端 `source /opt/ros/humble/setup.bash` 和对应工作空间。新shell、sudo环境与已启动进程的环境可能不同。
- `ros2 pkg prefix 包名` 可检查实际加载路径；消息缺失、版本不匹配或需要部署时按21、31、41号文档处理。不要覆盖原厂 `/home/firefly/imu_ws`。

### 明明改了配置，节点仍按旧参数运行
- 修改源码或YAML不会改变已经安装的文件，也不会自动更新运行中的进程。区分源码路径、安装路径、实际launch参数与节点实际参数，记下修改前版本。
- 【201】默认UWB按21号第7节检查安装版 `fusion.yaml` 和启动日志；更新源码后按41号文档重新构建，再在原算法终端正常停止、重启。
- 用 `ros2 node list` 确认节点全名，再按实际节点名执行 `ros2 param list /节点名` 和 `ros2 param get /节点名 参数名`；不要把参数名猜成话题名。

### 不同盒的域号或RMW不一致
- 各检查终端打印域与RMW，同时核查对应进程实际环境；只看当前shell不代表已运行驱动使用相同设置。跨盒UWB按本轮统一约定；车载IMU及雷达按21号文档使用本机隔离。
- 各DDS实现并非简单地“名字不同就必定无法通信”，实际兼容性应通过发布者、订阅QoS和真实消息验证；不要仅改环境变量就宣布恢复。

### ROS终端卡住、CPU很高或发现速度很慢
- 【当前盒】先停止终端里的持续大消息打印，检查 `top`、`free -h`、`df -h` 和网络；对 `/livox/lidar` 不要长期打印点数组。
- 改用21号文档的 `--no-arr`、短时 `timeout` 和本地录包，检查是否有重复驱动、大量订阅或同时压缩。观察端卡顿不自动证明硬件停采。

## 三、UWB测距

### `/uwb/range` 完全没有消息
- 【各盒】确认 `gnss_uwb` 是否按21号第2节启动、串口是否被占用、日志是否有持续RMC；【201】在共享ROS环境下检查话题类型和发布者。
```bash
pgrep --list-full --full 'gnss_uwb'
fuser --verbose /dev/ttyS5 /dev/ttyS6
```
- 有其他进程占用时先确认其用途，在原终端正常停止重复实例；未确认设备型号和串口映射前不要改配置。仍无消息时保留驱动日志和线缆、供电状态。

### 只能看到一个方向，或者只有两条车间边
- 【201】连续观察 `src_id`、`target_id` 和 `distance`，不要把总话题有频率等同三边都存在。三车逻辑编号1、2、3时应检查1—2、1—3、2—3三条无向边。
```bash
timeout 12s ros2 topic echo --no-daemon /uwb/range
```
- 核对三盒 `node_id`/`uwb_id`、各自UWB驱动和自组网；分别在对应盒验证其发出的消息。收发可有六个有向流，不要求每个观测窗口六方向同时齐全才认定三条无向边存在。

### 收到 `src_id` 或 `target_id`，却不是1、2、3
- 【各盒】核对当前配置与上报字段；201、202、203是盒名，算法使用逻辑ID，不能靠盒名末位猜测实际消息编号。
```bash
grep --extended-regexp 'node_id|uwb_id' /home/firefly/imu_ws/install/gnss_uwb/share/gnss_uwb/config/params.yaml
```
- 检查算法 `node_ids` 和 `reference_node_id` 与实际消息一致。修改ID需按现场部署规范协调，停止相关进程、备份配置后统一处理；不要临时把未知编号映射成1、2、3。

### 三盒都在发数据，但边被重复、顺序混乱或来源搞错
- 记录原始 `src_id`、`target_id`、盒号、Header和实际距离；1→2与2→1是两个方向，1—2是无向边，分析时不要把方向数量当作边数量。
- 检查重复驱动、盒子ID冲突和多个录包来源。一次 `echo --once` 只抽到一条，需观察一段或查看 `uwb/UWB测距数据.csv`。

### 距离为0、负数、NaN或跳出明显不合理范围
- 【201】保留原始消息、两盒位置和环境。先确认消息单位、天线连接、设备间实际距离与遮挡；`distance`应为有限正数。
- 不用将异常点手工改成正常值。偶发异常与持续异常分别记录，用短包对照；持续异常先检查对应链路的两端和设备状态。

### 两盒静止，距离却周期跳变、断续或突然偏大
- 比较对应边的两方向曲线、两端现场遮挡及金属、人体、水面或地面的反射；记录换位置、遮挡前后的时段，不把所有波动直接归因于算法。
- 【本地Ubuntu】在该盒 `uwb/UWB测距分析.md` 和 `UWB测距曲线与时间戳.png` 查缺口、分布、跳变时刻；用卷尺记录天线位置之间的真实距离。静止标准差小只能证明稳定，不能单独证明绝对误差小。

### UWB总频率很高，但在线定位仍低频
- 总频率包括所有来源和方向。分别看三条边是否连续、各边Header是否能组成同一历元，及201接收是否完整。
- 当前默认实现按三条边的消息头时间分组，配置示例为最大跨度10毫秒；这是分组参数，不是硬件同步精度结论。查看201启动日志和安装版配置；不要把缺边误判成算法算得慢。

### 两方向的测距不一样
- 记录双方来源、测量时刻和距离；运动中不同采样时刻本来可能不同，静止时再检查遮挡、天线延迟和测距模式。
- 当前配置中部分旧名称仅为兼容保留，不一定在适配层执行过滤；以实际节点与安装版本为准，不靠随意改旧参数消除现象。

### 看见测距曲线很平稳，是否代表厘米级精度？
- 不能仅凭波动判断准确度。对每条边测量两端天线参考点的实际距离，记录量具误差、安装高度和站位；与相同时段测距中位数比较。
- 同时看随机波动、固定偏差、离群和遮挡前后变化。没有独立距离参考时，只能评价稳定性和完整性，不能声称测距绝对精度。

## 四、车载IMU与本地航位推算

### `/imu/raw` 没有话题或消息
- 【故障盒】先按前文“车载IMU终端环境”设置 `ROS_LOCALHOST_ONLY=1`；确认 `navcore` 已运行，再分别检查发布者和短时频率。
```bash
pgrep --list-full --full 'navcore'
ros2 topic info --no-daemon /imu/raw
timeout 10s ros2 topic hz /imu/raw
```
- 确认设备串口、驱动日志及是否重复启动。看不到话题时不要在共享域反复启动另一份驱动；按21号第3节在本盒排查。

### IMU有频率，但 `topic info` 偶尔报 Unknown topic
- 先判断 `hz` 是否确实持续收到本盒消息。CLI缓存可能未刷新，执行 `ros2 daemon stop`，再用 `ros2 topic info --no-daemon /imu/raw`。
- 若仍无发布者或停止出数，再查域、驱动进程和设备，不应把全部Unknown topic都归因于缓存。

### IMU频率明显降低、长间隔或时好时坏
- 查该盒进程负载、供电、串口连接，记录发生时段；对比本盒原始包 `IMU分析.txt` 中消息数、Header间隔中位数、最大间隔和大间隔次数。
- 历史车载IMU约1000 Hz仅作参考，实际以驱动配置为准。终端打印会降低观察端接收速度；一帧也可能因网络或观察工具负载丢失，需结合原始包与驱动日志。

### 静止时加速度不是9.8，或数值全零
- 先确认单位和该话题含义：静止且包含重力的原始加速度，三轴合成模长通常接近9.8米/秒²，单个轴取决于安装姿态；不是每个轴都应接近9.8。
- 如果上游输出的是已去重力的量，不能用相同判断。持续全零、NaN或明显超出设备量程时先查消息字段、单位、驱动和设备，保存原始数据。

### 静止时角速度持续偏大，或转动方向与实际相反
- 原地静止一段、分别绕三个轴缓慢转动，记录动作和方向；看各轴角速度是否有限、符号是否一致。
- 检查当前驱动单位（标准IMU角速度为弧度/秒）、传感器安装方向及车辆轴定义；项目配置将上游FRD转换为算法FLU。不要对已转换数据再转换一次。

### IMU姿态四元数突然翻转，但原始角速度变化不大
- 区分上游姿态消息和原始角速度/加速度；在 `IMU分析.txt` 中找到突变时刻，与Header回退、数据间隔、上游日志逐项对照。
- 四元数 `q` 与 `-q` 表示同一姿态，符号反转不必然是姿态跳变；需要按旋转角比较。项目实际采用的姿态来源以当前配置为准，不能直接把上游姿态当真值。

### 静止时本地惯导位置或航向仍缓慢漂移
- 单纯IMU积分会累积零偏和噪声；先确认启动时静止初始化是否完成、消息时间是否连续、单位与轴变换是否正确。
- 记录漂移随时间的变化，复核传感器固定、温度和振动；不要把静止积分轨迹当作独立真值，也不要单纯调整阈值掩盖漂移。

### 车辆真实朝前走，估计轨迹却朝侧面或反方向
- 检查设备安装朝向、FLU/FRD轴变换、参考车局部轴、各车坐标系和符号，分别做短距离、已知方向的单轴动作；先确认单位和初始姿态。
- 默认纯UWB的X轴沿201至202，并不自动等于车头或地图东向；不要将它直接与车体前向比较。

- 不能。两路来自雷达只说明各自出数；要分别检查 `/livox/lidar` 和 `/livox/imu` 的消息头，再与 `/imu/raw`、`/uwb/range` 比较时间基准，并通过同步链路或共同事件核实。

### `/livox/lidar` 正常，`/livox/imu` 时间却不同或回退
- 两路分开检查Header的首末、相邻间隔、回退和重复；明确是某一条消息的Header，还是点内逐点时间。
- 保存短包、驱动版本和PTP日志；不要用点云Header代替雷达IMU Header，也不要用bag写入时间替代测量时间。

### `/imu/raw` 的Header出现回退、重复或整秒跳变

- 需修复时保存原包、日志及前后消息，复现后再录新包；不要手工排序、改Header或把回退时段当连续惯导输入。

### UWB和IMU的Header日期都像当前日期，是否已经同步？
- 只能说明数值可能在相近时间域。需要检查消息连续、两路真实覆盖时段、时间源及驱动的采样时间定义；必要时用共同物理事件或硬件同步信号验证。
- 首末时间接近、平均频率正确或都显示UTC日期，都不能量化传感器之间的真实同步误差。

### 一路Header是2024年，其他路是2026年或开机秒数
- 分别记录异常盒、具体话题、Header首末和原值；核对设备是否使用绝对时间、开机单调时钟、仿真时间或PTP未同步。
- 优先检查本盒同步链路和驱动时间解释；不要靠加一个猜测常数直接修包。时基不明时不能把不同流Header直接配对。

### bag记录时间和Header相差很多，是网络延迟吗？
- 不一定。记录时间、测量时间可能使用不同的时钟，还受缓存和写盘过程影响。`记录时间−Header` 只能作为排查线索，不能直接当网络延迟或传感器同步误差。
- 先确认每种时间的来源、记录时钟是否被校准及是否回退；可比较同源消息并结合独立时间参考，不用接收时间替代Header做传感器同步验收。

### 三盒同一条UWB消息Header一致，是否就是传感器同步？
- 这只能说明相同消息被记录时其消息头值一致，不能直接证明UWB与各盒IMU、雷达的物理采样同时，也不能证明其他话题的时钟一致。
- 分别核对四类消息的时间源、时间连续性和共同事件，再判断能否用于融合。

### 时间曲线重合或相关性很高，是否就是同步？
- 不一定。若每路单独减去各自首时间，曲线重合只说明时间推进形态相近，可能隐藏固定偏移。
- 查看未分别归零的首末Header、差值来源和共同事件；没有外部共同时间参照时，不能给出真实对时误差。

### PTP恢复后多久能继续录下一包？
- 本盒授时和PTP稳定后，再确认雷达、IMU、UWB均持续出数，然后录新包。三盒分别完成；若中途重新校时、切换源或重启相关服务，应重新核对。
- 已经稳定且没有时间跳变的连续多轮，不需要每轮机械重启PTP。不要在录包中停止或启动时间服务。

### 三条UWB边看起来都有，但 `/cooperative_localization/poses_2d` 没有话题

### 位置在发布，但 `position_valid` 是false
- 先查看三车各自的有效位、输出Header是否推进和三条输入边是否新鲜；检查丢边、输入时间异常、无效距离、三边几何和节点日志。

### 有效位置频率不到10 Hz，或者一会儿有效一会儿无效
- 本次配置输出频率为10 Hz，但可用输出依赖三边测距及历元组成；分别检查每条边的Header跨度、间断、负载和算法日志。
- 当前默认安装配置示例将三边Header最大跨度设为10 ms；这是分组参数。先确认安装YAML与启动日志版本一致，别为了“凑10 Hz”直接放宽阈值。

### 202的位置总在X轴上，203总在Y轴正侧，是不是车没动？
- 默认 `coop_ref_1_relative` 每帧以201当前位置为原点，201指向202的方向为X轴，并对203使用正Y镜像分支。这是相对三角形的坐标约定。
- 201坐标为零、202通常在X轴上是正常几何表达；整体平移或整体旋转时三边不变，默认输出也可能不变。单独移动一辆并观察三条距离及位置变化，需现场安全条件允许。

### 默认结果的 `yaw_valid` 为false，是否是算法故障？
- 纯UWB三边只输出规范相对队形，不提供车辆自身航向；默认结果 `yaw_valid=false` 是预期行为。
- 不应把 `yaw_rad=0` 当成车头朝向，也不能将201→202的方向当作201车辆航向。需要车头方向时，应使用有有效航向的对应算法及坐标定义。

### 三车距离看着对，但地图方向或车头方向不对
- 先看输出 `header.frame_id` 和参考车编号。默认相对三角形轴不是北向、地图东向或车头方向；需要地图坐标时，应有参考车地图位姿和轴向变换。
- 将输出导入规划/显示前，与接收方核对参考点、坐标系、单位、时间和有效位，避免直接把相对位置解释为地图绝对位置。

### 三车几乎排成直线时，位置抖动或突然无效
- 记录同一时段三条距离、Header和实测站位；测量噪声下细长或近共线队形可能使横向位置对小距离变化敏感，也可能出现几何不一致。
- 别用不同时间的三条边凑一个三角形。安全条件允许时，记录不同队形对照；是否有效取决于当前求解器和实际配置，不凭肉眼定义固定合格角度。

### 某辆车位置跳到了另一侧，或画面方向突然反了
- 默认纯UWB对第三车使用固定正Y镜像约定；当真实车辆跨过201—202连线时，显示不会自然保留另一侧的有符号信息。
- 检查是否切换到RTE固定轴输出、参考车或节点编号发生变化，比较原始三边、有效位和每条消息的frame。不要把坐标约定变化直接当成硬件跳变。

### 测得三条距离无法组成三角形，算法没位置
- 用相近Header时刻的1—2、1—3、2—3距离核对：任意两边之和应不小于第三边。测距噪声、遮挡、高度和采样不同步会造成近似不一致。
- 先检查原始三边、时间分组和安装；不要把误差较大的值手工改成可组成三角形。异常包、距离和现场站位一起保留。

### 移动201后，202和203都动了，是不是两辆从车漂移？
- 原点跟随201时，201移动会改变其他车辆相对于201的位置；这可能是正常相对运动。结合单车实际动作和参考车编号判断。
- 如看的是每帧旋转的默认三角形轴，201—202方向变化还会转动坐标轴；如看RTE固定轴，轴定义又不同，不能直接比较数值符号。

### 算法输出与卷尺测得的盒间距离对不上
- 先确认两者比较的是同一时刻、同一对逻辑ID和相同天线参考点。输出坐标需先计算对应两车位置之差的模长；卷尺测的是盒体边缘时要考虑天线位置和高度差。
- 默认输出为二维队形表示，现场高度差或时序不一致会影响直接比较。先录同时段UWB和输出，复核坐标系、单位与有效位。

### 画面在刷新，但位置始终不变
- 检查输出Header是否推进，而不仅是屏幕刷新或话题频率；下游可能重复显示上一帧。确认当前 `position_valid`、订阅话题和网域。
- 默认UWB只能反映相对形状：三车刚体平移或共同转动时距离可不变。要检验变化，可在允许的条件下单独移动一辆并观察原始距离。

### 在线结果偶尔大跳，测距残差却很小
- 保留跳变前后的原始三边、状态和输出。距离拟合好只说明所选位置能解释当时距离，不证明绝对方向、镜像选择或真实位置正确。
- 排查坐标系切换、三边时间、近共线、反射遮挡与参考车重启。带动态位置真值的测试才能定量评估误差。

## 九、可选RTE及坐标转换

### 为什么默认UWB能出位置，RTE话题却没有？
- RTE是独立、可选的算法路径；默认 `uwb_only.launch.py` 不启动它。先确认现场是否已部署并明确启用RTE，不要在已跑通的默认路径上随意切换。
- 真实RTE还需要三辆车各自的本地运动状态和三条UWB边。具体构建、话题与配置见45号、46号参考文档；当前部署状态以各盒实际安装为准。

### RTE状态一直是 `INITIALIZING` 或 `NEED_MORE_MOTION`
- 【RTE融合节点所在机器】先查看 `/cooperative_localization/rte/status`、三车 `node_state`、UWB边和Header；状态话题存在的前提是该链路确已启用。
```bash
timeout 5s ros2 topic echo --once --no-daemon /cooperative_localization/rte/status
timeout 8s ros2 topic echo --once --no-daemon /cooperative_localization/rte/node_state
```
- 静止或信息不足时距离可能无法区分初始关系。当前仓库 `rte_fusion.yaml` 的内部判据为5秒窗口、窗口内运动范围10米；现场安装版可能不同，先以实际节点参数和状态日志为准。这个数值是现有实现判据，不是要求规划必须走某个固定距离，也不能不经验证就放宽。
- 【RTE融合节点所在机器】先用 `ros2 node list` 找到实际节点名；若节点名正好为 `/zju_three_vehicle_rte_node`，可以查看以下参数，再由现场负责人员根据实际条件安排可行运动。
```bash
ros2 param get /zju_three_vehicle_rte_node window_duration_ms
ros2 param get /zju_three_vehicle_rte_node minimum_initialization_motion_span_m
```

### RTE显示 `STALE`，之前还能工作
- 查三车NodeState、UWB的Header是否推进，确认输入不是只显示旧值；看每车ID、边、发布频率和网络。
- 源码示例的节点状态和测距超时分别为300 ms和500 ms，实际以安装运行参数为准；它们是算法输入时效参数，不是同步精度指标。

### RTE显示 `AMBIGUOUS`、`NOT_CONVERGED` 或 `RESIDUAL_REJECTED`
- 先记录完整状态JSON、三条测距、各车NodeState及动作。`AMBIGUOUS`提示可能有多种位置关系；`NOT_CONVERGED`提示当前求解未收敛；`RESIDUAL_REJECTED`提示残差检查未通过。
- 核对时间、有效边、运动信息和遮挡；状态含义不等于唯一根因。不要仅通过抬高阈值把状态改成有效，也不要为了通过测试要求车辆盲目大幅运动。

### RTE状态为 `TRACKING`，但位置可能仍是错的？
- 可能。状态表示内部计算通过当前检查，不等于位置已达精度要求。记录 `initialized`、`active_edges`、`sample_counts`、`rms_m`、不确定度、每车有效位及Header。
- 直线起步或测距几何不足时可能出现镜像/错误初始关系，残差较小也可能选错。与独立真值或已知实际队形核对；`initialized=true`也只表示曾完成初始化。

### RTE只有两辆状态，或三车全是同一个ID
- 检查三辆本地节点是否分别运行、是否实际发布、DDS本机隔离与桥接是否按部署配置接通。`NodeState.node_id` 要与UWB中的逻辑ID一致。
- 逐条核对 `NodeState.header.frame_id`，该RTE配置示例为 `rte_odom_1`、`rte_odom_2`、`rte_odom_3`；按实际 `local_frame_prefix` 判断，不将三盒设置成相同ID。

### RTE节点已启动，但NodeState被忽略
- 查看NodeState的 `node_id`、`valid`、Header是否递增、frame是否与 `local_frame_prefix + node_id` 一致，以及UWB和NodeState是否属于同一时间域。
- 检查实际节点参数和上游日志，尤其是上游重启或本地里程计原点改变；单次看到一帧不代表持续有效。

### RTE在实车上越走越偏，IMU航位推算也漂移
- 检查初始化是否正确、原始IMU时序、轴变换、单位、静止起步和UWB边质量，再查本地里程计的有效性与frame。
- 当前RTE持续修正的是三车相对变换输出，不会把修正回灌到各车本地惯导。不要把本地IMU积分输出当作真实轨迹；需要独立参考轨迹评价误差。

### RTE结果突然镜像、方向翻转或重启后方向不同
- 判断是否发生了不同的初始候选解、本地里程计会话重启或输入时钟跳变。对比新旧会话的Header、原点、frame、各车位置和原始测距。
- 坐标转换器只做坐标变换，不修正错误RTE初值。上游会话重置后按46号文档协调重启RTE与适配器，不把两段任务轨迹直接拼接。

### RTE坐标网页有图，但没有实时结果
- 先看是否打开了 `--demo` 几何演示或直接打开静态HTML；这不是实盒实时输出。实机模式需要实际RTE位姿和参考车NodeState，且相关ROS环境及域正确。
- 按46号文档核对网页的“坐标数据”、输入话题、frame与有效位；出现“等待/不可用”时查上游，不手工填补坐标。

### 默认UWB、RTE原始输出和网页固定轴输出为什么不一样？
- 看 `frame_id`：默认 `coop_ref_1_relative` 每帧以201→202为X；RTE原始 `coop_rte_1_local` 用201本地初始轴；转换器输出 `coop_rte_1_relative_fixed` 将首次有效的201→202方向固定为X。
- 这几套轴表达不同，不能直接按坐标数值逐项比较；比较前统一参考时刻、坐标变换和有效状态。变换不自动提供地图北向，也不代表动态精度通过。

### 网页持续刷新，但坐标显示过期或无效
- 检查上游Header是否持续前进和 `position_valid`，并核对参考车NodeState能否按Header配对；定时刷新不是新测量。
- 46号文档规定适配器在无新有效输入约0.5秒时撤销有效位。应检查该适配器实际版本，不把此时长当成传感器同步指标。

- 【201】确认当前仍在201，分别测试到202、203的SSH，查 `ssh-add -l`、远端 `/home/firefly/sensor_test/` 权限与磁盘。

- 确认终端是否仍在运行、是否处于等待远端、写盘、压缩或下载；录制180秒后压缩传输还需时间。检查打印的实验目录和 `box*.log`。

### 某个压缩包很小，或者 `metadata.yaml` 里消息数为0
- 先查该包实际采了什么、录包日志和相应ROS环境。空IMU包可能仍带有metadata；小包不自动代表损坏，但消息数为0就是没有录到该路。
- 不通过重跑分析程序制造数据；修复对应驱动/订阅后另录新包，并保留故障包及日志。

### 三盒各有UWB包，是否等于有三次独立测量？
- 联合包的每盒UWB目录可能记录共享的同一话题；同一个 `src_id/target_id/header` 被不同盒记录，不是三次独立测距。
- 按盒、逻辑ID、方向和Header核对数据来源。各盒车载IMU和Livox仍要分别检查，不能用共享UWB代替。

### 录了180秒，数据时长和帧数不完全一致
- 计算每个话题的实际Header跨度及消息数，考虑启动/停止过程、频率、数据丢失和工具观测方式。历史脚本曾出现串行停止导致Livox更长；当前版本需按本轮日志核对。
- 差几秒与只录到几秒不是同一问题；不要仅根据文件大小或bag的记录时间推断同步。

### 传回电脑后解压失败、缺文件或中途断传
- 保留原压缩包和源端文件，先核对文件大小、压缩包完整性、磁盘余量和传输日志；有条件时比对两端 `sha256sum`。
- `.db3` 可能有多个分片，必须连同 `metadata.yaml` 和采集日志完整保留。不要把半包覆盖正常备份，也不要只留分析图。

### 多轮实验同名或不知道哪个才是最新包
- 三盒脚本默认自动生成轮次，不必手动反复输入；以终端打印的最终路径、时间和本轮备注确认。各盒系统时钟异常时，文件名时间不保证真实采集时间或先后。
- 本地分析脚本会打印自动选中的目录，且会跳过不符合其筛选条件的轮次。若选择不符合预期，先检查解压与目录完整性，再按21号或31号指定目标，不要误读旧报告。

### 当前三盒联合包为什么没有在线位置或相机？
- `record_three_boxes.py` 配套单盒脚本记录UWB、车载IMU、Livox点云及内置IMU；不因为算法或相机在运行就自动录入其他话题。
- 若需在线输出，按21号第7节单独录201的 `/uwb/range` 与 `/cooperative_localization/poses_2d`，或使用支持 `--include-poses` 的IMU/UWB录包模式。相机话题和录制方式先按实际驱动确认。

### 重复启动录包、占用磁盘或录到多份数据
- 【201及相关盒】核对正在运行的录包进程、终端与输出目录，确认哪一轮有效；不要同时运行两套对同一设备的高负载录包而不记录。
- 在对应启动终端正常结束不需要的录制，保留已有文件和日志；不要直接删除其他人的进程或未备份的实验数据。

### 执行分析后返回提示符，是已完成还是后台还在跑？
- 当前脚本按盒、按步骤等待子程序结束；正常运行时显示“开始/运行中/成功或失败”，最终打印总结果并返回shell。检查实际版本及退出信息。

### 分析脚本报 `cooperative_interfaces` 找不到或消息定义过旧
- 【本地Ubuntu】在同一终端加载 `/opt/ros/humble/setup.bash` 和项目对应install，再检查消息类型；记录完整错误。

- 当前脚本要求包含 `header、src_id、target_id、rolling、distance` 的匹配消息定义。接口版本不匹配先按31号文档构建/加载正确版本；不因环境缺包就判定原始录包损坏。

### 联合时间报告说成功，但缺一盒或缺一路
- 程序执行成功只表示它完成对可见输入的统计；联合时间报告可能只列实际存在的流。先逐盒检查 `uwb/metadata.yaml`、`imu/metadata.yaml`、`livox/metadata.yaml` 中四个计划话题及消息数。
- 缺失的传感器不能通过其他盒同名话题或分析图片补齐。若是计划外未采，记录“未采”；若本应采集，定位原因并补录。

### 报告中某个话题频率为0或显示1970、2262等异常日期
- 先看对应话题消息数量和实际Header。0消息时异常日期可能是空包占位；非零消息的零Header或不同时间域需进一步查驱动与授时。
- 不能仅按文件名或bag记录时间推断真实测量时间；保留原始值、设备日志和生成分析版本。

### 三盒的Header时间区间没有交集
- 对每盒四类流分别看首末Header、时基、采样时段和回退；确认是否真为同一轮、同一时段，以及三盒启动/授时状态。
- 没有有效共同时间区间时可以单独分析出数和数值质量，但不能直接把它们配对为同一时刻的三车融合输入。

### 联合时间详细表里有“记录时间回退”，这和Header回退一样吗？
- 不一样。分别查看“消息时间回退数”和“记录时间回退数”：前者针对该话题消息头，后者针对bag记录时间。先以原始记录顺序核实。
- 记录钟的跳变不能自动证明传感器Header回退；反过来Header回退也不能自动归咎录包程序。结合驱动、校时和录包日志查原因。

### 生成了大量图，应该先看哪些文件？
- 依次打开每盒的 `分析执行结果.md`、各bag的 `metadata.yaml`、`联合时间验收.md` / `联合时间详细统计.csv`、`IMU分析.txt`、`雷达分析.txt`、`uwb/UWB测距分析.md` 和测距曲线。
- 重点找失败项、缺消息、Header零值/回退/重复、长间断、三边、无效点和静止值。21号第6.3.2节逐项给出看哪里；记录时间相关字段仅作为辅助诊断。

### 想看三盒Livox三维画面，应该怎么做？
- 【本地Ubuntu工程根目录】先完整解压各盒Livox包，运行以下命令，程序会打印所选实验目录：
```bash
python3 tools/visualize_livox_bags.py
```
- 查看该轮 `livox_visualization/README.md`、`livox_overview.png`、各盒 `box*_livox_3d.html` 和 `点云可视化统计.csv`。这是代表窗口的本地雷达坐标可视化，不是整段地图或融合定位结果。

### 在线输出录到了，但离线回放没有位置
- 先区分“打开原包中当时的在线输出”和“用现有算法重新处理原始UWB”。检查包里是否同时有 `/uwb/range` 和 `/cooperative_localization/poses_2d`、消息数、域及接口版本。
- 项目文件、install版本和实际运行节点必须对应；回放步骤看31号与41号，不要把录包时原有输出与当前算法新算输出混成一次结果。

### 回放时与实时设备相互干扰，或者显示了两套结果
- 先停止/隔离与回放相同话题的实时发布者，在独立ROS域或离线环境按文档启动；确认 `/use_sim_time` 和 `/clock` 配置与这次回放一致。
- 分别查看话题发布者和Header；不要让回放消息在不知情的情况下进入真实规划控制链路。

### 静止时位置很稳定，可以宣布达到亚米级吗？
- 稳定只说明该条件下输出波动较小。实际精度需要独立参考，例如RTK、全站仪、动捕或准确记录的天线参考点；无参考时不能给出绝对误差。
- 动态、不同距离、遮挡和运动方式应分别采集并有对应真值；仿真结果和实测结果分开统计。

### RTE残差很小或状态正常，能作为定位精度吗？
- 不能。测距残差衡量估计距离与测量距离的符合程度；镜像或方向错误时也可能残差小。状态、有效位和残差是诊断信息。
- 用独立真值按同一时间与坐标系比较相对位置；无真值时如实记录输出连续性、测距与状态，不将其表述为定位误差。

### 仿真中低于1米，现场实测也应低于1米吗？
- 仿真输入、测距误差、初始化与现场不一定相同；视觉纹理、雷达特征、遮挡、振动和时间/标定都会影响实际输出。
- 先核查实车传感器是否真的输出相应运动估计，再用同口径参考轨迹评估。报告中VIO/LIO误差档位是仿真输入模型，不代表现场测得的前端精度。

## 十二、异常记录、交接和恢复

### 出问题时，至少保留什么？
- 记录轮次、盒号/逻辑ID、时间、实际站位与动作、现象、预期结果、发生概率、使用的节点、topic、frame、运行命令及安装版本；系统时间或同步状态变化也注明。
- 保留原始总包、三盒子包、各 `metadata.yaml`、全部 `.db3` 分片、`box*.log`、启动终端日志、关键参数和必要的现场照片。根据问题类型补充 `分析执行结果.md`、CSV和曲线。
- 输出与输入至少覆盖异常前后一段；如果现场没有发生可辨别的动作和独立真值，注明这一点，便于后续解释。

### 需要设备维护方协助排查，发哪些材料？
- 网络/驱动：故障盒号、设备供电和连接、启动命令、进程状态、终端原文及对应时间段日志。
- 时间：原始bag及metadata、故障话题的Header回退/跳变具体时刻、驱动与PTP日志、授时源和启动顺序；明确 `/imu/raw`、`/livox/imu`、`/livox/lidar` 和 `/uwb/range` 中哪一路异常。
- 相机：设备节点、三路实际画面、格式和频率、V4L2/ROS话题、时钟与标定信息；不要发送包含密码、私钥或无关个人信息的文件。

### 需要算法或规划控制人员协助，发哪些材料？
- 提供原始UWB及在线输出包、三车实际站位/动作、逻辑ID与盒号对应、坐标系、参考车、有效位、异常时间点和配置版本。
- 若是RTE，还提供三车NodeState、status、UWB和当前RTE配置；若涉及VIO/LIO，提供其实际输出及对应相机/雷达时间与标定信息。不要把模拟轨迹当成实测轨迹。

### 修复后怎么确认问题真的解决？
- 先保持除故障项外的条件尽量一致，重新采一段并记录新的轮次；比较故障前后同一话题、同一字段、同一动作及时间范围。
- 依次核对出数、Header、三边、有效位和结果。需要证明定位精度时加入独立参考；只修改阈值或只看状态变绿不足以证明问题解决。

### 调试中途有人重启盒子、IMU或改了时间，该怎么继续？
- 记录发生的盒、时间和操作；检查该盒UWB、IMU、雷达及PTP状态和消息头是否连续。
- 本地惯导会话或RTE坐标系可能改变，原始旧包保留并开始新一轮，不直接拼接当作连续轨迹。确需跨会话对齐，应使用独立参考和明确的变换。

### 某项暂时查不出原因，怎样描述而不是猜结论？
- 按“哪盒、哪个话题/节点、哪个时刻、看到什么、已排除什么、保留了哪些文件”记录；把直接观察与推测分开。
- 例如“202盒 `/imu/raw` Header发生回退，具体时间见CSV；已记录同步和驱动日志，原因待确认”，不要直接写成“录包程序导致”或“硬件损坏”。

## 十三、GNSS、授时来源与环境

### 室内没有GNSS定位，是不是UWB和所有传感器都不能用？
- 先区分GNSS定位、盒端授时和UWB测距。室内卫星信号弱时GNSS可能无定位；当前三盒室内测试按21号文档核对 `pps_source: 1` 和UWB授时链路。
- 是否必须启动某个驱动取决于本盒时间同步和设备依赖，不能把“同步链路需要”直接表述成“相机、IMU和雷达必须靠UWB才能产生数据”。分别查每路实际出数与Header。

### `gnss_uwb` 启动后没有连续的UWB RMC
- 【故障盒】保留启动终端日志，检查驱动是否重复启动、UWB串口占用、设备供电、节点配置和 `pps_source`；按照21号第2节核对。
- RMC没有连续输出时，先查该盒授时源和驱动，不直接开始需要统一时间的联合录包。只有一个终端的显示不能代替三盒分别检查。

### `pps_source` 不是本轮约定的值，怎样处理？
- 【故障盒】先只读核对安装目录中的参数，以及实际运行进程和启动日志；室内三盒UWB PPS示例为1，户外其他授时方案以现场约定为准。
```bash
grep --line-number 'pps_source' /home/firefly/imu_ws/install/gnss_uwb/share/gnss_uwb/config/params.yaml
```
- 需要调整时按21号第2节备份并由设备负责人员处理，确认后重新启动相关驱动；授时稳定后再按每盒PTP流程检查雷达。录包期间不要切换授时源。

### 户外 `/gnss/fix` 没消息，或有消息但没有有效定位
- 【实际安装GNSS的盒】先检查天线、视野、驱动和实际话题；不是每盒都保证有GNSS。观察消息状态和持续输出，而不是只看话题存在。
```bash
timeout 8s ros2 topic echo --once --no-daemon /gnss/fix
```
- 具体状态码、质量字段和坐标含义以该消息类型与设备文档为准。室内或遮挡环境接收条件不同，不能把单次无定位自动归因于协同算法。

### GNSS坐标跳变或轨迹与实车不一致
- 检查定位状态、天空遮挡、天线安装和杆臂、坐标参考、单位和时间；比较连续段而不是只看一条消息。
- 如果要把GNSS/RTK作为定位真值，还需确认天线参考点、基准、解算状态、精度及与车辆测量点的外参；普通GNSS数值不能自动当作亚米级真值。

### 系统显示时间是对的，但传感器Header仍不对
- 分别读取UWB、车载IMU、雷达点云和雷达内置IMU的Header；系统墙钟正确不保证每个驱动的时间源、PTP链路或传感器内部时钟已同步。
- 对照各盒授时和PTP日志，明确是某一路、某一次重启还是整机发生跳变；不要只调整显示时区或拿系统时间覆盖消息头。

### 卫星时间可用，但三盒UWB相对定位仍无效
- 默认位置依赖三条有效车间测距及其时间分组，不会因为GNSS有定位就自动补齐缺失UWB边。
- 按UWB和默认在线定位章节分别核对边、ID、距离、Header、算法日志及 `position_valid`；GNSS是否参与某条其他链路，以实际启动配置为准。
