# 整个工程调用关系

本文说明当前工程的文件分层、启动入口、ROS 2 回调、C ABI 边界和核心算法调用。阅读时先看第 2、3、4 节，再按需要进入具体算法文件。

当前实物最小实现是：

~~~text
三车本地 IMU
  -> 三个 zju_local_inertial_node
  -> 三车 NodeState
  -> 参考车 zju_cooperative_fusion_node
三车 UWB 测距
  -> 参考车融合节点
  -> CooperativePose2DArray
~~~

点云、视觉、SLAM、GNSS 距离兜底均是可选链路，默认不加入这条最小链路。

## 1. 先区分三个“程序层次”

| 层次 | 作用 | 是否依赖 ROS 2 | 当前用途 |
| --- | --- | --- | --- |
| `src/core` | 惯导、测距、分布式修正、质量和拓扑算法 | 否 | 算法本体 |
| `src/api/c_api.cpp` + `include/zju_coop/c_api.h` | 把 C++ 算法包装成稳定 C ABI | 否 | ROS 2/外部程序的唯一算法接口 |
| `ros2/*` | ROS 2 消息、参数、话题、启动和传感器适配 | 是 | 盒端、仿真、Gazebo |

因此 ROS 2 节点不是另一套滤波算法。它们负责：

1. 订阅 ROS 2 消息；
2. 检查坐标系、时间戳、编号和数值；
3. 把字段填入 `zju_coop_*` C ABI 结构；
4. 调用算法库；
5. 把算法输出重新填入 ROS 2 消息。

## 3. 编译依赖关系

### 3.1 原生算法库

根目录 [CMakeLists.txt](../CMakeLists.txt) 依次生成：

~~~text
src/core/*.cpp + src/config + src/protocol
  -> zju_coop_core          静态库，只给工程内部使用

src/api/c_api.cpp + zju_coop_core
  -> libzju_coop.so         对外共享库，只导出 c_api.h 的 C 符号

src/apps/*.cpp + zju_coop_core + libzju_coop.so
  -> zju_coop_online        UDP 在线程序
  -> zju_coop_replay        ZJLG 日志重放程序
  -> zju_coop_self_check    SDK 自检程序
~~~

ROS 2 节点不链接 `src/core` 的私有头文件，而是通过 `ZJU_COOP_SDK_ROOT` 找到：

~~~text
${ZJU_COOP_SDK_ROOT}/include/zju_coop/c_api.h
${ZJU_COOP_SDK_ROOT}/lib/libzju_coop.so
~~~

典型构建顺序：

~~~bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=ON
cmake --build build -j"$(nproc)"
cmake --install build --prefix stage/zju_coop

colcon build --base-paths ros2 --cmake-args \
  -DZJU_COOP_SDK_ROOT="$PWD/stage/zju_coop"
~~~

`stage/zju_coop` 必须与目标机架构一致。给 RK3588/aarch64 盒子部署时，`libzju_coop.so` 和 ROS 2 节点必须用 aarch64 编译，不能把 x86_64 的库直接复制过去。

### 3.2 ROS 2 包依赖

~~~text
cooperative_localization_msgs

cooperative_interfaces

zju_coop_ros2

zju_coop_perception

zju_coop_bringup / zju_coop_gazebo

~~~

## 4. ROS 2 运行总图

~~~text
传感器驱动或仿真器
  ├─ sensor_msgs/msg/Imu
  ├─ cooperative_localization_msgs/msg/NodeState（跨车共享）
  ├─ cooperative_interfaces/msg/UwbRange
  ├─ sensor_msgs/msg/PointCloud2（本机可选）
  └─ sensor_msgs/msg/Image（本机可选）
             │
             ▼
ROS 2 适配节点
  ├─ zju_local_inertial_node
  │    └─ 单车 Engine + CooperativeInertialEkf(仅一个节点) + InertialEskf15
  └─ zju_cooperative_fusion_node（仅参考车启动）
       └─ DistributedFusion2D
             │
             ▼
输出
  ├─ /cooperative_localization/node_state
  ├─ /cooperative_localization/poses_2d
  └─ /cooperative_localization/feedback/poses_2d（参数开启时）
~~~

盒端启用 `use_localhost_imu_bridge:=true` 时，`zju_local_inertial_node` 与
`zju_node_state_local_sender` 在 `ROS_LOCALHOST_ONLY=1`，
`zju_node_state_shared_relay` 与融合节点在 `ROS_LOCALHOST_ONLY=0`：

~~~text
/imu/raw（本机DDS） -> local_inertial -> node_state_local（本机DDS）
  -> 127.0.0.1 校验数据报 -> node_state_shared_relay
  -> /cooperative_localization/node_state（共享DDS）
~~~

回环包只承载ROS序列化后的NodeState，并校验魔数、版本、长度、node_id和CRC；
它不转发IMU、雷达或RGB，也不监听外部网卡。

这里有两个容易混淆的“15维”概念：

| 路径 | 内部状态 | 当前是否为 ROS 2 最小实现 |
| --- | --- | --- |
| 每车本地惯导 | 一车 15 维误差状态 `[δp, δv, δθ, δbg, δba]` | 是；每辆车各自维护 |
| 集中式惯导 | 三车联合 `15N`，三车即 45 维，并保留交叉协方差 | 否；仅 `zju_coop_online/replay` 的惯性配置回归路径 |
| 分布式修正 | 每个非参考车 2 维 `[δe, δn]` | 是；参考车融合节点当前使用 |

本地惯导的零偏字段存在于 15 维状态中，但盒端本地节点没有本地位置观测更新，因此零偏通常只按初值传播。集中式 `CooperativeInertialEkf` 收到测距后可通过 15N 误差注入更新零偏；分布式 `DistributedFusion2D` 不估计零偏。

## 5. 本地惯导节点调用链

入口文件：[local_inertial_node.cpp](../ros2/zju_coop_ros2/src/local_inertial_node.cpp)。每车启动一个实例，实例只持有本车 SDK 句柄。

~~~text
main()
  -> rclcpp::init()
  -> LocalInertialNode 构造
       -> 读取 node_id、初始位置/速度/四元数/零偏、频率和开关
       -> zju_coop_node_initialization_init()
       -> zju_coop_config_init()
       -> zju_coop_create()                 建立单车 Engine
       -> zju_coop_inertial_node_initialization_init()
       -> zju_coop_inertial_config_init()
       -> zju_coop_configure_inertial()      启用单车15维惯导
       -> 创建 IMU 订阅、可选点云/图像订阅、NodeState发布定时器
  -> rclcpp::spin()
~~~

### 5.1 `on_imu()` 的逐层调用

~~~text
ROS executor 收到 sensor_msgs/msg/Imu
  -> IMU subscription lambda
  -> on_imu(message)
       -> stamp_ns(header.stamp)
       -> SensorTimeBridge 映射接收时刻
       -> 拒绝零时间、回拨、超前/过期样本
       -> 填 zju_coop_imu_packet_t
       -> zju_coop_push_imu(handle, packet, result)
            -> c_api.cpp: C结构校验和异常隔离
            -> Engine::push_imu()
                 -> CooperativeInertialEkf::push_imu()
                      -> 找到 packet.node_id 对应的 InertialEskf15
                      -> InertialEskf15::push_imu()
                           -> 首帧建立时间基线
                           -> 后续帧用实际时间戳计算 dt
                           -> 中值角速度/比力积分
                           -> 四元数姿态传播
                           -> 15×15 Phi/Qd 协方差传播
       -> 仅对 BASELINE_ESTABLISHED / PROPAGATED 记录时间桥锚点
       -> 时间回退、时间窗失配或 INTERVAL_REJECTED 时锁存故障
       -> 锁存后停止解算和 NodeState 发布，修复上游时间后重启节点
~~~

`InertialEskf15::push_imu()` 的入口判断顺序是：节点编号、`valid`/有限值、`frame_id`、重复包、时间递增、时间间隔范围。时间戳异常时不盲目用 `0.001 s` 代替；SDK 按真实时间戳算 `dt`，长间隔内部只建立新基线，盒端 ROS 节点则锁存故障并停算、停发，避免把缺失运动后的状态继续标成有效。

### 5.2 20 Hz NodeState 输出

IMU 回调频率和状态输出频率相互独立：

~~~text
IMU 约 1000 Hz
  -> 每帧都进入 on_imu() 和本车15维传播

publish_timer_（默认 20 Hz）
  -> publish_state()
       -> zju_coop_get_node_state()
       -> 读取当前名义位置、速度和姿态
       -> 填 NodeState.msg
       -> 发布 /cooperative_localization/node_state
~~~

定时器不会每 50 ms 重新积分 50 帧；积分已在每个 IMU 回调中完成。定时器只取当前快照，且相同 `timestamp_ns` 不重复发布。

### 5.3 本地节点的可选输入

参数 `enable_point_cloud_input`、`enable_camera_input` 默认 `false`。打开后本地节点分别订阅 `PointCloud2` 和 `Image`，执行时间、frame、尺寸、字段和字节长度检查，再调用：

~~~text
zju_coop_push_point_cloud()
zju_coop_push_camera_image()
~~~

当前 C ABI 会确认原始输入格式，但不会把点云或图像送入 15 维惯导，也不会自动改变 NodeState。真正的点云/视觉定位在 `zju_coop_perception` 中是独立节点。

## 6. 参考车融合节点调用链

入口文件：[cooperative_fusion_node.cpp](../ros2/zju_coop_ros2/src/cooperative_fusion_node.cpp)。默认只在参考车启动，`reference_node_id` 默认 1。

~~~text
main()
  -> rclcpp::init()
  -> CooperativeFusionNode 构造
       -> 读取 node_ids、reference_node_id、range_std、超时和反馈开关
       -> zju_coop_config_init()
       -> zju_coop_distributed_create()      建立 DistributedFusion2D
       -> 创建 NodeState/UWB 订阅
       -> 创建 poses_2d 定时器
  -> rclcpp::spin()
~~~

### 6.1 `on_node_state()`

~~~text
NodeState.msg
  -> on_node_state(message)
       -> 检查 frame_id == common_enu
       -> 检查 node_id 属于配置集合
       -> 检查 stamp 非零且对本车严格递增
       -> 参考车首帧建立 UWB_SYSTEM_TIME 锚点
       -> SensorTimeBridge 计算 receive_timestamp_ns
       -> 填 zju_coop_node_state_t
       -> zju_coop_distributed_push_node_state()
            -> c_api.cpp 翻译结构
            -> DistributedFusion2D::push_node_state()
                 -> 检查 valid、有限值、四元数归一化和时间窗口
                 -> 保存本车历史（最多固定长度）
~~~

NodeState 的位置是公共 ENU 下的绝对位置，不是相对参考车位置；它的作用是给参考车提供每车航位推算基线。参考车在测距时刻从历史中取两端状态，必要时线性插值或有限外推。

### 6.2 `on_uwb_range()`

~~~text
UwbRange.msg（当前测试消息）
  -> on_uwb_range(message)
       -> 检查 src_id/target_id、距离和时间
       -> 取参考车时间桥的 receive_timestamp_ns
       -> 填 zju_coop_range_packet_t
       -> zju_coop_distributed_push_range()
            -> DistributedFusion2D::push_range()
                 -> 找到测距时刻两端 NodeState
                 -> 计算基线位置和预测距离
                 -> 构造距离残差与二维雅可比
                 -> 计算创新方差和 NIS
                 -> NIS 超门限：只记录拒绝，不改状态
                 -> 通过：更新非参考车二维修正量和协方差
~~~

当前分布式状态为每个非参考车 `[delta_e, delta_n]`，参考车修正固定为零。它会修正相对平面位置，不会从 UWB 直接估计单车航向或 IMU 零偏。

### 6.3 `publish_pose()`

~~~text
publish_timer_（默认 10 Hz）
  -> current_time_ns()
  -> zju_coop_distributed_get_pose2d_v2()
       -> 取当前各车 NodeState 基线 + 二维修正
       -> 输出参考车为原点、轴向与 common_enu 平行的 Pose2D 快照
  -> 填 CooperativePose2DArray.msg
  -> 发布 /cooperative_localization/poses_2d
  -> enable_follower_feedback=true 时
       -> 同一消息再发布 /cooperative_localization/feedback/poses_2d
~~~

`position_valid` 需要有效的本车状态、参考车状态和近期可用测距路径；`yaw_valid` 只表示 NodeState 中的航向时间和数值有效，不表示 UWB 修正了航向。

## 7. 核心算法文件与内部数据流

### 7.1 `Engine`：输入总闸门和模式选择

文件：[engine.hpp](../src/core/engine.hpp)、[engine.cpp](../src/core/engine.cpp)。主要职责：

~~~text
Engine::validate_config()
  -> 节点编号、参考车、边数、状态维数和资源上限

Engine::configure_inertial()
  -> 首个输入前一次性启用 CooperativeInertialEkf

Engine::push_imu()
  -> 时间窗口检查 -> 惯性滤波器

Engine::push_range()
  -> 端点/距离/时间/重复/乱序检查
  -> DegradationMonitor 质量统计
  -> 正常、降权、暂缓或拒绝
  -> 惯性模式走 CooperativeInertialEkf
  -> 未启用惯性时走 RangeEkf

Engine::step(now_ns)
  -> 淘汰超时边
  -> 分析刚性/可达性/可观性
  -> 组装定位、网络和观测的一致快照
~~~

`step()` 不读取传感器，也不凭空推进 IMU；它只处理质量窗口、边超时和输出快照。

### 7.2 `InertialEskf15`：单车 15 维误差状态

文件：[inertial_eskf15.hpp](../src/core/inertial_eskf15.hpp)、[inertial_eskf15.cpp](../src/core/inertial_eskf15.cpp)。误差状态顺序为：

~~~text
[δp_x, δp_y, δp_z,
 δv_x, δv_y, δv_z,
 δθ_x, δθ_y, δθ_z,
 δbg_x, δbg_y, δbg_z,
 δba_x, δba_y, δba_z]
~~~

名义状态另存位置、速度、FLU->ENU 四元数、陀螺零偏和加速度计零偏。传播过程：扣除当前零偏，取相邻 IMU 中值，按 `dt` 用四元数传播姿态，旋转比力到 ENU 并加入重力，再传播 `P`。零偏只有在后续观测更新注入误差时才会改变。

### 7.3 `CooperativeInertialEkf`：集中式 15N 回归路径

文件：[cooperative_inertial_ekf.cpp](../src/core/cooperative_inertial_ekf.cpp)。它为每车保留一个 `InertialEskf15`，并维护完整 `15N x 15N` 协方差：

~~~text
每车 IMU
  -> 只传播该车名义状态
  -> 同时传播该车协方差行/列和交叉协方差

一条测距
  -> H 只在两端位置块非零
  -> K=P H^T / (H P H^T + R)
  -> 保留交叉协方差对所有车辆的影响
  -> 注入每车15维误差（包括零偏）
~~~

三车时状态维数是 45，而不是因为当前 NodeState 只传位置/速度/姿态就变成 6 维；NodeState 是跨车低带宽接口，内部集中式滤波仍可保留完整零偏和协方差。当前 ROS 2 参考车不走这个类，而走下一节的分布式修正器。

### 7.4 `DistributedFusion2D`：当前 ROS 2 最小修正路径

文件：[distributed_fusion2d.cpp](../src/core/distributed_fusion2d.cpp)。它不复制各车 15 维协方差，只保存：

~~~text
每个非参考车：二维修正 [delta_e, delta_n]
协方差：2(N-1) x 2(N-1)
各车 NodeState 历史：位置、速度、姿态、时间
每条边：最近测距时间、最近接受时间和新鲜度
~~~

测距更新的几何量是：

~~~text
predicted_range = ||p_target(t_range) - p_source(t_range)||
innovation      = measured_range - predicted_range
NIS             = innovation^2 / innovation_variance
~~~

通过 NIS 后只修正非参考车平面位置；参考车为原点，姿态由 NodeState 直接输出。三车从“初始相对摆放 + 本地航位推算”得到基线，再由 UWB 距离逐步压缩平面位置误差。

### 7.5 `RangeEkf`：仅测距兼容路径

文件：[range_ekf.cpp](../src/core/range_ekf.cpp)。这是 `Engine` 未调用 `configure_inertial()` 时的兼容滤波器，状态为非参考车的二维位置和速度 `[x,y,vx,vy]`。它用于 UWB-only 的原生/回归测试，不等于当前 ROS 2 的 `DistributedFusion2D`。

### 7.6 质量与拓扑

~~~text
DegradationMonitor
  -> 统计每条边的有效率、频率、NLOS比例、NIS拒绝和最近时间
  -> NORMAL / DEGRADED / SUSPENDED / REJECTED / RECOVERING
  -> 决定正常融合、降权、暂缓或拒绝

rigidity.cpp
  -> 根据当前活动边构造二维距离约束的刚性/可观性判断

Engine::step()
  -> 输出 connected、observable、active_edge_count 和 reason_mask
~~~

质量状态不是单包的 `valid` 字段；单包可以有效但因 NIS 被拒绝，长期窗口也可能因此进入退化状态。

## 8. ROS 2 消息、话题和坐标系

### 8.1 共享消息

| 消息 | 方向 | 主要字段 | 作用 |
| --- | --- | --- | --- |
| `sensor_msgs/msg/Imu` | 传感器 -> 本车节点 | `header.stamp`、角速度、比力、可选姿态 | 本车 15 维传播 |
| `cooperative_localization_msgs/msg/NodeState` | 各车 -> 参考车 | `node_id`、ENU 位置/速度、FLU->ENU 四元数、`valid` | 跨车航位推算基线 |
| `cooperative_interfaces/msg/UwbRange` | UWB -> 参考车 | `header.stamp`、`src_id`、`target_id`、`distance` | 正式测距输入 |
| `cooperative_interfaces/msg/GnssPosition` | 三车GNSS -> 参考车 | `header.stamp`、`node_id`、status、经纬高、协方差 | 默认关闭的GNSS测距兜底 |
| `cooperative_interfaces/msg/Identity` | 本车身份 -> 共享链路 | `node_id`、`uwb_id` | 设备身份核对；当前算法不订阅 |
| `cooperative_localization_msgs/msg/CooperativePose2DArray` | 参考车 -> 外部模块 | `reference_node_id`、每车 x/y/yaw 和有效位 | 协同定位结果 |

当前融合节点已直接订阅 `cooperative_interfaces/msg/UwbRange`，ROS适配层逐字段转换后调用核心滤波接口。实盒仍须确认 `src_id/target_id` 的逻辑编号语义、距离单位和输入QoS。

### 8.2 话题和 QoS

节点内使用相对话题名，launch 通过 namespace/remap 形成实际名称：

| 节点内名称 | 默认实际名称/作用 | QoS |
| --- | --- | --- |
| `imu` | 每车本地 IMU 输入 | `SensorDataQoS` |
| `node_state` | `/cooperative_localization/node_state` | best effort，深度 5 |
| `uwb_range` | `/uwb/range` 或 remap 后的范围话题 | best effort，深度 20 |
| `poses_2d` | `/cooperative_localization/poses_2d` | reliable，深度 1 |
| `feedback_poses_2d` | `/cooperative_localization/feedback/poses_2d` | reliable，深度 1 |

同名 `navcore_node` 只在外部传感器驱动的三个盒子之间可能重复；本仓库的仿真本地节点由 launch 显式命名。是否能互相看见由 `ROS_DOMAIN_ID`、RMW 和 `ROS_LOCALHOST_ONLY` 决定，不由算法决定。

### 8.3 坐标系

~~~text
common_enu
  +x East，+y North，+z Up；三车共用，NodeState 的位置/速度所在坐标系

vehicle_N/base_link 或 imu_link（车体 FLU）
  +x Forward，+y Left，+z Up；IMU 瞬时量和姿态外参的车体坐标系

coop_ref_N_enu
  原点为参考车同历元位置，轴向与 common_enu 平行；Pose2D 输出坐标系

vehicle_N/base_link/front_lidar、front_camera
  传感器外参坐标系；只在点云/视觉链路中使用
~~~

核心滤波器只计算数值状态，不自动发布完整 TF 树。当前 `CooperativePose2DArray.header.frame_id` 表示协同结果参考坐标系；点云 ICP/RTAB-Map 在各自可选节点中发布自己的 odom/map TF。

## 9. 启动编排

### 9.1 车辆启动 `vehicle.launch.py`

文件：[vehicle.launch.py](../ros2/zju_coop_bringup/launch/vehicle.launch.py)。关键参数：

~~~text
namespace                  默认 vehicle_1
local_config               默认 config/<namespace>.yaml
imu_topic                  默认 imu/data
run_fusion                 默认 false，只在参考车显式 true
enable_follower_feedback  默认 false
enable_point_cloud_input  默认 false
enable_camera_input       默认 false
enable_lidar_frontend     默认 false
enable_lidar_slam         默认 false
use_gnss_range_fallback   默认 false
~~~

因此最小三车角色是：

~~~text
车1：vehicle.launch.py namespace=vehicle_1 run_fusion=true
车2：vehicle.launch.py namespace=vehicle_2 run_fusion=false
车3：vehicle.launch.py namespace=vehicle_3 run_fusion=false
~~~

三个本地节点共同发布 NodeState；只有车 1 的融合节点订阅全部 NodeState 和 UWB，并发布协同结果。

### 9.2 三车仿真 `simulation.launch.py`

文件：[simulation.launch.py](../ros2/zju_coop_bringup/launch/simulation.launch.py)：

~~~text
zju_three_vehicle_simulator
  -> /vehicle_N/imu/data
  -> /uwb/range
  -> truth（仅测试/对比）

三个 zju_sim_local_inertial_node
  -> remap 各自 imu
  -> 汇聚 /cooperative_localization/node_state

一个 zju_sim_cooperative_fusion_node
  -> NodeState + /uwb/range
  -> /cooperative_localization/poses_2d
~~~

仿真使用 `/clock` 和 `use_sim_time`，不访问串口；算法回调和实物路径相同。

### 9.3 Gazebo `three_vehicle_gazebo.launch.py`

文件：[three_vehicle_gazebo.launch.py](../ros2/zju_coop_gazebo/launch/three_vehicle_gazebo.launch.py)：

~~~text
gz_sim.launch.py
  -> three_vehicle.sdf 和三车模型
  -> ros_gz_bridge
       -> /clock、IMU、cmd_vel、可选 PointCloud2/Image
  -> gazebo_scenario.py
       -> 循环路线、truth/辅助话题和场景控制
  -> bringup/算法节点
~~~

Gazebo GUI 只负责场景渲染；RViz 只订阅结果和传感器显示，不参与滤波。点云桥接、视觉桥接、ICP、RTAB-Map 和 RViz 均通过 launch 参数显式打开。

## 10. 可选感知和 GNSS 链路

### 10.1 点云 ICP

文件：[lidar_odometry_node.cpp](../ros2/zju_coop_perception/src/lidar_odometry_node.cpp)。调用关系：

~~~text
PointCloud2
  -> XYZ/距离/有限值检查
  -> 过滤到平面点云
  -> 检查点数和二维几何可观性
  -> PCL TransformationEstimation2D + ICP
  -> fitness、位移、偏航跳变检查
  -> nav_msgs/Odometry
~~~

它默认不启动，也不把 ICP 输出自动送入协同滤波；要融合必须另行定义观测接口。

### 10.2 激光 SLAM

`enable_lidar_slam=true` 时，launch 自动打开 ICP 前端和 `rtabmap_slam` 二维模式：

~~~text
PointCloud2 -> ICP odometry -> lidar_odom
PointCloud2 + lidar_odom -> RTAB-Map -> lidar_slam/map + map TF
~~~

这是本车建图/定位链路，默认关闭，不改变 NodeState/UWB 核心算法。

### 10.3 视觉地标定位

文件：[colored_landmark_localizer.py](../ros2/zju_coop_perception/scripts/colored_landmark_localizer.py)：

~~~text
Image + CameraInfo
  -> RGB 颜色分割
  -> 红/绿/蓝/黄地标质心
  -> 已知地标平面投影和小范围 x/y/yaw 最小二乘
  -> 重投影误差、跳变、深度检查
  -> nav_msgs/Odometry
~~~

视觉节点默认不启动，当前输出也不进入协同滤波。

### 10.4 GNSS 距离兜底

文件：[gnss_range_fallback.py](../ros2/zju_coop_ros2/scripts/gnss_range_fallback.py)。只有同时设置 `use_gnss_range_fallback=true`、`run_fusion=true` 才启用：

~~~text
共享 cooperative_interfaces/msg/GnssPosition
  -> 按 node_id 分流三车数据
  -> 经纬高有效性检查
  -> WGS84 ECEF/ENU 转换
  -> 同历元三车两两欧氏距离
  -> /cooperative_localization/gnss_derived_range
  -> 参考车融合节点替代 /uwb/range
~~~

这是 UWB 不可用时的低置信度后备；GNSS 时间戳必须和算法统一时间域一致，不能仅把 ROS 接收时间当测量时间。

## 11. 非 ROS 在线、回放和 GCS 路径

### 11.1 在线 UDP

入口：[online_main.cpp](../src/apps/online_main.cpp)。

~~~text
UDP socket
  -> wire_protocol::decode_frame()
  -> CRC/版本/长度/消息类型检查
  -> decode_imu_payload() 或 decode_range_payload()
  -> AlgorithmSession::push_imu()/push_range()
       -> C ABI
       -> Engine
       -> InertialEskf15 / CooperativeInertialEkf / RangeEkf
  -> 固定输出周期 AlgorithmSession::step()
  -> encode_snapshot()/TelemetryEncoder
  -> UDP GCS
~~~

`config/demo.ini` 的 `[inertial]` 段启用集中式 15N 路径；`range_only_demo.ini` 保持 UWB-only 兼容路径。

### 11.2 日志回放

入口：[replay_main.cpp](../src/apps/replay_main.cpp)。

~~~text
ZJLG EventLogReader
  -> 只读取 Direction=Input 的历史 IMU/Range
  -> 重新创建 AlgorithmSession
  -> 按原顺序再次 push
  -> Direction=Output 的旧定位结果只计数、不重新输入
  -> 当前版本 step() 生成新的定位/网络/告警输出
~~~

因此回放是算法回归，不是播放旧结果。`--speed 0` 表示尽快重放，`--output-mode none` 可关闭 UDP 输出。

## 12. C ABI 调用顺序

外部程序或 ROS 2 节点都遵循以下顺序：

~~~text
结构 init
  -> zju_coop_create() 或 zju_coop_distributed_create()
  -> （惯性模式）zju_coop_configure_inertial()
  -> zju_coop_push_imu() / zju_coop_push_range()
     或 distributed_push_node_state() / distributed_push_range()
  -> zju_coop_step()、zju_coop_get_node_state()
     或 distributed_get_pose2d_v2()
  -> 读取完整输出
  -> zju_coop_destroy() / zju_coop_distributed_destroy()
~~~

`c_api.cpp` 的边界职责包括版本号、`struct_size`、数组容量、stride、有限值、保留字段和异常转换。C ABI 返回 `ZJU_COOP_OK` 只代表调用成功；量测是否真正融合必须查看 processing/update disposition 和 NIS。

## 13. 最短排查路径

按数据从外到内排查：

~~~text
1. ros2 topic list -t
2. ros2 topic echo 检查字段、node_id、frame_id、时间戳
3. ros2 topic hz 检查频率
4. ros2 topic info --verbose 检查发布者/订阅者和 QoS
5. 节点日志检查 on_imu/on_node_state/on_uwb_range 的拒绝原因
6. /cooperative_localization/node_state 是否三车都有有效输出
7. /cooperative_localization/poses_2d 是否出现 position_valid=true
8. 最后再查 NIS、边超时、connected/observable 和规划反馈
~~~

判断依据对应关系：

| 现象 | 先查文件/入口 |
| --- | --- |
| IMU 话题没有数据 | 上游驱动、`on_imu()`、`SensorTimeBridge` |
| NodeState 没有发布 | `publish_state()`、`zju_coop_get_node_state()` |
| NodeState 有但融合无结果 | `on_node_state()` 的 frame/id/时间门控 |
| UWB 被拒绝 | `on_uwb_range()`、`Engine::push_range()`、NIS |
| 位置有效但 yaw 无效 | NodeState 姿态、共同历元和 `yaw_valid` 条件 |
| 三车互相看不到 | ROS_DOMAIN_ID、RMW、ROS_LOCALHOST_ONLY、DDS网卡 |
| 点云/图像有话题但无定位 | 对应可选前端是否启动，且当前前端尚未接入协同滤波 |
