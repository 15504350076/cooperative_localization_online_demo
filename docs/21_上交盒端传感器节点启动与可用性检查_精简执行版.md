这页只做现场最基本的检查。详细解释和排障看 [22号详细版](22_上交盒端传感器节点启动与可用性检查.md)，录包看 [30号说明](30_record_joint_time_使用说明.md)，在线定位看 [41号说明](41_201盒UWB最小在线相对定位部署步骤.md)。

包已收回、没有互联网或AI时，按[31_离线数据验收与算法回放步骤](31_离线数据验收与算法回放步骤.md)检查完整性、时间和新输出。

**三盒同时录 UWB＋车载IMU＋Livox：直接看第6.1.2节，在201一个终端控制三盒；第5节不录Livox。**

当前连接：上交电脑用网线连接201（`192.168.1.201`），201通过自组网连接202（`192.168.2.202`）、203（`192.168.2.203`）。

本轮三盒统一使用 ROS 2 默认通信域0。旧的107进程要先结束，再按本页重新启动；只改当前终端不会改变旧进程。

三盒新终端的 `ROS_DOMAIN_ID` 为空表示默认域0，`RMW_IMPLEMENTATION` 为空表示使用系统默认DDS；两者都不需要专门设置。跨盒通信时保持 `ROS_LOCALHOST_ONLY=0`（默认值）；只改当前终端不会改变已经运行的旧进程。进程检查用于避免重复启动或核对驱动环境，出数以实际消息为准。

🟥 表示需要新开终端。终端按“盒号＋编号”区分，例如“201终端1”“202终端1”；启动终端保持运行。

## 1. 先查三盒状态

> 🟥 **新开终端1：201、202、203各开一个SSH终端，检查本盒状态。**


## 2. 启动并检查 UWB/GNSS

三盒都要检查。室内三盒联测使用 UWB PPS，配置中的 pps_source 应为 1：

**继续使用各盒终端1。**


如果输出是 pps_source: 0，先备份并改为1（已经是1就跳过）：

```bash

sed --in-place --regexp-extended 's/^([[:space:]]*pps_source:[[:space:]]*)0([[:space:]]*)$/\1 1\2/' "$CFG"
grep --line-number 'pps_source' "$CFG"
```

改过配置或原进程来源不明时，先在原启动终端按 Ctrl+C，确认串口空闲：


### 6.2 相机

**在当前盒子的相机终端执行。** 三盒命令结构相同，但`/dev/video*`和`/dev/media*`编号必须以当前盒子的查询结果为准，不能直接假定所有硬件完全相同。201、202、203本次都看到`video33、video42、video51`；若系统或驱动版本变化，仍需重新查询。

```bash
v4l2-ctl --list-devices
ros2 topic list --no-daemon --show-types | grep --extended-regexp --ignore-case 'camera|image|rgb|camera_info'
```

若V4L2列出`rkisp_mainpath`下的三个`/dev/video*`，说明候选采集节点已注册；若ROS话题筛选没有输出，说明当前没有发现ROS 2图像/标定发布节点。`/dev/video0`不存在时不改用它，先使用实际列出的`rkisp_mainpath`节点。当前201、202、203均已看到对应主节点，但这不代表三路都能真正出帧。

把当前盒实际列出的三个候选节点、三个CIF媒体节点和三个ISP媒体节点填入变量。201、202、203本次都可使用下面九行；其他硬件按各自`v4l2-ctl --list-devices`结果替换：

```bash
CAM1=/dev/video33
CAM2=/dev/video42
CAM3=/dev/video51
CIF1=/dev/media0
CIF2=/dev/media1
CIF3=/dev/media2
ISP1=/dev/media3
ISP2=/dev/media4
ISP3=/dev/media5
v4l2-ctl --device="$CAM1" --list-formats-ext
v4l2-ctl --device="$CAM2" --list-formats-ext
v4l2-ctl --device="$CAM3" --list-formats-ext
timeout 10s v4l2-ctl --device="$CAM1" --stream-mmap --stream-count=30 --stream-to=/dev/null
timeout 10s v4l2-ctl --device="$CAM2" --stream-mmap --stream-count=30 --stream-to=/dev/null
timeout 10s v4l2-ctl --device="$CAM3" --stream-mmap --stream-count=30 --stream-to=/dev/null
```

变量名`CAM1/CAM2/CAM3`只是本轮的三个采集节点编号，不代表左、中、右镜头；镜头对应关系仍需上交确认。

三路只列出格式不算通过；如果出现`VIDIOC_STREAMON returned -1 (Operation not permitted)`，说明当前还没有真正采到帧。先查占用、媒体拓扑和当前格式：

```bash
fuser --verbose "$CAM1" "$CAM2" "$CAM3"
media-ctl --device="$CIF1" --print-topology
media-ctl --device="$CIF2" --print-topology
media-ctl --device="$CIF3" --print-topology
media-ctl --device="$ISP1" --print-topology
media-ctl --device="$ISP2" --print-topology
media-ctl --device="$ISP3" --print-topology
v4l2-ctl --device="$CAM1" --all
```

再用支持范围内的明确格式重试一条：

```bash
v4l2-ctl --device="$CAM1" --set-fmt-video=width=800,height=600,pixelformat=NV12
timeout 10s v4l2-ctl --device="$CAM1" --stream-mmap --stream-count=30 --stream-to=/dev/null
```

仍然`STREAMON`失败时，当前结论只能写“202相机节点已注册，但采集未通过”；需要上交检查MIPI供电、媒体链路、ISP配置或实际相机节点映射，不能继续保存裸帧或判断视觉数据可用。

如果`fuser`没有占用输出、`v4l2-ctl --all`已显示`Streaming`且当前格式为`800×600 NV12`，但仍`STREAMON`失败，问题就不是简单的设备占用或格式未设置。继续看`media-ctl`拓扑：若CSI/D-PHY的`Sink`没有上游MIPI传感器实体或启用链路，优先判断为相机传感器未枚举、未供电、驱动未加载或MIPI链路未建立；同时保存下面的内核日志给上交：

```bash
dmesg --ctime | grep --extended-regexp --ignore-case 'mipi|csi|dphy|rkcif|rkisp|camera|imx|ov'
```

连续取帧只证明采集通路。**要检查实际画面**，在当前盒相机终端各保存一帧（重复执行会覆盖同名样本）：

```bash
mkdir --parents /home/firefly/sensor_test/camera_samples
for DEV in "$CAM1" "$CAM2" "$CAM3"; do
  NAME=${DEV##*/}
  v4l2-ctl --device="$DEV" --all > /home/firefly/sensor_test/camera_samples/${NAME}.txt
  timeout 10s v4l2-ctl --device="$DEV" --stream-mmap --stream-count=1 --stream-to=/home/firefly/sensor_test/camera_samples/${NAME}.raw
```

#### 6.3.1 怎样确认程序已经结束

每盒依次显示“1/4 联合时间统计及绘图、2/4 车载IMU、3/4 Livox、4/4 UWB”。处理超过10秒时会提示“运行中”和已用时间。程序会等待当前子程序结束，再进行下一项；单项失败后继续其余项目。

- `[全部完成]`：本盒四项程序均执行成功，接着人工判断数据质量。
- `[部分失败]`：至少一项失败，终端直接打印错误摘要；先打开本盒 `分析执行结果.md` 中对应的失败日志。最终退出码为1。
- Ctrl+C：本次分析中断，正在运行的子程序也停止，未完成项目不能算成功。

程序只在成功时替换 `IMU分析.txt`、`雷达分析.txt` 等重定向报告；失败的详细输出写入同名的 `.失败.log`，旧报告可能保留。**以本次 `分析执行结果.md` 的状态和执行时间为准，不能以“目录中已经有报告或图片”判断本次完成。** 联合时间程序可能在缺少某个传感器时仍成功，它只统计存在的消息，必须继续核对清单。

例如 `three_boxes_20260811_012046` 的203盒：`imu/metadata.yaml` 为0消息、没有 `/imu/raw`，因此车载IMU分析失败属于输入缺失；联合时间、Livox和UWB仍可分别分析。空IMU包不能靠等待生成有效统计，需要补录该路。返回 shell 提示符表示这次脚本已经结束；之后看到的旧文件或编辑器刷新不代表仍在后台分析。

#### 6.3.2 分析后按什么顺序看、怎样判断好坏

下面路径均相对于**终端打印的本盒目录**；201、202、203分别检查，不能用一个盒子的结果代替另一个。消息头时间就是 `header.stamp`，记录时间是录包机写入bag的时间。

| 顺序与文件/图片 | 重点看哪些内容 | 基本正常表现与异常判断 |
|---|---|---|
| 1. `分析执行结果.md` | 本次执行时间、四项成功/失败、错误日志 | 先确认本次程序运行结果；某项失败先查该项日志，不能读取旧报告当成本轮结论 |
| 2. `uwb/metadata.yaml`、`imu/metadata.yaml`、`livox/metadata.yaml` | 话题、消息数、采集跨度 | `/uwb/range`、`/imu/raw`、`/livox/lidar`、`/livox/imu` 均应非空；采集跨度覆盖计划过程。0条消息就是未录到；消息数应与配置频率和时长大致相符 |
| 3. `联合时间验收.md` | 各数据流是否齐全、消息首末时间、消息零值/回退/重复、记录回退/重复 | 连续测量时间应非零、严格递增；某路只有开机计时而其他路是绝对时间、出现大跳/回退，均须先核对时间源，不能直接融合 |
| 4. `联合时间详细统计.csv` | 中文表头中的“消息数量”“消息间隔中位数/最大间隔”“消息时间回退数”“记录时间回退数”“记录减消息时间中位数” | 比较典型间隔与配置周期，定位漏帧、大间隔和异常时钟；固定时间差或偏差分位宽度仅用于诊断，不能当成同步精度。统计的“超过100毫秒”不是所有传感器的合格门限 |
| 5. `联合时间轴对比.png` | 上图各流时间推进斜率；下图“记录减消息时间”相对首帧的变化 | 平稳推进是初步正常表现；阶跃、折返、明显不同斜率需要查时间跳变/时间源。横轴按每流首帧置零，曲线重叠不能证明三盒同步 |
| 6. `IMU与UWB原始时间戳对比.png` | 相同共同起点下的消息时间与记录时间；全程图和局部放大 | 检查不同传感器是否处于相近时间区间、是否存在固定偏移或突然变化；这张图也包含Livox等实际录到的流。记录时间不同步时不能据此量化跨盒采样误差 |
| 7. `IMU分析.txt` | 消息数、标称间隔、回退/重复/正向大跳、角速度/线加速度、姿态突变 | 车载IMU常见约1000赫兹、约1毫秒周期，以配置为准。静止时角速度应稳定接近零，标准比力模长约9.8米/秒²；非有限数、大跳和频繁间断需处理。上游四元数突变单独记录，不能作为姿态真值；协方差全零表示未提供，不表示无误差 |
| 8. `雷达分析.txt` | 点云与内置IMU数量、消息/记录时间间隔、点云尺寸、有限XYZ和全零XYZ比例、逐点时间 | 常见点云约10赫兹、内置IMU约200赫兹，以驱动配置为准；201历史还有96点小消息模式，不能机械按10赫兹判定。非空且有足够有效场景点是基础；全零比例明显偏高须核对设备无效点语义和遮挡，不能只看有限比例。逐点时间单位必须与驱动定义一致 |
| 9. `uwb/UWB测距分析.md`、`uwb/UWB测距数据.csv` | 三条无向边1—2、1—3、2—3，六个有向流、非法距离、回退/重复、间断、波动 | 距离应为正且有限，预期边齐全；每方向常见约10赫兹。静止时突跳/长间断/明显异常波动需查遮挡和NLOS；标准差小只说明稳定，有卷尺真值才能评价绝对误差 |
| 10. `uwb/UWB测距曲线与时间戳.png` | 距离时序、分布、消息时间与记录时间推进 | 静止数据应围绕各边距离波动；尖峰/突变/长空段提示异常。运动时距离变化可以正常，应结合现场备注；消息推进与记录推进不一致要查时钟，两者各自置零也不能证明同步 |
| 11. 本轮根目录 `livox_visualization/livox_overview.png`、`box201_livox_3d.html`等 | 墙/地面等场景结构是否可见，是否只有原点点团、条纹或严重重影 | 可见结构只证明该窗口能成像，不能证明点云时间、外参和定位精度合格；三盒各在自身雷达系，不可把直接叠加当作公共地图。可视化是上面的独立命令生成，可能选到与联合分析不同的一轮，以打印目录为准 |

最终建议按“采集是否完整 → 单路数值与时间是否连续 → 跨传感器时间是否可直接比较 → 有真值时再评价误差”记录结论；不要把“程序运行成功”“有图片”“曲线靠近”写成“数据同步通过”或“定位精度通过”。
