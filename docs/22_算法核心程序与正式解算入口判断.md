# 算法核心程序与正式解算入口判断

本文只回答两个问题：算法核心在哪些文件，以及一帧数据在什么条件下才会进入正式解算。
当前最小实物链路是“本车 IMU 航位推算 + 参考车接收 NodeState/UWB 后做二维位置修正”。

## 1. 先看哪条程序链

```text
sensor_msgs/Imu
  → local_inertial_node.cpp
  → zju_coop_push_imu()
  → InertialEskf15（本车15维名义状态传播）
  → NodeState（位置、速度、姿态）

NodeState + UWB测距
  → cooperative_fusion_node.cpp
  → zju_coop_distributed_push_node_state()
  → zju_coop_distributed_push_range()
  → DistributedFusion2D（非参考车二维位置修正）
  → CooperativePose2DArray（相对位置和航向）
```

当前 ROS 2 适配层不是集中式 45 维滤波节点：每车本地只维护自己的惯导状态，参考车的首版分布式修正器只维护非参考车的二维位置修正量。

## 2. 算法核心文件

| 文件 | 作用 | 当前地位 |
|---|---|---|
| [`src/core/inertial_eskf15.hpp`](../src/core/inertial_eskf15.hpp) / `.cpp` | 单车 15 维误差状态 ESKF；用 IMU 传播位置、速度、姿态、陀螺零偏、加计零偏，并生成 `Phi/Qd` | 当前每车本地惯导核心 |
| [`src/core/distributed_fusion2d.hpp`](../src/core/distributed_fusion2d.hpp) / `.cpp` | 参考车二维协同修正；以 NodeState 航位推算为基线，用 UWB 距离修正非参考车平面位置 | 当前最小协同核心 |
| [`src/core/cooperative_inertial_ekf.hpp`](../src/core/cooperative_inertial_ekf.hpp) / `.cpp` | 15N 联合误差协方差和三维测距更新，保留车辆间交叉协方差 | 集中式回归基线，当前 ROS 分布式节点不直接调用 |
| [`src/core/engine.hpp`](../src/core/engine.hpp) / `.cpp` | 统一编排输入检查、时间、去重、质量监视、惯性/仅测距滤波和输出 | C++算法库总入口；离线程序和旧接口使用 |
| [`src/core/range_ekf.hpp`](../src/core/range_ekf.hpp) / `.cpp` | 无 IMU 时的二维恒速 + UWB 兼容滤波 | 回退/演示路径，非当前默认路径 |
| [`src/core/degradation_monitor.hpp`](../src/core/degradation_monitor.hpp) / `.cpp` | 统计每条 UWB 边的有效率、频率、NLOS、残差，输出正常/降权/暂缓/剔除动作 | `Engine` 质量链使用；分布式 ROS 首版暂未接入完整状态机 |
| [`src/core/rigidity.hpp`](../src/core/rigidity.hpp) / `.cpp` | 检查有效测距图的参考车可达性、连通性和二维刚性/可观性 | `Engine` 输出网络状态使用 |
| [`src/core/quaternion.hpp`](../src/core/quaternion.hpp) / `.cpp` | FLU→ENU 姿态四元数、旋转和小角度注入 | ESKF 和 Pose2D 输出依赖 |
| [`src/core/dense_matrix.hpp`](../src/core/dense_matrix.hpp) / `.cpp` | 联合协方差、矩阵乘法、对称化等基础运算 | ESKF/联合滤波基础 |
| [`ros2/zju_coop_ros2/src/local_inertial_node.cpp`](../ros2/zju_coop_ros2/src/local_inertial_node.cpp) | ROS IMU 转 C ABI、时间桥、调用本地 ESKF、发布 NodeState | 本车 ROS 入口 |
| [`ros2/zju_coop_ros2/src/cooperative_fusion_node.cpp`](../ros2/zju_coop_ros2/src/cooperative_fusion_node.cpp) | 接收 NodeState/UWB、调用分布式修正器、发布相对 Pose2D | 参考车 ROS 入口 |
| [`include/zju_coop/c_api.h`](../include/zju_coop/c_api.h) | C ABI 生命周期、输入包、处理结果和输出接口 | ROS 适配层与算法库的稳定边界 |

### 2.1 当前真正调用的函数

本车节点构造阶段调用：

```text
zju_coop_create()
  → zju_coop_configure_inertial()
```

每帧 IMU 调用：

```text
zju_coop_imu_packet_init()
  → zju_coop_push_imu()
  → zju_coop_get_node_state()
```

参考车节点构造和运行阶段调用：

```text
zju_coop_distributed_create()
  → zju_coop_distributed_push_node_state()
  → zju_coop_distributed_push_range()
  → zju_coop_distributed_get_pose2d_v2()
```

`zju_coop_push_point_cloud()`、`zju_coop_push_camera_image()` 目前只做元数据校验，返回 `VALIDATED_NOT_USED`，不进入定位算法。

## 3. 正式解算前的判断入口

### 3.1 启动期：配置必须先合法

入口文件：`local_inertial_node.cpp` 构造函数、`cooperative_fusion_node.cpp` 构造函数、`c_api.cpp` 的配置转换。

必须通过：

1. `node_id`、参考车编号和节点列表有效且不重复；
2. 初始位置、速度、零偏和姿态四元数全部为有限值；
3. 初始四元数范数接近 1；
4. `frame_id`、公共 ENU 名称和 C ABI 字符数组长度合法；
5. 发布频率、测距标准差、超时门限和 NIS 门限为正；
6. 惯性配置在第一帧输入前完成，运行中不能改状态维度。

任一项失败，节点应启动失败或拒绝创建句柄，不会带着半初始化状态解算。

### 3.2 IMU 入口：`on_imu()` → `zju_coop_push_imu()`

按实际执行顺序理解：

```text
ROS消息到达
  → header.stamp 有效且非零
  → 时间桥得到有效 receive_timestamp
  → node_id/sequence/数值/frame_id 检查
  → 时间严格递增、dt 在允许区间内
  → UWB时间相对接收时刻不明显超前/滞后
  → 通过后进入 push_imu()
```

SDK 内部还会检查：

- 首帧只建立时间基准，不做积分；
- 后续帧使用前后两帧中值进行名义状态传播；
- 姿态、状态、`Phi`、`Qd` 必须有限；
- 任一数值失败则回滚，不提交半次传播。

可用的处理结果：

| 结果 | 含义 | 是否产生一次传播 |
|---|---|---:|
| `BASELINE_ESTABLISHED` | 第一帧合法，已建立时间基准 | 否 |
| `PROPAGATED` | 通过全部检查，已完成一次 ESKF 传播 | 是 |
| `DUPLICATE` | 序号和时间与上一帧重复 | 否 |
| `OUT_OF_ORDER` | 时间回退 | 否 |
| `INTERVAL_REJECTED` | `dt` 太小或太大 | 否；SDK 内部记录新边界，ROS 盒端节点随即锁存时间故障并停算、停发，修复上游时间后重启节点 |
| `FRAME_MISMATCH` / `INVALID_PACKET` | 坐标系或字段不合法 | 否 |
| `NUMERICAL_FAILURE` | 数值计算失败并回滚 | 否 |

### 3.3 NodeState 输出入口：`publish_state()`

本地 ESKF 状态查询成功且 `valid=true` 后，才发布 NodeState。另有三个保护：

- 状态时间戳必须前进；
- 同一时间戳不重复发布；
- 运行中发生时间回退、时间窗失配或积分间隔拒绝后锁存故障，不再把旧状态作为新有效结果发布；修复上游时间后重启本地惯导节点。

NodeState 只带位置、速度、FLU→ENU 四元数和 `valid`；零偏及 15×15 协方差留在本车，不能据此判断从车是否完成了完整零偏估计。

### 3.4 参考车 NodeState 入口：`on_node_state()`

参考车收到消息后，进入分布式修正器前依次判断：

1. `header.frame_id == common_enu`；
2. `node_id` 在配置的车辆集合内；
3. `header.stamp` 非零且对该车严格递增；
4. 消息 `valid=true`，位置、速度和四元数有限；
5. 测量时间与接收时间通过 future-skew / receive-delay 门限；
6. 参考车首个有效 NodeState 能建立 UWB 时间锚点。

任一项失败，该 NodeState 不进入融合历史。全部车辆至少各有一帧状态后，UWB 才具备状态对齐条件。

### 3.5 UWB 入口：`on_uwb_range()` → `push_range()`

在 ROS 适配层先检查节点编号和参考时间；SDK 分布式修正器再依次检查：

```text
valid/status/时间/接收时刻
  → 距离和标准差为正
  → from_node != to_node 且两端均已配置
  → 同一无向边时间严格递增
  → 所有车辆已有 NodeState
  → 在测距时刻对齐两端状态（插值或有限外推）
  → 预测距离可线性化
  → 计算创新方差和 NIS
  → NIS ≤ nis_gate 才提交位置修正
```

UWB 的处理结果：

- `Accepted`：完成二维位置修正并提交协方差；
- `NisRejected`：数据格式合法但创新过大，只推进时间边界，不改位置修正；
- `OutOfOrder`、`InvalidPacket`、`UnknownNode`、`SelfRange`：不进入更新；
- `NumericalFailure`：计算失败并回滚。

当前参考车 ROS 节点已直接订阅 `cooperative_interfaces/msg/UwbRange`，并逐字段转换到核心 C ABI。进入核心前还会拒绝零时间戳、非有限或非正距离、自测距、未知车辆号及超出 `uint16` 范围的ID。

### 3.6 Pose2D 输出入口：`publish_pose()`

分布式修正器以所有车辆最近历史状态的最小时间作为公共输出时刻，然后判断：

- 参考车状态是否新鲜；
- 目标车状态是否新鲜；
- 目标车是否通过近期有效 UWB 边与参考车连通；
- 位置数值是否有限。

通过后 `position_valid=true`。航向来自 NodeState 的惯性姿态，仅在状态时间新鲜且姿态可转换时 `yaw_valid=true`；UWB 本身不直接估计车辆自转航向。

## 4. 看到日志时先按这张表定位

| 现象 | 先看哪里 | 是否已经进入正式算法 |
|---|---|---:|
| 节点启动即退出 | 参数、初值、ABI 创建 | 否 |
| IMU频率正常但 `stamp=0` | `on_imu()` 时间入口、上交授时 | 否 |
| 第一帧 `BASELINE_ESTABLISHED` | ESKF 时间基准 | 尚未传播，正常 |
| 连续 `PROPAGATED` | `inertial_eskf15.cpp` | 是，已做本车传播 |
| NodeState 被拒绝 | frame、ID、时间、valid | 否，未进入参考车历史 |
| UWB `NisRejected` | 创新、创新方差、`nis_gate` | 未提交本次修正 |
| `position_valid=false` | 状态新鲜度、UWB边连通性 | 输出不可给规划控制使用 |
| 点云/图像 `VALIDATED_NOT_USED` | 原始输入入口 | 只校验，未进入定位算法 |

## 5. 学习时的最短阅读顺序

1. `inertial_eskf15.hpp/.cpp`：先看 `push_imu()` 的检查、首帧和中值传播；
2. `cooperative_fusion_node.cpp`：看 ROS 消息如何变成 NodeState/UWB 输入；
3. `distributed_fusion2d.hpp/.cpp`：看状态对齐、距离雅可比、NIS 和位置修正；
4. `quaternion.cpp`、`dense_matrix.cpp`：只在遇到姿态或矩阵细节时查；
5. `cooperative_inertial_ekf.cpp`、`engine.cpp`：最后作为集中式 15N 回归基线阅读。
