# 41 201盒UWB最小在线相对定位部署步骤（详细讲解版）

现场只想直接执行命令时，看[21号精简执行版第7节](21_上交盒端传感器节点启动与可用性检查_精简执行版.md#7-201在线uwb协同定位)；本文件说明部署条件、架构、编译、验收和排障原因。

## 1. 本次部署要达到什么结果

本次只把已经通过离线回放和ROS测试的纯UWB相对定位链路部署到201盒：

```text
201、202、203已有 gnss_uwb
  -> 共享DDS中的 /uwb/range
  -> 201上的 zju_cooperative_fusion_node
  -> /cooperative_localization/poses_2d
```

边界如下：

- 只在201部署和运行浙大融合节点；
- 202、203继续运行上交已有的`gnss_uwb`，不部署浙大程序；
- 不修改、替换或删除`/home/firefly/imu_ws`；
- 不接入IMU、GNSS、雷达和相机；
- 不安装Gazebo、Foxglove、RViz、PCL、OpenCV或RTAB-Map；
- 首次部署只在SSH终端临时运行，不配置开机自启；
- 输出是人为定义相对坐标系下的三车队形，不能给出北向或车辆自身航向。

当前开发电脑中的ROS可执行文件是x86-64，不能直接复制到RK3588。必须在201盒原生编译，或使用与201完全兼容的AArch64构建环境交叉构建。本文采用更直接的“201盒原生编译”。

## 2. 部署前必须具备的条件

开始前应确认：

1. 能通过SSH登录`firefly@192.168.1.201`；
2. 三盒`gnss_uwb`均已运行；
3. 201能持续收到三车形成的`/uwb/range`；
4. 三盒UWB进程处于同一个ROS域，后续联合测试按21号说明统一使用`ROS_DOMAIN_ID=0`；
5. 201安装了ROS 2 Humble、CMake、C++编译器和colcon；
6. 上交当前`UwbRange`仍为以下字段和顺序：

```text
std_msgs/Header header
uint32 src_id
uint32 target_id
uint16 rolling
float32 distance
```

只要其中一项不满足，先停止部署并处理输入链路，不要通过改融合算法掩盖上游问题。

## 5. 确认上交UWB进程和通信环境

```bash
hostname --all-ip-addresses

GNSS_UWB_PID=$(pgrep --newest --full \
  '^/home/firefly/imu_ws/install/gnss_uwb/lib/gnss_uwb/gnss_uwb( |$)')
printf 'GNSS_UWB_PID=%s\n' "${GNSS_UWB_PID:-未运行}"

test -n "$GNSS_UWB_PID" && \
  tr '\0' '\n' < "/proc/$GNSS_UWB_PID/environ" | \
  grep --extended-regexp '^(ROS_DOMAIN_ID|RMW_IMPLEMENTATION|ROS_LOCALHOST_ONLY)='
```

然后在当前终端加载与联合测试一致的环境：

```bash
source /opt/ros/humble/setup.bash
source /home/firefly/imu_ws/install/setup.bash

export ROS_DOMAIN_ID=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOCALHOST_ONLY=0
```

检查消息定义和实时输入：

```bash
ros2 topic type --no-daemon /uwb/range
ros2 interface show cooperative_interfaces/msg/UwbRange
ros2 topic info --no-daemon --verbose /uwb/range

timeout --signal=INT 5s ros2 topic echo --no-daemon --once \
  --qos-profile sensor_data \
  /uwb/range cooperative_interfaces/msg/UwbRange
```

应看到：

- Topic类型为`cooperative_interfaces/msg/UwbRange`；
- 接口字段与第2节完全一致；
- 5秒内能收到`src_id`、`target_id`不同且`distance>0`的消息。

如果`GNSS_UWB_PID`进程环境不是0，或者当前终端在0看不到`/uwb/range`，按21号说明将三盒相关驱动统一重启到0；不再沿用旧域。

当前源码的`uwb_only.launch.py`默认将算法进程设为域0（`domain_id`启动参数默认0），不继承终端残留的旧域号。旧版启动文件只继承终端环境；无需重编译算法，在原算法终端按Ctrl+C后，按本文件第10节设置`export ROS_DOMAIN_ID=0`并重新启动即可。修改本地源码或终端变量都不会改变已经运行的进程。

在201盒另一个SSH终端可查看实际算法进程的域号，输出应为`ROS_DOMAIN_ID=0`：

```bash
FUSION_PID=$(pgrep --newest --full '/zju_cooperative_fusion_node( |$)')
printf 'FUSION_PID=%s\n' "${FUSION_PID:-未运行}"
test -n "$FUSION_PID" && tr '\0' '\n' < "/proc/$FUSION_PID/environ" | grep '^ROS_DOMAIN_ID='
```

构建结束后先核对安装参数，再启动：

```bash
grep --fixed-strings 'uwb_epoch_max_span_ms: 10' \
  install/ros2-box/zju_coop_bringup/share/zju_coop_bringup/config/fusion.yaml
```

若出现`Clock skew detected`，表示上传文件修改时间晚于201系统时间；它不是算法报错。只要四个包均显示`Finished`，仍要以上面的安装参数和启动日志`uwb-span=10 ms`为准。若参数或日志缺失，再按本节重新构建，不能继续使用旧`install/ros2-box`。

若参数已更新但日志仍没有`uwb-span=10 ms`，使用新的构建/安装目录，避免复用旧的中间文件：

```bash
colcon build --cmake-force-configure \
  --base-paths ros2 \
  --packages-up-to zju_coop_bringup \
  --build-base build/ros2-box-span10 \
  --install-base install/ros2-box-span10 \
  --cmake-args \
    -DCMAKE_BUILD_TYPE=Release \
    -DBUILD_TESTING=OFF \
    -DZJU_COOP_SDK_ROOT="$PWD/install-arm64"

strings install/ros2-box-span10/zju_coop_ros2/lib/zju_coop_ros2/\
  zju_cooperative_fusion_node | grep --fixed-strings 'uwb-span='
source install/ros2-box-span10/setup.bash
```

之后启动和检查都使用`install/ros2-box-span10`；确认日志后再将该安装目录作为201当前版本。

## 10. 启动最小在线相对定位

### 10.1 最小排障入口

第一次上盒建议只启动融合节点：

```bash
ros2 launch zju_coop_bringup uwb_only.launch.py \
  reference_node_id:=1 \
  uwb_topic:=/uwb/range \
  poses_topic:=/cooperative_localization/poses_2d
```

这个launch不启动或占用IMU、GNSS、雷达、相机和串口。它与通用入口调用同一个`zju_cooperative_fusion_node`，只是减少首次排障时的无关节点。

保持这个终端打开。关闭SSH或按`Ctrl+C`会停止本次临时运行。

#### “重新启动融合节点”具体怎么做

这里的“重新启动”仅指重新运行浙大的ROS融合节点，不是重启201盒，也不是重启上交的`gnss_uwb`。

如果上一次已经按`Ctrl+C`并看到`process has finished cleanly`，融合节点已经停止。先检查：

```bash
pgrep --list-full --full '/zju_cooperative_fusion_node( |$)' || echo '融合节点当前未运行'
```

若只输出“融合节点当前未运行”，就在当前201终端重新加载正确环境并启动：

```bash
source /opt/ros/humble/setup.bash
source /home/firefly/imu_ws/install/setup.bash
source /home/firefly/zju_coop_ws/install/ros2-box/setup.bash

export ROS_DOMAIN_ID=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOCALHOST_ONLY=0

ros2 launch zju_coop_bringup uwb_only.launch.py \
  reference_node_id:=1 \
  uwb_topic:=/uwb/range \
  poses_topic:=/cooperative_localization/poses_2d
```

这个201融合终端保持不动，用另开的201观察终端执行第11节的`topic hz`和`topic echo`。如果`pgrep`已经显示一个融合进程，不要再启动第二份，直接去观察终端检查输出。临时测试结束后，在运行launch的融合终端按一次`Ctrl+C`即可。

### 10.2 通用入口

最小入口验证完成后，也可以停止它，再改用统一车辆入口：

```bash
ros2 launch zju_coop_bringup vehicle.launch.py \
  namespace:=vehicle_1 \
  run_fusion:=true \
  input_mode:=uwb_only
```

两条启动命令不能同时运行。首次验证只选10.1即可。

## 11. 在201观察终端检查输出

加载同样的环境：

```bash
source /opt/ros/humble/setup.bash
source /home/firefly/imu_ws/install/setup.bash
source /home/firefly/zju_coop_ws/install/ros2-box/setup.bash

export ROS_DOMAIN_ID=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOCALHOST_ONLY=0
```

检查节点、Topic和频率：

```bash
ros2 node list | grep zju
ros2 topic info --no-daemon --verbose \
  /cooperative_localization/poses_2d
timeout --signal=INT 15s ros2 topic hz \
  /cooperative_localization/poses_2d
```

读取一条结果：

```bash
timeout --signal=INT 15s ros2 topic echo --no-daemon --once \
  /cooperative_localization/poses_2d \
  cooperative_localization_msgs/msg/CooperativePose2DArray
```

若15秒后没有输出并自动返回，表示这15秒内没有形成一帧可发布的有效三角形，不表示终端卡死，也不表示需要重启盒子。

正常结果应满足：

- `header.frame_id`为`coop_ref_1_relative`；
- `reference_node_id`为1；
- `vehicles`包含节点1、2、3；
- 有效历元的三车`position_valid`为`true`；
- `yaw_valid`为`false`，这是纯UWB不能观测车辆航向的正常结果；
- 车1坐标约为`(0,0)`；
- 车2位于相对坐标系`+X`轴；
- 车3取`+Y`镜像分支。

不是每条输入都必须产生有效输出。缺边、互惠测距差过大、距离突变或不满足三角不等式时，算法会丢弃该历元或发布`position_valid=false`。

## 12. 建议录制一次在线输入和输出

在另开的201录包终端执行60秒录包：

```bash
source /opt/ros/humble/setup.bash
source /home/firefly/imu_ws/install/setup.bash
source /home/firefly/zju_coop_ws/install/ros2-box/setup.bash

export ROS_DOMAIN_ID=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOCALHOST_ONLY=0

ONLINE_TIME=$(TZ=Asia/Shanghai date +%Y%m%d_%H%M%S)
ONLINE_BAG=/home/firefly/uwb_test/\
zju_online_v1_${ONLINE_TIME}

mkdir --parents /home/firefly/uwb_test
timeout --foreground --signal=INT --kill-after=5s 60s \
  ros2 bag record --output "$ONLINE_BAG" \
  /uwb/range /cooperative_localization/poses_2d

if [ -f "$ONLINE_BAG/metadata.yaml" ]; then
  ros2 bag info "$ONLINE_BAG"
  ONLINE_ARCHIVE="${ONLINE_BAG}.tar.gz"
  tar --directory "$(dirname "$ONLINE_BAG")" --create --gzip --file "$ONLINE_ARCHIVE" \
    "$(basename "$ONLINE_BAG")"
  ls --format=long --human-readable "$ONLINE_ARCHIVE"
  sha256sum "$ONLINE_ARCHIVE"
  printf '下载文件：%s\n' "$ONLINE_ARCHIVE"
else
  printf '录包失败：未生成 metadata.yaml\n' >&2
fi
```

该包同时保留算法输入和输出，便于对比“哪些UWB历元被接受、哪些被拒绝”。原始录包目录不会删除，并会在同一目录生成`zju_online_v1_<北京时间>.tar.gz`压缩包，终端同时打印文件大小、SHA-256校验值和下载路径。

下载到开发电脑后，按本文件第17节运行`tools/analyze_online_bag.py`，自动生成Markdown、JSON和CSV结果。

## 13. 停止和回退

首次部署没有修改上交进程。停止浙大算法只需在启动终端按一次`Ctrl+C`，然后检查：

```bash
pgrep --list-full --full 'zju_cooperative_fusion_node|zju_local_inertial_node' || \
  echo '浙大在线节点已停止'

pgrep --list-full --full \
  '^/home/firefly/imu_ws/install/gnss_uwb/lib/gnss_uwb/gnss_uwb( |$)'
```

预期是浙大节点停止，而上交`gnss_uwb`继续运行。不要使用模糊的`pkill ros2`，它可能停止无关ROS进程。

## 14. 常见问题

### 14.1 `Package 'zju_coop_bringup' not found`

当前终端没有加载浙大安装目录：

```bash
source /home/firefly/zju_coop_ws/install/ros2-box/setup.bash
```

### 14.2 启动时报`Exec format error`

误用了x86-64产物。执行`file`检查可执行文件和`libzju_coop.so`，必须重新在AArch64环境构建。

### 14.3 有`/uwb/range`但没有相对位置输出

依次检查：

1. 当前终端与上交进程的`ROS_DOMAIN_ID`、RMW和`ROS_LOCALHOST_ONLY`；
2. `UwbRange`消息定义是否完全一致；
3. 是否确实同时出现1—2、1—3、2—3三条无向边；
4. 同一物理历元的三条边`header.stamp`跨度是否不超过当前10 ms配对门限；
5. 距离是否大于0并满足三角不等式；
6. 启动日志是否显示`uwb-span=10 ms`；是否仍有缺边或几何拒绝日志。

### 14.4 输出存在但经常`position_valid=false`

先保存输入输出录包，不要立即放宽门限。离线区分是UWB本身异常、历元拼接问题，还是当前保护参数过严，再修改`fusion.yaml`。

### 14.5 GCS看不到自定义消息

本步骤只证明201能发布浙大消息。GCS如果直接订阅该Topic，还需要安装`cooperative_localization_msgs`；如果上交GCS已有自己的消息类型，需要增加一个薄转换节点。GCS接口未冻结前，不要把转换逻辑写进核心融合程序。

## 15. 本轮验收通过标准

只有同时满足以下条件，才算“201盒纯UWB最小在线实现已部署”：

- AArch64算法自检显示`SELF_CHECK PASS`；
- 四个ROS包都能被`ros2 pkg prefix`找到；
- 201实时订阅到三盒UWB测距；
- `/cooperative_localization/poses_2d`持续产生消息；
- 有效消息含三辆车且`position_valid=true`；
- 纯UWB下`yaw_valid=false`；
- 停止浙大节点不会影响上交`gnss_uwb`；
- 保存了一份同时包含输入和输出的在线验证包。

完成以上验收后，下一步才是与上交冻结GCS消息契约并做端到端显示；IMU、GNSS、雷达和相机接入不属于本轮首次部署。

## 16. 当前已跑通后的继续步骤

201盒已经能够在线发布三车相对位置。后续按下面顺序做，不要跳过在线输出包的保存。

### 16.1 先做60秒连续输出验收

保持第10节启动的融合节点运行，在201录包终端执行第12节的60秒录包命令。录包同时保存：

- `/uwb/range`：融合输入；
- `/cooperative_localization/poses_2d`：融合输出。

录包结束后执行：

```bash
ros2 bag info "$ONLINE_BAG"
```

重点确认输出Topic存在、消息数量大于0、消息频率约为9～10 Hz，并抽查输出消息中的：

```text
reference_node_id: 1
vehicles: 1、2、3
position_valid: true
yaw_valid: false
```

这一步只评价在线链路的连续性、有效输出比例和异常拒绝情况，不评价绝对定位精度。

### 16.2 再确认GCS接口

把在线包和一条实际输出消息交给上交接口负责人，确认以下内容：

```text
订阅Topic
消息类型
QoS
节点号字段
坐标系名称和方向
时间戳含义
```

接口未确认前，继续使用`/cooperative_localization/poses_2d`作为浙大内部输出，不改核心融合节点。

### 16.3 接着做单盒动态试验

在三盒UWB均正常运行、融合节点保持运行的情况下，只移动一个盒子约0.5～1米，另外两个盒子保持静止。保存这次输入输出包，检查：

- 被移动盒子的相对坐标是否连续变化；
- 未移动盒子的坐标是否基本稳定；
- 移动过程中有效输出是否持续；
- 停止移动后，三角形是否回到合理形状。

没有这组动态数据前，只能确认静态在线输出，不能评价运动定位效果。

### 16.4 动态UWB通过后再考虑其他传感器

- IMU：先确认时间戳和公共航向初值，再接入惯性传播或融合；
- GNSS：有有效`/gnss/fix`时优先用作真值或绝对坐标对齐；
- 激光雷达：先完成点云Topic、频率、时间戳和坐标外参验收；
- 视觉：先确认相机Topic、消息类型和标定，再单独接入。

这些传感器都不能替代第16.1节的UWB-only连续输出验收。

## 17. 在线结果包的离线分析

如果第12节录制了 `/uwb/range` 和 `/cooperative_localization/poses_2d`，在开发电脑加载消息工作空间后运行：

```bash
python3 tools/analyze_online_bag.py data/zju_online_实验编号
```

默认会在录包目录生成 `online_analysis/`，包括中文结论、JSON 汇总、UWB 明细 CSV 和位置明细 CSV。重点查看输出频率、`position_valid` 比例、三车是否同一参考坐标系、六个有向 UWB 流是否有回退，以及静止坐标抖动。没有卷尺、GNSS 或其他独立真值时，只能评价连续性和重复性，不能称为绝对定位精度。

## 18. 无外网或暂时连不到201

没有互联网但三盒局域网正常时，仍按21第7节实测。连不到201时，照[GCS离线验证步骤](GCS离线验证步骤.md)在开发电脑只回放UWB输入，由算法重新生成位置并供GCS显示；该验证不需要盒子在线。
