# 工程使用、学习与编写思路

## 1. 先明确这个工程是什么

本工程是浙大协同定位算法库及其独立在线演示环境。当前默认闭环为：

```text
上交统一时间轴下的各节点瞬时IMU
                    │
                    ▼
每节点15维名义惯性状态传播
                    │
平台间直接测距 ────┼──→ 15N联合误差状态更新
                    │
                    ▼
观测质量状态机 → 动态协同拓扑 → 主参考相对定位
                    │
                    ▼
Localization / Observation / Network → GCS或ROS 2适配层
```

算法库不负责传感器驱动、上交时间同步、无线转发/路由、交大GCS实现或车辆控制。`ZJCL/UDP`、Python模拟器和浏览器面板用于硬件到位前的独立联调，正式AIBrainBox部署应由上交ROS 2节点调用C ABI动态库。

## 2. 最快验证方法

### 2.1 Windows 10/11开发机

环境：64位Windows、Visual Studio 2022“使用C++的桌面开发”、CMake 3.16以上、Python 3。VS Code建议安装Microsoft C/C++和CMake Tools扩展。

用VS Code打开工程根目录后，第一次选择：

```text
CMake: Select a Kit
→ Visual Studio Community 2022 Release - amd64
```

工程内`.vscode/settings.json`会让CMake Tools在打开时自动配置到`build-vscode`。也可以在Developer PowerShell中执行：

```powershell
cmake -S . -B build-vscode -G "Visual Studio 17 2022" -A x64 -DBUILD_TESTING=ON
cmake --build build-vscode --config Release
ctest --test-dir build-vscode -C Release --output-on-failure
```

如果普通PowerShell找不到`cmake`，可以从“Developer PowerShell for VS 2022”运行，或直接使用VS Code的`CMake: Configure`、`CMake: Build`和`CMake: Run Tests`。

最小自检：

```powershell
.\build-vscode\Release\zju_coop_self_check.exe
```

看到`SELF_CHECK PASS`且进程退出码为0，说明动态库、C ABI、三车静止IMU传播、三边测距、主参考输出、重复包、超时和恢复的软件闭环通过。该结果不代表真实传感器精度、时间同步和盒端性能已经验收。

### 2.2 Ubuntu 22.04与RK3588

```bash
sudo apt update
sudo apt install -y build-essential cmake python3
cmake -S . -B build-arm64 -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=ON
cmake --build build-arm64 -j"$(nproc)"
ctest --test-dir build-arm64 --output-on-failure
./build-arm64/zju_coop_self_check
cmake --install build-arm64 --prefix install-arm64
```

Windows生成的`.dll/.lib/.exe`不能复制到RK3588运行；RK3588必须重新生成AArch64的`libzju_coop.so`。`.vscode`不是运行依赖，`build-vscode`也不得从Windows复制到Linux继续使用。

## 3. 没有真实数据时的完整在线演示

### 3.1 Windows 10/11 PowerShell

本小节全部命令都在**工程根目录下的PowerShell终端**执行。命令中的反引号是PowerShell续行符，反斜杠是Windows路径分隔符，`.exe`来自Visual Studio多配置构建；不要把这些写法直接复制到Ubuntu Bash。Windows Visual Studio构建的可执行程序位于`build-vscode/Release`，依次打开三个PowerShell终端：

```powershell
# 终端1：演示GCS
python -B tools\gcs_dashboard.py --udp-port 39002 --http-port 8080

# 终端2：在线算法
.\build-vscode\Release\zju_coop_online.exe --config config\demo.ini

# 终端3：三车100 Hz静止IMU和20 Hz三边测距
python -B tools\imu_uwb_simulator.py --host 127.0.0.1 --port 39001
```

浏览器打开`http://127.0.0.1:8080/`。正常情况下应看到节点1为主参考、三个节点定位、三条活动边和网络状态。停止模拟器超过`edge_timeout_ns`后，活动边减少并产生网络告警；重新启动模拟器后应看到恢复过程。

一条命令完成进程级验证：

```powershell
python -B tools\imu_online_smoke_test.py `
  --online-exe build-vscode\Release\zju_coop_online.exe `
  --replay-exe build-vscode\Release\zju_coop_replay.exe `
  --config config\demo.ini
```

仅测距兼容模式只用于缺少IMU时回退或历史回归：

```powershell
.\build-vscode\Release\zju_coop_online.exe --config config\range_only_demo.ini
python -B tools\uwb_simulator.py --host 127.0.0.1 --port 39001 --rate-hz 20
```

### 3.2 Ubuntu 22.04 Bash

本小节全部命令都在**工程根目录下的Bash终端**执行。假设已经按第2.2节构建到`build-arm64`；Linux单配置生成器的可执行程序直接位于该目录，不带`Release`子目录，也没有`.exe`后缀。依次打开三个Bash终端：

```bash
# 终端1：演示GCS
python3 -B tools/gcs_dashboard.py --udp-port 39002 --http-port 8080

# 终端2：在线算法
./build-arm64/zju_coop_online --config config/demo.ini

# 终端3：三车100 Hz静止IMU和20 Hz三边测距
python3 -B tools/imu_uwb_simulator.py --host 127.0.0.1 --port 39001
```

浏览器同样打开`http://127.0.0.1:8080/`。Ubuntu上的一条命令进程级验证为：

```bash
python3 -B tools/imu_online_smoke_test.py \
  --online-exe build-arm64/zju_coop_online \
  --replay-exe build-arm64/zju_coop_replay \
  --config config/demo.ini
```

若是在RK3588盒端直接运行但没有桌面浏览器，可在同一网络内的开发机访问盒端HTTP地址；同时应根据网络边界显式设置GCS监听地址，不能把`127.0.0.1`误解为跨设备地址。

以上Windows和Ubuntu命令只验证“模拟数据→算法→临时UDP遥测→演示GCS→日志/回放”的软件闭环。它们不能替代AIBrainBox上的真实IMU/UWB驱动、ROS 2消息与QoS、统一时间轴、ARM64负载、长稳和实车精度验收。

## 4. 推荐学习顺序

不要从最大的实现文件开始逐行阅读，建议按“契约→数据→算法→编排→适配→验证”学习。

### 第一步：掌握系统边界

先读`README.md`、`docs/01_算法与可观测性说明.md`和`docs/04_AIBrainBox部署与上交ROS2适配说明.md`。需要回答：输出为什么是主参考相对位置、上交/浙大/交大分别负责什么、为什么临时UDP不是最终ROS 2接口。

### 第二步：掌握公开调用契约

读`include/zju_coop/c_api.h`和`examples/sdk_consumer.cpp`，重点理解：

- `struct_size + abi_version`如何防止接口布局误用；
- 初始化数组为什么带`stride`；
- 为什么输入结构由适配层填充、算法库深拷贝；
- `zju_coop_step`为什么先查询容量再取结果；
- 为什么同一个handle必须串行调用。

随后运行`zju_coop_sdk_consumer`和`zju_coop_self_check`，把接口声明与真实输出对应起来。

### 第三步：掌握单节点IMU传播

依次读：

```text
include/zju_coop/types.hpp
src/core/quaternion.hpp/.cpp
src/core/inertial_eskf15.hpp/.cpp
tests/test_inertial_eskf15.cpp
```

重点跟踪：ROS四元数x/y/z/w到内部w/x/y/z的换序、ENU/FLU方向、静止比力`+g`、相邻瞬时量中值、误差状态`δp/δv/δθ/δbg/δba`、`Phi/Qd`以及失败回滚。当前实现是在线递推，不要求ROS 2适配层提供预积分量。

### 第四步：掌握协同测距更新

读`cooperative_inertial_ekf`和对应测试。自己在纸上写出：

```text
h(x) = ||p_j - p_i||
H_i = -(p_j-p_i)^T / ||p_j-p_i||
H_j = +(p_j-p_i)^T / ||p_j-p_i||
NIS = innovation² / innovation_variance
```

再从代码定位完整15N增益、Joseph协方差更新、每节点误差注入和相对主参考协方差`Pii+Prr-Pir-Pri`。

### 第五步：掌握质量与动态拓扑

读`degradation_monitor`、`rigidity`和`engine`。理解所有到达量测为什么都要进入质量窗口，降权/暂缓/剔除/试探恢复如何转换为有效边，以及`step`如何从活动边计算主参考可达性和二维刚度秩。

### 第六步：掌握工程适配与回放

读`src/api/c_api.cpp`、`src/apps/app_support.cpp`、`online_main.cpp`和`replay_main.cpp`。重点观察“先校验、候选副本计算、全部成功后原子提交”的共同模式，以及在线和回放如何复用同一C ABI调用顺序。

最后再读`wire_protocol`、`event_log`和Python工具。它们是演示基础设施，不是滤波算法本体。

## 5. 编写思路

### 5.1 核心与框架解耦

核心只接受普通C/C++结构。上交wrapper负责把ROS 2消息字段、坐标轴和时间戳转换后调用库，因而算法可以在Windows无ROS环境测试，也能在Ubuntu/RK3588编译为`.so`。

### 5.2 先冻结数据语义再写算法

每个输入必须先明确节点号、序号、测量时间、接收时间、单位、坐标系、有效位和质量字段。缺少统一时间戳的距离值不能直接进入协同滤波；仅改变`frame_id`字符串也不能代替真实轴系变换。

### 5.3 名义状态与误差状态分离

每节点维护位置、速度、姿态和两类零偏名义状态；15维小误差用于协方差传播与量测更新。IMU高频传播对应节点状态块和交叉协方差，低频平台间测距在同一联合状态上异步更新。

### 5.4 失败必须可诊断且不污染状态

乱序、重复、时间超限、NLOS、NIS拒绝和数值失败分别返回不同结果。矩阵或误差注入先在候选副本完成，只有全部检查成功才提交，避免在线状态出现难以复现的半更新。

### 5.5 质量、拓扑和滤波分层

质量监测决定一条观测正常、降权、暂缓还是剔除；滤波器只执行数值更新；拓扑模块依据当前有效边计算可达与可观状态。三者分开后，后续视觉/激光观测可以复用质量和拓扑框架，不必重写通信或GCS。

### 5.6 配置代替源码调参

运行阈值进入INI并接受严格解析。增加新参数时必须同时修改配置模型、白名单、范围/组合校验、默认配置、C ABI映射、测试和文档，不能只在`.cpp`中增加隐藏常量。

## 6. 后续增加激光雷达和视觉的正确顺序

1. 先与上交冻结原始`PointCloud2`/图像、相机内外参、时间同步状态和算力边界；
2. 在浙大前端模块中从原始数据提取`from_node/to_node/timestamp/measurement/covariance`及专用质量字段；
3. 为核心增加普通C++相对位姿观测结构，不把ROS消息写入核心；
4. 扩展质量评价和联合滤波量测模型；
5. 通过新增C ABI结构或升级ABI版本暴露接口，不能修改v1结构中既有字段顺序；
6. 上交wrapper再映射ROS 2输入，交大GCS只接收定位、拓扑、状态和告警结果。

当前没有真实激光/视觉前端资料时，不应伪造已经实现这些算法；已有扩展边界只保证未来可以按上述顺序接入。

## 7. 修改后的最低验证要求

每次改动至少执行：

```text
1. Release重新编译
2. zju_coop_self_check
3. ctest --output-on-failure
4. 与修改模块对应的异常/边界测试
5. 若改协议，同时运行C++和Python黄金字节测试
6. 若改在线链路，同时运行IMU+测距进程级冒烟测试
```

若修改C ABI、坐标系、时间语义、状态维数或协议布局，必须在提交说明中单独列出兼容性影响，不能只写“优化代码”。

## 8. 常见误区

- `namespace zju::coop`是C++17合法语法；VS Code报错时先检查IntelliSense工具链，不要改回旧语法掩盖配置问题。
- 标准`sensor_msgs/Imu`没有温度；温度属于模组私有状态，不应向标准消息或当前算法输入虚构字段。
- 三车三边测距不能给出全球绝对位置；当前初值和主参考只固定相对坐标自由度。
- `yaw_valid=false`、`z_valid=false`必须由GCS尊重，不能因内部状态是三维就显示为有效航向/高度。
- Windows测试通过不能替代RK3588实测，实机仍须重新记录编译、ABI、负载、时钟和长时间运行结果。
