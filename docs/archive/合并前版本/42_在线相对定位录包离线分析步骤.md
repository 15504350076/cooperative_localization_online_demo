# 在线相对定位录包离线分析步骤

本说明用于分析同时包含以下两个Topic的ROS 2录包：

```text
/uwb/range
/cooperative_localization/poses_2d
```

分析程序为`tools/analyze_online_bag.py`。它直接读取`.db3`，自动生成中文结论、完整统计和CSV明细，不需要回放录包，也不依赖AI。

## 1. 加载环境

在Ubuntu开发电脑进入工程根目录：

```bash
cd /home/pdq/Code/cooperative_localization_online_demo/cooperative_localization_online_demo
source /opt/ros/humble/setup.bash
source install/ros2-uwb-online/setup.bash
```

第二条命令用于提供两个自定义消息类型。如果本机没有`install/ros2-uwb-online`，执行一次：

```bash
source /opt/ros/humble/setup.bash
colcon build --base-paths ros2 \
  --packages-select cooperative_interfaces cooperative_localization_msgs \
  --build-base build/online-analysis-msgs \
  --install-base install/online-analysis-msgs
source install/online-analysis-msgs/setup.bash
```

## 2. 先看录包基本信息

把目录替换成实际录包目录：

```bash
ONLINE_BAG=data/zju_online_v1_20260808_151205
ros2 bag info "$ONLINE_BAG"
```

至少应看到两个目标Topic，而且消息数均大于0。

## 3. 一条命令完成分析

```bash
python3 tools/analyze_online_bag.py "$ONLINE_BAG"
```

默认把结果写到：

```text
<录包目录>/online_analysis/
```

也可以指定其他输出目录：

```bash
python3 tools/analyze_online_bag.py "$ONLINE_BAG" \
  --output data/online_analysis_result
```

## 4. 输出文件

| 文件 | 用途 |
|---|---|
| `在线相对定位分析.md` | 直接阅读的中文结论、频率、边长、位置和时间检查 |
| `analysis.json` | 完整机器可读汇总，便于后续程序或批量比较 |
| `uwb_records.csv` | 每条UWB的录包接收时间、Header时间、收发ID、距离 |
| `pose_records.csv` | 每帧每辆车的相对坐标和有效标志 |

优先看Markdown；需要逐条定位异常时再打开CSV。

## 5. 如何判断结果

先确认输出链路：

- `/cooperative_localization/poses_2d`消息数大于0；
- 接收频率与约10Hz的UWB更新处于同一量级；
- 坐标帧为`coop_ref_1_relative`；
- 参考节点为1；
- 输出包含节点1、2、3；
- 纯UWB时`yaw_valid=false`属于正常结果。

再看位置质量：

- `position_valid_frame_count`是三车位置全部有效的输出帧数；
- `position_valid_ratio`是有效输出帧占全部输出帧的比例；
- 节点2的`x_m`对应当前车1至车2基准边；
- 节点3的`x_m、y_m`体现三角形第三个顶点；
- 标准差反映静止时输出抖动，但没有卷尺或GNSS真值时不能称为定位精度。

时间统计要按有向流看。六个`src_id→target_id`流混在同一Topic中，多个流可能共用Header历元，消息到达顺序也可能交错。因此总流中出现Header重复或表面回退不等于某个UWB时钟回退；脚本会分别统计六个有向流。`bag_receive_ns-header_ns`包含时钟基准差、处理和传输过程，只用于时间诊断，不能直接称为网络延迟。

输入UWB消息数与输出帧数不能直接相除得到算法接受率。一个输出历元需要三条无向边，而输入中最多包含六个有向流。要精确区分缺边、互惠不一致和三角形无效，还需要结合融合节点日志。

## 6. 本包`zju_online_v1_20260808_151205`的结果

- 录包持续约59.42秒；
- UWB输入3429条，总接收率约57.79Hz；六个有向流分别约9.51～9.71Hz；
- 相对位置输出563帧，约9.46Hz；
- 527帧三车位置全部有效，36帧无效，有效比例约93.61%；
- UWB共有1186个Header时间标签，其中563个收齐三条无向边；562个输出时间标签与包内完整三边精确对应；另1个输出使用了录包开始前已经进入融合节点的输入，属于录包边界效应；
- 六个UWB有向流分别检查均为0次Header回退、0次重复；
- UWB三条边的距离中位数分别为：1—2约1.36m、1—3约0.89m、2—3约1.71m；
- 1—2出现过3.94m，明显偏离1.36m中位水平，说明原始测距仍有外点；
- 有效输出中车2位置中位数约为`(1.350, 0)`，车3约为`(-0.121, 0.866)`；
- 静止输出中车2的x标准差约0.068m，车3的x/y标准差约0.177m/0.143m；
- 全部输出的`yaw_valid=false`，符合纯UWB不可观测车辆自身航向的预期。

因此该包证明201盒在线UWB相对定位链路能够连续工作，但原始测距仍有外点，且车3位置抖动较明显。没有同步记录卷尺、GNSS或其他真值，本包只能评价连续性、有效率和稳定性，不能给出绝对定位精度。

## 7. 为什么目录名时间与看到的时间不同

目录名由201盒执行下面的shell命令生成：

```bash
date +%Y%m%d_%H%M%S
```

它使用201盒的系统时钟和本机时区，不使用UWB消息Header，也不使用操作电脑的时间。本包目录中的`20260808_151205`表示201当时显示`2026-08-08 15:12:05`。

本包第一条录包接收时间约为Unix时间`1786201926`：

```text
UTC：          2026-08-08 15:12:06
Asia/Shanghai：2026-08-08 23:12:06
```

因此目录名与开发电脑上`ros2 bag info`显示的`23:12:06`相差8小时，原因是201按UTC命名、开发电脑按北京时间显示。同一时刻只是在两个时区下表达。目录时间比第一条消息早约1秒，是启动录包进程和订阅Topic所需的正常时间。

如果录制当天实际日期并不是2026-08-08，则还存在201系统日期未校准的问题。录包前可在201检查：

```bash
date '+local=%F %T %Z %z'
date -u '+utc=%F %T %Z %z'
timedatectl status
```

后续在线包命名已经显式采用北京时间：

```bash
ONLINE_TIME=$(TZ=Asia/Shanghai date +%Y%m%d_%H%M%S)
```

这能消除UTC与北京时间的8小时显示差，但不能修复系统日期本身错误。若系统日期与真实日期不符，应由盒端维护人员统一校准三盒时钟，再继续时间同步验收。
