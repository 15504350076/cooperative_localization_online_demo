# 联合录包在线输出就绪失败排查

本页用于 `record_joint_time.py --include-poses` 录包失败时的离线判读和现场复现。命令可在没有互联网、没有AI时执行。

## 1. 这次两包的结论

`joint_time_20261016_142731.zip` 和 `joint_time_20261016_143629.zip` 的问题完全相同：

| 检查项 | 142731 | 143629 |
|---|---:|---:|
| manifest 的 `include_poses` | `true` | `true` |
| `all_subscribed` | `false` | `false` |
| 下载错误 | 无 | 无 |
| IMU三包 | 均有 `/imu/raw`，约17.95万条/包 | 均有 `/imu/raw`，约17.94万条/包 |
| 201共享包已有话题 | `/uwb/range`、`/node/id` | `/uwb/range`、`/node/id` |
| 201共享包缺少话题 | `/cooperative_localization/poses_2d` | `/cooperative_localization/poses_2d` |

UWB日志给出了直接原因：

```text
Topic '/cooperative_localization/poses_2d' has unknown type
'cooperative_localization_msgs/msg/CooperativePose2DArray'
Reason: package 'cooperative_localization_msgs' not found
```

因此这两次不是UWB或IMU没有录到，也不是压缩、下载失败。201录包端只加载了`imu_ws`，没有加载包含`cooperative_localization_msgs`的`zju_coop_ws`。`rosbag2`知道这个话题存在，但不认识消息类型，所以反复跳过它；日志最终只出现`/uwb/range`和`/node/id`。`--include-poses`只会把话题加入录包清单，不会启动融合节点，也不会自动加载消息包。

## 2. 在Windows上查看一轮是否相同

在上交电脑PowerShell执行；`$run`换成实际目录：

```powershell
$run = ".\data\joint_time_20261016_142731"
Get-Content "$run\manifest.json"
Get-Content "$run\采集状态.json"
Get-Content "$run\*_uwb_rec_v1.log" | Select-String "Subscribed to topic|unknown type|not found|Recording"
```

应重点看三点：

1. `include_poses`是否为`true`；
2. `采集状态.json`中`all_subscribed`是否为`false`，`errors`是否为空；
3. UWB日志是否有`cooperative_localization_msgs not found`。

`errors=[]`只表示SSH、远端录包、压缩和下载没有失败；它不表示所有请求话题都已订阅。

## 4. 录包前在201盒确认融合输出

录包程序不会启动融合节点。必须先在201保持一个融合终端运行，并使用与录包相同的通信域。现场按当前默认环境执行即可；下面显式写出域0和Fast DDS，便于排查时保证一致。

### 201终端A：启动融合节点并保持运行

```bash

source /home/firefly/imu_ws/install/setup.bash
source /home/firefly/zju_coop_ws/install/ros2-box/setup.bash
export ROS_DOMAIN_ID=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOCALHOST_ONLY=0
ros2 launch zju_coop_bringup uwb_only.launch.py
```

### 201终端B：确认话题、类型和消息都能看到

```bash
source /opt/ros/humble/setup.bash
source /home/firefly/imu_ws/install/setup.bash
source /home/firefly/zju_coop_ws/install/ros2-box/setup.bash
export ROS_DOMAIN_ID=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOCALHOST_ONLY=0
ros2 topic info /cooperative_localization/poses_2d
ros2 interface show cooperative_localization_msgs/msg/CooperativePose2DArray
ros2 topic echo --once /cooperative_localization/poses_2d
```

判读：

- `Unknown topic`：融合节点没有运行，或节点不在同一Domain/DDS环境；
- `Unknown message type`：当前终端没有source `zju_coop_ws`；
- `topic info`正常但`echo`一直没有消息：先查UWB三边和融合节点日志；
- `echo`能收到一帧后，再启动PowerShell联合录包。

确认融合进程实际环境时，在201执行：

```bash
FUSION_PID=$(pgrep --newest --full 'zju_cooperative_fusion_node')
test -n "$FUSION_PID" && tr '\0' '\n' < "/proc/$FUSION_PID/environ" |
  grep --extended-regexp '^(ROS_DOMAIN_ID|ROS_LOCALHOST_ONLY|RMW_IMPLEMENTATION)='
```

录包脚本使用`ROS_DOMAIN_ID=0`、`rmw_fastrtps_cpp`和共享DDS；融合节点的实际值必须能互相发现。启动后才修改终端环境不会改变已经运行的进程。

## 7. 录包脚本就绪判定的含义

脚本对每路远端`rosbag2 record`日志等待40秒，检查是否出现`Subscribed to topic '<话题>'`：

- `全部就绪`：指定话题都建立了订阅；不代表数据持续、三边齐全或时间同步；
- `40秒内未全部就绪`：至少一个指定话题没有建立订阅。脚本仍会让远端录包完成限定时长，并尝试压缩和下载，方便诊断；
- 四个压缩包都收回、但最后提示“本轮就绪检查失败”：说明采集和下载完成，但订阅就绪条件未满足；必须看`*.log`和`metadata.yaml`。

这两次的判定链是：

```text
include_poses=true
  → 录包请求在线位置话题
  → 201缺少 cooperative_localization_msgs 环境
  → rosbag2 报 unknown type / package not found
  → 只订阅 UWB 和 node/id
  → all_subscribed=false
  → 包仍然正常录满并下载
```

### 8.3 在线定位结果

`analyze_online_bag.py`生成的结果：

- UWB输入：6933条，约38.63 Hz（四条有向流合计）；
- 在线位置：1660帧，约9.244 Hz；
- 在线位置接收间隔中位数约100.0 ms，最大约305.2 ms；
- 三车位置有效：1660/1660，100%；
- `yaw_valid`有效帧：0，纯UWB模式下正常；
- 坐标帧：`coop_ref_1_relative`，参考车为1；
- 车2坐标中位数约`(0.860, 0.000) m`；
- 车3坐标中位数约`(0.604, 0.890) m`；
- 输出Header无回退、无重复。

UWB三条无向边均有数据：

| 无向边 | 消息数 | 距离中位数 |
|---|---:|---:|
| 1—2 | 1732 | 0.86 m |
| 1—3 | 3483 | 1.07 m |
| 2—3 | 1718 | 0.93 m |

严格按“Header完全相等”统计只有18个三边历元；这不是算法实际使用的10 ms判定。算法会在`uwb_epoch_max_span_ms=10`窗口内归并相近时间的三条边，所以本轮仍输出1660帧且全部有效。严格相等统计只能用于检查原始时间标签，不能替代10 ms窗口统计。

### 8.4 本轮仍存在的时间问题

联合时间分析得到：

| 数据流 | Header首时间 | Header末时间 | 回退/重复 |
|---|---:|---:|---:|
| 201 IMU | 1785906722.857 s | 1785906902.454 s | 0/0 |
| 202 IMU | 342834.862 s | 343014.282 s | 0/0 |
| 203 IMU | 1785906722.533 s | 1785906901.949 s | 0/0 |
| UWB | 1785906722.123 s | 1785906901.584 s | 各有向流均0/0 |

202盒IMU没有发生回退，但它的Header时间约为`342834`秒，与201、203 IMU和UWB的`1785906xxx`秒不在同一时间基准。其`R−H`中位数约为`1.719×10^12 ms`，这是时间基准不同的证据，不是网络延迟。

本轮结论应写为：

```text
在线位置已成功录包，纯UWB输出约9.24 Hz且位置帧全部有效；
三盒IMU数据均有且无单流回退，但202盒IMU Header时间基准仍与201/203及UWB不一致，
因此暂不能直接进行跨盒IMU融合或IMU-UWB时间同步验收。
```

### 8.5 后续复现要求

后续按“问题/数据类型”归并记录：同一录包条件、同一根因的多个压缩包放在同一张表或同一小节，只补充包名和关键证据；只有测试条件或结论发生变化时才新建小节。不要把上一轮的完整过程、消息数量或时间结论重复复制到新包。

在线输出录包的最低复现顺序仍是：

1. 201先启动融合节点并保持运行；
2. 201终端确认`ros2 topic echo --once /cooperative_localization/poses_2d`能收到消息；
3. PowerShell电脑使用最新`record_joint_time.py --include-poses`；
4. 结束后先看`采集状态.json`和UWB日志，再看metadata；
5. 只有metadata含`/cooperative_localization/poses_2d`时，才运行`analyze_online_bag.py`评价在线输出；
6. 再运行`analyze_joint_time.py`检查三盒传感器Header时间，不能用在线输出成功替代时间同步验收。
