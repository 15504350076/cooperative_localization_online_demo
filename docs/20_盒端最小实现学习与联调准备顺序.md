# 盒端最小实现学习与联调准备顺序

## 1. 学习目标

本文只覆盖当前盒端最小实现主线：

```text
各车 IMU
  → 各车本地 15 维惯导
  → NodeState 通过 ROS 2/DDS 汇总到参考车
  → 参考车使用 UWB 测距估计二维位置修正
  → CooperativePose2DArray
  → 规划控制模块
```

完成本文后，应能独立回答以下问题：

- 每个 ROS 2 Topic 由谁发布、谁订阅、消息类型和频率是什么；
- `header.stamp`、`frame_id`、`node_id` 分别表示什么；
- 本地 15 维惯导保存哪些状态，哪些状态会发送给参考车；
- 参考车如何把 NodeState 和 UWB 测距变成二维位置修正；
- `position_valid=false` 和测距被 NIS 拒绝分别意味着什么；
- 现场无结果时，应先检查通信、时间、坐标还是算法。

点云配准、视觉定位、SLAM、GNSS 测距后备和旧 45 维集中式滤波不属于第一轮必学内容。

### 3.2 必须理解

- 每辆车都运行自己的惯导，参考车不接收其他车的原始 IMU；
- 从车发给参考车的是精简 NodeState，不是 15 维误差状态和协方差；
- 参考车只估计每个非参考车的 `[delta_e, delta_n]`；
- UWB 当前修正相对平面位置，不直接修正航向和 IMU 零偏；
- 输出 `x/y` 是相对参考车的位置，坐标轴仍与公共 ENU 平行。

### 4.2 当前主线接口

| Topic | 消息类型 | 主要发布者 | 主要订阅者 |
|---|---|---|---|
| `/vehicle_N/imu/data` | `sensor_msgs/msg/Imu` | 各车 IMU 驱动 | 各车本地惯导节点 |
| `/cooperative_localization/node_state` | `cooperative_localization_msgs/msg/NodeState` | 三车本地惯导节点 | 参考车融合节点 |
| `/uwb/range` | 当前为 `zju_coop_test_msgs/msg/UwbRange` | UWB 驱动或模拟器 | 参考车融合节点 |
| `/cooperative_localization/poses_2d` | `cooperative_localization_msgs/msg/CooperativePose2DArray` | 参考车融合节点 | 参考车规划控制/GCS |
| `/cooperative_localization/feedback/poses_2d` | 同上 | 参考车融合节点，可选 | 从车规划控制，默认关闭 |

正式 UWB 消息仍需与上交冻结；当前 `UwbRange.msg` 是测试替身。

## 5. 第三阶段：优先掌握时间和坐标约定

时间和坐标错误会让正确的滤波算法拒绝数据，是实盒联调的最高风险项。

### 5.1 阅读顺序

1. [上交盒端 UWB 统一时间接入约定](19_上交盒端UWB统一时间接入约定.md)
2. [2026-08-25 UGV 时钟同步框图](images/UGV多模态传感器时钟同步框图20260825.png)
3. 工程外层的 `project_time_sync_spec.md`
4. [sensor_time_bridge.hpp](../ros2/zju_coop_ros2/src/sensor_time_bridge.hpp)

### 5.2 时间语义

- 实盒 `header.stamp` 使用 `UWB_SYSTEM_TIME`；
- 首轮协同定位固定选择 UWB_PPS，不支持运行中静默切换 GNSS_PPS；
- 真实 GNSS RMC 与 `UWB_GPRMC` 是两种不同语义，不得混用；
- 时间戳表示传感器测量发生时刻，不是 ROS 消息发布或网络接收时刻；
- `steady_clock` 只提供本机经过时间，不能直接冒充 UWB 时间；
- `SensorTimeBridge` 只把本机经过时间映射到 UWB 时间域，不负责设备授时；
- IMU、NodeState 和 UWB 时间必须单调；发生 UWB 时间纪元回拨后应重启定位链路；
- `max_future_skew` 和 `max_receive_delay` 是异常包门限，不是同步精度指标。

### 5.3 坐标语义

- 公共导航系：ENU，`+x` 东、`+y` 北、`+z` 上；
- 车体系：FLU，`+x` 前、`+y` 左、`+z` 上；
- 姿态四元数表示 `FLU → ENU`，存储顺序 `[x, y, z, w]`；
- 航向向东为 `0 rad`，向北为 `+pi/2 rad`，逆时针为正；
- 三车 NodeState 必须使用同一个 `common_enu` 定义和原点。

### 6.2 按函数追踪

```text
LocalInertialNode()
  → 读取 node_id、初始位置/速度/姿态/零偏
  → 创建 SDK 单车实例
  → 配置本车惯导
  → 订阅 Imu

on_imu()
  → 校验时间、顺序、frame_id
  → ROS Imu 转 zju_coop_imu_packet_t
  → zju_coop_push_imu()
  → 本地 ESKF 传播

publish_state()
  → zju_coop_get_node_state()
  → 发布 NodeState
```

### 6.3 15 维状态需要掌握到什么程度

名义状态为：

```text
p, v, q, bg, ba
```

误差状态为：

```text
[delta_p, delta_v, delta_theta, delta_bg, delta_ba]
```

第一轮学习只要求理解：

- 陀螺仪推进姿态，加速度计经姿态和重力补偿后推进速度、位置；
- `bg/ba` 是陀螺仪和加速度计零偏；
- 第一帧 IMU 建立积分基线，后续帧才形成传播区间；
- 当前最小闭环主要依赖本地传播，完整本地观测更新能力有限；
- 零偏和 15×15 协方差不通过 NodeState 跨车传输。

不要求第一遍逐项推导 `Phi/Qd` 的每个矩阵元素。

## 7. 第五阶段：学习参考车协同融合

### 7.1 阅读顺序

1. [cooperative_fusion_node.cpp](../ros2/zju_coop_ros2/src/cooperative_fusion_node.cpp)
2. [fusion.yaml](../ros2/zju_coop_bringup/config/fusion.yaml)
3. [distributed_fusion2d.hpp](../src/core/distributed_fusion2d.hpp)
4. [distributed_fusion2d.cpp](../src/core/distributed_fusion2d.cpp)

### 7.2 按函数追踪

```text
on_node_state()
  → 校验 common_enu、node_id、时间顺序
  → 保存各车历史状态

on_uwb_range()
  → 构造测距包
  → 在测距时刻插值/有限外推两端 NodeState
  → 计算预测距离、创新和 NIS
  → 更新 [delta_e, delta_n] 与协方差

publish_pose()
  → 读取同一公共时刻快照
  → 输出相对参考车 x/y 和各车航向
  → 发布 position_valid/yaw_valid
```

### 7.3 必须理解

- 每个非参考车对应两个位置修正状态；三车时共四维；
- UWB 量测模型是两车修正后位置之间的距离；
- NIS 超门限时该测距不更新位置修正；
- Joseph 形式更新用于保持协方差数值稳定；
- `position_valid` 还要求 NodeState 新鲜并存在近期有效测距连通路径；
- UWB 停止超过配置门限后，从车位置有效位必须变为 false；
- 航向来自本地 NodeState，当前 UWB 不修正航向。

## 11. 第一轮暂缓内容

以下功能已经预留或实现了独立路径，但不应阻塞最小闭环联调：

- `gnss_range_fallback.py`：UWB 未调通时的显式后备，默认关闭；
- 点云和图像原始输入：当前仅校验，不进入本地惯导；
- 激光点云配准、视觉定位和 SLAM：独立前端，默认关闭；
- Gazebo/RViz：用于仿真和显示，不是实盒最小算法依赖；
- `cooperative_inertial_ekf.*`：旧 15N/45 维集中式回归基线；
- `range_ekf.*`、临时 UDP 在线程序和浏览器 GCS：兼容与回归工具。

主线稳定后，再按“GNSS 后备 → 点云/视觉前端 → SLAM → 与协同滤波融合”的顺序扩展。
